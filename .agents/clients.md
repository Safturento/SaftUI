# Clients and references

## Two clients

- **WoW Forever.** Interface 16001, game type "Camelot". A mainline-family client with Classic-flavored overrides under `*/Camelot/` dirs in Blizzard's source. **The user plays Forever.** Test against it first.
- **Retail.** Midnight, interface 120000.
- **Flags** (`SaftUI-Core/constants.lua`): `st.forever` (`GAME_VERSION == 16001`) is true only on Forever and is the only client test. The old `st.retail` flag, which was true on both clients, is gone. "Not Forever" means `not st.forever`. Prefer feature checks (does the frame or API exist?) over version checks where you can.
- **Forever specifics found so far:**
  - **Swing timer.** Forever has `Blizzard_SwingTimer` (an Edit Mode system); retail doesn't.
  - **Totem bar.** `MultiCastActionBarFrame` is protected; `TotemFrame` isn't loaded.
  - **Action bars.** The same bars as retail (`MainActionBar`, the four multibars and `MultiBar5`–`7` on pages 13–15), with the same binding commands. LibActionButton-1.0 treats Forever as mainline.
  - **Extra action button.** Forever has none: `ActionButtonUtil.IsExtraActionButtonDisabled` (`Blizzard_ActionBar/Camelot`) returns true, there's no `EXTRAACTIONBUTTON1` binding, and Edit Mode hides its Extra Abilities option. `ExtraActionBarFrame` and `ExtraAbilityContainer` still exist, and `Blizzard_ZoneAbility` loads (`AllowLoadGameType: mainline`, which takes in Camelot), so test those on retail.
  - **Minimap.** The day/night indicator is `MinimapCluster.DielFrame`, and the player coordinates under the minimap (`minimapShowPlayerCoords`) are `MinimapCluster.MinimapContainer.PlayerCoords`. Retail has neither. SaftUI hides both.
  - **Queue eye.** `QueueStatusButton` is an Edit Mode system.
  - **Cooldown Manager** (`Blizzard_CooldownViewer`, checked 2026-11-12 against both clients' source at 1.60.1.70888 and 12.1.5.70783). It loads on both, at startup, not on demand: Forever's TOC adds `camelot` to `AllowLoadGameType`, and Forever's Options offer it (`InterfaceOverrides.HasCooldownViewer` is true in `Blizzard_SettingsDefinitions_Frame/Camelot`; it shows while the `cooldownViewerEnabled` setting is on). The four viewers (`EssentialCooldownViewer`, `UtilityCooldownViewer`, `BuffIconCooldownViewer`, `BuffBarCooldownViewer`), the item templates and their frame pools are the same on both. Forever differs in its viewers' `layoutIndex` in the bottom managed container (13, 14 and 12 for Essential, Utility and the buff icons; retail's 10, 11 and 9), its edit mode refresh callback (`EditMode.RefreshCooldownViewer`), its placeholder icons in edit mode, and how an item reads a spell category's cooldown (`CooldownViewerItemData.lua`: Forever can show the cooldown and icon of the item last used from a category). None of it reaches SaftUI's skin (`SaftUI-Misc/Skinning/blizzard/Blizzard_CooldownViewer.lua`), which is the same on both.
  - **Objective tracker** (`Blizzard_ObjectiveTracker`, checked 2026-11-13 against both branches). The same files on both, loaded at startup; Forever adds `Camelot/Blizzard_QuestObjectiveTrackerOverride.lua` (its quest module shows no timer bars, `CanShowTimerBar`, and takes its own quest tags). Forever's tracker also has gamepad navigation (`ObjectiveTrackerFrameMixin`: `InitializeGamepad` hides the header's collapse button), top padding providers that move its header down (`UpdateHeaderPosition`, and the container's `topModulePadding` from them, 38 fixed on retail), a `topPadding` of 15 (0 on retail), so in Blizzard's right container it sits 15 lower, and block titles in the quest's difficulty color (`UpdateHighlight`). The rest SaftUI touches is the same on both: the templates it styles (headers, blocks, lines, the progress, bonus, scenario and timer bars, `QuestObjectiveItemButtonTemplate`), the module and block methods it hooks (`GetBlock`, `GetProgressBar`, `GetTimerBar`, `GetRightEdgeFrame`, `GetLine`, the headers' `SetCollapsed`), the right managed container (`RightManagedFrameContainer`, `RIGHT_CONTAINER_OFFSET_Y` -260) and the Edit Mode system (Height 400 to 1000, Opacity, Text Size; its `AnchorSelectionFrame` sets no clamp insets). **The quest API SaftUI's own tracker reads** (`SaftUI-Tracker/model.lua`, checked 2026-11-14 against `QuestLogDocumentation.lua` on both branches): the same on both except that `C_QuestLog.IsEliteQuest(questID)`, `C_QuestLog.GetQuestTimers()` (a list of `{ questID, questTimer }`, the time left) and `GetTrivialRange` are Forever's only. So elite is `IsEliteQuest` where it exists and the tag's `isElite` (`GetQuestTagInfo`) where not, and the time left is `GetQuestTimers`' where it exists and `total - elapsed` from `GetTimeAllowed` (MayReturnNothing) where not. Forever's own title prefix is `"[" .. difficultyLevel .. ("+" if elite) .. "] "` (`Camelot/QuestUtilsOverrides.lua`: `GetQuestTitlePrefix`, from `C_QuestLog.GetQuestDifficultyLevel`, which is `QuestInfo.difficultyLevel`), and its tag text names only the Elite, Dungeon, PvP and Raid tags; its quest module shows no timer bar (`CanShowTimerBar` is false). Neither client marks a quest function's return secret, so SaftUI still treats a secret value as missing (a secret title is shown as it is, with no level or tags; a quest whose header's title is secret goes in the Other group). Blizzard's `ShouldDisplayQuest` tests `quest.isBounty and not isComplete`, where `isComplete` is an undefined global on both branches, so Blizzard never shows a bounty and SaftUI leaves bounties out too (ruling 10); it also leaves campaign quests out and SaftUI draws them. `C_QuestLog.GetInfo` over `1..GetNumQuestLogEntries()` returns every entry, the quests under a header the player collapsed in the quest log included (from Blizzard's source, both branches: `QuestLogQuests_ShouldShowQuestButton` hides those by `info.header.isCollapsed`, and `GetHeaderIndexForQuest` gives a collapsed header's index); not yet confirmed in game. The log's size is not 35 everywhere: both clients have `C_QuestLog.GetMaxNumQuestsCanAccept()`, and Forever's `QuestConstantsDocumentation.lua` has `QuestLogConstsMainlineCamelot.MAXIMUM_NUM_QUESTS_LOG_CAN_ACCEPT = 40` (retail has no such constant), so SaftUI reads it through `TR.MaxQuests()` and assumes no number. `C_QuestLog.GetTitleForQuestID` answers from the quest cache, so an offered quest (an auto quest popup before it is in the log) has a title. No frame of it is secure on either client: the quest item button and the scenario's spell buttons are plain buttons whose own OnClick calls the protected function (`SaftUI-Misc/Skinning/blizzard/Blizzard_ObjectiveTracker.lua`, `Blizzard_ObjectiveTrackerPosition.lua`).
  - **Durability figure** (`Blizzard_DurabilityFrame`, checked 2026-11-14 against both branches: byte-identical files). `DurabilityFrame` is a 60 by 75 right managed frame (`RightManagedFrameTemplate`, `layoutIndex` 9) and an Edit Mode system (`EditModeDurabilityFrameSystemTemplate`, with a Size setting and an account setting to show it), shown by `DurabilityFrameMixin:SetAlerts` on `UPDATE_INVENTORY_ALERTS` and `PLAYER_ENTERING_WORLD` while any slot is damaged or broken, and hidden while the vehicle seat indicator or arena frames show. Its `OnEnter` is its own (the XML's `<OnEnter method="OnEnter"/>`): while `anyItemBroken` or `anyItemBreaking` it owns `GameTooltip` at `ANCHOR_BOTTOMLEFT` with the title `REPAIR_ARMOR_TOOLTIP_TITLE` ("Repair Armor") and one line, then `Show()`; `OnLeave` hides it while the frame owns it. Both clients' `TooltipData` carries `repairCost` for `C_TooltipInfo.GetInventoryItem('player', slot)` (Blizzard's `TooltipDataRules.FinalizeItemTooltip` reads it), and `tooltip:SetInventoryItem` returns it as its third value; `GetMoneyString` is in `Blizzard_SharedXML/FormattingUtil.lua`. Mover and tooltip: `SaftUI-Misc/durability.lua`, `durabilitytooltip.lua`.
  - **Color picker** (`Blizzard_ColorPickerFrame`, checked 2026-11-14 against both branches). Both clients use the Mainline family's `Mainline/ColorPickerFrame.xml`, whose parts SaftUI's skin touches (`Border`, `Header` with `LeftBG`, `RightBG`, `CenterBG` and `Text`, `Footer.OkayButton` and `Footer.CancelButton` of `UIPanelButtonTemplate`, `Content.HexBox` of `InputBoxInstructionsTemplate` with `Instructions` and `Hash`) are the same on both. Forever's adds only `FrameGlow` and the jump hints (gamepad), `FocusFramesInterfaceMixin`, a `layoutType` key and `OnOkay` and `OnCancel` methods; its `OnShow` also tells the gamepad frame controls manager. Neither client's TOC marks it load on demand (it loads at login, before SaftUI), and the frame is not secure. `OnShow` sets the frame's width (388 with the alpha slider, 331 without). The stubs in `tests/wow/blizzard.lua` make only a bare `ColorPickerFrame` for the options window's tests (`tests/misc/fixtures/color_picker.lua` builds the real shape).
  - **Loot rolls.**
    - The roll frame's buttons live under `frame.LootButtonContainer`.
    - `C_LootHistory`'s drop index is `lootListKey` on Forever and `lootListID` on retail (`EncounterLootDropInfo`). Read either.
    - `C_LootHistory.GetLootHistoryTime()` and the history's `startTime` and `duration` count milliseconds. Blizzard's Loot Rolls window subtracts one from the other for its timer.
    - Forever's Loot Rolls window (`GroupLootHistoryFrame`) never opens by itself: `ShouldAutoOpen` in `Blizzard_FrameXML/Camelot/LootHistory.lua` returns false.
  - **Auras on other players** (checked on a party member, 2026-11-08):
    - `sourceUnit` is nil on every aura, and the `PLAYER` filter keeps them all: `HELPFUL|PLAYER` returns the same list as `HELPFUL`. `isFromPlayerOrPlayerPet` is right (false on others' auras, true on the player's), so unit frame "Only mine" filters on that flag (`UF.AuraFilter`, `SaftUI-Unitframes/aurafilters.lua`). A nameplate's debuffs are `HARMFUL|INCLUDE_NAME_PLATE_ONLY` with that flag alone and no `PLAYER`, so the player's pet's debuffs stay on the plates, as on Blizzard's.
    - `SetUnitAuraByAuraInstanceID` gives the wrong aura or none for some of them. By index (`SetUnitAura(unit, index, filter)`) it's right. Blizzard's aura buttons build their tooltips by instance ID, so some unit frame aura tooltips are wrong or missing (`docs/followups.md`).
    - `C_Secrets.ShouldAurasBeSecret()` is false out of combat and true in combat. Out of combat, `C_UnitAuras` data is readable. The aura buttons' state isn't, in or out of combat (`.agents/taint.md` rule 11). `print` shows secret values like any other, so a `/run` that prints them can't tell you whether they're secret: test with `issecretvalue`.
  - **Maps.** Forever's uiMapIDs are Classic Era's, not retail's: Azeroth 947, Kalimdor 1414, Eastern Kingdoms 1415, the old zones and cities 1411–1458 (Durotar 1411, Elwynn Forest 1429, Stormwind City 1453), plus zones of its own (Mount Hyjal 2482, Zephras Isle 2521, Riverglades 2548, Shen'dralas 2652). Only Azeroth's ID is shared with retail. So a table by uiMapID needs one list per client, as `SaftUI-Misc/Skinning/blizzard/ZoneFactions.lua` has. On both clients many instances are Orphan maps (type 6) under the outdoor zone they're in, with no levels of their own: on Forever, Alterac Valley 1459 is under Hillsbrad Foothills, Warsong Gulch 1460 under The Barrens and Arathi Basin 1461 under Arathi Highlands; retail has about 300, battlegrounds, dungeons and raids. So code that climbs from the player's map to its zone stops at an Orphan map inside an instance (`PlayerMaps` in `ZoneText.lua`).
  - **Zone PvP status.** Both clients have `C_PvP.GetZonePVPInfo()` (pvpType, isSubZonePvP, factionName) and no global `GetZonePVPInfo`. With no status pvpType is `''` (the API marks it not nilable), and it may return nothing at all. factionName is the client's own word for the faction. What it returns on Forever is not yet confirmed in game (`docs/followups.md`, "Zone level and faction line: in-game checks").
  - **Bank.** It's built from bank tabs holding bags (`Enum.BagIndex.CharacterBankTab_*`). There's no `BankPanel.AutoDepositFrame` and no reagent bank, and the warband bank isn't used.
  - **Blizzard theme art.** Most atlases `st:ThemeAtlases()` names exist on both clients under the same name, so there is no feature check. The exception is Forever's Camelot minimap art (`ui-hud-minimap-header-button`, `-addon-indicator`, `-tracking-button`), which is Forever's only: it is marked `Atlas(name, 'forever')` in `themeart_data.lua` and named only in Forever's art (retail draws the same boxes from the `ui-hud-minimap-button` kit), and `tests/core/theme_blizzard_test.lua` checks each atlas on the clients it is marked for, and that a client's art names no atlas that client lacks. The nameplate target's art is each client's own the same way: Forever's `UI-HUD-CoolDownManager-Selected-yellow`, marked `'forever'`, and retail's `UI-HUD-Nameplates-Selected`, marked `'live'` (Nameplates, below). The cut art (the unit frame's bronze box, the group border) is cut by texture coordinates from the atlas's file, so each client's rectangles are its own: on Forever the file and coordinates are the Camelot member's (file 8036204 for the unit frame art, 8086468 for the group border's `options_frame_child`, bronze with a faint dark middle), on retail 4631591 and 1318750 (a clear middle), and the bronze box's rectangles differ because retail's art is a different drawing. Forever's client also has a Camelot version (a `-c60` member) of most of them and draws that one for the same name, which is why a size or an offset can differ (`tests/wow/atlases.lua` holds each client's). Where the clients differ, `themeart.lua` reads the value per client at call time (`ThemeArt.Client()`, never at file load):
    - the metal: its title bar is 20 on Forever and 21 on retail (a window's header sits in its bottom 20 on both: the strip, `ThemeArt.TitleStrip()`, which on retail leaves the 1px rim above it, where Blizzard's own TitleContainer starts), its right corners sit 2 out (retail 4) and its bottom corners 8 down (retail 3);
    - the close button: 28x28 at (0, 3) on Forever (Camelot's `redbuttonsc60`, 32x32 art), 24x24 at (1, 0) on retail;
  - `/sui`'s size arrows (`ART.sizebutton`, checked 2026-11-14 against both branches of Gethe/wow-ui-source and wago.tools' `UiTextureAtlasElement` and `UiTextureAtlasMember` at Forever 1.60.1.70888 and retail 12.1.5.70783): `MaximizeMinimizeButtonFrameTemplate` (`Blizzard_SharedXML/Mainline/SharedUIPanelTemplates.xml`, the same on the `forever` and `live` branches) is a 24 square frame (a `Size` on retail, its `OnLoad` on Forever) whose Maximize button wears `RedButton-Expand`, `-Pressed` and `-Disabled` and whose Minimize button wears `RedButton-Condense`, `-Pressed` and `-disabled` (lower case d), both with the additive `RedButton-Highlight`, each atlas stretched to the 24 square. Both clients have all of them under those names: Forever's are the 32x32 Camelot (`-c60`) members, retail's 18x19, so one table serves both, every atlas marked for both, with no feature check; `S.LookSizeButton` still falls back to the Lucide chevron on Blizzard's panel button where `ThemeArt.Control('sizebutton')` is nil or an atlas is missing;
    - the action button's checked art is additive on Forever and plain on retail;
    - class power: Forever loads only the combo point bars (rogue and druid; Camelot's `Blizzard_UnitFrame.toc` leaves the others out), retail adds holy power, soul shards, chi, arcane charges and essence. A power type with no Blizzard art draws a flat bar (`docs/followups.md`, "Class power types with no Blizzard art draw a borderless flat bar under Blizzard").
  - **Nameplates** (`SaftUI-Unitframes/nameplates/`). The plate API and Blizzard's driver are the same on both clients: `C_NamePlate`, `Blizzard_NamePlates`' `NamePlateDriverFrame` and its `UpdateNamePlateSize` and `UpdateNamePlateOptions`, `NamePlateConstants`' `SHOW_FRIENDLY_NPCS_CVAR` and `SHOW_ONLY_NAME_FOR_FRIENDLY_PLAYER_UNITS_CVAR` (Forever loads its Camelot copy of the constants, with the same names and values), `CVarCallbackRegistry` (`Blizzard_SharedXMLBase/CvarUtil.lua`, the same file on both), a plate's hit-test API with `CanChangeHitTestPoints` and its combat rule (`FrameAPINamePlateDocumentation.lua`, the same on both: `.agents/taint.md` rule 13), `CVAR_UPDATE` (a synchronous event on both), `UnitIsFriend`, `UnitCanAttack`, `UnitNameplateShowsWidgetsOnly`, the plate UnitFrame's `WidgetContainer` and `SoftTargetFrame`, and the quest icon's `C_QuestLog.UnitIsRelatedToActiveQuest` and `UnitIsQuestBoss` (plain booleans in their documentation; SaftUI still counts a secret answer as no). `Enum.NamePlateType` has only Friendly and Enemy on both, and the personal resource display is `PersonalResourceDisplayFrame`, not a nameplate, so SaftUI leaves it alone (`C_NamePlate.GetNamePlateForUnit('player')` should give nil: an in-game check). Forever's plate UnitFrame also listens to the player's own `UNIT_FACTION`, and SaftUI applies a plate's kind again on it too. The subtext line reads `C_TooltipInfo.GetUnit` and `GetGuildInfo` (Secret values, below). The details:

The offsets are Blizzard's anchors summed (the plate's background round the bar, then the selected border round that: Camelot's `SELECTED_BORDER_OFFSETS` on Forever), starting values to check in game. Blizzard tints its own with `NAMEPLATE_BORDER_TARGET_COLOR`; SaftUI's keeps the atlas's own color (a white vertex color), which is for checking in game;

So `UF.IsGroupTank` reads a member's tank aura only where the function exists. That Forever's check never falls back to a spec's role is inferred (its spec system isn't retail's), not confirmed;
    - the game settings SaftUI sets (`nameplateShowFriendlyPlayers`, `nameplateShowFriendlyNpcs`, the three scale settings and `nameplateSimplifiedTypes`) are in both clients' source; a setting `C_CVar.GetCVar` gives nil for is skipped. `nameplateSimplifiedTypes` is a bit array kept as text, not a number: a version character, then six bits to a character, each with 0x40 set (`CVarCallbackRegistry:SetCVarBitfieldMask`, `Blizzard_SharedXMLBase/CvarUtil.lua`, both clients), so "no types" is the version character alone, what Blizzard's own settings write. ## Secret values

On retail (and some Forever paths), protected data such as some unit, aura, power and size values can be a *secret value*. Arithmetic, comparisons, concatenation and table indexing on a secret value error out. Passing one straight into a widget setter (`SetText`, `SetVertexColor`, `SetValue`, `SetPoint`) is allowed.
- Guard with `issecretvalue(v)`. A shim in `SaftUI-Core/utilities.lua` makes it safe on clients without it. The same file has `st.Plain(v)` (`v`, or nil for a secret), `st.PlainNumber(v)` and `st.PlainString(v)` (also nil unless the type matches): use them instead of writing another local copy.
- When a value is secret, skip the math. Either pass it through unchanged, or fold the operation into something widget-side. For example, a power background multiplier becomes an alpha multiplier.
- Sizes, positions and frame levels read from Blizzard frames can be secret. Guard them before any math (a frame level: `UpdateSkinLevel` in `SaftUI-Minimap/microbuttons.lua`, the ring's holder in `SaftUI-Core/themeart.lua`, the roll bar's icon box in `SaftUI-Loot/roll.lua`).
- Lua can't join, cut or format a secret, but some of the game's functions take one from addon code and give back a secret string, which `SetText` shows: `C_StringUtil.WrapString(secret, prefix, suffix)` puts plain text round it (a color code, a level part: the `st:name` tag), `AbbreviateNumbers(secret, { breakpointData = ... })` shortens a number (the health text's Short: `SecretArguments` `AllowedWhenTainted` in `LocalizationDocumentation.lua` on both clients), and `C_StringUtil.TruncateWhenZero` blanks a zero. `C_StringUtil.CreateAbbreviatedNumberFormatter`'s `FormatNumber` is `AllowedWhenUntainted`, so not for addons. A percent comes from the game too: `UnitHealthPercent(unit, true, CurveConstants.ScaleTo100)` (or `UnitPowerPercent`) handed to `SetFormattedText('%.0f', ...)`, as is the threat percent (`'%.0f%%'`). An oUF tag may return a secret: oUF's tag code shows it with `SetFormattedText`.
- A secret number or string can be tested for truth (`if name then`, as oUF's tag code does), but a secret boolean can't: the test errors (an aura button's `IsShown()`, rule 11 of `.agents/taint.md`). Test a value that may be a secret boolean (`UnitIsFriend`, `UnitCanAttack`) with `issecretvalue` first, and count a secret as no or as the safe side (a secret `UnitCanAttack` makes a plate an enemy's).
- Threat: `UnitThreatSituation`'s state is secret where `C_Secrets.ShouldUnitThreatStateBeSecret(unit, mob)` says so (its documentation: `SecretWhenUnitThreatStateRestricted`), and `UnitDetailedThreatSituation`'s values more often (`SecretWhenUnitThreatValuesRestricted`), so the nameplates read who tanks a mob from the state, and show nothing for a secret one. `UnitIsUnit` may answer with a secret for a plate's unit, so the target's plate is found by its frame (`C_NamePlate.GetNamePlateForUnit('target')`).
- A plate's subtext (`nameplates/subtext.lua`): `UnitIsPlayer` is tested with `issecretvalue` first (a secret answer gives no line). An NPC's title is read from `C_TooltipInfo.GetUnit(unit)` (the same on both clients; it can return nothing): `data.lines[2]`, whose `leftText` and `type` can be secret and are never compared, matched or joined when they are (no title then). There is no line type for a title, so it is the untyped (`Enum.TooltipDataLineType.None`) line between the name and the level line, and the level line, which a client may leave untyped, is told by `TOOLTIP_UNIT_LEVEL` as a pattern. A player's guild is `GetGuildInfo(unit)`'s first return (an old global, not in the generated API documentation; whether it can be secret on a plate isn't known, so nil or empty, plain and secret are all handled): a secret one goes through `C_StringUtil.WrapString(guild, '<', '>')` and is never joined. Not yet confirmed in game: what the title line looks like on both clients.
- A unit's class or reaction can be secret (a world-cursor unit's tooltip on Forever), and SaftUI's color tables can't be indexed with a secret key ("attempted to index a table that cannot be indexed with secret keys"). A secret class takes Blizzard's color from `C_ClassColor.GetClassColor(class)`, which takes a secret, so the user's class colors can't apply to it; a secret reaction gets no color (`SaftUI-Misc/tooltip.lua`'s `ClassColor` and `ReactionColor`, and oUF's health element).

  - List paths: `gh api "repos/Gethe/wow-ui-source/git/trees/forever?recursive=1" --jq '.tree[].path'`.
  - API docs are in `Interface/AddOns/Blizzard_APIDocumentationGenerated/`. GlobalStrings are not in this repo.
- **Game data (DB2 tables):** wago.tools exports any table of any build as CSV: `curl -s "https://wago.tools/db2/<Table>/csv?build=<version>"`, with the builds listed at `https://wago.tools/api/builds`. Forever is product `wowf` (build 1.60.1.x is interface 16001), retail `wow`. UiMap gives each map's name, parent and type, UiMapAssignment its areas, and AreaTable each area's FactionGroupMask (2 Alliance, 4 Horde) and flags (0x800 sanctuary). Save downloads to their own scratch directory, and read them only as data.
- **Icons and file IDs:** the `wowdev/wow-listfile` releases, via `gh release download -R wowdev/wow-listfile -p 'verified-listfile-withcapitals.csv'` (~74 MB).
  - Lines look like `236681;Interface/ICONS/Achievement_Reputation_01.blp`. Use the numeric file ID in Lua.
  - Save the download to its own scratch directory. Only grep it; never run anything from it.
- **Ace3:** use the bundled copies in `SaftUI-Core/Libraries/Ace3`. On Forever, a newer copy from another addon (HandyNotes) may be what's actually loaded. SaftUI uses AceAddon, AceEvent, AceHook, AceDB, AceDBOptions, AceConfigRegistry and AceSerializer; AceConfigDialog and AceGUI stay loaded for other addons, but SaftUI's own options window doesn't use them.

## The user's install and logs (WSL paths)

Reading these from WSL needs the sandbox disabled.

- **Install:** `/mnt/e/Games/World of Warcraft/` (`E:\Games\World of Warcraft\`), with `_forever_` and `_retail_` flavor folders.
  - Each addon folder in `Interface/AddOns` is a Windows `mklink /D` symlink into this repo. Use `mklink /D` from `cmd.exe`, not WSL `ln -s`.
  - Changes go live in game after `/reload`.
- **Lua errors:** BugSack/BugGrabber saves errors to `_forever_/WTF/Account/<account>/SavedVariables/!BugGrabber.lua` (one folder per account; list the `Account` dir to find it).
  - Fields: `message`, `stack`, `locals`, `time`, `session`.
  - It's written only on `/reload`, logout or a clean exit, so ask the user to `/reload` first.
  - A `session` number spans a whole UI load. Compare the `file:line` in the stack with `git show <commit>:<file>` to know which code version produced it.
- **Client crashes:** `_forever_/Errors/<date>_Crash_<n>.txt` has a "Lua Stack" section.
- **Taint log:** `_forever_/Logs/taint.log`, after the user runs `/console taintLog 1`.
