# Testing

`tests/` holds SaftUI's Lua tests. They check logic that can be computed outside the game (math, layout and ordering, state, settings get/set mappings, pure helpers) by loading SaftUI's real files on WoW's Lua 5.1, over stubbed WoW API. They're for agents and development. Nothing in `tests/` is linked into AddOns, listed in a TOC or loaded by the game, and the user's in-game check stays the final word.

## Running the suite

- `tests/run` from the repo root runs every `tests/**/*_test.lua`. `tests/run PATH...` runs those files, or the `*_test.lua` files in those folders. Paths are relative to where you are, so `cd SaftUI-Core && ../tests/run ../tests/core` works. `-v` lists every case and shows what the tests printed. `-jN` runs N files at once (default: the CPU count); `-j1` runs them one after another in the runner's own process, with no worker processes, so a problem in the parallel runner can be told apart from a problem in a test. A bad `-j` value (not a whole number, or under 1) exits 2.
- It exits 0 only if every file loaded, ran at least one check and had no failures. Exit 1 means test failures, 2 bad arguments, 70 a crash of the runner itself (traceback on stderr); only 0 is a pass. A file that errors while loading, registers no `test()` cases, or has a case that runs no checks fails the run.
- Each file runs in its own fresh Lua state, so files can't leak into each other. In parallel each file also gets its own worker process, and the report is printed in file order whatever order they finish in: the same text as `-j1` (a test that prints its own timings, like `slowest layout: ... ms` under `-v`, differs between any two runs). A worker that dies, or raises a Python exception, is a runner crash: exit 70, naming the file. The run's wall time is about the slowest file plus the rest divided over the cores, so on a shared machine it varies; `--timings=FILE` (hidden, like `--crash-for-self-check`) writes each file's seconds, for measuring.
- The first run makes `tests/.venv` (git-ignored) with lupa 2.8, Python's binding to genuine Lua 5.1. If that fails (no network), the message names the commands to run by hand, or set `SAFTUI_TEST_PYTHON` to a Python that already has lupa (made in a virtual environment, not the system Python). It never falls back to another Lua version.
- A git worktree with no `tests/.venv` of its own uses the main checkout's (`<git common dir>/../tests/.venv`) when that exists, and makes its own only if neither does.
- A file's loading, and each of its cases, may run 4 billion Lua instructions (the biggest unit today runs about 300 million, a few seconds), then the harness stops it with an error naming the file and case, so an endless loop fails instead of hanging the run.
- **The limit does not follow coroutines.** Lua 5.1's `debug.sethook` is per coroutine, so code running inside a coroutine (a `coroutine.wrap` body, or anything resumed from a test) is not counted, and an endless loop there hangs the run instead of failing it. Keep a loop a test drives out of coroutines, or bound it by hand.
- `tests/run --self-check` checks the runner itself: it runs each file in `tests/lib/runner_fixtures/` (no `_test` suffix, so discovery skips them) and asserts the passing one exits 0 and every broken one (a syntax error, no cases, a case with no checks, a failing check, an error in a case, an endless loop) exits 1 with its own failure text in the output and no Python traceback. It also runs the runner with a hidden `--crash-for-self-check=main`, `--crash-for-self-check=run_file` (serial, and in a worker) and `--crash-for-self-check=worker_death` (a worker that exits before running its file) and `--crash-for-self-check=worker_exit` (a worker that exits non-zero after sending its result): a crash before any file runs, one inside running a file, and a dead worker. It asserts each comes out as a crash (exit 70), not a pass or a caught failure. It asserts that `-j1` and `-j2` give the same report and exit status for all the fixtures, and that a bad `-j` value exits 2. A Python exception anywhere in the runner is a crash; a Lua error inside the harness is that file's failure (exit 1). Run it after touching `runner.py`, `harness.lua`'s `run_file` or `tests/run`; a new failure mode gets a fixture and a line in `FIXTURE_EXPECTED` in `runner.py` (exit status and expected output text).

## Writing a test

```lua
-- What this file checks, and the real files it loads.
load_core_helpers()
load_saftui('SaftUI-Core/EditMode/editmode.lua')
load_saftui('SaftUI-Core/EditMode/grid.lua')
local EM = SaftUI.EditModeFrames

test('GridLinePositions repeats out from the center', function()
	local p = EM.GridLinePositions(960, 0, 1920, 32)
	eq(#p, 61, 'line count')
	check(p[1] == 0 and p[#p] == 1920, 'first and last lines on the edges')
end)
```

The API (globals, defined in `tests/lib/harness.lua`):

| Call | Does |
| ---- | ---- |
| `test(name, fn)` | Registers a case. Cases run in order once the file has loaded. An error in `fn` fails the case with its traceback, and the next case still runs. |
| `check(cond, message)` | Records a pass, or a failure with `message` and its file:line. Doesn't stop the case. Returns `cond` as a boolean. Only inside a case. |
| `eq(actual, expected, message)` | `check(actual == expected)`, failing with `expected <e>, got <a>`. |
| `near(a, b)` | Whether two numbers differ by float drift only (under 1e-6); false when either is nil. For `check(near(a, b), message)`. |
| `load_saftui(path)` | Runs a SaftUI file by its path from the repo root (`'SaftUI-Core/api.lua'`), as WoW does: `...` is the addon folder name and that addon's namespace table, one per addon. Returns what the file returns. |
| `load_test_file(path)` | Runs a helper or fixture by its path from `tests/`. |
| `read_saftui_source(path)` | The text of a file in a `SaftUI-*` folder, by its path from the repo root (`'SaftUI-Core/SaftUI-Core_Forever.toc'`), CRLF made LF, under `load_saftui`'s path rules; nil and the reason for a file that isn't there. For a test that reads source instead of running it (`tests/core/theme_kinds_test.lua` reads every TOC, XML and Lua file the game loads). |
| `addon_namespace(addon)` | The namespace table `load_saftui` gives that addon's files (e.g. `addon_namespace('SaftUI-Unitframes').oUF`). |
| `reset_world()` | Rebuilds the stubs and the shell in the same Lua state, for files that want a fresh world per case. Globals made since the harness loaded are removed, and a base global or `string` / `table` / `math` member a test replaced (`print`, `pairs`, `string.format`) gets its value back; the test file's locals survive. Load SaftUI files again after it. |
| `take_errors()` | The errors reported to the game's error handler so far in this case, as a list, cleared. |
| `debugprofilestop()` | WoW's timer, in milliseconds (the process's CPU time), for a check on how long code takes. |
| `REPO_ROOT`, `TESTS_DIR` | Absolute paths. |

- Cases share the file's world and run in order. A case may build on the one before, or call `reset_world()` for a clean start.
- Keep test state in locals: `reset_world()` removes globals.
- The parts of Lua's library WoW lacks aren't there: `io`, `os`, `require`, `dofile`, `loadfile`, `package` and `module` are nil, for test files and SaftUI files alike. Load files with `load_saftui` or `load_test_file`, never end a run yourself (the runner owns the exit status), and add WoW's own `time` or `date` to `tests/wow/lua.lua` if SaftUI code needs them.
- `print` output is captured, and shown for a failing case (or with `-v`).
- The game shows an error passed to `geterrorhandler()` and carries on. So the stubbed handler records it, the code goes on as in game, and the case fails unless the test takes it with `take_errors()`. AceAddon-style `Enable`, event dispatch, scripts and `EventRegistry` callbacks all report errors this way.

## The test world

Every file starts with the WoW stubs and the core shell loaded.

- **The core shell** (`tests/lib/shell.lua`) stands in for `init.lua` and Ace3's plumbing, mimicking their behavior:
  - `SaftUI`, which is SaftUI-Core's namespace, as in game;
  - `NewModule` / `GetModule` / `IterateModules`, and on each module `Enable` (every `OnInitialize` in the module's subtree first, as AceAddon does at ADDON_LOADED, then `OnEnable`, then its modules', once each, errors to the error handler), `IsEnabled` (AceAddon's: true by default), `RegisterEvent` / `UnregisterEvent` (AceEvent's calling conventions; handlers run in registration order, but real CallbackHandler iterates with `pairs`, so **tests must not rely on handler order**), `SecureHook`, `SecureHookScript`, `HookScript` and `IsHooked` (AceHook's); `SetDefaultModuleLibraries` (AceAddon's, before any module exists);
  - `st.config.profile` (empty until `apply_defaults()`), `st:BindModuleConfig`, and `st.Config` with `Refresh` and `GetWindow` (no `/sui` window, so `nil`);
  - `remove_shell_config()`, which takes that Config module out so a test can load Core's real `Config/config.lua` (it makes the module itself). `tests/core/config_helpers.lua` does that, and sets up the rest of `config.lua`'s world.
  - `apply_defaults()`: Fills `st.config.profile` from `st.defaults` as AceDB's `copyDefaults` does (same conditions: a `false` under a table default is replaced by a table, a truthy non-table value stays): missing keys get deep copies, existing values stay, and the `['*']` / `['**']` wildcard keys work (never keys of the profile; a `'**'` table's defaults fill every sibling key, including keys made later by reading them, so `rawget` tells whether a key was made). Load the defaults files first.
  - `load_core_helpers()`: Loads Core's frame helpers for real: LibSharedMedia, `Widgets/button.lua`, `skinning.lua` (`st:SkinIcon`, and `st:IconTexCoords`, which the General tab's Icon zoom preview crops with), `panels.lua`, `theme.lua` (`st:SetTemplate`, `st:SetBackdrop` and the theme they draw), `themeart_data.lua` (the Blizzard theme's tables, which make `st.ThemeArt`) and `themeart.lua` (its accessors and drawing), the media, fonts and colors, `Media/theme.lua` (the Theme module, Global Settings' Theme tab, and `st:ThemeChanged`), `Config/defaults.lua` (then `apply_defaults()`), `Config/generators.lua` and `Config/general.lua` (Global Settings' General tab), and enables the Fonts module. Use it before anything that calls `st:CreateFrame`, `st:SetBackdrop`, `st:CreateButton`, `st:GetFont` or `st.Config.generators`.

Load `Config/optionsmodel.lua` first.   - `tick_options_window(elapsed)`: One frame passes on the `/sui` window's clock: its ticker's `OnUpdate` runs with `elapsed` seconds (0.01 by default); nothing runs before the window is built. It reads the window from `SaftUI` when called, so it follows a `reset_world()`.
  - `load_options_window()`: Loads the `/sui` window's own files (`st.OptionsWindow`: `Config/optionslayout.lua`, `optionswindow.lua` and the files after it) in the order `SaftUI-Core/Config/load.xml` loads them, the list `options_window_files()` returns. A test that needs the window calls this instead of loading its files one by one, so a new window file needs only the shell's list, and `tests/lib/harness_self_test.lua` fails when that list and `load.xml` disagree.
  - `load_editmode()`: Loads edit mode's files (`st.EditModeFrames`, `st:RegisterMover` and the rest) in the order `SaftUI-Core/EditMode/load.xml` loads them, the list `editmode_files()` returns, and `tests/lib/harness_self_test.lua` fails when the two disagree. Load Core's helpers first.
  - `load_string_format()`: Loads LibStringFormat-1.0 and makes it `st.StringFormat`, as `init.lua` takes it from LibStub. Load Core's helpers first.
  - `use_client(name, before)`: A fresh world on `'forever'` or `'retail'`: `reset_world()`, then `before()` if given (on the fresh stubs, to change what `constants.lua` reads, such as the player's name), `stub.interface` set to the client's, the globals that client lacks dropped (`stub.apply_client()`) and `constants.lua` run again, so `st.forever` follows; returns SaftUI. The caller loads the rest of its world after it (`load_core_helpers()`, or `core/config_helpers.lua`); `T.client`, `tests/bags/bag_world.lua`'s `W.fresh` and the worlds of `tests/bags/theme_test.lua` and `tests/core/options_settings_test.lua` start from it. An unknown client is an error.

  It then loads Core's real `constants.lua`, `api.lua` and `utilities.lua` in TOC order, and sets UIParent's scale to `st.scale`, as `init.lua` does.
- **The `stub` table** puts the game in a state: `stub.interface` (16001, Forever), `stub.screen_width` / `screen_height` (UIParent follows them and its scale), `stub.in_combat` (with `stub.blocked`, the calls blocked on a protected frame in combat), `stub.cursor_x` / `cursor_y`, `stub.cursor_item` (what the cursor holds, for `GetCursorInfo`: nil, or an item picked up, `{ id, link }`; `ClearCursor` drops it), `stub.time` (GetTime), `stub.epoch` (`time()`), `stub.shift_down` / `ctrl_down` / `alt_down`, and `stub.loaded_addons` (a set of names for `C_AddOns.IsAddOnLoaded`), `stub.installed_addons` (the addons the client has, loaded or not, for `C_AddOns.DoesAddOnExist`; a loaded one exists too), the player's experience: `stub.max_level`, `level`, `xp`, `xp_max` and `rested_xp` (nil for none), where the player is: `stub.maps` (the game's maps by uiMapID: name, map type, parent, levels and where it sits on its parent), `stub.player_map`, `stub.pvp` (`C_PvP.GetZonePVPInfo`'s answer; its type is `''` by default, as the game gives with no status), `stub.instance` (nil outside one) and `stub.zone_text` / `stub.subzone_text`; and `stub.units`, other units by token (e.g. `stub.units.target = { name, level, class, classification, reaction, player, controlled, party_ai, dead, friend, attackable, quest, quest_boss, role }`) for the unit API (`UnitName`, `UnitClass`, `UnitLevel`, `UnitClassification`, `UnitIsPlayer`, `UnitPlayerControlled`, `UnitInPartyIsAI`, `UnitReaction` between a listed unit and the player, `UnitIsDead`, `UnitIsFriend`, `UnitCanAttack`, `UnitExists`, the quest icon's two questions and `UnitGroupRolesAssigned`; a field may hold a secret from `tests/lib/secrets.lua`), the player's own being `stub.dead`, `stub.class` and `stub.role`; a unit not listed doesn't exist. The nameplates', the game settings', the spellbooks', threat's and the group's controls are with `game.lua` in the table above. Its helpers:
  - `stub.state(widget)` reads what the API has no getter for (e.g. `.color_texture`);
  - `stub.fire_event(event, ...)` fires a game event to every registered frame, and so to shell modules;
  - `stub.fire_script(widget, script, ...)` runs a script handler and its hooks;
  - `stub.click(button, ...)` is the user clicking it: its `OnClick` through `stub.fire_script`, with any arguments given.
- **Layout.** Frames are laid out from their anchors and sizes, so `GetLeft`, `GetWidth`, `GetRect` and the rest work as in game. `UIParent` fills the screen. A scroll frame places its scroll child as the game does, at its own top left moved up by the vertical scroll, at the child's own size, whatever anchors the child has; so rows in a scrolled list, and `IsMouseOver` on them, follow the scroll (`tests/bags/categories_scroll_test.lua`'s scrolling tests).
- **Alpha.** `SetAlpha` keeps an alpha within 0 to 1 on a frame and on a region, as the game does (below 0 is 0, above 1 is 1), and still wants a number, so a test that sets 1.5 reads back 1.

2. **Strict.** A stub widget answers only the methods `tests/wow/` defines. Any other name is nil, so calling it errors with the method's name. Never add a catch-all `__index` that turns unknown names into no-ops. When a test needs a method, add it.
3. **Faithful.** A stub behaves like the real API, including how it fails:
   - a widget method called with the wrong type of self errors "Wrong object type" (a FontString's `SetText` on a Button);
   - `SetText` on a font string with no font errors "Font not set";
   - `SetFontObject(nil)`, an unknown template, point, strata or script name, and an anchor loop all error.
   - `SetTexCoord` takes 4 numbers (left, right, top, bottom) or 8 (the corners) and errors on any other count, and `GetTexCoord` gives the eight corners, the whole texture before any `SetTexCoord`.
   - `GetStringWidth` of a font string with a width and `SetWordWrap(false)` is cut to that width, as in the modern client; `GetUnboundedStringWidth` is the text's full width. Code that sizes a reused label from its text uses the unbounded one.
   - `SetFontObject` keeps a font set with `SetFont`: in game a reused dropdown kept a font list's face through `SetFontObject` with the same object (whether another object clears it is unverified; the stub keeps it either way). Code that reuses a font string sets its font outright (`SetFieldFont` in `optionslook.lua`).

   A stub kinder than the real thing is a bug in the stub: it lets a test pass where the game errors. Check real behavior in Blizzard's source (Gethe/wow-ui-source, `forever` branch; widget methods in `Blizzard_APIDocumentationGenerated`), as `.agents/clients.md` describes.
4. **Say what can't be mimicked.** The stubs don't run the game's layout pass (so `OnSizeChanged` never fires by itself, and a font string is one line, never wrapped), `OnUpdate`, secret values or taint, and can't tell which frames are protected: a test marks one with an `IsProtected` of its own, and then its moves, sizes and shows are blocked in combat (`stub.blocked`). Nothing is placed on whole pixels: `SetRoundLayoutToNearestPixel` and the textures' snapping are only remembered, so a test checks that the rounding was turned on, not where things land. They are also kinder than the game in three ways a test can't see: `RegisterEvent` takes any event name (the game errors "Attempt to register unknown event"), `SetFont` and `SetTexture` always succeed (a missing file fails in game), and the trimmed `Enum.PowerType` errors on a name nobody stubbed while the game has the value. A test that needs one drives it by hand (`stub.fire_script`, a method overridden on one frame), with a comment saying so. A secret value is a `newproxy` userdata that errors on indexing, calling, `#`, `..`, arithmetic and ordering (`tests/lib/secrets.lua`'s `S.secret`; `tests/unitframes/power_text_test.lua` has its own). Lua 5.1 can't catch `==` against a number (`__eq` only fires between two tables or two userdata), so `secret == 5` quietly gives false where the game errors: code must guard with `issecretvalue` before any `==`, and a green test doesn't prove it did. Nor can it catch `string.format('%s', secret)` (it gives the label) or a boolean test (`if secret`, `not secret`): a userdata is always true in Lua, where the game errors on a secret boolean, so a test can't show that code checked one with `issecretvalue` first. A test that passes one to a font string overrides `SetText` / `SetFormattedText` on that one font string, since the stub's take only strings and numbers. Also not mimicked: a cooldown draws and times nothing (its swipe, edge and numbers' settings are only remembered, the color `SetSwipeTexture` takes after the texture is ignored, and `SetCooldown` isn't stubbed); a Slider keeps its `SetValueStep` and `SetObeyStepOnDrag` but never snaps a value to the step or passes `OnValueChanged` a `userInput` argument (code that needs a grid snaps itself and a test moves the slider with `SetValue`, between `OnMouseDown` and `OnMouseUp` for a drag); an EditBox takes and loses focus by `SetFocus` / `ClearFocus` only (the game also drops it when the box hides, and a box made with autofocus, the default, takes focus when shown; `SetAutoFocus` just remembers the setting); `SetClampRectInsets`, `SetWordWrap` and `SetMaxLetters` only remember the setting (text set or typed past the cap isn't cut); `StartMoving` doesn't follow the cursor and `StopMovingOrSizing` leaves the anchors as they are (a test places the frame between the two); a scroll frame doesn't clip its child (a part scrolled out of view is still drawn and still under the cursor by `IsMouseOver`, as the game's rectangle test has it) and has no horizontal scroll; `GameTooltip:Show()` doesn't size the tooltip to its lines (a test that needs its size gives it one with `SetSize`, as the Categories tab's tooltip test does); `ColorPickerFrame` is the Mainline-family picker (opacity is alpha), with no wheel or hex box and no `GLOBAL_MOUSE_DOWN` cancel, and not the Classic-family fields, and keeps whatever strata and level the code gave it (Blizzard's is DIALOG; a test sets that first) (a test swaps in a frame without `SetupColorPickerAndShow` to check the swatch then does nothing). The mouse is a position (`stub.cursor_x` / `cursor_y`): `IsMouseOver` is the rectangle test, and `IsMouseMotionFocus` is true for the topmost visible mouse-enabled frame under it. `C_Map.GetMapInfoAtPosition` finds a child map by the rectangle a test gives it (`area`), not the zone's real outline, one level down only.
5. **Pinned paths.** Tests name the real files they load, by path from the repo root.
6. **Shared stubs, local fixtures.** WoW's API goes in `tests/wow/`, for every test. Stand-ins for other addons (RestedXP, LibCandyBar) are fixtures beside their tests.

## When tests are required

- **Required:** any change to logic that can be checked outside the game (math, layout and ordering, state, settings get/set mappings, pure helpers) comes with tests in `tests/`.
- **Bug fixes:** a fix in tested logic starts with a failing test.
- **Not required:** visuals and interaction with Blizzard's frames stay in-game checks. Tests never replace the user's in-game check list.
- Before claiming work complete, run `tests/run`. It must pass.

## When a check goes red

1. Read it. A failure gives the file:line and message, and an error gives its traceback. An error the game would have shown is listed as reported to the error handler.
2. **Your change caused it:** fix the code. If the behavior changed on purpose, update the check to the new behavior and say why in the commit.
3. **Stricter or more faithful stubs caused it** (a stub now fails like the game): fix the test's setup, not its assertion.
4. **Otherwise it may be a real SaftUI bug** (including syntax Lua 5.1 lacks): stop, and report it with the failing output.
5. Never loosen an assertion, delete a failing check, or make a stub kinder to get a green run.
