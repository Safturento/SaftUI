# Testing

`tests/` holds SaftUI's Lua tests. They check logic that can be computed outside the game (math, layout and ordering, state, settings get/set mappings, pure helpers) by loading SaftUI's real files on WoW's Lua 5.1, over stubbed WoW API. They're for agents and development. Nothing in `tests/` is linked into AddOns, listed in a TOC or loaded by the game, and the user's in-game check stays the final word.

## Running the suite

- `tests/run` from the repo root runs every `tests/**/*_test.lua`. `tests/run PATH...` runs those files, or the `*_test.lua` files in those folders. Paths are relative to where you are, so `cd SaftUI-Core && ../tests/run ../tests/core` works. `-v` lists every case and shows what the tests printed. `-jN` runs N files at once (default: the CPU count); `-j1` runs them one after another in the runner's own process, with no worker processes, so a problem in the parallel runner can be told apart from a problem in a test. A bad `-j` value (not a whole number, or under 1) exits 2.
- **Scaled runs.** A file with `scaled_test` cases (see Writing a test) runs once more after its normal run, with only those cases, in a world at one other UI scale: 0.75 (1920 x 1080, Automatic), 1.25 (3200 x 1800) or 1.55 (3456 x 2234), in turn by the sum of the bytes of the file's repo-relative path (`ROTATION[sum % 3 + 1]` over 0.75, 1.25, 1.55), so files spread over the three. The runner gives that scale to each scaled run's own Lua state (under `--scales=all`, three of them, one per scale) as the global `TEST_SCALE` (nil in a normal run); the shell then builds every world (`reset_world`, `use_client`) at `use_scale(TEST_SCALE)`. `tests/run --scales=all` runs each file's scaled cases at all three, for the end of a phase and before a merge. `SAFTUI_TEST_SCALE=1.55 tests/run ...` (0.75, 1.25 or 1.55; any other value exits 2) puts every file's scaled run at that scale, to chase a failure seen at one scale; `--scales=all` wins over it, but a bad value still exits 2. Phase 1's scaled files, by their planned paths, get `tests/core/theme_scale_test.lua` 1.25, `tests/core/screen_margin_test.lua` 0.75 and `tests/unitframes/nameplate_pixel_test.lua` 1.25 in a normal run: 1.55, where lines are two pixels, runs only under `--scales=all` (or `SAFTUI_TEST_SCALE=1.55`), so a task that adds scaled cases runs `tests/run --scales=all` on its files. A scaled case shows in the report as `<name> [at 0.75]`, counts in the file's cases, checks and failures, and `--timings` counts the scaled runs' seconds in the file's.
- It exits 0 only if every file loaded, ran at least one check and had no failures. Exit 1 means test failures, 2 bad arguments, 70 a crash of the runner itself (traceback on stderr); only 0 is a pass. A file that errors while loading, registers no `test()` cases, or has a case that runs no checks fails the run.
- Each file runs in its own fresh Lua state, so files can't leak into each other. In parallel each file also gets its own worker process, and the report is printed in file order whatever order they finish in: the same text as `-j1` (a test that prints its own timings, like `slowest layout: ... ms` under `-v`, differs between any two runs). A worker that dies, or raises a Python exception, is a runner crash: exit 70, naming the file. The run's wall time is about the slowest file plus the rest divided over the cores, so on a shared machine it varies; `--timings=FILE` (hidden, like `--crash-for-self-check`) writes each file's seconds, for measuring.
- The first run makes `tests/.venv` (git-ignored) with lupa 2.8, Python's binding to genuine Lua 5.1. If that fails (no network), the message names the commands to run by hand, or set `SAFTUI_TEST_PYTHON` to a Python that already has lupa (made in a virtual environment, not the system Python). It never falls back to another Lua version.
- A git worktree with no `tests/.venv` of its own uses the main checkout's (`<git common dir>/../tests/.venv`) when that exists, and makes its own only if neither does.
- A file's loading, and each of its cases, may run 4 billion Lua instructions (the biggest unit today runs about 300 million, a few seconds), then the harness stops it with an error naming the file and case, so an endless loop fails instead of hanging the run.
- **The limit does not follow coroutines.** Lua 5.1's `debug.sethook` is per coroutine, so code running inside a coroutine (a `coroutine.wrap` body, or anything resumed from a test) is not counted, and an endless loop there hangs the run instead of failing it. Keep a loop a test drives out of coroutines, or bound it by hand.
- `tests/run --self-check` checks the runner itself: it runs each file in `tests/lib/runner_fixtures/` (no `_test` suffix, so discovery skips them) and asserts the passing one exits 0 and every broken one (a syntax error, no cases, a case with no checks, a failing check, an error in a case, an endless loop) exits 1 with its own failure text in the output and no Python traceback. It also runs the runner with a hidden `--crash-for-self-check=main`, `--crash-for-self-check=run_file` (serial, and in a worker) and `--crash-for-self-check=worker_death` (a worker that exits before running its file) and `--crash-for-self-check=worker_exit` (a worker that exits non-zero after sending its result): a crash before any file runs, one inside running a file, and a dead worker. It asserts each comes out as a crash (exit 70), not a pass or a caught failure. It asserts that `-j1` and `-j2` give the same report and exit status for all the fixtures, and that a bad `-j` value exits 2. A Python exception anywhere in the runner is a crash; a Lua error inside the harness is that file's failure (exit 1). Run it after touching `runner.py`, `harness.lua`'s `run_file` or `tests/run`; a new failure mode gets a fixture and a line in `FIXTURE_EXPECTED` in `runner.py` (exit status and expected output text). The scaled run has its own lines, `SCALED_EXPECTED` (a fixture, flags, `SAFTUI_TEST_SCALE`, exit status, text the output has and lacks): `scaled_ok.lua` in its rotation and under `--scales=all`, `scaled_fail_155.lua` failing at 1.55 only, and an unknown `SAFTUI_TEST_SCALE` exiting 2. The self-check runs with `SAFTUI_TEST_SCALE` taken out of the environment.

## Writing a test

```lua
-- What this file checks, and the real files it loads.
load_core_helpers()
load_saftui('SaftUI-Core/EditMode/editmode.lua')
load_saftui('SaftUI-Core/EditMode/grid.lua')
local EM = SaftUI.EditModeFrames

test('GridLinePositions repeats out from the center', function()
	local p = EM.GridLinePositions(960, 0, 1920, 32)
	eq(#p, 61, 'line count')
	check(p[1] == 0 and p[#p] == 1920, 'first and last lines on the edges')
end)
```

The API (globals, defined in `tests/lib/harness.lua`):

| Call | Does |
| ---- | ---- |
| `test(name, fn)` | Registers a case. Cases run in order once the file has loaded. An error in `fn` fails the case with its traceback, and the next case still runs. |
| `scaled_test(name, fn)` | A case of the file's normal run (k = 1, exactly as `test` is) that also runs in the file's scaled run, at `TEST_SCALE`. Its name shares `test`'s: a name either took errors. |
| `test_scale()` | The k the run's world is at: `TEST_SCALE` in a scaled run, else 1. |
| `check(cond, message)` | Records a pass, or a failure with `message` and its file:line. Doesn't stop the case. Returns `cond` as a boolean. Only inside a case. |
| `eq(actual, expected, message)` | `check(actual == expected)`, failing with `expected <e>, got <a>`. |
| `near(a, b)` | Whether two numbers differ by float drift only (under 1e-6); false when either is nil. For `check(near(a, b), message)`. |
| `load_saftui(path)` | Runs a SaftUI file by its path from the repo root (`'SaftUI-Core/api.lua'`), as WoW does: `...` is the addon folder name and that addon's namespace table, one per addon. Returns what the file returns. Loading `SaftUI-Core/Config/optionsmodel.lua` also loads `Config/optionsdefault.lua` right after it (the game's `load.xml` loads it later, after `generators.lua`; no file uses the kit at load, so the order doesn't matter), so a model loaded again keeps the reset kit (`harness_self_test.lua` pins it): a test never loads `optionsdefault.lua` itself. |
| `load_test_file(path)` | Runs a helper or fixture by its path from `tests/`. |
| `read_saftui_source(path)` | The text of a file in a `SaftUI-*` folder, by its path from the repo root (`'SaftUI-Core/SaftUI-Core_Forever.toc'`), CRLF made LF, under `load_saftui`'s path rules; nil and the reason for a file that isn't there. For a test that reads source instead of running it (`tests/core/theme_kinds_test.lua` reads every TOC, XML and Lua file the game loads). |
| `addon_namespace(addon)` | The namespace table `load_saftui` gives that addon's files (e.g. `addon_namespace('SaftUI-Unitframes').oUF`). |
| `reset_world()` | Rebuilds the stubs and the shell in the same Lua state, for files that want a fresh world per case. Globals made since the harness loaded are removed, and a base global or `string` / `table` / `math` member a test replaced (`print`, `pairs`, `string.format`) gets its value back; the test file's locals survive. Load SaftUI files again after it. |
| `take_errors()` | The errors reported to the game's error handler so far in this case, as a list, cleared. |
| `debugprofilestop()` | WoW's timer, in milliseconds (the process's CPU time), for a check on how long code takes. |
| `REPO_ROOT`, `TESTS_DIR` | Absolute paths. |
| `TEST_SCALE` | 0.75, 1.25 or 1.55 in a scaled run, set by the runner; nil in a normal run. The shell builds every world at it. Read it through `test_scale()`. |

- **When a case is a `scaled_test`.** Only when it holds at any scale, so it asserts whole pixels (`P.off`, the tokens), no overlap, inside its window or its fixed corners, and never a number of units (`eq(frame:GetWidth(), 24)` is a `test`: units change with k). A `scaled_test` runs at k = 1 in the normal run and again at one other scale; its world is built by `reset_world` / `use_client` at that scale, so a case that builds its own world gets it for free, and a case that calls `use_scale(k)` itself defeats the run. Read `test_scale()` for the k to expect. A tolerance of 1e-6 (or `P.off`) is right off a whole k, since the tokens carry about 1e-7 noise there. Three warnings:
  - The scaled run loads the file and runs only its scaled cases, so a scaled case builds its own world (or uses only the file's top level) and leans on no earlier case: state a plain `test` built is missing there, and the case fails as `<name> [at 0.75]`, which reads like a scale bug.
  - `set_screen` (edit mode's helper, Pixel for pixel) defeats the run as `use_scale(k)` does: the world is off the scale after it.
  - `use_client(name, before)` applies the scale again after `constants.lua`, so a screen its `before` sets is put back to the scale's, and a case that changes the screen on its own does it after the world is built.
- Cases share the file's world and run in order. A case may build on the one before, or call `reset_world()` for a clean start.
- Keep test state in locals: `reset_world()` removes globals.
- The parts of Lua's library WoW lacks aren't there: `io`, `os`, `require`, `dofile`, `loadfile`, `package` and `module` are nil, for test files and SaftUI files alike. Load files with `load_saftui` or `load_test_file`, never end a run yourself (the runner owns the exit status), and add WoW's own `time` or `date` to `tests/wow/lua.lua` if SaftUI code needs them.
- `print` output is captured, and shown for a failing case (or with `-v`).
- The game shows an error passed to `geterrorhandler()` and carries on. So the stubbed handler records it, the code goes on as in game, and the case fails unless the test takes it with `take_errors()`. AceAddon-style `Enable`, event dispatch, scripts and `EventRegistry` callbacks all report errors this way.

## The test world

Every file starts with the WoW stubs and the core shell loaded.

- **The core shell** (`tests/lib/shell.lua`) stands in for `init.lua` and Ace3's plumbing, mimicking their behavior:
  - `SaftUI`, which is SaftUI-Core's namespace, as in game;
  - `NewModule` / `GetModule` / `IterateModules`, and on each module `Enable` (every `OnInitialize` in the module's subtree first, as AceAddon does at ADDON_LOADED, then `OnEnable`, then its modules', once each, errors to the error handler), `IsEnabled` (AceAddon's: true by default), `RegisterEvent` / `UnregisterEvent` (AceEvent's calling conventions; handlers run in registration order, but real CallbackHandler iterates with `pairs`, so **tests must not rely on handler order**), `SecureHook`, `SecureHookScript`, `HookScript` and `IsHooked` (AceHook's); `SetDefaultModuleLibraries` (AceAddon's, before any module exists);
  - `st.config.profile` (empty until `apply_defaults()`), `st:BindModuleConfig`, and `st.Config` with `Refresh` and `GetWindow` (no `/sui` window, so `nil`);
  - `remove_shell_config()`, which takes that Config module out so a test can load Core's real `Config/config.lua` (it makes the module itself). `tests/core/config_helpers.lua` does that, and sets up the rest of `config.lua`'s world.
  - `apply_defaults()`: Fills `st.config.profile` from `st.defaults` as AceDB's `copyDefaults` does (same conditions: a `false` under a table default is replaced by a table, a truthy non-table value stays): missing keys get deep copies, existing values stay, and the `['*']` / `['**']` wildcard keys work (never keys of the profile; a `'**'` table's defaults fill every sibling key, including keys made later by reading them, so `rawget` tells whether a key was made). Load the defaults files first.
  - `load_core_helpers()`: Loads Core's frame helpers for real: LibSharedMedia, `Widgets/button.lua`, `skinning.lua` (`st:SkinIcon`, and `st:IconTexCoords`, which the General tab's Icon zoom preview crops with), `panels.lua`, `theme.lua` (`st:SetTemplate`, `st:SetBackdrop` and the theme they draw), `themeart_data.lua` (the Blizzard theme's tables, which make `st.ThemeArt`) and `themeart.lua` (its accessors and drawing), the media, fonts and colors, `Media/theme.lua` (the Theme module, Global settings' Theme tab, and `st:ThemeChanged`), `Config/defaults.lua` (then `apply_defaults()`), `Config/generators.lua` and `Config/general.lua` (Global settings' General tab), and enables the Fonts module. Use it before anything that calls `st:CreateFrame`, `st:SetBackdrop`, `st:CreateButton`, `st:GetFont` or `st.Config.generators`. It also loads `Config/optionsmodel.lua` and `Config/optionsdefault.lua` (after the generators, as the TOC does), so a page's table can call `st.Config.SavedIn` and `SavedAt` in any world.
  - `load_options_widgets()`: Loads the `/sui` window's widget files (`st.OptionsWidgets`: `Config/optionswidgets.lua` and the files after it) in the order `SaftUI-Core/Config/load.xml` loads them, the list `options_widget_files()` returns. Load `Config/optionsmodel.lua` first (it brings `optionsdefault.lua`).   - `load_options_window()`: Loads the `/sui` window's own files (`Config/optionsshare.lua`, the body's shareable options, then `st.OptionsWindow`: `Config/optionslayout.lua`, `optionswindow.lua` and the files after it) in the order `SaftUI-Core/Config/load.xml` loads them, the list `options_window_files()` returns. A test that needs the window calls this instead of loading its files one by one, so a new window file needs only the shell's list, and `tests/lib/harness_self_test.lua` fails when that list and `load.xml` disagree.
  - `tick_options_window(elapsed)`: One frame passes on the `/sui` window's clock: its ticker's `OnUpdate` runs with `elapsed` seconds (0.01 by default); nothing runs before the window is built. It reads the window from `SaftUI` when called, so it follows a `reset_world()`.
  - `load_editmode()`: Loads edit mode's files (`st.EditModeFrames`, `st:RegisterMover` and the rest) in the order `SaftUI-Core/EditMode/load.xml` loads them, the list `editmode_files()` returns, and `tests/lib/harness_self_test.lua` fails when the two disagree. Load Core's helpers first. `load_editmode_bar()` loads the bar's files (`EditMode/Bar/load.xml`, which `EditMode/load.xml` includes last; `editmode_bar_files()` lists them, checked the same way) after the options window's world (`tests/core/options_window_helpers.lua`), which gives it the kit's controls.

3. **Faithful.** A stub behaves like the real API, including how it fails:
   - a widget method called with the wrong type of self errors "Wrong object type" (a FontString's `SetText` on a Button);
   - `SetText` on a font string with no font errors "Font not set";

4. **Say what can't be mimicked.** The stubs don't run the game's layout pass (so `OnSizeChanged` never fires by itself, and a font string is one line, never wrapped (`FontString:IsTruncated()` says true for a text that doesn't wrap and is wider, by the stubs' guess of half the font's height a character, than its anchors' room)), `OnUpdate`, secret values or taint, and can't tell which frames are protected beyond the ones made from a secure template (`SecureActionButtonTemplate`, `SecureHandlerStateTemplate`) or given an `IsProtected` of the test's own, and don't spread protection to a protected frame's parents or anchor targets (a region of a protected frame is protected with it: the anchor family and scale of `REGION_PROTECTED` are refused on it in combat, its texture, color, text and alpha are not, and making a region is not refused, which the game's docs don't mark protected either): their moves, sizes and shows are blocked in combat (`stub.blocked`), but a frame that the game would count as protected by its anchors is not (a test checks those anchors), and a secure frame made in combat is not refused (the tracker's world counts the ones made in `TW.counts.secure`). Nothing is placed on whole pixels: `SetRoundLayoutToNearestPixel` and the textures' snapping are only remembered, so a test checks that the rounding was turned on, not where things land. Rects are worked out in double precision, where the game's layout works in single: a frame laid out 560 tall can come back 559.99994 in game and comes back 560 here, so a test of code that must allow for that drift sets the drifted size by hand (`options_small_dialog_test.lua`'s `OB.ScrollTo` case), or sets `stub.size_noise`, which adds a hair to every size read back (a button set to 26 reads 26.000002 in game: the whole-pixel cases of the small dialog, the menu and the Categories editor). They are also kinder than the game in three ways a test can't see: `RegisterEvent` takes any event name (the game errors "Attempt to register unknown event"), `SetFont` and `SetTexture` always succeed (a missing file fails in game), and the trimmed `Enum.PowerType` errors on a name nobody stubbed while the game has the value. A test that needs one drives it by hand (`stub.fire_script`, a method overridden on one frame), with a comment saying so. A secret value is a `newproxy` userdata that errors on indexing, calling, `#`, `..`, arithmetic and ordering (`tests/lib/secrets.lua`'s `S.secret`; `tests/unitframes/power_text_test.lua` has its own). Lua 5.1 can't catch `==` against a number (`__eq` only fires between two tables or two userdata), so `secret == 5` quietly gives false where the game errors: code must guard with `issecretvalue` before any `==`, and a green test doesn't prove it did. Nor can it catch `string.format('%s', secret)` (it gives the label) or a boolean test (`if secret`, `not secret`): a userdata is always true in Lua, where the game errors on a secret boolean, so a test can't show that code checked one with `issecretvalue` first. A test that passes one to a font string overrides `SetText` / `SetFormattedText` on that one font string, since the stub's take only strings and numbers. Also not mimicked: a cooldown draws and times nothing (its swipe, edge and numbers' settings are only remembered, the color `SetSwipeTexture` takes after the texture is ignored, and `SetCooldown` isn't stubbed); a Slider keeps its `SetValueStep` and `SetObeyStepOnDrag` but never snaps a value to the step or passes `OnValueChanged` a `userInput` argument (code that needs a grid snaps itself and a test moves the slider with `SetValue`, between `OnMouseDown` and `OnMouseUp` for a drag); an EditBox takes and loses focus by `SetFocus` / `ClearFocus` only (the game also drops it when the box hides, and a box made with autofocus, the default, takes focus when shown; `SetAutoFocus` just remembers the setting); `SetClampRectInsets`, `SetWordWrap` and `SetMaxLetters` only remember the setting (text set or typed past the cap isn't cut); `StartMoving` doesn't follow the cursor and `StopMovingOrSizing` leaves the anchors as they are (a test places the frame between the two); a scroll frame doesn't clip its child (a part scrolled out of view is still drawn and still under the cursor by `IsMouseOver`, as the game's rectangle test has it) and has no horizontal scroll; `GameTooltip:Show()` doesn't size the tooltip to its lines (a test that needs its size gives it one with `SetSize`, as the Categories tab's tooltip test does); `ColorPickerFrame` is the Mainline-family picker (opacity is alpha), with no wheel or hex box and no `GLOBAL_MOUSE_DOWN` cancel, and not the Classic-family fields, and keeps whatever strata and level the code gave it (Blizzard's is DIALOG; a test sets that first) (a test swaps in a frame without `SetupColorPickerAndShow` to check the swatch then does nothing). The mouse is a position (`stub.cursor_x` / `cursor_y`): `IsMouseOver` is the rectangle test, and `IsMouseMotionFocus` is true for the topmost visible mouse-enabled frame under it. `C_Map.GetMapInfoAtPosition` finds a child map by the rectangle a test gives it (`area`), not the zone's real outline, one level down only. A texture keeps two alphas here, `SetAlpha`'s (a region alpha) and its vertex color's, stored as two numbers (`Region.GetEffectiveAlpha` ignores the vertex alpha); whether the client keeps one value that `SetAlpha` and an explicit vertex alpha both write is unverified (the opaque micro button hover of 2026-11-16 points to it; the `/run` lines that decide are in `docs/followups.md`, "Micro buttons' hover: one alpha a texture or two"), so a case that needs one models it on its own texture (`one_alpha` in `tests/minimap/interaction_states_test.lua`), never on the stubs. That model assumes a 3-argument `SetVertexColor` leaves the alpha alone (the repo's evidence: SaftUI fades Blizzard's performance bar and loot row art once with `SetAlpha(0)` while Blizzard recolors them with 3 arguments, and they stay faded), not that it resets it to 1.
5. **Pinned paths.** Tests name the real files they load, by path from the repo root.
6. **Shared stubs, local fixtures.** WoW's API goes in `tests/wow/`, for every test. Stand-ins for other addons (RestedXP, LibCandyBar) are fixtures beside their tests.

## When tests are required

- **Required:** any change to logic that can be checked outside the game (math, layout and ordering, state, settings get/set mappings, pure helpers) comes with tests in `tests/`.
- **Bug fixes:** a fix in tested logic starts with a failing test.
- **Not required:** visuals and interaction with Blizzard's frames stay in-game checks. Tests never replace the user's in-game check list.
- Before claiming work complete, run `tests/run`. It must pass.

## When a check goes red

1. Read it. A failure gives the file:line and message, and an error gives its traceback. An error the game would have shown is listed as reported to the error handler.
2. **Your change caused it:** fix the code. If the behavior changed on purpose, update the check to the new behavior and say why in the commit.
3. **Stricter or more faithful stubs caused it** (a stub now fails like the game): fix the test's setup, not its assertion.
4. **Otherwise it may be a real SaftUI bug** (including syntax Lua 5.1 lacks): stop, and report it with the failing output.
5. Never loosen an assertion, delete a failing check, or make a stub kinder to get a green run.
