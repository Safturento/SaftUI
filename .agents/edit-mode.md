# Edit mode and `/sui`

SaftUI has its own edit mode. It never adds frames to Blizzard's Edit Mode.
- `/sui edit` or the `/sui` "Edit mode" button toggles it. It also follows Blizzard's Edit Mode opening and closing.
- Registered frames get a draggable overlay. Arrow keys nudge 1px, Shift+arrows 10px.
- Where overlays overlap, a list by the cursor names every one under it and marks the one a click or drag gets; the rest dim. Alt brings the next one to the front (`EditMode/picker.lua`, like `/fstack`). Overlays share one strata, so their frame levels decide which is on top: each gets its own pair (backdrop one below), handed out rising by `EM:BringToFront`. Don't set an overlay's level anywhere else.
- Clicking a frame opens `/sui` at that frame's section.
- A grid shows behind the UI while edit mode is on and Grid is enabled (`EditMode/grid.lua`). Two center lines sit on UIParent's center, rounded to a physical pixel (`EM:GetGridCenter`), and the other lines repeat outward every Grid size (`EM.GridLinePositions`), each 1 physical pixel thick. Snapping reads the same two functions, so what's drawn is what snaps. The grid also redraws from its own frame's `OnSizeChanged` (the screen events can fire before UIParent resizes). The lines are pooled textures on a SaftUI frame at `BACKGROUND` strata that never takes the mouse.
- The `/sui` footer has Grid, Snap to grid and Snap to frames toggles (green text when on), and `-` / size / `+` buttons that step Grid size by 4 between 8 and 128 (`EditMode/settings.lua`). `EditMode/footer.lua` (`EM:AddFooterButton`, `EM:UpdateFooter`) puts them on the window's footer region (`st.OptionsWindow:GetFooter()`, between Reload UI and Close) while edit mode is on and `/sui` is open, and takes them off otherwise; the window's status line then starts clear of them (`OW:SetFooterInset`). Edit mode works with `/sui` closed; the buttons just don't show. The "Edit mode" section in `/sui` holds the same toggles and a Grid size slider. The values are in the profile (`st.defaults.editmode`: `grid`, `grid_size`, `snap_grid`, `snap_frames`), and `EM:UpdateConfig` redraws the grid and toggles after a profile change.
- **The outline.** An overlay draws one 1px line (white, or blue with a blue tint when selected) `EM.OUTLINE_OUTSET` (2px) outside its rect, between two dark lines. That's where a thick SaftUI border's line sits, so frames look as far apart in edit mode as out of it. A frame whose border line sits elsewhere re-anchors its overlay so the line lands on it. Chat does this: its backdrop is `padding` outside the holder, so its overlay goes `padding - OUTLINE_OUTSET` out (`CHT:UpdateFootprint`). Don't color the overlay's dark lines; that widens the outline past the border.
- Dragging snaps (`EditMode/snap.lua`, wired into `EM:StartDrag` / `EM:UpdateDrag`). The dragged mover's outline (`EM.GetOutlineRect`: its overlay's rect plus `OUTLINE_OUTSET`) has its left, middle and right (and bottom, middle and top) pulled onto the nearest line within `EM.SNAP_REACH` (8 UIParent units). Snap to grid uses the grid's lines (same `EM.GridLinePositions` and `EM:GetGridCenter`, so it works with the grid hidden). Snap to frames uses the screen's center lines and the outline edges and centers of every other mover whose overlay is shown and on screen; with both on, the nearest line wins per axis. Snapping only corrects the drag's `x_off`/`y_off` (converted by the ratio of effective scales, rounded with `st:RoundToPixel`), never the anchor. Holding Ctrl suspends it, and arrow-key nudges ignore it. Movers whose frame moves with the dragged one (`st:MovesWith`: anchored to it, directly or through other frames, or its children) are skipped as targets, since they would shift during the drag. The lines are computed once at drag start. `EM.GetRectInUI` returns nil for a frame with a secret edge or scale (the Minimap's frame is Blizzard's), and that mover is skipped.
- It closes on combat and refuses to open in combat.

The spec is in `docs/superpowers/specs/2026-11-06-saftui-edit-mode-design.md`, and the plan (Tasks 1–15) in `docs/superpowers/plans/2026-11-06-saftui-edit-mode.md`. The grid and snapping have their own spec, `docs/superpowers/specs/2026-11-09-saftui-edit-mode-grid-snap-design.md`, and plan, `docs/superpowers/plans/2026-11-09-saftui-edit-mode-grid-snap.md`.

## Registering a mover

```lua
st:RegisterMover('key', {
	frame = holderOrFrame,        -- the overlay does SetAllPoints on this; it needs a real size
	label = 'Name',
	getPosition = function() return self.config.position end,   -- read through self.config at call time
	setPosition = function(pos) self.config.position = pos end,
	apply = function() self:ApplyPosition() end,                 -- can run in combat lockdown
	configPath = { 'ModuleName', 'section', 'general' },         -- keys from the /sui root to a leaf group
})
```

- **Offsets.** Drags and nudges write pixel-rounded `x_off`/`y_off` into the table from `getPosition()`, call `setPosition`, then `apply` (about every 0.1s while dragging, and once at drag end). Drags keep the frame's anchor point and relative frame. Only the offsets change.
- **`apply`** must go through `st:SafeReposition`, because a secure frame anchored to yours makes it protected in combat.
- **`configPath`** must resolve in `Config:GetOptionsTable`. Module tables are keyed by module name. End the path at a leaf group, usually `general`, since selecting a parent that only holds subgroups shows an empty pane.
- **Holder pattern.** Use a SaftUI holder frame when the real frame:
  - can be empty or hidden (loot rolls, boss and party/raid groups, closed bag windows),
  - has no size (the micro menu container), or
  - belongs to Blizzard (swing timer, buffs, chat, the extra action button and zone ability).

  Size the holder from the config, place it from the profile, and anchor the real frame to it. The overlay then always has a footprint.

  A SaftUI frame that's only hidden, and still sized and placed from the profile while hidden, can be its own mover frame: the overlay follows its edges either way. SaftUI's action bars (`SaftUI-ActionBars/options.lua`) move their secure headers this way, also while a bar is disabled or hidden by its Visibility setting, and while the pet bar has no pet or the stance bar no forms (laid out as one button then, so the outline keeps a size). Label the outline when the frame may not be visible (`mover.label:SetText`), as the action bars and the swing timer do. The extra buttons' outlines (`SaftUI-ActionBars/options.lua`) always say when they show, as they mostly don't.
- **Taking over a Blizzard Edit Mode frame.** The swing timer bars (`SaftUI-Misc/Skinning/Blizzard_SwingTimerPosition.lua`), buffs (`Blizzard_BuffFramePosition.lua`), chat (`SaftUI-Chat/chatframe.lua`), the default tooltip's `GameTooltipDefaultContainer` (`SaftUI-Misc/tooltipposition.lua`; the tooltip itself is never moved) and, on a shaman, Forever's totem bar `MultiCastActionBarFrame` (`SaftUI-Misc/totembar.lua`, mover `totembar`) all follow the same pattern:
  - Use a holder.
  - Re-anchor the Blizzard frame with `st:SetPointDirect` / `st:ClearAllPointsDirect` in post-hooks on its `SetPoint` / `ClearAllPoints` / `UpdateSystem`. If it's protected (the totem bar holds secure buttons), the re-anchor waits for the end of combat (`st:QueueAfterCombat`), and the holder goes through `st:SafeReposition`.
  - Where Blizzard's Edit Mode can read the frame's anchor (a snap break, when the frame it's snapped to hides, records it into the layout through `UpdateSystemAnchorInfo`, and a layout save keeps it), don't anchor the frame straight to a SaftUI holder. Place it on UIParent at the holder's spot instead, from the holder's rect, and again whenever the holder moves or resizes (the totem bar's `TB:AnchorBar`, run from a post-hook on the holder's `SetPoint`). Otherwise the layout names the holder, and Blizzard anchors the frame to a missing frame wherever the holder doesn't exist. Chat copies its holder's own anchor instead (`CHT:PlaceChatFrame`), so the layout would name the holder's relative frame, UIParent by default.
  - Hide its `Selection` box with a `HookScript('OnShow', Hide)`.
  - List which Blizzard settings become unreachable, and rebuild the useful ones in `/sui`.
  - Keep first load from moving anything. Profiles saved before the takeover have no position, so either give `position` a default that reproduces Blizzard's default layout (swing timer, buffs) or give it none and capture the frame's spot on screen once Blizzard's Edit Mode has placed it (the totem bar, `TB:CapturePosition`, and chat's size, `CHT:CaptureSize`). Blizzard's layout can arrive after SaftUI loads, and a frame in its default position can sit somewhere temporary until Blizzard lays it out (a totem bar in its default position waits at UIParent's top-left until it first shows), so capture outside Blizzard's re-places, on the next frame.

  Read `.agents/taint.md` first.
- **When post-hooks can't hold it.** The extra action button and the zone ability (`SaftUI-ActionBars/extras.lua`) live in Blizzard's `ExtraAbilityContainer`, which lays its frames out again each time one is added, in combat too. `ExtraActionBarFrame` holds a secure button, so a post-hook couldn't move it back until combat ends. So SaftUI moves none of Blizzard's frames. It anchors what Blizzard never re-anchors (`ExtraActionButton1`, the zone's `SpellButtonContainer` and `Style` art) to the holder once, out of combat, and the buttons then show at SaftUI's spot even when they first appear mid-fight. Blizzard's empty frames stay in Blizzard's layout; make any that take the mouse click-through (`AB:DisableMouse` in `SaftUI-ActionBars/hideblizzard.lua`), so they don't block clicks to what's under them. Before using this, grep both branches to confirm nothing re-anchors the inner frame. The totem bar combines both patterns: Blizzard re-places the bar itself in combat, so its buttons are anchored straight to the holder too and only the empty bar frame moves until combat ends. Blizzard's own button update re-anchors two of them to the bar (the first element and the summon pages), so in a fight that runs it while the bar is elsewhere they follow the bar until combat ends. Size Blizzard's buttons with a Scale setting (the widget's own `SetScale`), since their art is laid out for one size.
- **Validating anchors.** The Position editor's typed relative frame is validated with `st:ValidateAnchor(target, name)`. Always pass `target` (the frame being moved) so self-anchors, anchor loops and descendants are rejected.
- **Profile switches.** `EM:ClearPositions` then `EM:UpdateConfig` re-apply every mover. Implement `UpdateConfig` in your module too (see `.agents/architecture.md`).
- **Test modes.** Loot rolls/feed and party/raid groups have session-only test toggles that draw SaftUI-owned previews anchored to the holder. Never fake units or override Blizzard APIs.

## `/sui` options

- `/sui` is SaftUI's own window (`st.OptionsWindow`, below), drawn from the tree `Config:GetOptionsTable` builds from each module's `GetConfigTable()`. AceConfigDialog no longer draws it.
- `st.Config:Open(...path)` rebuilds the tree, registers it with AceConfigRegistry as `st.name`, and opens the window at the path's page, picker value and tab (`OM.SelectionForPath`). `st.Config:Close()` closes it, and `st.Config:GetWindow()` is its frame while it's open, else nil. `st.Config:Refresh()` (AceConfigRegistry's NotifyChange) re-renders an open window on the next frame.
- **How a table maps onto the window.** The model (`SaftUI-Core/Config/optionsmodel.lua`, `st.OptionsModel`) reads AceConfig option tables as AceConfig defines them, so a module's `GetConfigTable` is a plain AceConfig table:
  - A top-level group is a sidebar page: its `name` is the page title and its `desc` the line under it.
  - The page's child groups that aren't inline are its tabs (whatever its `childGroups`, except `'select'`, which makes them the picker). Inside the chosen tab or pick, child groups that aren't inline are a second tab row, or the picker when that group says `'select'`. Anything deeper is drawn as sections on the page; nothing is dropped.
  - Inline groups (`inline = true`, or the parent's `childGroups = 'inline'`) are sections titled with their `name`, with any `desc` as a note. A `header` starts a section titled with its name. Options after a nested group continue in an untitled section.
  - Options are rows in `order` (100 by default, negative orders last, then by name), packed by `size`: `'small'` (toggle, color, execute, input only) takes a quarter of a line, two to a half; no `size` is normal and takes a half; `'wide'`, and every `description` and `position` row, take a line of their own. Ace's `width` is not read.
  - Hidden and `guiHidden` options are left out; disabled ones are dimmed and don't respond. `get`, `set`, `func`, `validate`, `confirm`, `disabled`, `hidden` and `handler` are inherited from parent groups, method-name strings resolve on the handler, and function-valued `name`, `desc`, `values`, `disabled` and `hidden` are called with an AceConfigDialog-style `info`.
  - A failed `validate` shows in the footer's status line (an input keeps the text typed). `confirm` asks in SaftUI's confirm dialog. A `set` re-renders the page.
  - Each type has a widget: toggle, range (slider and value box), select (a dropdown; `dialogControl = 'LSM30_Font'` lists each font in its own face), multiselect (checkboxes), input, color (Blizzard's color picker), execute (a button), keybinding, description.
- **Sidebar groups.** A module's top-level table sets `category`: Frames (Unitframes, ActionBars, Inventory, Chat, Minimap, MicroMenu), Combat (Auras, SwingTimer, TotemBar) or Info (Loot, Experience, Tooltip, Skinning). A page without one lists under Other (Edit mode does). Fonts shows as Global Settings and AceDBOptions' table as Profiles, at the top. `category` is SaftUI's field (as are `size`, `target` and `nameKey`, and the `position` type), and AceConfigRegistry's validator rejects what it doesn't know, so the tree is registered with validation skipped (AceConfigRegistry only validates when its getter hands the table to a UI, which nothing does for SaftUI's). `tests/core/options_validate_test.lua` (and `tests/unitframes/config_test.lua` for the unit frames) runs the validator over the built tree instead, through `ace_ready` (`tests/core/options_walk.lua`: a copy with SaftUI's fields and Position options left out), so a malformed module table fails the suite. `tests/core/options_desc_test.lua` checks that every option on a finished page has a `desc` and none has a `width`.
- **Subcommands.** `st.Config:AddCommand(command, label, func)` makes `/sui <command>` run `func`, and adds a `label` button after "Edit mode" at the top of the window's sidebar (`st.Config:GetCommands()` lists them). Call it at file load or in `OnEnable`. SaftUI-ActionBars adds `kb` (Keybind mode, `SaftUI-ActionBars/bindings.lua`).
- **Section shape.** A mover's section is a group with a `general` subgroup whose last option is its Position option (`order = 1000`, after everything else in General), plus any others it needs (e.g. the action bars' Text and Visibility). Size and position sit together, and the mover's `configPath` ends at `general`. A Position option that isn't in a General group (a unit frame element's) still comes after every other option of its group: the window gives it a section of its own, and options after it would follow on untitled. `Config:GetOptionsTable` then:
  - moves a `position` *group* beside General into it (`MergePositionIntoGeneral`); the generators' Position is an option, which modules place themselves;
  - turns innermost subgroups into tabs (`UseTabsForInnermostSections`, `childGroups = 'tab'`) unless the group already sets `childGroups`.
  - A page of many of one thing sets `childGroups = 'select'` on its top-level table: its child groups become the picker (a dropdown under the tabs), and theirs the tabs. Unitframes (its units, in the fixed order its `UNIT_ORDER` gives, Player first, and its Profile group, which sorts last) and ActionBars (its bars and extra buttons) do.
  - A unit frame's section shows its elements as tabs (General, Health, Castbar, ...): one per element that registered a `GetConfigTable` and whose `ValidUnit` accepts the unit. Keep sub-areas inside a tab as inline groups.
- **Widgets** are `st.Config.generators` in `SaftUI-Core/Config/widgets.lua`. None sets Ace's `width`; `desc` is the tooltip, and `size` (where taken) is `'small'` or `'wide'`:
  - `position(order, global_frame, get, set, target, desc)` is the full SetPoint editor: one option of type `position` (the Position block), whose `get`/`set`/`validate` take the part first (`point`, `rel_point`, `x_off`, `y_off`, and with `global_frame` a typed `frame`, so `target = 'name'`). `get`/`set` are the caller's `get(key)` / `set(key, value)`, or a table for `get` and no `set`. Offsets read as numbers and are stored as numbers rounded to the pixel. `target` (the frame being placed, or a function returning it) is what typed anchors are checked against with `st:ValidateAnchor`. `desc` defaults to a general line about placing a frame.
  - `uf_element_position(order, get, set, target, desc)` places a unit frame element, text or icon. Its TO part is a dropdown (`target = 'select'`, part `relative_to`: Unit frame, another element, or Global frame, whose name box shows while it's picked, `nameKey = '__global'`) that reads and writes `position.element` / `position.frame` the way `UF:GetFrame` resolves them, and clears a key with `false` so it overrides an AceDB default. Pass `UF:ConfigTarget(unit, element, key)` as `target`.
  - `toggle(order, name, desc, size)`, `range(order, name, min, max, step, desc, size)`, and `enable`, `alpha`, `framelevel`, `template`, `font`, `width`, `height`, each `(order, desc)`.
  - `width`/`height` are input boxes that display numbers and save numbers.
  - An `input` is text both ways (its `set` gets what was typed, as a string), so use these generators rather than raw inputs for numbers: they show the number and store a number.
- Option `get`/`set` must read through `self.config` (or `UF:GetProfileConfig()`) at call time, never a captured table.

## Options window (`SaftUI-Core/Config/optionswindow.lua`)

`st.OptionsWindow` (`OW`) draws `/sui` as the approved mockup lays it out (`docs/superpowers/specs/assets/2026-11-09-options-window-mockup.html`): 1040x700 in the thick template, at `FULLSCREEN_DIALOG` level 100, so edit mode's outlines draw under it. The model (`optionsmodel.lua`, `st.OptionsModel`) turns the tree into pages, tabs, a picker, sections and rows; the window draws them:
- **Sidebar** (210 wide): Edit mode and the command buttons, then Global Settings, Profiles and the category groups (`OW.SidebarEntries`), and the profile's name at the bottom.
- **Header:** the page's name (Colus 34) and desc (15, grey), and the close X (`st:CreateCloseButton`). Dragging the header or the sidebar's title moves the window; where it's left is saved as `st.config.global.optionsWindow = { point, x, y }` (account-wide) and restored on open.
- **Tabs** (17, the active one underlined blue), wrapping to more lines when they don't fit; a page's single tab isn't drawn. A second row for subtabs, then the picker row (the group's name and a select widget). The search box sits at the right of the first tab line.
- **Body:** a scroll frame of sections, drawn by a body object (`st.OptionsBody`, `optionsbody.lua`: `OB.New(content, root, onChanged, width)`, then `body:Draw(sections)` or `body:DrawResults(sections, onPick)`, and `body:Release()`). Sections (`OB.LayoutSections`) have a 1px `#2e2e2e` line and a Colus 15 title between them, never boxes. An untitled section after another (rows that follow a nested group) gets no line, so it reads as a continuation. Rows (`OB.LayoutRows`) are 34 high in two 367-wide columns 40 apart, each two quarters 24 apart (`OB.QUARTER_GAP`); a wide row takes a line of its own. The label (16) is on the left and the widget right-aligned, except a toggle's check box and a color's swatch, which sit 10 after the end of the label's text; a small input's box is 60 wide (`OB.SMALL_INPUT_WIDTH`); an execute button stands alone, and a desc shows as the label's tooltip. The window's fonts live in `optionsbody.lua` too (`OB.Font`), since it loads first.
- **Footer:** Reload UI, the region `OW:GetFooter()` returns (edit mode's buttons go there while edit mode is on), the status line (validate errors, `OW:SetStatus`; `OW:SetFooterInset` starts it clear of edit mode's buttons), and Close.
- **Re-rendering** redraws the page, keeping the page, tab, picker value and scroll when they still exist. It runs straight away after the window's own set, except mid-drag (a slider's `onChanged` says so; the render waits for the mouse to be let go) and while Blizzard's color picker is open. On `ConfigTableChange` for `st.name` it runs on the next frame, several in a frame coalesced; never during a render (UF's profile select's `get` notifies), and not while the user is busy (a list or confirm dialog open, a drag, the color picker, typing in one of the window's boxes).
- **Search** runs `OM.Search` once typing pauses for 0.25s, and shows the results grouped by page, tabs and section. A click opens the row's page and scrolls it into view. Going to a page, tab or pick (or `Open` with a path) clears the search, a pending one too.
- **Esc** closes the window through a keyboard catcher that is on only while it's shown, not `UISpecialFrames`. Other keys pass on, and so does Esc while a box has the keyboard, the dialog is shown (its own catcher closes it) or Blizzard's color picker is open. It does nothing in combat; the window closes on `PLAYER_REGEN_DISABLED` and refuses to open in combat.
- The fonts are the window's own objects with the profile's title and normal faces at fixed sizes (`OW:UpdateFonts` on a profile change).
- **A small dialog:** `OW:OpenDialog(title, options)` shows an option table of its own (a group) in a small SaftUI window over `/sui`, drawn by a body of its own: the title (text, or a function read on each render), the close X, two columns of rows, a status line for validate errors. Its own set re-renders it. Esc closes it (its own keyboard catcher; the window's passes keys on while it shows), and so do closing the window and entering combat; it refuses to open in combat. It draws no tabs or picker. `OW:CloseDialog()`, `OW:IsDialogShown()`. UF's Copy from (`UF:OpenCopyTable`) uses it, with `confirm` on its Confirm copy button. Closing it cancels a confirm or prompt open over it.

Tests: `tests/core/options_window_test.lua` (the window, the dialog, edit mode's footer buttons) and `tests/unitframes/config_test.lua` (UF's Copy from).

## Options window widgets (`SaftUI-Core/Config/optionswidgets.lua`)

`st.OptionsWidgets` (`W`) draws the controls of SaftUI's own options window. `W.Create(parent, rowType)` gives a pooled widget (toggle, range, select, multiselect, input, color, execute, keybinding, description, position). `position` is the Position block: dots for the point and relative point, a frame name box or a dropdown, and X over Y with nudges; its `get`/`set`/`validate` take the part first (`point`, `rel_point`, `x_off`, `y_off`, `frame`, `relative_to`). `widget:Bind(root, row, onChanged)` reads with `OM.Get`, and a change the user makes runs `OM.Validate`, then `OM.Confirm` (asked with `W.Confirm`), then `OM.Set`, and calls `onChanged(ok, err)`. `widget:Release()` returns it to the pool. The select list and the confirm dialog are at `TOOLTIP` strata, above the window. `W.Prompt(text, initial, onAccept, opts)` is the same dialog with an edit box (one modal at a time: opening a confirm or prompt answers the open one No); it replaces StaticPopups, which sit under the window. UF's profile New, Copy, Rename, Delete, Export and Import use it (`SaftUI-Unitframes/config/config.lua`). Text heights count `\n` as line breaks. Widgets are SaftUI frames; the color picker is Blizzard's `ColorPickerFrame`, used only through `SetupColorPickerAndShow` (the swatch does nothing without it), and no Lua field is written onto it. Before showing it the swatch calls `SetFrameStrata('FULLSCREEN_DIALOG')` and `SetFrameLevel(swatch level + 10)` on it, since its own DIALOG strata opens it behind the window. Tests: `tests/core/options_widgets_test.lua`.

`st:CreateCloseButton(frame)` (`panels.lua`) makes the 24x24 close button (`st.CLOSE_X_BUTTON_SIZE`; `st.CLOSE_BUTTON_SIZE` stays the Blizzard buttons' size) (`close.tga`, a 16x16 canvas with the 10x10 X in the middle) and remembers it in a side table (`st:GetCloseButton(frame)`; nothing is written onto the frame, which may be Blizzard's); `st:CreateHeader` seats such a button in the header and leaves any other button the old look.

## Ace3's own windows

SaftUI doesn't use AceConfigDialog or AceGUI: `/sui`, its dialog and every option widget are SaftUI's. Core's TOCs still load both (with the LibSharedMedia AceGUI widgets) as libraries for other addons. SaftUI's reskin of them (`aceskin.lua`) is gone; it only ever styled SaftUI's own windows, so other addons' Ace windows look as they did. Don't hook `AceGUI:Create`, a widget constructor or `AceGUI:Release`: AceGUI's widgets are pooled and shared with every addon.
