# Edit mode and `/sui`

SaftUI has its own edit mode. It never adds frames to Blizzard's Edit Mode.
- `/sui edit` or the `/sui` "Edit mode" button toggles it. It also follows Blizzard's Edit Mode opening and closing.
- Registered frames get a draggable overlay. Arrow keys nudge 1px, Shift+arrows 10px.
- Where overlays overlap, a list by the cursor names every one under it and marks the one a click or drag gets; the rest dim. Alt brings the next one to the front (`EditMode/picker.lua`, like `/fstack`). Overlays share one strata, so their frame levels decide which is on top: each gets its own pair (backdrop one below), handed out rising by `EM:BringToFront`. Don't set an overlay's level anywhere else.
- Clicking a frame opens `/sui` at that frame's section.
- A grid shows behind the UI while edit mode is on and Grid is enabled (`EditMode/grid.lua`). Two center lines sit on UIParent's center, rounded to a physical pixel (`EM:GetGridCenter`), and the other lines repeat outward every Grid size (`EM.GridLinePositions`), each 1 physical pixel thick. Snapping reads the same two functions, so what's drawn is what snaps. The grid also redraws from its own frame's `OnSizeChanged` (the screen events can fire before UIParent resizes). The lines are pooled textures on a SaftUI frame at `BACKGROUND` strata that never takes the mouse.
- The `/sui` footer has Grid, Snap to grid and Snap to frames toggles (green text when on), and `-` / size / `+` buttons that step Grid size by 4 between 8 and 128 (`EditMode/settings.lua`). `EditMode/footer.lua` (`EM:AddFooterButton`, `EM:UpdateFooter`) puts them on the window's footer region (`st.OptionsWindow:GetFooter()`, between Reload UI and Close) while edit mode is on and `/sui` is open, and takes them off otherwise; the window's status line then starts clear of them (`OW:SetFooterInset`). Edit mode works with `/sui` closed; the buttons just don't show. The "Edit mode" tab of Global Settings in `/sui` holds the same toggles and a Grid size slider. The values are in the profile (`st.defaults.editmode`: `grid`, `grid_size`, `snap_grid`, `snap_frames`), and `EM:UpdateConfig` redraws the grid and toggles after a profile change.
- **The outline.** An overlay is drawn in SaftUI's theme (`'theme'`, `'solid'`, kind `small`): one 1px line (white, or blue with a blue tint when selected) `EM.OutlineOutset()` outside its rect, which is the theme's border, `st:ThemeInset('theme', 'solid')` (2px under Thick, between two dark lines; 1px under Thin, with none). That's where a SaftUI frame's own border line sits, so frames look as far apart in edit mode as out of it, under either theme. A frame whose border line sits elsewhere re-anchors its overlay so the line lands on it. Chat does this: its backdrop is `padding` outside the holder, so its overlay goes `padding - EM.OutlineOutset()` out (`CHT:UpdateFootprint`), or `0` under None. Don't color the overlay's dark lines; that widens the outline past the border. A theme recolor would wipe the line's white or blue, so `EM:OnColorsChanged('theme')` puts it back on every mover.
- Dragging snaps (`EditMode/snap.lua`, wired into `EM:StartDrag` / `EM:UpdateDrag`). The dragged mover's outline (`EM.GetOutlineRect`: its overlay's rect plus `EM.OutlineOutset()`) has its left, middle and right (and bottom, middle and top) pulled onto the nearest line within `EM.SNAP_REACH` (8 UIParent units). Snap to grid uses the grid's lines (same `EM.GridLinePositions` and `EM:GetGridCenter`, so it works with the grid hidden). Snap to frames uses the screen's center lines and the outline edges and centers of every other mover whose overlay is shown and on screen; with both on, the nearest line wins per axis. Snapping only corrects the drag's `x_off`/`y_off` (converted by the ratio of effective scales, rounded with `st:RoundToPixel`), never the anchor. Holding Ctrl suspends it, and arrow-key nudges ignore it. Movers whose frame moves with the dragged one (`st:MovesWith`: anchored to it, directly or through other frames, or its children) are skipped as targets, since they would shift during the drag. The lines are computed once at drag start. `EM.GetRectInUI` returns nil for a frame with a secret edge or scale (the Minimap's frame is Blizzard's), and that mover is skipped.
- Drags and nudges stop at the screen edge margin (below): after snapping, `EM.MarginCorrection` (`mover.lua`) pulls the move back so the frame's rect (not its outline) stays the margin in from each edge, so the margin wins over a snap line. A drag or nudge starts from where the frame shows, not where its anchor says (`st:GetClampShift`: the game shows a frame anchored into the margin at the margin), so what's stored is where it ends. A frame whose rect can't be read (a secret edge) gets no margin from a drag.
- It closes on combat and refuses to open in combat.

The spec is in `docs/superpowers/specs/2026-11-06-saftui-edit-mode-design.md`, and the plan (Tasks 1–15) in `docs/superpowers/plans/2026-11-06-saftui-edit-mode.md`. The grid and snapping have their own spec, `docs/superpowers/specs/2026-11-09-saftui-edit-mode-grid-snap-design.md`, and plan, `docs/superpowers/plans/2026-11-09-saftui-edit-mode-grid-snap.md`.

## Registering a mover

```lua
st:RegisterMover('key', {
	frame = holderOrFrame,        -- the overlay does SetAllPoints on this; it needs a real size
	label = 'Name',
	getPosition = function() return self.config.position end,   -- read through self.config at call time
	setPosition = function(pos) self.config.position = pos end,
	apply = function() self:ApplyPosition() end,                 -- can run in combat lockdown
	configPath = { 'ModuleName', 'section', 'general' },         -- keys from the /sui root to a leaf group
	blizzardFrame = nil,          -- true only when frame is Blizzard's own, with no holder (the Minimap)
})
```

- **The screen edge margin.** `st:RegisterMover` keeps the frame inside it (`st:KeepInScreenMargin`, below), so `frame` is SaftUI's own frame or holder. A mover on a Blizzard frame moved with no holder (the Minimap) sets `blizzardFrame = true`: SaftUI never clamps a Blizzard frame, so only its drags and nudges keep it in.

- **Offsets.** Drags and nudges write pixel-rounded `x_off`/`y_off` into the table from `getPosition()`, call `setPosition`, then `apply` (about every 0.1s while dragging, and once at drag end). Drags keep the frame's anchor point and relative frame. Only the offsets change.
- **`apply`** must go through `st:SafeReposition`, because a secure frame anchored to yours makes it protected in combat.
- **`configPath`** must resolve in `Config:GetOptionsTable`. Module tables are keyed by module name. End the path at a leaf group, usually `general`, since selecting a parent that only holds subgroups shows an empty pane.
- **Holder pattern.** Use a SaftUI holder frame when the real frame:
  - can be empty or hidden (loot rolls, boss and party/raid groups, closed bag windows),
  - has no size (the micro menu container), or
  - belongs to Blizzard (swing timer, buffs, chat, the extra action button and zone ability).

  Size the holder from the config, place it from the profile, and anchor the real frame to it. The overlay then always has a footprint.

  A SaftUI frame that's only hidden, and still sized and placed from the profile while hidden, can be its own mover frame: the overlay follows its edges either way. SaftUI's action bars (`SaftUI-ActionBars/options.lua`) move their secure headers this way, also while a bar is disabled or hidden by its Visibility setting, and while the pet bar has no pet or the stance bar no forms (laid out as one button then, so the outline keeps a size). Label the outline when the frame may not be visible (`mover.label:SetText`), as the action bars and the swing timer do. The extra buttons' outlines (`SaftUI-ActionBars/options.lua`) always say when they show, as they mostly don't.
- **Taking over a Blizzard Edit Mode frame.** The swing timer bars (`SaftUI-Misc/Skinning/Blizzard_SwingTimerPosition.lua`), buffs (`Blizzard_BuffFramePosition.lua`), chat (`SaftUI-Chat/chatframe.lua`), the default tooltip's `GameTooltipDefaultContainer` (`SaftUI-Misc/tooltipposition.lua`; the tooltip itself is never moved) and, on a shaman, Forever's totem bar `MultiCastActionBarFrame` (`SaftUI-Misc/totembar.lua`, mover `totembar`) all follow the same pattern:
  - Use a holder.
  - Re-anchor the Blizzard frame with `st:SetPointDirect` / `st:ClearAllPointsDirect` in post-hooks on its `SetPoint` / `ClearAllPoints` / `UpdateSystem`. If it's protected (the totem bar holds secure buttons), the re-anchor waits for the end of combat (`st:QueueAfterCombat`), and the holder goes through `st:SafeReposition`.
  - Where Blizzard's Edit Mode can read the frame's anchor (a snap break, when the frame it's snapped to hides, records it into the layout through `UpdateSystemAnchorInfo`, and a layout save keeps it), don't anchor the frame straight to a SaftUI holder. Place it on UIParent at the holder's spot instead, from the holder's rect, and again whenever the holder moves or resizes (the totem bar's `TB:AnchorBar`, run from a post-hook on the holder's `SetPoint`). Otherwise the layout names the holder, and Blizzard anchors the frame to a missing frame wherever the holder doesn't exist. Chat copies its holder's own anchor instead (`CHT:PlaceChatFrame`), so the layout would name the holder's relative frame, UIParent by default.
  - Hide its `Selection` box with a `HookScript('OnShow', Hide)`.
  - The holder is kept inside the screen edge margin and the Blizzard frame follows it: anchored to it (buffs, swing timers, the tooltip container, the extra buttons), or placed from its rect (the totem bar, whose `TB:AnchorBar` also runs after `st:UpdateScreenMargin`). Chat copies the holder's anchor rather than its spot, so it adds the holder's `st:GetClampShift` and places ChatFrame1 again after `st:UpdateScreenMargin`. Never clamp the Blizzard frame itself: Blizzard's Edit Mode rewrites its clamp insets on every layout apply.
  - List which Blizzard settings become unreachable, and rebuild the useful ones in `/sui`.
  - Keep first load from moving anything. Profiles saved before the takeover have no position, so either give `position` a default that reproduces Blizzard's default layout (swing timer, buffs) or give it none and capture the frame's spot on screen once Blizzard's Edit Mode has placed it (the totem bar, `TB:CapturePosition`, and chat's size, `CHT:CaptureSize`). Blizzard's layout can arrive after SaftUI loads, and a frame in its default position can sit somewhere temporary until Blizzard lays it out (a totem bar in its default position waits at UIParent's top-left until it first shows), so capture outside Blizzard's re-places, on the next frame.

  Read `.agents/taint.md` first.
- **When post-hooks can't hold it.** The extra action button and the zone ability (`SaftUI-ActionBars/extras.lua`) live in Blizzard's `ExtraAbilityContainer`, which lays its frames out again each time one is added, in combat too. `ExtraActionBarFrame` holds a secure button, so a post-hook couldn't move it back until combat ends. So SaftUI moves none of Blizzard's frames. It anchors what Blizzard never re-anchors (`ExtraActionButton1`, the zone's `SpellButtonContainer` and `Style` art) to the holder once, out of combat, and the buttons then show at SaftUI's spot even when they first appear mid-fight. Blizzard's empty frames stay in Blizzard's layout; make any that take the mouse click-through (`AB:DisableMouse` in `SaftUI-ActionBars/hideblizzard.lua`), so they don't block clicks to what's under them. Before using this, grep both branches to confirm nothing re-anchors the inner frame. The totem bar combines both patterns: Blizzard re-places the bar itself in combat, so its buttons are anchored straight to the holder too and only the empty bar frame moves until combat ends. Blizzard's own button update re-anchors two of them to the bar (the first element and the summon pages), so in a fight that runs it while the bar is elsewhere they follow the bar until combat ends. Size Blizzard's buttons with a Scale setting (the widget's own `SetScale`), since their art is laid out for one size.
- **Validating anchors.** The Position editor's typed relative frame is validated with `st:ValidateAnchor(target, name)`. Always pass `target` (the frame being moved) so self-anchors, anchor loops and descendants are rejected.
- **Profile switches.** `EM:ClearPositions` then `EM:UpdateConfig` re-apply every mover. Implement `UpdateConfig` in your module too (see `.agents/architecture.md`).
- **Test modes.** Loot rolls/feed, party/raid groups and boss frames have session-only test toggles that draw SaftUI-owned previews anchored to the holder. Group previews stand in for the header and hide while it shows. Boss frames have no header, so their previews (`UF:UpdateGroupPreview('boss')`) go where `UF:PlaceUnitFrame` puts each boss frame (always one line, Growth and Spacing its only Layout options: `UF.GetUnitGroupLayout` ignores any column key a profile saved), and hide while any real boss frame is shown (`UF:WatchFramesForPreview` hooks their `OnShow`/`OnHide`). Never fake units or override Blizzard APIs.

## Screen edge margin

`misc.clamp_inset` (default `st.CLAMP_INSET`, 20), Screen edge margin on Global Settings' General tab, is how far in from the screen's edges SaftUI keeps the frames the user can move (below 0, how far past them they can go). It's measured by the frame's rect, not its outline or border, in the frame's own units (UIParent's for SaftUI's frames). The defaults sit at least that far in by their rects (the buffs at `-st.CLAMP_INSET`), so first load pushes nothing.
- **How.** `st:KeepInScreenMargin(frame)` (`SaftUI-Core/api.lua`) clamps the frame to the screen with insets of `-m, m, m, -m` (the game keeps its rect, grown by them, on screen) and remembers it. `st:UpdateScreenMargin()` re-applies the margin to every frame it remembers: the General tab's row and a profile switch (`Config:UpdateConfig`, before the modules place their frames) run it. Both are blocked in combat on a protected frame, which keeps its margin until combat ends; one queued re-apply (`QueueAfterCombat('ScreenMargin')`) then does them all.
- **Who gets it.** Every mover's frame (`st:RegisterMover`), holders included; every window with a header (`st:CreateHeader`: the bags and bank); `/sui`'s window and dialog; and the holders of the Blizzard frames SaftUI moves, which follow them (see the takeover pattern above).
- **Who doesn't.** Blizzard's frames. The Minimap (its mover sets `blizzardFrame`) keeps to the margin only when dragged or nudged. `st:EnableMoving` only keeps its frames on screen: every caller hands it a Blizzard UI panel (`SettingsPanel`, `AddonList`, `TransmogFrame`, `WorldMapFrame`, `TimeManagerFrame`). ChatFrame1's insets are Blizzard's Edit Mode's; chat follows its holder instead.
- **Where it shows.** The game shows a frame anchored into the margin at the margin, and leaves its anchor as set: a Position typed in `/sui`, or saved before the margin, stays in the profile. `st:GetClampShift(frame)` is how far the clamp moved it, so a drag or nudge starts from where it shows and stores that; chat adds it to ChatFrame1's copied anchor.

Tests: `tests/core/screen_margin_test.lua` (who gets it, when it's re-applied, combat, Blizzard frames, drags and nudges, `st:GetClampShift`), `tests/core/general_tab_test.lua` (the row) and `tests/misc/screen_margin_defaults_test.lua` (the buffs' default).

## `/sui` options

- `/sui` is SaftUI's own window (`st.OptionsWindow`, below), drawn from the tree `Config:GetOptionsTable` builds from each module's `GetConfigTable()`. AceConfigDialog no longer draws it.
- `st.Config:Open(...path)` rebuilds the tree, registers it with AceConfigRegistry as `st.name`, and opens the window at the path's page, picker value and tab (`OM.SelectionForPath`). `st.Config:Close()` closes it, and `st.Config:GetWindow()` is its frame while it's open, else nil. `st.Config:Refresh()` (AceConfigRegistry's NotifyChange) re-renders an open window on the next frame.
- **How a table maps onto the window.** The model (`SaftUI-Core/Config/optionsmodel.lua`, `st.OptionsModel`) reads AceConfig option tables as AceConfig defines them, so a module's `GetConfigTable` is a plain AceConfig table:
  - A top-level group is a sidebar page: its `name` is the page title and its `desc` the line under it.
  - The page's child groups that aren't inline are its tabs (whatever its `childGroups`, except `'select'`, which makes them the picker). Inside the chosen tab or pick, child groups that aren't inline are a second tab row, or the picker when that group says `'select'`. Anything deeper is drawn as sections on the page; nothing is dropped.
  - Inline groups (`inline = true`, or the parent's `childGroups = 'inline'`) are sections titled with their `name`, with any `desc` as a note. A `header` starts a section titled with its name. Options after a nested group continue in an untitled section.
  - Options are rows in `order` (100 by default, negative orders last, then by name), packed by `size`: `'small'` (toggle, color, execute, input only) takes a quarter of a line, two to a half; no `size` is normal and takes a half; `'wide'`, and every `description` and `position` row, take a line of their own. Ace's `width` is not read.
  - Hidden and `guiHidden` options are left out; disabled ones are dimmed and don't respond. `get`, `set`, `func`, `validate`, `confirm`, `disabled`, `hidden` and `handler` are inherited from parent groups, method-name strings resolve on the handler, and function-valued `name`, `desc`, `values`, `disabled` and `hidden` are called with an AceConfigDialog-style `info`.
  - A failed `validate` shows in the footer's status line (an input keeps the text typed). `confirm` asks in SaftUI's confirm dialog. A `set` re-renders the page.
  - Each type has a widget: toggle, range (slider and value box), select (a dropdown; `dialogControl = 'LSM30_Font'` lists each font in its own face), multiselect (checkboxes), input, color (Blizzard's color picker), execute (a button), keybinding, description (its text, and AceConfigDialog's image: `image`, `imageCoords`, `imageWidth` and `imageHeight`, the image at the row's left and the text to its right).
- **Sidebar groups.** A module's top-level table sets `category`: Frames (Unitframes, ActionBars, Inventory, Chat, Minimap, MicroMenu), Combat (Auras, SwingTimer, TotemBar) or Info (Loot, Experience, Tooltip, Skinning). A page without one lists under Other, and a group with no pages isn't drawn (today every module page has a category, so Other doesn't show). Fonts shows as Global Settings and AceDBOptions' table as Profiles, at the top. Global Settings has five tabs, General, Fonts, Colors, Theme, then Edit mode (grid, grid size, snap to grid, snap to frames), and opens on General: `Config:GetOptionsTable` nests the tables of the modules its `GLOBAL_TABS` list names, in the list's order (a new tab is a line there), under the page, whose key stays `Fonts`:
  - General's (tab key `general`, the General module in `SaftUI-Core/Config/general.lua`): an Icons section with Icon zoom (`misc.icon_trim`, a range with `isPercent`, so the window shows the profile's fraction as a percent) and its preview (`icon_preview`, a description row: `Interface\Icons\Spell_Nature_Lightning` at 36x36, its `imageCoords` a function giving `st:IconTexCoords` at the zoom set now), and a Layout section (key `windows`) with Title bar height (`headers.height`) and Screen edge margin (`misc.clamp_inset`, how far in from the screen's edges SaftUI's frames are kept; below 0 they can go that far past them; see the screen edge margin, below). Each row is bound to its profile key. Title bar height runs `st:UpdateHeader`, which re-applies every header's height and title font (and footers' height); the margin runs `st:UpdateScreenMargin`. Icon zoom reaches SaftUI's icons after a reload; the preview changes at once, while the slider is dragged too. Each section's note says what waits for a reload. `st:IconTexCoords(trim, width, height)` (`SaftUI-Core/skinning.lua`) gives the left, right, top and bottom `st:SkinIcon` crops an icon to (trim off each edge, after a wide or tall icon's art is cut to its shape), so the preview can't drift from the icons; `st:SkinIcon` keeps its own square crop for an icon whose size is secret.
  - Fonts' (`fonts`, `SaftUI-Core/Media/fonts.lua`): a Kinds of text section first (which font window titles, button text and check box labels use: `headers.font`, `buttons.font`, `panels.font`; window titles change at once through `st:UpdateHeader`, the rest after a reload), then a section per font with its name, face, size and outline, Shadow offset X and Y (`shadow_offset[1]` and `[2]`) and Line spacing (`spacing`). A font change re-applies its font object (`FN:UpdateFontConfig`), so every text set to it changes at once.
  - Colors' (`colors`, from `SaftUI-Core/Media/colors.lua`: an inline section per color group, a swatch per color and a Reset button).
  - Theme's (`theme`, the Theme module in `SaftUI-Core/Media/theme.lua`): Theme (Thick, Thin or Blizzard, `theme.name`, a sorted select), the chosen theme's colors (Border, Outer border, shown for Thick only, Window background, shown for Blizzard only, and Background: `templates[name].bordercolor`, `altbordercolor`, `windowcolor` and `backdropcolor`, written into the arrays in place with their alpha left alone; under Blizzard the Border and Background descs say what they color there), Transparent background (`theme.transparent`), Opacity (`theme.opacity`, a percent, disabled while the toggle is off) and Reset (asks first; puts the chosen theme's colors, `windowcolor` under Blizzard, and the transparency back to the defaults). Each row reads `st.config.profile` at call time. A color or Opacity change recolors every drawn frame; Theme, Transparent background and Reset redraw them and re-apply every module (`st:ThemeChanged`); both wait for the end of combat. See Themes in `.agents/architecture.md`.
  - Edit mode's (`editmode`, its `general` group inline so it's a section of the tab, not a second tab row).

  The Fonts and Edit mode `get`/`set` read the end of the path (`info[#info]`, and `info[#info-1]` for a font), so the nesting changes nothing for them. General's and Colors' getters and setters, and Kinds of text's, are bound to their row's setting, read `st.config.profile` at call time and don't read `info`. `panels.tab_height` has no option: nothing live reads it (see the followups). There is no separate Edit mode page; the sidebar's Edit mode button is unchanged. `category` is SaftUI's field (as are `size`, `target` and `nameKey`, and the `position` type), and AceConfigRegistry's validator rejects what it doesn't know, so the tree is registered with validation skipped (AceConfigRegistry only validates when its getter hands the table to a UI, which nothing does for SaftUI's). `tests/core/options_validate_test.lua` (and `tests/unitframes/config_test.lua` for the unit frames) runs the validator over the built tree instead, through `ace_ready` (`tests/core/options_walk.lua`: a copy with SaftUI's fields and Position options left out), so a malformed module table fails the suite. `tests/core/options_desc_test.lua` checks that every option on a finished page has a `desc` and none has a `width`. `tests/core/general_tab_test.lua` and `tests/core/fonts_tab_test.lua` check the General and Fonts tabs: their rows (Icon zoom's preview and its crop among them), what each changes at once, and a profile switch; `tests/core/skinning_test.lua` checks that `st:IconTexCoords` and `st:SkinIcon` agree.
- **Subcommands.** `st.Config:AddCommand(command, label, func)` makes `/sui <command>` run `func`, and adds a `label` button after "Edit mode" at the top of the window's sidebar (`st.Config:GetCommands()` lists them). Call it at file load or in `OnEnable`. SaftUI-ActionBars adds `kb` (Keybind mode, `SaftUI-ActionBars/bindings.lua`).
- **Section shape.** A mover's section is a group with a `general` subgroup whose last option is its Position option (`order = 1000`, after everything else in General), plus any others it needs (e.g. the action bars' Text and Visibility). Size and position sit together, and the mover's `configPath` ends at `general`. A Position option that isn't in a General group (a unit frame element's) still comes after every other option of its group: the window gives it a section of its own, and options after it would follow on untitled. `Config:GetOptionsTable` then:
  - nothing reshapes the tree. Each module's table declares its own tabs (`childGroups = 'tab'` on the group that holds them) and places its Position option itself; `MergePositionIntoGeneral` and `UseTabsForInnermostSections` are gone.
  - A page of many of one thing sets `childGroups = 'select'` on its top-level table: its child groups become the picker (a dropdown under the tabs), and theirs the tabs. Unitframes (its units, in the fixed order its `UNIT_ORDER` gives, Player first, and its Profile group, which sorts last) and ActionBars (its bars and extra buttons) do. The picker's label is the page's name, or the page's `pickerLabel` when it sets one (ActionBars says `'Bar'`); `pickerLabel` is SaftUI's own field, left off for AceConfig like `size`.
  - A unit frame's section shows its elements as tabs (General, Health, Castbar, ...): one per element that registered a `GetConfigTable` and whose `ValidUnit` accepts the unit. Keep sub-areas inside a tab as inline groups.
- **Widgets** are `st.Config.generators` in `SaftUI-Core/Config/widgets.lua`. None sets Ace's `width`; `desc` is the tooltip, and `size` (where taken) is `'small'` or `'wide'`:
  - `position(order, global_frame, get, set, target, desc, name)` is the full SetPoint editor: one option of type `position` (the Position block), whose `get`/`set`/`validate` take the part first (`point`, `rel_point`, `x_off`, `y_off`, and with `global_frame` a typed `frame`, so `target = 'name'`). `get`/`set` are the caller's `get(key)` / `set(key, value)`, or a table for `get` and no `set`. Offsets read as numbers and are stored as numbers rounded to the pixel. `target` (the frame being placed, or a function returning it) is what typed anchors are checked against with `st:ValidateAnchor`. `desc` defaults to a general line about placing a frame. `name` titles the Position's section and defaults to 'Position', a frame's own; a Position that places a part of it (a text, an icon) passes one such as 'Count position', so no tab has two sections of one title.
  - `uf_element_position(order, get, set, target, desc, name)` places a unit frame element, text or icon. Its TO part is a dropdown (`target = 'select'`, part `relative_to`: Unit frame, another element, or Global frame, whose name box shows while it's picked, `nameKey = '__global'`) that reads and writes `position.element` / `position.frame` the way `UF:GetFrame` resolves them, and clears a key with `false` so it overrides an AceDB default. Pass `UF:ConfigTarget(unit, element, key)` as `target`.
  - `toggle(order, name, desc, size)`, `range(order, name, min, max, step, desc, size)`, and `enable`, `alpha`, `framelevel`, `font`, `width`, `height`, each `(order, desc)`.
  - `theme(order, desc)` and `background(order, desc)` are a module's override of SaftUI's theme: selects listing their choices in a fixed order (`sorting`), Theme "Use SaftUI's theme", Thick, Thin, Blizzard, None (`theme`, `thick`, `thin`, `blizzard`, `none`) and Background "Use SaftUI's theme", Solid, Transparent (`theme`, `solid`, `transparent`). Theme's desc is the caller's, saying which frames it governs, then what the choices do; Background's is its own unless the caller gives one. Every page whose frames SaftUI draws has the pair, Background at Theme's order + 0.5, keyed `theme` and `background` (Bags' Look also has Slot theme and Slot background, `buttontheme` and `buttonbackground`; each unit frame element tab has its own, and the castbar's Bar and Icon sections one each). A unit frame bar's own fill for its empty part, beside the Background override, is the section Bar background (`bg`), so no tab has two settings named Background. "Template", "Highlight" and "Close Button" are never shown (`tests/core/theme_kinds_test.lua`, and every page test, walk the trees for them); descs say "Global Settings > Theme", never an arrow, which SaftUI's fonts may not have.
  - `width`/`height` are input boxes that display numbers and save numbers.
  - An `input` is text both ways (its `set` gets what was typed, as a string), so use these generators rather than raw inputs for numbers: they show the number and store a number.
- Option `get`/`set` must read through `self.config` (or `UF:GetProfileConfig()`) at call time, never a captured table.

## Options window (`SaftUI-Core/Config/optionswindow.lua`)

`st.OptionsWindow` (`OW`) draws `/sui` as the approved mockup lays it out (`docs/superpowers/specs/assets/2026-11-09-options-window-mockup.html`): 1040x700, drawn as a panel in SaftUI's theme with a Solid background (so it never turns see-through), at `FULLSCREEN_DIALOG` level 100, so edit mode's outlines draw under it. It and its dialog are kept inside the screen edge margin. The model (`optionsmodel.lua`, `st.OptionsModel`) turns the tree into pages, tabs, a picker, sections and rows; the window draws them:
- **Sidebar** (210 wide): Edit mode and the command buttons, then Global Settings, Profiles and the category groups (`OW.SidebarEntries`), and the profile's name at the bottom.
- **Header:** the page's name (Colus 34) and desc (15, grey), and the close X (`st:CreateCloseButton`). Dragging the header or the sidebar's title moves the window; where it's left is saved as `st.config.global.optionsWindow = { point, x, y }` (account-wide) and restored on open.
- **Tabs** (17, the active one underlined blue), wrapping to more lines when they don't fit; a page's single tab isn't drawn. A second row for subtabs, then the picker row (the group's `pickerLabel`, else its name, and a select widget). The search box sits at the right of the first tab line.
- **Body:** a scroll frame of sections, drawn by a body object (`st.OptionsBody`, `optionsbody.lua`: `OB.New(content, root, onChanged, width)`, then `body:Draw(sections)` or `body:DrawResults(sections, onPick)`, `body:Refresh(except)` mid-drag (see Re-rendering), and `body:Release()`). Sections (`OB.LayoutSections`) have a 1px `#2e2e2e` line and a Colus 15 title between them, never boxes. An untitled section after another (rows that follow a nested group) gets no line, so it reads as a continuation. Rows (`OB.LayoutRows`) are 34 high in two 367-wide columns 40 apart, each two quarters at least 24 apart (`OB.QUARTER_GAP`); a wide row takes a line of its own. Every cell starts and ends on a whole pixel (`body:CellRect(col, quarter)`): halves and quarters round down, and the second of each pair sits flush with the outer edge, so a 367 column's quarters are 171 wide and 25 apart. A 1px border on a frame between two pixels blurs, since SaftUI's scale makes a unit a pixel; for the same reason the select's caret rows are placed by their left edge. The label (16) is on the left and the widget right-aligned, check boxes and swatches too. A 1px `#2e2e2e` vertical line (`OB.Dividers`, as tall as its line, so the lines of rows that follow each other join up) runs between the halves of a line with a row in each, and between the quarters of a half with two small rows, so a right-aligned control reads with its own label; a small input's box is 60 wide (`OB.SMALL_INPUT_WIDTH`); an execute button stands alone, and a desc shows as the label's tooltip. The window's fonts live in `optionsbody.lua` too (`OB.Font`), since it loads first.
- **Footer:** Reload UI, the region `OW:GetFooter()` returns (edit mode's buttons go there while edit mode is on), the status line (validate errors, `OW:SetStatus`; `OW:SetFooterInset` starts it clear of edit mode's buttons), and Close.
- **Re-rendering** redraws the page, keeping the page, tab, picker value and scroll when they still exist. It runs straight away after the window's own set, except mid-drag (a slider's `onChanged` says so; the render waits for the mouse to be let go) and while Blizzard's color picker is open. Mid-drag, each set refreshes the other drawn widgets in place instead (`body:Refresh(widget)`; the slider passes itself to `onChanged` after `isDragging`): each reads its value again, whether it's disabled (`OM.IsDisabled`, greying or un-greying its label), and a description its image and imageCoords, so a row that shows the value, like Icon zoom's preview, follows the slider. Nothing is released or re-acquired, and the dragged slider is left as its own commit leaves it. Rows that would show, hide or change height wait for the render when the mouse is let go. On `ConfigTableChange` for `st.name` it runs on the next frame, several in a frame coalesced; never during a render (UF's profile select's `get` notifies), and not while the user is busy (a list or confirm dialog open, a drag, the color picker, typing in one of the window's boxes).
- **Search** runs `OM.Search` once typing pauses for 0.25s, and shows the results grouped by page, tabs and section. A click opens the row's page and scrolls it into view. Going to a page, tab or pick (or `Open` with a path) clears the search, a pending one too.
- **Esc** closes the window through a keyboard catcher that is on only while it's shown, not `UISpecialFrames`. Other keys pass on, and so does Esc while a box has the keyboard, the dialog is shown (its own catcher closes it) or Blizzard's color picker is open. It does nothing in combat; the window closes on `PLAYER_REGEN_DISABLED` and refuses to open in combat.
- The fonts are the window's own objects with the profile's title and normal faces at fixed sizes (`OW:UpdateFonts` on a profile change).
- **A small dialog:** `OW:OpenDialog(title, options)` shows an option table of its own (a group) in a small SaftUI window over `/sui`, drawn by a body of its own: the title (text, or a function read on each render), the close X, two columns of rows, a status line for validate errors. Its own set re-renders it, after the drag for a slider's; meanwhile its other rows follow the drag in place, as the window's do. Esc closes it (its own keyboard catcher; the window's passes keys on while it shows), and so do closing the window and entering combat; it refuses to open in combat. It draws no tabs or picker. `OW:CloseDialog()`, `OW:IsDialogShown()`. UF's Copy from (`UF:OpenCopyTable`) uses it, with `confirm` on its Confirm copy button. Closing it cancels a confirm or prompt open over it.

Tests: `tests/core/options_window_test.lua` (the window, the dialog, edit mode's footer buttons, the other rows following a drag) and `tests/unitframes/config_test.lua` (UF's Copy from).

## Options window widgets (`SaftUI-Core/Config/optionswidgets.lua`)

`st.OptionsWidgets` (`W`) draws the controls of SaftUI's own options window. `W.Create(parent, rowType)` gives a pooled widget (toggle, range, select, multiselect, input, color, execute, keybinding, description, position). `position` is the Position block: dots for the point and relative point, a frame name box or a dropdown, and X over Y, each with a 14x22 nudge box (up and down are separate buttons) sharing the edit box's right seam; its `get`/`set`/`validate` take the part first (`point`, `rel_point`, `x_off`, `y_off`, `frame`, `relative_to`). The range's track is textures of its slider, under the knob by draw layer: a child frame given a lower frame level drew over the knob in game once the widget was reparented (reparenting and level changes move children back above their parent). `widget:Bind(root, row, onChanged)` reads with `OM.Get`, and a change the user makes runs `OM.Validate`, then `OM.Confirm` (asked with `W.Confirm`), then `OM.Set`, and calls `onChanged(ok, err)` (with `true` and the widget after them while a slider is dragged). `widget:Refresh()` reads the row again. `widget:Release()` returns it to the pool. A description draws its `image` (a texture path or fileID, or a function giving that with a width and height; else `imageWidth` and `imageHeight`, 32 each by default) at its left, cropped by `imageCoords` (4 or 8 numbers, or a function giving them; any other count shows the whole texture, as AceGUI's label), with its text to the right, in the image's middle when the image is taller, and it's as tall as the taller of the two. Anything but a path or fileID draws no image. The image has a border in SaftUI's theme, drawn like an action button's icon (`'theme'`, `'theme'`, kind `action`), shown only with an image: Icon zoom's preview is one. The border lies outside the image, so `Fit` places the image the border's width (`st:ThemeInset('theme', 'theme')`) in from the row's top-left and counts the border in the text's left and the row's height: the row's edge is the scroll area's, which cuts what's drawn past it. A theme picked on the Theme tab reaches the row when it's drawn again. The select list and the confirm dialog are at `TOOLTIP` strata, above the window. `W.Prompt(text, initial, onAccept, opts)` is the same dialog with an edit box (one modal at a time: opening a confirm or prompt answers the open one No); it replaces StaticPopups, which sit under the window. UF's profile New, Copy, Rename, Delete, Export and Import use it (`SaftUI-Unitframes/config/config.lua`). Text heights count `\n` as line breaks. Widgets are SaftUI frames; the color picker is Blizzard's `ColorPickerFrame`, used only through `SetupColorPickerAndShow` (the swatch does nothing without it), and no Lua field is written onto it. Before showing it the swatch calls `SetFrameStrata('FULLSCREEN_DIALOG')` and `SetFrameLevel(swatch level + 10)` on it, since its own DIALOG strata opens it behind the window. Tests: `tests/core/options_widgets_test.lua`.

`st:CreateCloseButton(frame)` (`panels.lua`) makes the 24x24 close button (`st.CLOSE_X_BUTTON_SIZE`; `st.CLOSE_BUTTON_SIZE` stays the Blizzard buttons' size) (`close.tga`, a 16x16 canvas with the 10x10 X in the middle) and remembers it in a side table (`st:GetCloseButton(frame)`; nothing is written onto the frame, which may be Blizzard's); `st:CreateHeader` seats such a button in the header and leaves any other button the old look.

## Ace3's own windows

SaftUI doesn't use AceConfigDialog or AceGUI: `/sui`, its dialog and every option widget are SaftUI's. Core's TOCs still load both (with the LibSharedMedia AceGUI widgets) as libraries for other addons. SaftUI's reskin of them (`aceskin.lua`) is gone; it only ever styled SaftUI's own windows, so other addons' Ace windows look as they did. Don't hook `AceGUI:Create`, a widget constructor or `AceGUI:Release`: AceGUI's widgets are pooled and shared with every addon.
