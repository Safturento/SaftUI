# Architecture

## Addons and load order

- Every folder `SaftUI-<Name>/` is a separate WoW addon. All of them `## RequiredDeps: SaftUI-Core` and `## Group: SaftUI-Core`.
- **SaftUI-Tracker** is SaftUI's own objective tracker: module `Tracker` (`st.Tracker`), profile key `tracker` (`st.defaults.tracker`, `SaftUI-Tracker/config.lua`), per-character data in `st.config.char.tracker` (`TR:CharData()`: `zones`, each collapsed zone group's header title (`TR.OTHER_KEY` for Other) to `true`, and `collapsed`, the whole tracker's). One TOC for both clients, with `## OptionalDeps: SaftUI-Misc` (Blizzard's tracker's skin and mover live there). It ships switched on (`tracker.enable = true`; AceDB drops a saved value equal to the default, so a profile that never chose is on, and one that had ticked it on still is), and the switch is read once, at login: `TR:IsOn()` latches on its first call (the switch on and none of `TR.TRACKER_ADDONS`, other tracker addons, loaded), so Misc's code may ask it before `TR:OnEnable` runs and every reader gets one answer all session. `TR:OnEnable` binds the config, then returns while `not TR:IsOn()`, else runs `TR:Build()` once. While off, the addon makes no frame, hook, event, mover or binding change at load or enable. `Bindings.xml` (read by the game, not listed in the TOC) names the nearest quest item key; its strings are in `config.lua`. A profile change or theme change runs `TR:UpdateConfig`, which says in chat, once per value, that a profile's differing switch "changes after a reload". The data layer is pure and made of functions only (nothing at file scope reads the profile, registers an event or makes a frame): `model.lua`'s `TR.Model.Read(show)` reads the game's quest API into `{ quests, popups, counts, zoneNames, focused, arena }` (every API guarded by presence, a secret value counted as missing, a quest with no title skipped), with `TR.Model.Shown`, `Compare`, `Finished` and `ZoneNames`, and `TR.MaxQuests()` (the log's size from `C_QuestLog.GetMaxNumQuestsCanAccept()`, else Forever's constant, else `TR.FALLBACK_MAX_QUESTS`: nothing assumes 35, the item pool is sized by it), and `TR.TitleText`, `TR.QuestLines` and `TR.TimeText` for what a row says; `groups.lua`'s `TR.Groups.Build(quests, settings, zoneNames, collapsed)` makes the zone groups (current zone first, campaigns, the log's header order, Other last under `TR.OTHER_KEY`, one `TR.ALL_KEY` list with Group by zone off), with `IsCurrent` and `Sort`. The window: `layout.lua` has `TR.LAYOUT` (every length the tracker draws with) and the pure `TR.Layout` (`WindowHeight`, `ViewHeight`, `ChildWidth`, `ScrollRange`, `Wheel`); `window.lua`'s `TR:BuildWindow()` (called by `TR:Build`) makes `TR.holder` (the mover's frame, Width by Max height), `TR.window` (`SaftUITracker`, `st:CreateFrame` on UIParent, strata `LOW`, level 10, drawn as a `'panel'` in the page's Theme and Background by `TR:DrawWindow`), `TR.header` (the title, `count`, `collapse` made by `TR:NewChevron`, a one pixel `line` in the drawn theme's border color), `TR.scroll` (`TR.NewScrollFrame`, in the game the bags' `st:CreateScrollFrame`) with child `TR.content`, and `TR.watcher`, whose one `OnUpdate` runs only while a hover rule needs it. Rows put their content in `TR.content` and tell the window its height with `TR:SetContentHeight(h)`, which sizes the window (up to Max height, then the list scrolls, with `st:ScrollBarRoom` kept while it does); `TR:ScrollTo(offset)` and `TR:GetScroll()` move and read the offset (clamped, whole pixels), `TR:SetCollapsed` / `TR:IsCollapsed()` the header-only state (per character, ignored with Header off), `TR:UpdateHeader(model)` the count. A size read back from the game (the bar's room) is rounded, never ceiled. The window is never protected. The window and the list take the mouse wheel only while the list scrolls (`TR.scrollRange > 0`), so the camera still zooms over a tracker that fits; the bar's own wheel, steppers and drag go through the tracker (the bar's `OnMouseWheel` is the window's, `SetPanExtent(40)`, and a guarded `OnVerticalScroll` hook rounds the offset or puts it back while `TR:IsScrollLocked()`). Max height as drawn is `TR:MaxHeight()` (the saved value, no taller than the screen less the edge margins). The module's one `TR:OnColorsChanged` is in `init.lua` and calls each part's own (`TR:ColorWindow()`); later parts add their call there, never a second definition. **The refresh and its stages** (`init.lua`, `rows.lua`): `TR.EVENTS` (the design's list; `UNIT_QUEST_LOG_CHANGED` for the player only, `PLAYER_MONEY` only while a quest needs more money than the player has) are registered on one frame by `TR:Build` and only call `TR:MarkDirty(event)`, which schedules one refresh however many marks come before it, through one throttle for every event: the first mark after a quiet gap refreshes on the next frame (`C_Timer.After(0)`), marks within `TR.REFRESH_GAP` (0.1 s) of the last refresh are coalesced into one at the end of that gap, and a pending refresh is never pushed back (the controller's ruling of 2026-11-14, spec "Settled" 6; `QUEST_DETAIL` and `QUEST_DATA_LOAD_RESULT` joined the list, Settled 7). A quest is scrolled into view only when the game said it was tracked (`QUEST_WATCH_LIST_CHANGED` with `added`, kept in the list `TR.trackedQuests`) or the focus changed, never while the mouse is over the tracker, within `TR.SCROLL_QUIET` (3 s) of the player's own scrolling (real input only: the wheel, and a mouse-down on the bar's thumb, track or steppers, not the bar setting the offset itself after a range change), collapsed or locked; tracks inside one gap are kept in a list (`TR:NoteTracked`, an untrack takes its quest off) and the scroll goes to the last. A collapsed tracker updates its header's count and nothing else (`TR.rowsStale`, drawn once when it opens). `QUEST_DATA_LOAD_RESULT` refreshes only for a quest in `TR.knownIds` (shown, a popup's, or waiting for its title: `model.waiting`). A popup row is keyed by quest ID and kind (`TR:GetPopupRow(id, kind)`), a font change marks through the same throttle. `TR:Refresh()` reads `TR.Model.Read(quests.show)`, then `TR:Redraw()` (also what a zone header's click runs, from the model already read): `TR.Groups.Build` (collapsed zones from `st.config.char.tracker.zones`), `TR:BuildEntries` (popups, zone headers, quests, or the empty line; each entry claims a pooled row, `TR:AcquireRow(kind, key)`), `TR.Layout.Rows` (pure; the real font strings measure through `TR:Measure(row, fs, text, width)`, kept per text and width), `TR:DrawRows`, `TR:SetContentHeight`, a scroll of the focused or a newly tracked quest into view (`TR.Layout.IntoView`), then `RefreshItems`, `UpdateHandover` and `ApplyVisibility` (the probes run on their own events and after a module's layout, not from the refresh), each only once a later task's file defines it. The list's width depends on whether it scrolls (the bar's room), so a layout that guessed wrong runs once more. Every text goes through `TR.SetText(fs, text)` (set only when changed, a secret always), every frame is moved or sized only when its place changed (`LayoutWindow` keys on its inputs), and a refresh that changed nothing sets no text, makes no frame and calls no setter on any widget; an objective's dash is its own font string (`part.dash`, the text after it, `metrics.dash`); a popup row is its label, 2 and its title, at least 22 tall; rows of what went are freed before new ones are taken; a Fonts tab change redraws through `TR:OnFontsChanged` (`if TR.model then TR:MarkDirty('FONTS') end`, run by `st:FontsChanged()`; `tests/tracker/rows_test.lua` measures it). A color change recolors shown rows in place (`TR:ColorRows`, inside the one `OnColorsChanged`): colors are read at draw time, never cached in a way that survives a change. The focused quest's accent bar is the window's own texture (`TR.focusBar`), not a row's, because the list's scroll frame clips what is left of its rows. **Blizzard's tracker** (`blizzard.lua`, run by `TR:Build` after the window): `TR:OwnsBlizzard()` is `TR:IsOn()` and Blizzard's `ObjectiveTrackerFrame` existing (Misc's tracker mover asks it at call time to stand down); `TR:SetupBlizzard()` (once, through `st:OnBlizzardAddon` when `Blizzard_ObjectiveTracker` isn't loaded yet) post-hooks the tracker's `SetPoint`, `ClearAllPoints` and `UpdateHeight` (each in `xpcall`, where the game has the function), hides its Edit Mode box and calls `TR:PlaceBlizzard('concealed')`; `TR:BlizzardTarget(where)` gives `parent, point, x, y` (`'place'`: its top right on the window's, the holder's top right for Grow down and the window's for Grow up; `'concealed'`: the y of the spot the mode reveals at and an x of `TR.BLIZZARD_OFF` past UIParent's left); `TR:PlaceBlizzard(where)` sets the clamp (off concealed, on otherwise) and its one anchor with the three C methods, skipping what is already so, and keeps `TR.blizzardWhere`. `TR:ApplyHolder` and `TR:UpdateConfig` place it again (a moved holder, a changed Grow). What it may and may not call is `.agents/taint.md` rule 5. The first position (`FirstPosition`, `window.lua`, for a profile with no tracker position) is the skin's saved position when Misc's mover has one (a top point copied, another converted to the TOPRIGHT form from the skin's width and `OTP.HOLDER_HEIGHT`), else where Blizzard's Edit Mode had the tracker (`EditModeSpot`: `C_EditMode.GetLayouts()` only, never a field of Blizzard's tracker frame; a preset layout or a tracker in its default position gives Blizzard's default spot; a top point is copied as it is, any other point is converted to TOPRIGHT from the width (Misc's skin's, else 260) and Edit Mode's own Height setting from the same layout; an anchor to a frame other than UIParent gives the default), else Blizzard's default. If Blizzard's manager hasn't applied the layouts yet (`EditModeManagerFrame.layoutInfo` is nil: a read only) the default is written and `EDIT_MODE_LAYOUTS_UPDATED` is watched on the tracker's own small frame (`TR.layoutsFrame`, not `TR.EVENTS`): the first time it fires the position moves to Edit Mode's spot, only while `config.position` is still the very table written with its values unchanged, then the watch ends. **The handover** (`probes.lua`, `handover.lua`, `TR:WatchModules` in `blizzard.lua`): `TR:Build` starts `TR.handoverState` at `'own'` (a `/reload` always does), builds the probe tables (`TR:BuildProbes`) and, once Blizzard's tracker is set up, hooks each module's `Update` and asks for a first probe pass (`TR:RunProbes`, which coalesces any number of asks into one pass, `TR:ProbePass`, on the next frame and no sooner than `TR.REFRESH_GAP` after the last). A pass reads each section's probe (`TR.Probes`) and the module signal, keeps when each last had content and asks for itself again when a hold (`TR.HOLD`, 2 s) ends, and ends in `TR:UpdateHandover()`, which also runs after every refresh (`TR:RunStages`) and every `TR:UpdateConfig`. `TR.Handover.Next` (pure) gives the new state and its actions, which `TR:UpdateHandover` runs through `TR:PlaceBlizzard`, the window (`TR:ApplyWindowShown`, hidden while the state is `'blizzard'`) and the item buttons (`TR:RefreshItems`, whose `Wanted` hands out none while the state is `'blizzard'`): the parts SaftUI's tracker gives up are derived from the state, so a state that returns to `'own'` can never leave one hidden. Blizzard's tracker is placed at `'concealed'`, `'place'` or `'beside'` for the state (`own`, `blizzard`, `both`), at the y of SaftUI's spot kept `TR.BLIZZARD_FLOOR` above the screen's bottom, and the beside spot is `TR.Layout.BesideSpot` past `TR:ColumnWidth()`.
  - **Quest item buttons** (`SaftUI-Tracker/items.lua`, the rows' item slot in `rows.lua`, `TR:IsScrollLocked` and `window.barLock` in `window.lua`; the rules are `.agents/taint.md` rule 15): `TR:BuildItems` (with the window) makes the pool's tables and a plain watcher frame, and `TR:RefreshItems` (the first of `TR:RunStages`, followed by `TR:RefreshNearest`, the nearest quest item button's own pass in `nearest.lua`, which `TR:BuildNearest` sets up with the tracker: its holder, mover and watcher; `.agents/taint.md` rule 16) does the rest, and `TR:PlaceItems` (a placement-only pass: no item told, no style) follows the rows after a scroll, a collapse, a hide, a screen size change (the watcher frame fills UIParent: `OnSizeChanged`) and an edit mode drag (a post-hook on the holder's `SetPoint`, which the mover sets every frame): out of combat it makes the layer `SaftUITrackerItems` (`TR:BuildItemLayer`, a secure frame on UIParent under a visibility driver) and a `SecureActionButtonTemplate` button per quest drawn in a row with an item (up to `TR.ItemPoolMax()`), tells each its item (`TR:SetButtonItem` through `TR.ItemAttributes`, the P3 seam) and places it at its row's top right by offsets from UIParent; in combat it only dims (`TR.Items.CombatAlpha`) and draws, and queues `'tracker_items'`. A quest row's item slot (`row.slot`, `TR:SetSlotMode`) is hidden under a button, greyed in combat with no button, a plain icon with Item buttons Off or no button to be had. `TR:IsScrollLocked` holds the list still in combat while a row button shows. Beside the tracker (`placement` `'beside'`) the same buttons sit in a numbered column 4 outside the window on the side nearer the screen's middle (`TR.Items.Side`, `TR.Items.Column`, pure; `TR:ColumnWidth()` is its width for the beside spot), each level with its quest's title, 2 under the one above when they would overlap; `Wanted` takes the quests the list draws, in list order, and `PlaceColumn` places them (the rows' entries say `item = 'beside'`, leaving the title room for the number: `metrics.tagRoom`, `TR:TagRoom`); a button's number is `button.numberText` (Pixel font, bottom left) and its row's `row.tag` (accent, at the title's end, `TR:SetTag`), both only set out of combat except the tag's text following the button. The Items tab is `tracker.items` (`TR.ItemsTab`): `placement` (In the row, Beside the tracker, Off), `size`, `cooldown`, `count`, `range`.
  - **Clicks, menu, tooltips** (`SaftUI-Tracker/clicks.lua`, called from the rows' scripts in `rows.lua`, so nothing runs with the switch off): `TR.ClickAction(quest, button, state)` is the pure choice (`link`, `untrack`, `track`, `complete`, `map`, `focus`, `menu`), `TR:OnQuestClick` reads the state and does it, `TR.MenuEntries` and `TR:OpenMenu` are Blizzard's menu through `MenuUtil`, `TR:ShowRowTooltip` the quest link, party progress and a click hint. A quest row's icon is its own button (focus toggle), a zone header's left click collapses it. `TR.ShowOnMapAllowed()` is the P5 seam; the combat rules are `.agents/taint.md` rule 14. The Quests tab's `tooltips` and `left_click` (`map` or `focus`) are in `tracker.quests`.
  - **Fading and hiding** (`SaftUI-Tracker/visibility.lua`; `tracker.visibility`, the Visibility tab, `TR.VisibilityTab`): six triggers (In combat, Out of combat, Mouse off, In instances, Boss fights, Mythic+), each Show, Fade or Hide (Mouse off Show or Fade; Mythic+ only where `C_ChallengeMode.IsChallengeModeActive` exists), all Show by default. `TR.Visibility` is pure: `Applies(hovered)` reads the game (`InCombatLockdown` or the combat events' word `TR.combatNow`, `IsInInstance`, `C_InstanceEncounter.IsEncounterInProgress` (else the deprecated global) or the encounter events' word `TR.encounterNow`, `C_ChallengeMode`), `Resolve(applies, settings, hovered)` gives `{ window, alpha, items, itemAlpha, hideItemsDirectly, background }` (the strongest wins, Hide over Fade over Show; Show fully under the mouse turns Fade into Show, never Hide; Hide quest items with the tracker off keeps the buttons at full alpha, on fades them never under `TR.BUTTON_MIN_ALPHA`) and `Driver(settings)` builds the item layer's state driver (`[petbattle] hide`, then `[combat]`, `[nocombat]` and `[@boss1,exists]` hide for the triggers set to Hide while the buttons go with the tracker). `TR:ApplyVisibility()` is the one place that decides: it runs after every refresh (`TR:RunStages`), on the events (`TR.VISIBILITY_EVENTS`, `TR:OnVisibilityEvent`, `PLAYER_REGEN_*`, `PLAYER_ENTERING_WORLD`), on a settings change and from `TR:StepFade` when the mouse comes or goes. The window shows or hides in `TR:ApplyWindowShown` (with the handover and an empty list: `TR.visHidden`), a window faded to alpha 0 takes no mouse (`TR:SetInput`: rows, header, chevrons, the wheel, the scroll lock's strip; new rows too), the panel is the window's backdrop frame's alpha, and the fade is one `OnUpdate` (`TR.fader`) that runs only while an alpha moves (`TR.FADE_TIME`, 0.2 s from faded to full) or the mouse is watched. The quest item buttons: `TR:SetItemAlpha` wears the fade (`TR.itemFade`, `button.fades`) under the 25% floor, the layer's driver is set by `TR:ApplyItemDriver` out of combat (queued as `'tracker_items'`), and Hide for In instances, Mythic+ and Boss fights is direct (`TR.itemsHidden`, which `Wanted` reads like the handover's state), out of combat only. With the buttons staying and the window hidden by a trigger the list keeps being laid out, so out of combat they are assigned and placed by their rows as usual (`RowLaidOut`); in combat they stay put and dim as always. The nearest button is never touched: its driver frame has `TR.NearestDriver()`, the pet battle's condition alone. During a handover `TR:PlaceBlizzard` conceals Blizzard's tracker while `TR.visHidden`, and `TR:SetBlizzardAlpha` holds its faded alpha (the C `SetAlpha`, put back after Blizzard's own by a post-hook), the hover read by `TR:IsTrackerHovered` (the window, the column, and while Blizzard's tracker shows the holder plus the rectangle SaftUI placed it in, cached by `PlaceBlizzard`). The rules and the in-game checks are `.agents/taint.md` rule 17.
- **TOCs:** Core and Unitframes have per-client TOCs (`*_Forever.toc` = `## Interface: 16001`, `*_Mainline.toc` = `120000`). The other addons use one TOC listing both (`## Interface: 120000, 16001`). When you add a file, add it to **every** TOC of that addon (and to the folder's `load.xml` where one is used, e.g. `SaftUI-Core/Config/load.xml`, `SaftUI-Core/EditMode/load.xml`, `SaftUI-Misc/Skinning/load.xml`).
- Load order matters: Core loads first, then each module addon in its TOC order. Defaults (`st.defaults.*`) must be defined at file load, before Core creates the AceDB (see below).
- **Libraries:** Core bundles LibStub, CallbackHandler-1.0, Ace3 and the shared media libraries. An addon that needs more bundles them in its own `Libraries/` and lists them first in its TOC, without a second copy of LibStub or CallbackHandler: Unitframes has oUF, ActionBars has LibActionButton-1.0 and LibButtonGlow-1.0 (sources and versions in `SaftUI-ActionBars/Libraries/README.md`).

## The `st` object and modules

- `SaftUI-Core/init.lua` creates the addon: `SaftUI = AceAddon:NewAddon(st, 'SaftUI-Core', 'AceEvent-3.0', 'AceHook-3.0')`. Every file starts with `local st = SaftUI`.
- A module is `local M = st:NewModule('Name')` (AceAddon module, with AceEvent + AceHook mixed in). Module names are the keys used everywhere else: `st.modules[name]`, the `/sui` tree, and edit mode `configPath`s. Current modules include ActionBars, Auras, Chat, Colors, Config, EditMode, Experience, Fonts, General, Inventory, Loot, MicroMenu, Minimap, Movable, ObjectiveTracker, Skinning, SwingTimer, Theme, Tooltip, TotemBar, Tracker, Unitframes, Utilities.
- Lifecycle: `OnInitialize` (rarely used), `OnEnable` (build frames, register movers, hook Blizzard), `UpdateConfig` (re-apply everything from the profile; see below), `GetConfigTable` (the module's `/sui` page; its top-level table's `category`, Frames, Combat or Info, groups it in the window's sidebar). Core's General, Fonts, Colors, Theme and EditMode modules give the tabs of the Global settings page instead, in the order of `GLOBAL_TABS` in `SaftUI-Core/Config/config.lua` (see `.agents/edit-mode.md`). A `/sui <command>` with its own sidebar button is `st.Config:AddCommand(command, label, func, icon)`, whose optional icon is the button the collapsed sidebar's footer shows (see `.agents/edit-mode.md`).
- **A color change** (`SaftUI-Core/Media/colors.lua`). A Colors row's set and reset, and the Accent row's, say `st:ColorChanged(group, key)` (key nil for `accent` and `renown`), never `st:ColorsChanged`. While SaftUI's color picker is open that is an **edit** (`st:BeginColorEdit()` as it opens, `st:EndColorEdit()` as Okay or Cancel closes it, after Cancel's restore; `st:InColorEdit()`): the change only marks the color, and one **pass** per marked color runs on the next frame from `CO.ticker`'s `OnUpdate`, however many changes came; outside an edit it passes at once. A pass runs the color's followers, its group's followers, then every module's `OnColorsChanged(group, key)` (one per module: SaftUI-Loot's, in `init.lua`, hands it to the feed, the roll bars and the loot window's skin), each in `xpcall`. `key` is the color that changed; **nil means any color of the group may have**, so a handler that ignores the key does what it did before. `st:ColorsChanged(group)` is the **whole pass**: every follower of the group with key nil, then each module's handler with no key. It runs for each group an edit touched when the edit ends (in the order first touched; a pass still due is dropped, since this covers it), and the profile update runs every group's, after theme and accent (step 8 below). **Followers** are for what has no module to color it: `st:FollowColor(object, group, key, paint)` makes `paint(object, key)` run on every pass of that color (key nil: of any color of the group; the key passed is the changed one, nil on a whole pass); `paint` is a shared function that reads its colors as it runs and never closes over its object (the table holds the object weakly); a paint nil forgets that one registration, and `st:UnfollowColor(object)` every registration of the object (a pool that releases it calls this); nothing paints as it registers; a follow made during a pass takes effect after it; a paint that errors is reported once and forgotten. **A pass only colors** (color setters on regions and frames that exist, `SetText` on SaftUI's own font strings, a font object's `SetTextColor`, an oUF element's `ForceUpdate` and `UpdateTags`): no frame, texture or font string made, no `Show`, `Hide`, `SetShown`, `SetParent`, `SetPoint`, `ClearAllPoints`, `SetSize`, `SetWidth`, `SetHeight`, `SetAttribute` or `SetScript` on a frame, no `UpdateConfig`, layout or rebuild, no table or closure per pass, so it is safe in combat; `tests/lib/color_cost.lua` counts it. **The guard:** a frame's passes during an edit that took more than `CO.PASS_BUDGET_MS` (8 ms) make the next wait a frame for each 8 ms, at most `CO.MAX_WAIT` (3); `EditStats().waited` counts the frames actually waited. With `/sui debug` on an edit that ran a pass ends with one `<DEBUG:Colors>` line (passes, the slowest and its color, the mean, frames waited; `CO.EditStats()` has the numbers, `CO.Timed(group, key, fn, ...)` adds a call's time to them: the Theme tab's recolor runs through it as `theme`). `Config:OnColorsChanged` gives the kit's font objects Text's color on `text` with key nil or `normal` (`OB.ColorFonts()`: `SetTextColor` only, never `SetFont`; `OB.UpdateFonts()` stays for a font or profile change). `st:FollowColor` refuses a group that isn't in `st.COLOR_GROUPS` (or `theme`) and a key the group's defaults don't have (`accent` and `renown` take none). A color marked again while its frame's passes run is due next frame; an edit begun during an edit's whole passes keeps its own touched groups. `group` is `text`, `button`, `class`, `roles`, `reaction`, `renown`, `factions`, `power`, `item_quality`, `loot`, `status`, `threat` or `objectives` (a finished and a failed objective's line, `colors.objectives.completed` and `.failed`, shared by Blizzard's tracker's skin and SaftUI's own tracker), `theme` after a theme recolor or redraw put the theme's colors back on every drawn frame (see Themes, below), or `accent` (Theme > Accent, `st.config.profile.theme.accent`, read as `st:Color('accent')`; it has no key and no opacity), which fires right after every `theme` (the profile update's step 8, and the queued redraw in combat) and from the Accent row's set and reset (as `ColorChanged('accent')`). What draws in the accent listens for `accent`, not `button`: a held loot roll's lit border, label and timer, the bags' lit view buttons, loading bars (followers), bag bar slot hovers (followers) and selected bank window, the feed's lit buttons, a selected mover and the edit mode bar (edit mode passes every group on as its `ColorsChanged` event), and SaftUI's tracker, whose handler repaints for `text`, `objectives`, `accent` and `theme` only (`TR.ColorGroupReaches(group)`; a Class or Power pass repaints nothing in it). The zone text and the world map's zone line redraw on `factions`. **What stays as it is, by design:** `/sui` redraws once when the picker closes (its field font follows at once); a tooltip takes a color when it next shows (the unit tooltip on screen follows); chat lines already printed keep theirs; keybind mode's highlight takes it when the mode next opens; what is built when it shows (a roll that starts later, a new feed line, a plate that appears, a bag opened) reads the color then; a roll result line's baked-in colors (below). Nothing needs a reload. Skinning's skins are its submodules, which a pass doesn't reach, so `SK:OnColorsChanged(group, key)` passes the call on to them, each in its own `xpcall`; each filters by group (the color picker's skin only for `accent` and `theme`, Blizzard's objective tracker's for `text`, `objectives`, `accent` and `theme`), the character frame's item levels follow `text` > `strong`, and RestedXP's thumb, step numbers and titles `text` > `muted`. The unit tooltip is the Tooltip module's, called by the pass directly: a shown one takes its unit's `class` or `reaction` color (first line and borders) at once. Anything that colors by item quality uses `st:QualityColor(quality)` (the profile's color, else Blizzard's). The bags repaint by key (`INV:OnColorsChanged(group, key)`, `SaftUI-Bags/slot.lua`, never a re-sort, re-file or layout): `item_quality` with a key recolors the borders of the filled slots and shown currencies of that quality only (a currency slot remembers its `borderQuality`, so the game isn't asked); `text` recolors by key the item levels (`INV.ItemLevelKey(info)`: Warbound `shared`, Bind on Equip `success`, else `strong`), the reagent markers (`success`), the currency counts (`shared` for an account-wide currency, else `strong`), the footers' counts (`INV:ColorBagFooter`, `INV:ColorCombinedFooter`: set again from the counts last read), a special bag's title (`muted`, `INV:RetitleSections`: the laid-out title with only its grey swapped, cut to its laid-out room, no bag asked, no layout), a bank tab's price (`danger` or `strong`) and the view buttons' glyphs and the currencies' funnel (`normal`); `button` `danger` tints the unbought slots of the bank's and the combined bank's bag bar; `accent` relights the view buttons and the selected bank window (`INV:ColorSelectedBank`, kept through a recolor with `st:KeepOwnColors`); a Success pass during an edit colors only the reagent markers shown, the edit's whole pass the rest. The loading bars follow `accent`, the bag bar's hovers `accent` and the combined bank's eyes `muted`. Each Colors row (and `CO:AccentOption`) also names the picker's preview for its color in a `preview` field, chosen by `PreviewOf` (`Media/colors.lua`; one table per row, kept) and drawn by `Config/optionspreview.lua` (`.agents/edit-mode.md`): a new color row needs one, and `tests/core/options_color_preview_test.lua` fails for a row without.
  - Readers of the action bars, the totem bar and the minimap: the action buttons (`AB:OnColorsChanged`, `SaftUI-ActionBars/skin.lua`) follow Buttons > Danger (the flash, through `AB:ColorFlash`, under SaftUI's flat look only) and the Accent (the equipped buttons' border); the totem bar (`TB:OnColorsChanged`, `SaftUI-Misc/totemskin.lua`) follows Danger (the flash), the Accent (the hover), Text > Normal (the flyout's arrows) and Text > Normal and Danger (the timers: `TB:ColorTimers`, `totemtimers.lua`, drops the curves and colors each shown plain timer again, laying nothing out; a timer on secret values takes the new color at its own refresh, 0.1 s later, since a pass makes no curve).

The feed keeps an item's `plain` name, `quality` and, for a currency, `suffix` (its counts), and colors the name as it draws, `LT.FeedItemName(info)` (an entry without `plain` shows its `name`; a merge compares `plain` and `quality`); a progress snapshot keeps `colorGroup` and `colorKey` and the bar reads them as it draws, `LT.ProgressRGB`. - `SaftUI-Core/constants.lua` sets client flags. It reads nothing from the screen: the scale model (`uiscale.lua`) does. `st.forever` is the only client flag (there is no `st.retail`); see `.agents/clients.md`.
- **Textures and icons.** `st.textures` (`constants.lua`) names SaftUI's own texture files in `SaftUI-Core/Media/Textures/` (`st:TexturePath(file)` makes a path). `st.icons` names Lucide's icons the same way (`st.icons.x`, `chevronDown`, `chevronUp`, `rotateCcw`, `diff`, `ellipsis`, `ellipsisVertical`, `settings`, `funnel` (the file is `lucide-filter.tga`: the pinned Lucide 0.460.0 calls the funnel `filter`), `arrowDownToLine`, and the options window's `chevronLeft`, `chevronRight`, `panelLeftOpen`, `panelLeftClose`, `move`, `keyboard`, `list`, the size buttons' `minimize2` and `maximize2`, and the font row's `link`; see `docs/design-system/components/Icons/README.md` for where each is used): `lucide-<name>.tga`, 32x32, white on transparent so code tints one with `SetVertexColor`, no texture coordinates. Lucide draws on a 24 grid with its glyph in the middle half, so draw an icon at twice the glyph's size (a 10 px cross is `SetSize(20, 20)`, an 8 px wide chevron 16). Use a Lucide icon where one fits a hand-drawn glyph. The TGAs are committed; to add one, run `tools/lucide-to-tga.cjs` (its header says how, with `@resvg/resvg-js` installed outside the repo), register the name in `st.icons`, and `tests/core/icons_test.lua` checks the files. Lucide's ISC license is `Media/Textures/LUCIDE-LICENSE.txt`.
- Core helpers live in `SaftUI-Core/api.lua`. The ones you'll use most:
  - pixels: `st:GetPixelSize(frame)` (one pixel in the frame's units), `st:RoundToPixel(value, frame, minPixels)` (the nearest whole pixel; with `minPixels`, any value that isn't zero but is under that many pixels is that many pixels, its sign kept), `st:FloorToPixel` and `st:CeilToPixel` (the whole pixel below or above; a value within 1e-6 of a pixel stays on it), `st:EvenPixels` (the nearest whole pixel, one more away from zero when that count is odd) and `st:GetLineSize(frame)` (`st.lineWeight` pixels, never trimmed). All trimmed to 1e-4 but `GetLineSize`. `SaftUI-Core/uiscale.lua` is the scale model: `st.UIScale.Resolve(choice, screen, gameScale)` works out k (how many physical pixels one design pixel takes), UIParent's scale and the tokens from the screen and the player's choice, purely; `UIScale:SetTokens()` reads `st.pixel` (one pixel in UIParent's units), `st.lineWeight` (a line's whole pixels) and `st.line` (a line in UIParent's units) back from UIParent, so they are what is drawn, and `UIScale:Start()` (in `init.lua`'s `OnEnable`) sets UIParent's scale, pixel for pixel until a later phase reads the choice. At k 1 (a 1440p screen, or pixel for pixel) every token is 1 and every helper gives today's whole number. The game hands a scale back in single precision (768 / 1440 as 0.53333336, a pixel of 0.99999995), so `st:GetPixelSize` takes a pixel whose k (1 / pixel) is within 1e-6, relative, of a whole number as exactly 1 / that number: `st.pixel`, `st.lineWeight` and `st.line` are exactly `1 1 1` at k 1 in game, and a line built from them carries no noise. `UIScale.ReadScreen` (so `Start`) needs both a width and a height, as the model's units wide come from the width; `GetPixelSize` needs only the height.
  - position: `st:DefaultTrackerPosition()` (Blizzard's objective tracker's default spot as a saved position, a fresh table on every call; Misc's tracker mover and SaftUI-Tracker's first position both start from it), `st:CornerOffset(frame, parent, point, screenX, screenY)` (the offsets that put `frame`'s `point` at a screen spot, anchored by `point` to `parent`'s `point`: the screen point less the parent's over the frame's effective scale, through `st:RoundToPixel`; nil for a secret, missing or zero value; Misc's tracker mover and SaftUI-Tracker place Blizzard's tracker with it), `st:UnpackPoint`, `st:PlaceAtPosition` (clear and set a frame from a saved position, offsets as saved; see `.agents/edit-mode.md`), `st:ResolveFrame`, `st:ValidateAnchor`, `st:RoundToPixel`, `st:GetPixelSize`
  - **Half pixels from centred anchors.** SaftUI's scale makes one physical pixel `st.pixel` units (one unit at k 1), and `st:RoundToPixel` keeps sizes and offsets to whole pixels. But a frame anchored by its centre on an axis (TOP/BOTTOM centre it across, LEFT/RIGHT up and down, CENTER both) that's an odd number of pixels long on that axis has its edges half a pixel off the grid. So do its children. The game then rounds each child separately, and children either side of the centre round in opposite directions. Symptom: one gap in a row of buttons is a pixel short, right at the middle (a 12-button bar at 3px spacing is 573px wide). Fix: round the frame up to an even pixel length on each centred axis, so its edges and its centre stay on whole pixels and frames anchored to it line up too. `EvenIfCentred` in `SaftUI-ActionBars/bars.lua` does this, through `AB:PlaceFrame`, which sizes and places both the bars and the extra buttons' holders (`extras.lua`). `st:EvenPixels` (`api.lua`) is that rounding for any addon, rounding the count away from zero when odd; `EvenIfCentred` and the totem bar's `EvenPixels` move onto it in a later phase (they return an even-count length unrounded, so the move changes non-whole inputs). Where the anchor can change without SaftUI's sizing code seeing it, round up on both axes whatever it is. The totem bar (`SaftUI-Misc/totemlayout.lua`, `EvenPixels`) is always sized even, with the spare pixel as empty bar at the right and the top: on a shaman SaftUI places it from its holder, whose Position can be anchored by any point and is changed by drags, and on other classes Blizzard's Edit Mode places it.
  - combat-safe moves: `st:CanMoveNow`, `st:SafeReposition`, `st:QueueAfterCombat`, `st:GetPoints`/`st:RestorePoints`
  - binding keys: `st:ShortBindingKey(key)` (a key in a few characters: `SHIFT-BUTTON4` is `SM4`), which the action bars' hotkeys and the tracker's nearest button call
  - waiting for a Blizzard addon: `st:OnBlizzardAddon(name, fn)` runs `fn` at once if `C_AddOns.IsAddOnLoaded(name)`, else once on that addon's `ADDON_LOADED`, through one shared event frame (a wait made inside a waiting `fn` is kept; an error in a `fn` run from the event goes to the error handler and the others still run; a `fn` run at once raises into its caller). Use it instead of a module's own `ADDON_LOADED` method with `RegisterEvent`/`UnregisterEvent`. A site that already tests for its frame (`if SomeFrame then Setup() else st:OnBlizzardAddon('Blizzard_X', Setup) end`) keeps that test in front, and a guard such as `C_AddOns.DoesAddOnExist` goes before the wait. It is for one named Blizzard addon; a wait on any addon or on another author's addon stays a handler of its own
  - moving Blizzard frames whose methods are Lua overrides: `st:SetPointDirect`, `st:ClearAllPointsDirect`, `st:SetSizeDirect`
  - taking over a Blizzard Edit Mode frame: `st:PlaceHolder` (a holder of SaftUI's, from the profile), `st:HoldFrame` (the Blizzard frame over it), `st:KeepHolderInScreenMargin` (the holder no nearer the screen's edges than the frame's own clamp lets the frame go, where that clamp would hold back the frame: chat, the swing timers, the tooltip) and `st:HideEditModeSelection` (its Edit Mode box); see `.agents/edit-mode.md`
- Styling: `st:SetBackdrop`, `st:SetTemplate`, `st:SetBackdropIn` (`theme.lua`, below), `st:CreateFrame` (`panels.lua`), `st.OutlineFlag(outline)` (`Media/fonts.lua`; the font flag for a saved outline key, `'NONE'` giving `''`, so pass it to `SetFont` and never the raw key), `st.Clamp(value, low, high)` (`utilities.lua`; floors, nil is `low`), `st:CreateButton`/`st:SkinButton` (`Widgets/`). Colors other than the theme's live in `st.config.profile.colors`, and are read through `st:Color(group, key)` and `st:ColorRGBA(group, key, strength)` (`Media/colors.lua`), which read the active profile at call time, fall back to `st.defaults`, and error (`SaftUI: no color <group>.<key>`) on a key with no default, so a renamed or retired key fails where it is read; Every Text, Buttons, Roles, Factions and Loot read, and every read of the accent, goes through them: `tests/core/color_reads_test.lua` scans every loaded file for a retired key (the six Text hues, `text.white` to `cyan`, and `button.red` among them), a group alias of one, a Buttons read through `st:Color` (rule F: it would leave the opacity out), a literal key with no default, a retired wrapper by its hue name (`Blue`, `LinkBlue`, `OWN_TEXT`, `Grey`, `GreyRGB`, `DIFF_COLOR`) or the tip line's old field (`red = true`), and for a direct read of `colors.text`, `colors.roles`, `colors.factions`, `colors.loot`, `colors.button`, `Colors().text` and the like, in a one-line alias (`local c = …colors; c.text`), as `['colors']['text']` or in `rawget(Colors(), …)`, or `theme.accent` (rule D; `Media/colors.lua` is the one exempt file). Groups named for a game concept (class, reaction, power, item quality, status, threat, objectives) keep their own reads. **Buttons' opacity is drawn:** a Buttons color is read as `st:ColorRGBA('button', key, strength)`, whose alpha is the reader's own strength times the color's opacity (a color with no `a` is fully opaque), so at the defaults (100%) every reader draws the alpha it always drew and at 50% half of it. The strengths: a micro button's highlight 0.4 and pushed fill 0.6 (`HOVER_ALPHA`, `PUSHED_ALPHA`), the action bar and totem button flash 0.4, the bank's unbought slot 1 on the vertex (its region's own 0.3 is kept), and every other reader 1 (a button's highlight and pushed fill, a check box's fill and highlight, a scroll bar thumb, the resize corners, a micro menu item, the tracking, queue and expansion buttons' highlights). The accessor returns four numbers and allocates nothing, so a reader on a hot path (the scroll bar thumb's hover) stays cheap. Core's readers follow a pick at once through `st:FollowColor`: a SaftUI button's highlight and pushed fill (Normal, Pushed), a check box's checked fill and highlight (Hover, Normal; a pass leaves them under Blizzard's white art), a scroll bar thumb (its state's key, so Buttons > Danger paints nothing), the resize corners and /sui's grip (Hover), a radio group's picked button and `st:SkinActionButton`'s flat hover (the Accent; the picked button is a field of SaftUI's own frame, the hover is skipped under Blizzard's state art), and a close button (Text > Muted and Danger, drawn by the file-level `LookClose(close)` from the button's own `hovered` and `blizzard` fields); `st:KeepOwnColors`' list is unchanged. `st:IsBlizzardLook` builds no look table, so a pass may ask it, and so may `st:ThemeBorderColor(theme)` (the border color a Theme override draws, the profile's theme's for None: the two trackers' header lines). The action bars' own button hover (`SaftUI-ActionBars/skin.lua`, `HOVER_ALPHA`) is a white tint at 0.15, not a Buttons color. A bare check box (the bags' currency veil and the combined bank's eye) follows only its highlight: its caller restyles its checked texture, which no pass repaints. Text > Muted is `OB.Muted()` in the options kit (`r, g, b`, exported as `S.Muted`), `D.Muted()` in the bags' `dragparts.lua`, `MutedRGB()` in the RestedXP skin, and the diff icon draws it at `OB.DIFF_STRENGTH` (1); SaftUI's tracker's paint state for it is `'muted'`. Text's other rows are `strong` (plain item levels and counts, the character frame's item levels, the bank price you can afford, the share line under the mouse, loot roll timers over a minute, the tracker's progress percent, its paint state `'strong'`, and its chevron under the mouse), `danger` (errors and refusals, the chat's Error prefix and DEBUG label, urgency, remove icons and the close button's edge and cross under the mouse, hostile names, a much higher level, a durability under 20%), `warning`, `caution`, `success` and `shared`; Buttons > Danger is `st:ColorRGBA('button', 'danger', strength)` (locked bank slots at 1, the flash on an action bar or totem button at 0.4). A tip line (`W.ShowTip`) in Danger is `{ text = ..., danger = true }`. The accent is read as `st:Color('accent')`, or `OB.Accent()` in the options kit (`r, g, b`), and the own marks are the accent at `OB.OWN_STRENGTH` (1). Blue is not a color on the Colors tab: a profile's saved Buttons > Blue becomes its accent at migration step 2 (`st:MigrateColors`, `CO.MIGRATION_STEPS[2]`, which also retires Text > Blue, whose own saved value went to Tank and Alliance at step 1, and Buttons > Green). The chat prefix (`st:Print`, `st:Error`) is the accent's hex at print time, `00adf0` until the defaults exist, and `st:Error`'s word Error and `st:Debug`'s DEBUG are Text > Danger (`dc6464` until the defaults exist): the print reads the accessor inside a `pcall`, so a load-time print needs no direct read of a default.

## Themes

SaftUI draws its frames in one theme, Thick, Thin or Blizzard, set on Global settings' Theme tab, which any module can override. The design is `docs/superpowers/specs/2026-11-10-saftui-themes-design.md`, and the Blizzard theme's `docs/superpowers/specs/2026-11-10-saftui-blizzard-theme-design.md`. Blizzard draws each kind of frame in Blizzard's own art, on SaftUI's own frames: the engine resolves it, holds its art's tables and draws its art (`SaftUI-Core/themeart_data.lua` and `themeart.lua`). The Theme tab and every module's override offer it, and no default is Blizzard.

- **The profile.** `st.config.profile.theme = { name, transparent, opacity, optionsbackground, accent }` (the accent, `CreateColor(0, 0.68, 0.94)`, is one color for every theme; `thick`, see-through at 0.9 by default, `optionsbackground` `'theme'`; the Theme tab's Background color shows and sets the pair as its alpha: 100% when `transparent` is off, `opacity` when on). A `name` this version doesn't know (a later version's theme, in a profile opened by an older build) reads as Thick wherever it's read (`st:ResolveTheme`, and the Theme tab's rows), and stays saved until the user picks a theme. Each theme keeps its own colors, arrays in `st.config.profile.templates.thick`, `.thin` and `.blizzard` (`bordercolor`, `altbordercolor`, `backdropcolor`, and Blizzard's `windowcolor`, the fill of its windows; Thick's and Thin's windows take their `backdropcolor`; Blizzard's two fills both default to its dark grey, and can be set apart); `templates.close` is the close button's red. The key is still `templates`: saved variables may keep the word, only what the user sees changes.
- **A module's override** is a pair of config keys, `theme` (`'theme'`, `'thick'`, `'thin'`, `'blizzard'` or `'none'`) and `background` (`'theme'`, `'solid'` or `'transparent'`); `'theme'` follows SaftUI's. SaftUI's own config windows (the `/sui` window, edit mode's bar, floating window and History list, the small dialogs) are drawn with the Background `'options'`, which is not a choice but resolves (in `st:ResolveTheme`) to Global settings > Theme > Options windows (`theme.optionsbackground`: `'theme'` by default, which follows the theme's Background, or `'solid'` or `'transparent'`); what opens over content (lists, item menus, the search panel, the color picker) is drawn `'solid'`. The Bags have a second pair for their item and currency slots, `buttontheme` and `buttonbackground`, and the unit frames one per unit and element. Core's `buttons` and `panels` have the pair with no option, following the theme. The options come from `generators.theme` and `generators.background` (`.agents/edit-mode.md`), and a change re-runs the module's `UpdateConfig`, which draws with the new pair.
- **The engine** is `SaftUI-Core/theme.lua`:
  - `st:ResolveTheme(theme, background, kind)` turns a pair into the look a frame is drawn with as kind (`{ name, inset, alpha, colors, kind }`, or nil for None); a Transparent background uses the profile's Opacity even while the toggle is off. `st:ThemeInset(theme, background, kind)` is how far in its border reaches, with the kind required as a draw call's is (an error unless the Theme is None): where content sits, for layouts that used to read `frame.thick`. `st:DrawnInset(frame)` and `st:DrawnKind(frame)` give the inset and kind a frame was last drawn at (a drawn frame, or the owner of a backdrop the engine drew; 0 for None, nil for never drawn), which `st:CalculateSpacing` reads. By the same lookup, `st:DrawnTheme(frame)` is the theme it was last drawn in (nil for None) and `st:DrawnFrame(frame)` the frame its look is on (itself, or its backdrop): a window's close button sits in the metal's socket by them (`st:CloseButtonInSocket`, `panels.lua`), and its header in the metal's title bar (`st:HeaderInTitleBar`: the title, the header's buttons and the window's content, placed under the header, move up with it; see `.agents/edit-mode.md`, the close button). The inset is 2 for Thick and 1 for Thin whatever the kind, 0 for None, and the kind's own under Blizzard (`st.ThemeArt.Inset`). With no kind, `st:ResolveTheme` gives a Blizzard look no inset. `st:IsBlizzardLook(theme, background)` says whether a pair draws in Blizzard's art, for controls that show that art themselves.
  - `SaftUI-Core/themeart_data.lua` (loaded right after `theme.lua`; it makes `st.ThemeArt` and holds the tables and the `Atlas()` helpers that build them) and `SaftUI-Core/themeart.lua` (loaded next, with the accessors and the drawing) hold the Blizzard theme's tables: `KINDS` (each kind's inset per client, its art and its fill) and `ART` (the tooltip border, the character frame's metal, the unit frame's bronze box, the action and item buttons', the aura's and the close button's art, and every control's, among them the group border, the unit frame bars' fills, the resize grip, `/sui`'s size arrows (`sizebutton`: Blizzard's `MaximizeMinimizeButtonFrameTemplate` art, `RedButton-Expand` for grow and `RedButton-Condense` for shrink with their `-Pressed` and `-Disabled` and the additive `RedButton-Highlight`, 24 square, every atlas on both clients and marked for both, drawn by `S.LookSizeButton` in `SaftUI-Core/Config/optionssizes.lua` as textures of the arrow's own), the micro menu bar's art and the nameplate target's, `nameplatetarget`: Forever's `UI-HUD-CoolDownManager-Selected-yellow` and retail's `UI-HUD-Nameplates-Selected`, each marked for its client, with the offsets it sits at round the health bar). The accessors read them for the client at call time (`ThemeArt.Client()`, `'forever'` or `'live'`): `Inset`, `Top` (how far the art reaches down from the drawn frame's top: a window's title bar), `TitleHeight`, `TitleStrip` (the strip of the title bar a window's header sits in, 20 on both clients, its bottom on the window's top), `MetalAbove` (how far the metal's art reaches above its drawn frame, 16), `MetalReach` (its reach past the drawn frame on the left, right, top and bottom: 8, 2, 16, 8 on Forever and 8, 4, 16, 3 on retail, which `/sui`'s window gives `st:KeepInScreenMargin` as its `reach`), `Close`, `State`, `Control` and `ClassPower`. It also draws a Blizzard look for `theme.lua` (`ThemeArt.Paint`, `ThemeArt.Color`, `ThemeArt.Clear`): textures made once per drawn frame and kept in its weak tables (`ThemeArt.Get`). A border's pieces are on the drawn frame. A button's ring lies over the icon's edge: on a button of SaftUI's (`st:SetBackdrop`) it's a texture of the button's own, in ARTWORK below 0 (over an icon in BACKGROUND or BORDER, under its texts and cooldown), and otherwise, or on a frame marked with `st:MarkForeign` (someone else's, still drawn with `st:SetBackdrop`), it's on a frame of SaftUI's over the backdrop. Under Blizzard a backdrop has a fill and no edge (a small frame keeps one line), a window's backdrop reaches its title bar above it, and `header`, `close` and `control` are cleared; Thick and Thin hide the art. An art name is an atlas unless it's a file under `Interface\` (the resize grip's three files, so it isn't among the atlases). Each atlas is marked as the tables are built, `Atlas(name)` for one both clients have and `Atlas(name, client)` for one only that client has (`'forever'` or `'live'`): Forever's Camelot minimap art (`ui-hud-minimap-header-button`, `-addon-indicator`, `-tracking-button`) is Forever's only and named only in Forever's art. `st:ThemeAtlases()` gives `{ [name] = true | 'forever' | 'live' }`, and `tests/core/theme_blizzard_test.lua` checks each atlas exists on the clients it's marked for. **Cut art.** The bronze box and the group border don't set an atlas on their textures: `ThemeArt.Cut(texture, atlas, rect)` reads the atlas's file and its coordinates from `C_Texture.GetAtlasInfo` (on Forever the Camelot member's) and sets the texture coordinates of `rect` (`{ x0, x1, y0, y1 }`, exclusive ends, in the atlas's own pixels) within the member, hiding the texture and returning false when the client gives no file, no texture coordinates or no size; a cut's pieces are anchored corners of `size` and stretched edges (`LayCut`), with no size read back from a frame. `ART.unitframe` is eight pieces (corners 8 x 8) cut from the target and player frames' art, per client because retail's art is a different drawing; `ThemeArt.PaintCut(frame, name)` lays a cut on a frame that is only that art (the group border) and `ThemeArt.Clear` hides it; `st:SetBorderColor` tints a cut's pieces as it does a border's. `ThemeArt.LayBorder(pieces, frame, border)` lays a nine-piece border on a frame in the caller's own pieces table (the tooltip border's way, and its Center, anchored between the corners and untiled, when the border has one: retail's minimap button kit does) and `ThemeArt.HidePieces(pieces)` hides them. SaftUI places the art itself and never runs Blizzard's nine-slice code (`.agents/taint.md`).
  - Every draw call names its kind of frame, last: `st:SetTemplate(frame, theme, background, kind)`, `st:SetBackdrop(frame, theme, background, kind)` and `st:SetBackdropIn(backdrops, frame, theme, background, kind)`. The kinds are `st.THEME_KINDS`: `panel` (a background), `window` (a window with SaftUI's title bar), `bar`, `action`, `slot`, `aura`, `tooltip`, `header` (header and footer strips), `close` (the close button), `control` (a small frame Blizzard draws with art of its own), `unitframe` (a unit frame or one of its bars), `member` (a party or raid member's frame or bar) and `small` (everything else), thirteen in all. Under Thick and Thin only `header` and `close` draw differently (SaftUI's theme's fill, no lines): a window draws as a panel, a control as a small frame and `unitframe` and `member` as a `bar`. Under Blizzard `unitframe` is the bronze box (inset 2) and `member` a bare Background fill (inset 0, no art). Blizzard's look is the kind's own (`ThemeArt.KINDS` in `themeart_data.lua`). A call with no kind is an error, unless its theme is `'none'` (which only clears). `st:SetTemplate` also takes a fifth, optional argument, the button its ring and own-color piece are textures of (for a frame drawn on itself behind a button that isn't SaftUI's, which holds its own texts: the totem bar's). Use the `st:` form even inside Core's own methods: `tests/core/theme_kinds_test.lua` scans every file the TOCs load for draw calls without a kind, and fails on any other form.
  - Each drawn frame is recorded with the arguments it was last drawn with. `st:RecolorThemed()` puts the current colors and opacity back on every one, moving nothing; `st:RedrawThemed()` draws each again at the current inset, and moves a backdrop only while it still sits where the engine last put it (one its caller anchored itself is repainted where it is, even at the engine's own offsets). The engine knows that from its own record, never by measuring the backdrop: post-hooks on each backdrop's anchor setters (`Watch`) forget the record when anyone else moves it, since a backdrop on a nameplate is anchor restricted and `GetPoint` on it errors (`.agents/taint.md`, rule 13). Both color or draw each frame on its own (`xpcall` to `geterrorhandler()`): one that errors is reported, and every other frame still takes the theme.
- **The Theme module** (`SaftUI-Core/Media/theme.lua`) is the tab. A color or Background opacity change, or a change of Options windows, runs `st:RecolorThemed()`. A Theme change, or a Background alpha that turns the fills solid (100%) or see-through (under it), runs `st:ThemeChanged()`, which is `st.Config:UpdateConfig()`, the profile update: it redraws every drawn frame once (`st:RedrawThemed()`), has every module lay itself out again (the border's width moves what sits inside it), and ends with `st:ColorsChanged('theme')` and then `st:ColorsChanged('accent')`. Both wait for the end of combat (one pending run, `st:QueueAfterCombat`). The Accent row (`order` 5.5, built by `CO:AccentOption` in `Media/colors.lua`, one color for every theme with no opacity and its own reset) sits between Background and Options windows: its set and reset write the profile's `theme.accent` in place and say `accent`. The tab's last section, Window titles (`order` 7), is one Font row for `headers.font`, one setting for every theme: its set and reset run `st:FontsChanged()`, which every header's title (`st.CreateHeader`'s `st:FollowFont`), `/sui`'s Blizzard title bar and the color picker's title (`CP:OnFontsChanged`) answer at once. Each color has its own reset in place of a Reset for the tab (the options kit's `default` field, `.agents/edit-mode.md`): it puts the chosen theme's default back the same way, a recolor, or for Background, which puts back the shipped transparency and opacity too, the profile update when that turns the fills solid or see-through.
- **A profile switch, copy or reset is a theme change** when the two profiles' themes or theme colors differ, so `Config:UpdateConfig` always redraws and recolors (below): no frame keeps the old profile's look until a reload.
- **A frame's own border color** goes on through `st:SetBorderColor(frame, r, g, b, a)`, never `SetBackdropBorderColor` on a drawn backdrop (`tests/core/theme_kinds_test.lua` scans for it); `frame` is the drawn frame the caller holds (`x.backdrop`, `backdrops[x]`, or one drawn with `st:SetTemplate`). With no color it puts the look's own border back, with no redraw. Under Thick and Thin it is the backdrop's border. Under Blizzard it is the kind's own: the tooltip and metal pieces tinted, `action`'s `UI-HUD-ActionBar-IconFrame-Border` or `slot`'s and `aura`'s `Interface\Common\WhiteIconFrame` shown in the color over the icon's edge (`st.ThemeArt.Get(frame).own`, a texture on the button of SaftUI's the way the ring is, or on a frame of SaftUI's over the backdrop for a frame that isn't SaftUI's: mark Hekili's or WeakAuras' with `st:MarkForeign` before the first draw), a `small` frame's line; a `control`, a frame never drawn and a frame drawn None are left alone. A recolor or redraw takes the color off, so a module colors again in `OnColorsChanged('theme')`. It resolves no look table and, under Blizzard, `ThemeArt.SetBorder` textures and places its own-color piece only when it makes it, then only colors and shows it (`tests/core/theme_border_cost_test.lua`: 40 borders, 100 passes, no garbage and no forbidden call under every theme), so a color pass may call it.
- **Colors a frame's own code puts on its backdrop** (an item's quality border, a debuff's type, an equipped item, a tooltip's class border, a selected mover) would be wiped by a recolor or redraw, so they're put back two ways:
  - a module's `OnColorsChanged('theme')` colors the borders it tracks again (Bags, ActionBars, Loot's feed, Tooltip, the totem bar, Skinning's skins, edit mode's movers, and the unit frames: the target's border on every nameplate, `UF:UpdatePlateTarget`, each plate on its own);
  - `st:KeepOwnColors(frame, color)` registers `color(frame)` for one frame, run again after every recolor and redraw: Core's widgets, which have no module (a scroll bar thumb's hover, a radio group's picked button, a focused edit box; and Core's controls, which switch between their own look and Blizzard's art under the Blizzard theme: `st:SkinButton`'s panel button and tabs, `st:SkinCheckButton`'s check box and panel button, the scroll bar's own layers, an edit box's own border textures. `st:SkinButton` and `st:SkinCheckButton` register under a table of their own, since a module keeps its own colors under the same button), the lit border of a loot roll you've chosen on (`SaftUI-Loot/rollbar.lua`), the target's border on its nameplate (`SaftUI-Unitframes/nameplates/target.lua`, on both the health bar's and the plate frame's drawn frame, whichever carries it), and the unit frames' aura buttons (the dark line `auras.lua` draws inside each button's Thick border, `ColorInnerLine`, in Thick's outer border color, shown only under Thick; the dispel-type texture, a fill behind the icon or under Blizzard Blizzard's white icon border over the whole button, set by `StyleButton` when the element updates, is a separate texture a recolor or redraw never touches). nil forgets it. The frame is only a key, so it may be Blizzard's. A color function may keep another frame's colors (the plates' target border does, for a frame a redraw drew first): each pass walks a copy of the frames, so one kept during it runs from the next.
- **Saved template choices migrate.** Before themes, a module saved an old template name (`thicktransparent`, `thin`, `none`, ...) in a key named `template` or `<prefix>template` (`buttontemplate`). `st:MigrateTemplateKeys(tbl)` (`theme.lua`) walks a table and rewrites each such key holding a string into `<prefix>theme` and `<prefix>background` through the old names' table (`thicktransparent` is Thick and Transparent, `thin` Thin and Solid, `none` only None; `highlight`, `close` and any other string just go, so the module's defaults apply), and removes it. Every old choice was a string, so any other value under such a key is data and stays (a unit frame profile the user named `raid template` is a table, walked like any other). It reads only what's saved (never through AceDB's `**` defaults), and running it again changes nothing. `Config` runs it wherever saved data enters a profile: on `st.config.profile` right after `AceDB:New` at login, at the start of every `Config:UpdateConfig` (a profile switched to or copied from one the old version saved), and on the data `Config:Import` returns (so the unit frames' Import too). The unit frames' own profiles live inside the SaftUI profile, so they migrate with it, and their Copy copies a profile already migrated.

## Config, defaults and profiles

- Each module defines its defaults at file load in its own `config.lua`, as `st.defaults.<key> = { ... }`. Unit frames keep theirs in `SaftUI-Unitframes/config/`.
- `Config:InitializeAceConfig` (called from `SaftUI:OnEnable`) creates `st.config = AceDB:New('SaftUI_DB', { profile = st.defaults, ... })`. Read settings through `st.config.profile.<key>`.
- **A page says where its settings are saved, and the kit reads the default.** `st:DefaultAt(...) -> found, value` (`SaftUI-Core/Config/optionsdefault.lua`) is the default of a saved path in `st.defaults` as AceDB-3.0 fills a profile (the first table that names a key decides, tables merge, a `'**'` is merged into the child it sits beside and into a child an earlier table made, a key nothing names takes the last `'**'` or `'*'`), which `tests/core/default_at_acedb_test.lua` checks leaf for leaf against a real `AceDB:New` over every addon's defaults, so a reset icon needs no second copy of a default. A table it gives is `st.defaults`' own (one table) or a merged copy (several): copy it before writing. A group's options say where they are saved with SaftUI's `saved` field beside the `get` that reads them (`saved = st.Config.SavedIn('chat')` for `self.config[info[#info]]`; an option with its own `get` takes `st.Config.SavedAt('chat', 'editbox', 'height')`; `false` for a value that is not a profile key), or a hand `default`, or `noReset = '<why>'`; `tests/lib/reset_walk.lua` fails a value row with none, and a `saved` that names another setting's key. See `.agents/edit-mode.md`, "A setting's own reset". Read defaults from `st.defaults` (this function), never through `st.config.profile`: AceDB's `'**'` creates a table on read.
- **Bind, don't cache.** In `OnEnable`, call `st:BindModuleConfig(self, '<key>')` instead of `self.config = st.config.profile.<key>`. On a profile change, AceDB switches to the new profile's tables and strips defaults from the old ones, so any reference cached at enable time (including upvalues and closures holding sub-tables) returns nil fields. Bound modules are re-pointed automatically. In option `get`/`set` functions and hooks, read through `self.config` at call time.
- **Per-character saved data** (not settings) goes in AceDB's char namespace, `st.config.char.<key>`, which a profile switch doesn't touch. SaftUI-Loot keeps its saved feed and recorded roll drops there (`Feed/history.lua`; the recorded drops' accessor `RecordedDrops` is in `Feed/loothistory.lua`, and `Feed/rolls.lua` records them). Read it through an accessor at call time (`st.config` doesn't exist at file load). Save only plain data (strings, numbers, booleans and tables of them), never a secret value (`.agents/clients.md`) and never test-mode entries, and keep each record to the fields its readers need. SaftUI-Tracker's `st.config.char.tracker` (`TR:CharData()`) is the same kind of thing.
- **Account-wide saved values** (not settings) go in AceDB's `global` namespace, `st.config.global.<key>` (the options window's place, height, size and sidebar, `optionsWindow`; `debug`), which a profile switch, copy or reset never touches.
- **Profile changes** (`OnProfileChanged`/`Copied`/`Reset`) run `Config:UpdateConfig()` in `SaftUI-Core/Config/config.lua`. Order:
  1. Migrate the profile's saved template choices (`st:MigrateTemplateKeys`, see Themes) and its colors (`st:MigrateColors`, see below), then re-point every bound `module.config`.
  2. Redraw every drawn frame in the profile's theme (`st:RedrawThemed`), before any module lays itself out around its border. In combat the redraw and step 8 wait for the end of combat, as one pending run (`QueueAfterCombat('ThemeRedraw')`). In and out of combat they're two steps, each in `xpcall`, so a redraw that errors still has step 8 run after it.
  3. Clear mover anchors (`EM:ClearPositions`, which saves them and skips frames that are protected in combat).
  4. Apply fonts (the Fonts module's `UpdateConfig`: Heading's face step, then the objects; then `Config:UpdateConfig` runs `st:FontsChanged()`), then headers (`st:UpdateHeader`: every header's and footer's height and window title fonts, and each header in its window's metal title bar or back; a header or footer that's protected in combat waits for the end of it), then the screen edge margin (`st:UpdateScreenMargin`: every frame kept inside it; see `.agents/edit-mode.md`).
  5. Run every module's `UpdateConfig` inside `xpcall`, with errors going to `geterrorhandler()`.
  6. Re-apply edit mode movers (`EM:UpdateConfig`), restoring the old anchors of any frame left without points.
  7. Rebuild and refresh an open `/sui`.
  8. `st:ColorsChanged('theme')`, so what modules color themselves (quality borders, a selected mover) goes back on over the redrawn theme, then `st:ColorsChanged('accent')`, so what draws in the accent follows, then every other group's whole pass (`st:ColorsChanged(group)` for each of `st.COLOR_GROUPS` but `accent`, in the Colors page's order, each in `xpcall`: a switch, copy, reset or import can change any color), in combat too once it ends.

  In combat, protected work is deferred with `st:SafeReposition` / `st:QueueAfterCombat`, and one chat message says what will finish after combat.
- **Every module needs an `UpdateConfig`** that re-reads the profile and re-applies everything it controls (positions, sizes, its Theme and Background, fonts, colors, visibility). It must be idempotent: never create frames, font strings or hooks on each call. Create once, re-style on every call. Settings that genuinely can't apply live (module on/off toggles, secure header attributes) say "reload to apply" in their option description.
- Position config shape: `{ point, frame, rel_point, x_off, y_off }`, unpacked with `st:UnpackPoint`. Some older code used array positions (`{'BOTTOMRIGHT', -20, 20}`). Modules that converted (Bags, Chat, Experience) migrate saved arrays in place on enable and on profile change, filling missing slots from the old array defaults, because AceDB only saves slots that differ from the default.
- **Fonts** (`SaftUI-Core/Media/fonts.lua`, module `Fonts`). `FN.FONTS` is the fixed list of the six shared fonts, in the order of the Fonts tab and every font list: Text `normal`, Small text `pixel`, Large numbers `pixel_med`, Heading `heading`, Huge title `title`, Subtitle `subtitle`. Their names and jobs are in code (a profile's saved `name` is ignored), their objects are `SaftUI_<key>Font`, and every walk is over `FN.FONTS`, never `pairs(st.config.profile.fonts)`, which may hold a saved `version` and edits to a dropped font. `FN.DROPPED` has Pixel Huge and Normal Med, which no code reads but a profile's font setting may still name: such a key reads as the typeface it looked like, with `profile.fonts[key]` over it, and nothing is written. **Heading's defaults**: Heading is the default of `tracker.header_font` (SaftUI's tracker's header line, count and zone headers) and `inventory.fonts.titles` (the bags' category titles), and the face of RestedXP's guide title (`restedxp.lua`, at RestedXP's size plus 3). The tracker's header line and zone rows are 24 and 20 tall at least and grow with the Header font (`TR:HeaderHeight()`, `TR:ZoneHeight()`: `Layout.HeaderHeight`, `Layout.ZoneHeight`, about 1.25 times its size, even), so a large Heading neither overflows nor clips; every view of the bags cuts a category title to its column, Compact's too. A default change reaches only a profile that never saved the key (AceDB), so a profile that saved something other than the old default keeps it. **A profile that had picked the old default (Text) has nothing saved (AceDB drops a value equal to its default), so it moves to Heading**; the owner re-picks Text if he wants it. The bag window's search box and the bags' gold and free-slot texts are Text (`st:ApplyFont(fs, 'normal')`), not a title font. **A bag font setting restyles texts and nothing else**: Title font and Icon font (`inventory.fonts.titles`, `.icons`) write through `INV:ApplyFonts(which)` (`inventory.lua`: for `titles` the category titles, fitted to their column again (`INV.FitTitle` with the text and room `UpdateCategory` kept); for `icons` only each slot's count and item level, the item level's color put back (`INV:ColorItemLevel`) and `INV:ApplyCurrencyFonts()` for the currency counts and their color: a font object may bring its own color with it. `st:ApplyButtonFonts(button, font)` in `skinning.lua` is the whole-button font part of `st:SkinActionButton`, run by a full skin, not per step), never `INV:UpdateConfig()`, which skins every slot, lays the windows out and queues a re-sort of the bags and would run on every step of the dots menu's Size drag. A font setting's set must do the least that shows it, since a held slider writes on every step; one font object is made per new size, which is the only cost left. **A font setting has two shapes**: a shared font's key (a string, every default), or a typeface table with a shared font's own fields (`font_name`, `font_size`, `font_outline`, `shadow_offset = { x, y }`, `spacing`). `st:FontFields(value)` is the one normaliser (a wrong-typed or out-of-range field reads as the base's or is clamped; it returns a fresh table and writes nothing); the rest are built on it. **The rule for readers**: a text gets its font from `st:ApplyFont(fs, value)` (`SetFontObject(st:FontObject(value))`, Text's object when the value names nothing), never `SetFont` (in game `SetFontObject` does not undo an earlier `SetFont`); `st:GetFont(value)` is the shared object, or one `SaftUI_Typeface<n>Font` per distinct look (white, made once, never set again), or nil for anything else; a reader that only takes values uses `st:FontValues(value)` (path, size, flags, shadow X and Y, spacing), `st:FontLabel(value)` (a shared font's name, a typeface as "Colus 15, outline") for words, `st:IsSharedFont` and `st:FaceFont(font, size, outline)` for a saved face, size and outline. `FN:SetObject(object, fields)` sets any font object (the face from LibSharedMedia, size, outline, an opaque black shadow, the offset, spacing, then the size one up and back so texts measure again). Every face SaftUI registers (`st.SAFTUI_FACES`, `Media/sharedmedia.lua`) is set on a font object of its own at load (`FN.preloaded`): a font file draws reliably only once a font object has been set to it. **Following**: a text with no module to apply it again is kept with `st:FollowFont(region, getValue)` (weak; nil forgets, as `st:UnfollowFont(region)` does; a key with no `SetFontObject` of its own, a Button, takes a third argument, `apply(key, fontObject)`, which `Widgets/button.lua` uses for a button's normal, highlight and disabled font objects) and applied again by `st:RefollowFonts()`. **A pool that releases a region must call `st:UnfollowFont(region)`**: weak keys free nothing in the game, so a kept region is otherwise given the old setting's font after it is reused; a getter must not close over its region. The value helpers build no tables (`st:FontFields` is for callers that want one; `st:FontParts(value)` gives the same six answers as `Resolve` (names, not the file path `st:FontValues` gives) with none, for the options kit's compare of a typeface), so a reader on a hot path costs no garbage; a typeface's object is cached by its resolved look and the file its face fetches, so a face another addon registers later is a new look the next time it is asked for. `st:FontsChanged()` (beside `st:ColorsChanged`) runs `st:RefollowFonts()`, then every module's `OnFontsChanged()` in `xpcall` (the tracker's and the totem timers' re-layout); the Fonts tab's sets and Kinds of text's call it, and so does `Config:UpdateConfig` right after the Fonts module's update, so no code hooks `FN:UpdateFontConfig`. `FN:ConvertHeadingFace()` is Heading's one-time face step (`fonts.version`, below). **Which readers follow and which re-apply** (Core, Chat and Misc): a text SaftUI owns follows its setting with `st:FollowFont` (window titles in `st:CreateHeader` and `/sui`'s title bar: Window titles, on the Theme tab; a check button's label: `panels.font`, which has no row on the Fonts tab since no check box label is visible (the followup "Check box labels: no font setting until a SaftUI check box has a visible label"), and a label a module skins with `st:SkinButtonLabel` (one line, anchored by its sides, following Button text; the bank's Buy and the Edit toggle); the label of every button `st:CreateButton` makes (`button.text`) and `st:SkinButton` skins with no font of its own (its normal, highlight and disabled font objects, or its font strings on a frame with no states; `st:CreateButton` and `st:SkinButton` take a font, which the micro menu's clock uses to stay in Small text, since the bar sets it on every layout), the texts of a button `st:SkinActionButton` skins with no config, the bag slot bars' and bank bag slots', and the totem bar's key, count and name texts: Button text; A reader that only takes values or builds objects re-applies from its module's `OnFontsChanged`: chat (`CHT:OnFontsChanged` converts, then sets each window's font and its edit box's font, and nothing else; a window whose values from chat are unchanged is left alone, so Blizzard's own Font Size menu survives a Fonts tab change that does not touch chat's font), the buff and debuff timers (`AP:OnFontsChanged`: their font objects, from `st:FontValues(st:FaceFont(font, size, outline))`, a shared font's face, size, outline and shadow, and a face at the setting's size and outline), the Skinning skins (`SK:OnFontsChanged` hands the call to each submodule with one: the Cooldown Manager, whose bar items' count is as tall as the font, RestedXP and the color picker). The other skins (buff, swing timer, character frame, objective tracker) have none: their texts on a shared font follow its object, and a change of the Skinning font setting runs each skin's `UpdateConfig`; their fonts come from `st:FontObject` or `st:ApplyFont`. A face the game refuses to load is found by `st:FontLoads(path)`: SaftUI's preloaded faces count as loading with no probe; any other file is tried on a `CreateFont` object of SaftUI's own (the mechanism known to work: a file draws reliably only once a font object has been set to it), after putting the object on a known face (a file already known to load that is not the one probed: one of SaftUI's preloaded faces, never Text's own, which may be a face SaftUI does not preload or one that raises; that call is guarded too), and counts as refused when the call raises, returns false, or leaves the object on that known face (`Font:SetFont` has no return value and `Font:GetFont` returns a file, a height and flags, in the API documentation on both clients; a missing file's answer is not documented, so each of those counts). A positive answer is kept for the session; a refusal lasts only until the next `st:RetryFonts()`, which `st:FontsChanged()` runs and so does a font row picking a face and a font list opening, so a changed font setting, a pick or a reopened list tries the file again, and a path is probed once between two of those, so a hot path costs one lookup. A typeface object made in Text's face for a refused file is made again once the file loads. The color picker is restyled, not followed, because a follower would put SaftUI's font back on a text the skin has given Blizzard's. That is the bags' category titles, item levels and Icon font, the loot rolls', feed's and window's texts, the tracker's rows, header and count and its item buttons' count, number and key texts, the unit frames' elements and texts (`UF:UpdateElement`, `UF:UpdateText`, the aura count and timer, the name), and the action bars' texts. The objective tracker's colors (`OTP:MoveStatusColors`, `objectivetracker.colorsMoved`: the skin's old `status_colors`, `{ r, g, b }` arrays whose dropped slots come from `OTP.OLD_STATUS_COLORS`, written onto `colors.objectives` and then removed) convert in `OTP:OnEnable` after `st:BindModuleConfig` and first in `OTP:UpdateConfig`, and recolor the skin's lines. The bags' categories (`INV:MigrateCategories`, `categories.version`) do; so do the action bars: `actionbars.version = 1` (no default) marks a profile converted to All bars (`actionbars.all`) and per-bar own flags (`<bar>.own`), by `AB:ConvertProfile` in `SaftUI-ActionBars/shared.lua`. Every action bar reader takes `AB:GetBarConfig(id)`, never a bar's stored values, as a bar follows All bars for each setting it doesn't own. **The colors** (`st:MigrateColors(profile)`, `Media/colors.lua`; marker `colors.version`, which only rises: a non-number counts as 0, and one at or above the last step runs nothing) convert at login (in `xpcall`) and in `Config:UpdateConfig`, never in `Config:Import`. `CO.MIGRATION_STEPS` has one step per change of the colors' keys, each `{ copy, retire, opacity }`: a source color that was customized (its r, g and b differ from `CO.OLD_COLORS`'s shipped value as whole bytes; a channel that isn't a number takes the old value's) is written, r, g and b only and never an alpha, into every destination of its copy (in place when the destination is a table, so the active profile's keeps its methods; else a plain table, and its group, are made), then the retired keys are removed. A source still at its old value copies nothing, so its destinations keep their own defaults. `CO.OLD_COLORS` holds every retired key's value, the default in effect when its step ships, and is never edited after that (Text > Grey's is 180, #b4b4b4, not the 150 it first shipped with: its default changed before step 3 shipped, so a partial saved grey fills its missing channels from 180, a grey still at 180 copies nothing and one saved at exactly 150 is a customized Muted). Step 1 split Text > Red, Yellow, Green, Blue, White and Purple and Buttons > Yellow into Roles, Factions and Loot. Step 2 made Buttons > Blue the accent. Step 3 made Text > Grey Text > Muted (`st:Color('text', 'muted')`, `colors.text.muted`, default 180, 180, 180) and dropped Buttons > Grey, which folds into Muted: a customized Buttons > Grey is not kept. Step 4 made White, Red, Orange, Yellow, Green and Cyan Strong, Danger, Warning, Caution, Success and Shared (`colors.text.strong` and the rest) and Buttons > Red Buttons > Danger; it reads the same sources step 1 did, so a Text > Red changed after step 1 reaches Danger and never Pass, Damage or Horde. A step that raises part way leaves `colors.version` unwritten (accepted: it follows the plan's M2, and every read in a step is type-checked), so the next update runs the steps again from the old version, and a color changed in between can be overwritten by an earlier step's copy. A saved channel that is no number (a hand edit) reads as the default, in `st:Color` and `st:ColorRGBA`. Step 5 is the one step with an `opacity` list instead of copies: it sets the opacity of `button.normal`, `hover`, `pushed` and `danger` to the default's (100%) wherever the profile saved a table, in place and never nil, and makes no table, since no Buttons opacity was ever drawn before step 5 and the defaults became 100%; the colors themselves are untouched, and a chosen opacity from then on is kept (the profile's version is 5). Text > Muted is what the options kit, edit mode's hint lines, the bag categories' counts and edited marker, SaftUI's tracker's zone headers, counts and chevrons and a far lower level's tag draw in; it follows on the next draw (the window repaints its hints, notes and titles at each draw) or after a reload, as the Text section's note says. **The action bars' and buffs' texts** ship Small text, the key `'pixel'` (their `size` and `outline` defaults stay the old copy's, Homespun's 10 and monochrome outline, which only a typeface picked later reads), and Small text's shadow is 0, 0 as the copy's was, so an untouched profile draws what it did. `AB:ConvertFonts()` (marker `actionbars.fontsVersion = 1`, no default) and `AP:ConvertFonts()` (`auras.fontsVersion`) keep a saved text's look: a text on `'pixel'` whose size or outline is not the old copy's (a size or outline saved without a face, since AceDB kept only what differed from the old default) gets the old face, `Homespun` (`AB.OLD_TEXT_FONT`, `AP.OLD_TEXT_FONT`), as a typeface; a saved face is left. The action bars' runs first in `AB:ConvertProfile` (so in `OnEnable`, `UpdateConfig` and, through `AB:TryConvertProfile`, first in `AB:OnFontsChanged`, which the profile update calls before `UpdateConfig`): on a profile not yet converted to All bars it converts each bar's own text tables, before that step compares them, and on one already converted it converts All bars' text tables and then each bar's effective values, so a bar whose effective font is Small text (followed, or owned but never saved because it was the old default face) with a size or an outline that is not the old copy's owns the old face too (`own['<kind>.font']`); a bar that owns a typeface keeps it. The buffs' runs in `AP:OnEnable`, `AP:UpdateConfig` and `AP:OnFontsChanged`. The step cannot tell a Small text never set from one picked from the Font row once AceDB has put the defaults back, so a size or outline kept beside `'pixel'` reads as never set (a text that picked Small text in the old build with a size saved beside it draws Homespun at that size). A profile that customised Small text itself now sees it on these texts. **Chat's font** (`CHT:ConvertFonts()`, marker `chat.fontsVersion = 1`, no default, in chat's own profile table) took over the old Font size row (`chat.fontsize`, gone from the defaults and the page): while the marker is nil it reads `fontsize` (`CHT.OLD_FONT_SIZE`, 16, when none) and writes `chat.font` as a typeface (`st:FontFields(chat.font)` with `font_size = fontsize` and `shadow_offset = { 0, 0 }`, the shadow chat once forced) only where that differs from what chat's font setting reads now (its size, or a shadow other than 0, 0), so chat looks as before; as shipped (Text at 16, no shadow) nothing is written. It then clears `fontsize` and sets the marker. It runs in `CHT:OnEnable` right after `st:BindModuleConfig`, first in `CHT:UpdateConfig` and first in `CHT:OnFontsChanged` (the profile update calls that before the modules' `UpdateConfig`, with the new profile bound). Chat keeps Blizzard's line spacing (0): `CHT:ApplyChatFont` takes the face, size, outline, a black opaque shadow and its offset from `st:FontValues(chat.font)` and sets no spacing. **The fonts** (`FN:ConvertHeadingFace()`, marker `fonts.version = 1`, no default) give Heading the face a profile holds on Huge title when it is not Colus and Heading's own is still Colus, once: it runs while `fonts.version` is nil, in `FN:OnEnable` and first in `FN:UpdateConfig` (a switch, copy, reset or import, table writes only), then marks the profile, and a reset profile is unmarked again. It is independent of the colors' migration: `Config:UpdateConfig` runs `st:MigrateColors` first, then the Fonts module's update (the face step, then the objects), then `st:FontsChanged()`.

## Bag categories

- Which category an item goes to is data in the profile, not code. The design is `docs/superpowers/specs/2026-11-10-saftui-bag-categories-design.md`. `INV.config.categories = { version, order, edits, custom, deleted, nextId }` and `INV.config.categoryPins = { [itemID] = id }` have no AceDB defaults: `INV:EnsureConfigTables` makes them, and `INV:MigrateCategories` turns an old profile's hide flags and Auto Vendor list into Show in flags and pins, once. The header of `SaftUI-Bags/categories.lua` lists the profile keys and every getter and setter.
- **The list** (`INV:GetCategoryList`) is the shipped defaults (`categorydefaults.lua`: today's filters, as block rules, in today's order) with the profile's edits over them, then the user's categories, in the saved order. A default's id is the name it shipped with, so renaming it changes only what headers show. An edit is stored against the shipped default and a field equal to it is removed, so a default changed in a later SaftUI version still reaches users who haven't edited that field. Setters copy the tables they keep and end in `INV:CategoriesChanged()`. Equipment sets, Miscellaneous (always last and on), Empty Slots and Currencies are entries or keys outside the plain rule list.
- **Resets.** The Bags page declares where each row is saved (`saved = st.Config.SavedIn('inventory'[, id])`, the two font rows `SavedAt('inventory', 'fonts', key)`), so every row has a derived reset. In the Categories editor a shipped category's Name, On, Show in and rule each carry a hand `default` against `INV:GetDefaultCategory(id)` (a category of your own a `noReset`), and the list's order has `INV:CategoryOrderDiffers()` (the shipped categories are out of their order) and `INV:ResetCategoryOrder()` (the shipped order, each of yours right after the category it follows now, Miscellaneous last; pins, edits and your categories untouched). `INV:ResetCategory` and `INV:ResetAllCategories` stay in the store (tests use them) but no button calls them.
- **A rule** is a tree of groups (`and` or `or`, optionally negated) and blocks (`rules.lua`). `R.Compile` turns it into a closure that reads an item's facts (`INV:GetInventoryItemInfo`: class and subclass IDs, the lowercased and stripped name and tooltip text). A block or group it can't read matches nothing and NOT never flips that. A block with nothing set yet (a list with nothing picked, a level with no number, a yes/no with neither) can't be read, and new blocks of those types start that way, so no block matches everything as it's added. An OR skips children it can't read; an AND with any such child can't be read itself, so a half-built rule (an emptied group, a NOT on a block not yet filled in) catches less, never more. Every editor change saves at once, and for Grays/Auto Vendor more would mean selling the bag (see the `rules.lua` header). `INV:GetItemCategory(info)` returns the key and why (the block that caught it); the first category to catch an item wins, and a pin beats the rules.
- **Class and subclass names** are resolved to IDs per client (`itemclasses.lua`), so a block matches by ID where it can and by name where a client names a subclass differently (see `.agents/clients.md`).
- **An item whose tooltip hasn't arrived** is held for 10 reads, then filed without text and marked `tooltipMissing`, then refiled when its text arrives. Auto vendor never sells it, nor a Cosmetic, an equipment set item or a Protected one, whatever a pin or the Grays/Auto Vendor rule says (`INV:IsAutoVendorItem`). The seller is the category that carries the `sells` flag, found by the flag and not by name or place, so a rename or a move changes nothing; turned off, it sells nothing.
- **How auto vendor sells** (`SaftUI-Bags/autovendor.lua`, tests `tests/bags/autovendor_sale_test.lua`). `INV:GetVendorItems()` returns the stacks it would sell in sale order (`SaleOrder`: grays first, then everything else; each from the cheapest stack, vendor price times count, up, then by bag and slot) and their profit; the footer's Vendor profit reads it (the junk coin reads `IsAutoVendorItem` itself). A merchant's buyback list keeps the last 12 sales of any quality, one entry per stack sold (Blizzard's `MerchantFrame.lua`, both branches: `BUYBACK_ITEMS_PER_PAGE = 12`, `GetNumBuybackItems()` entries, the newest last), so the promise is per visit: every non-gray stack sold without asking is still in it when the visit ends, unless the player answers Sell them to a later question (which says how many stacks sold earlier this visit it would push out: `tailSold` plus the sales in flight, plus its own, over the size). `INV:BuybackSize()` is the game's constant, never more than 12. `MERCHANT_SHOW` (`INV:HandleMerchant`, not in combat) starts a visit; `INV:VendorPass()` runs every 2 seconds from one `OnUpdate` on `INV.vendorFrame` (the game throttles selling), paused in combat, and ends when the merchant closes (`MERCHANT_CLOSED`, or `MerchantFrame` hidden), the setting is turned off, or nothing is left. Grays are sold first and alone: the non-grays wait for a pass with no gray left. From the first non-gray sold, every stack sold counts toward the size (`tailSold`); the stacks left (non-grays, and a gray that turned up late) sell when they fit, else it asks once (`st.OptionsWidgets.Confirm` in the world, centered on the screen, `{ yes = 'Sell them', no = 'Keep them', enter = false }`: Enter answers nothing, only a click answers, Esc is Keep them). While the question is up nothing in it sells, whatever the count drops to. Sell them sells exactly the stacks the question named, each re-checked (same item and count, not locked, quality known) at the moment of sale; a stack not named needs its own question. Keep them (Esc, a click outside, the merchant closing) sells no more non-grays that visit; the next visit asks again. A fight taking the question down (`PLAYER_REGEN_DISABLED`; its key catcher can't hand keys on in combat) counts as not answered and it is asked again after the fight if still needed. A sale in flight (the stack still in its slot, locked) stays pending: counted in the tail and the budget until it lands, and a gray in flight keeps the non-grays waiting. A stack counts as sold when it has left its slot, and leaves the question's named list then (a stack bought back into its slot needs a new question); the chat summary counts only those, waits a second after a merchant that closed right after a pass, and names the stacks left after 3 tries. A locked stack is skipped without a try; one of unknown quality counts as non-gray and is not sold until known; a visit waiting on either reads the bags every 2 seconds until the merchant closes (accepted). The question's names are item links (their quality color) and its values are vendor prices. No setting: this is how it always sells.
- No frame or slot is made in combat for a new category: the frames are made by `INV:EnsureCategoryFrames` out of combat.

## Unit frames

- These are oUF (`SaftUI-Unitframes/Libraries/oUF`, oUF master). In this oUF the active unit is `frame.__unit`, **not** `frame.unit`.
- Elements register through `UF:RegisterElement(name, Constructor, UpdateConfig, GetConfigTable, ValidUnit)`.
  - `ValidUnit(unit)` gets the config unit (`player`, `boss`, `party`, ...). A unit it rejects gets neither the element nor its `/sui` tab. ClassPower and AdditionalPower are player-only, Castbar skips `targettarget` and `focustarget` (as oUF does), ReadyCheckIndicator is party and raid only, Power, GroupRoleIndicator and RaidRoleIndicator skip both plate units (`UF.IsPlateUnit`: `nameplate` and `friendlynameplate`), and Threat (the nameplates' threat text) is `nameplate` only, so the Friendly nameplates page has no Threat tab. Every plate's frame is built as `nameplate` (its unit token's), so it has every element `nameplate` takes, Threat included, whichever config it draws from later (Nameplates).
  - `GetConfigTable(unit)` returns the element's tab. Its `set` calls `UF:UpdateConfig(unit, '<Element>')`, which re-runs that element's `UpdateConfig` on every frame of the unit.
  - oUF shows and hides many elements itself (castbar on a cast, indicators by state, additional power by power type), so `UF:SetElementEnabled` alone doesn't keep a disabled one hidden. Those elements also hide themselves again in an oUF hook (`ShouldShow`, `PostVisibility`, `PostUpdate`): the castbar's `ShouldShow` and the indicators' `PostUpdate` while `UF:ElementWanted` (below) says no, the others while their config is off.
  - Texts made by `UF:AddText` sit on the unit frame's `TextOverlay`, not on their element, so they don't hide with it. `UF:UpdateElement` hides them when the element is disabled.
  - `UF:UpdateElement` draws an element's Theme and Background on the element, except for the aura areas (Buffs, Debuffs) and the class power row (`BARE_ELEMENTS` in `updaters.lua`): their own `UpdateConfig` draws each aura button and point instead (a class power point is a `control` where Blizzard has art for the power type and a `small` border where it has none, `PointKind` in `classpower.lua`), and the area gets no backdrop. An aura area is Blizzard's AuraContainer, so nothing of SaftUI's is anchored to it (`.agents/taint.md`, rule 11).
- **How oUF builds a frame.** `UF:OnEnable` registers `UF.InitUnit` as oUF's init callback first, before the style and before anything is spawned. oUF then builds each frame in this order: the style function (`UF.ConstructUnit`), then it enables every oUF element whose widget the frame has, then the init callbacks. Single units get their first update from OnEnable's `UF:ApplyConfig`. Group buttons (made by their header as members appear) and the nameplates' frames (made at a plate's first add) get theirs in `UF.InitUnit`, after oUF's Enables, so the update has the last word (oUF's aura Enable turns every aura area on, and the update sets each by its config). A plate's frame gets that first update from `nameplate` whatever its unit's kind, and its first `'added'` callback then moves it to its kind's config (Nameplates). A group button made in combat is updated at once and again when combat ends (`st:QueueAfterCombat('uf_init_' .. name)`), since a secure frame can't be sized in combat; a plate's frame isn't secure, and its update in combat is whole. A widget oUF must enable has to exist when the style function returns, so a group button's range fade table (`self.Range`) is made in `UF.ConstructUnit`, and its alphas come from the update.
- **Shown and enabled.** `UF:ElementWanted(element)` (`updaters.lua`) is the element's config Enable, except that a friendly unit's nameplate never wants the parts only an enemy's shows: the threat text (`UF.PLATE_ENEMY_ONLY`, `{ Threat = true }`, `frame.friendly`; see Nameplates). A plate's config is its kind's, so a friend's castbar, aura areas and quest icon show by the Friendly page's Enable. `UF:SetElementEnabled` shows or hides by it and returns the config's Enable, which `UF:UpdateElement` places and sizes by, so a part a friendly plate hides is still laid out, ready for the plate's next enemy. On a plate, a part its own config turns off is still sized and placed by that config too (`UF:UpdateElement`, before it returns), when it's a part other parts can anchor to (`unitframe[element.name] == element`, the parts `UF:GetFrame` finds; not an element's texts and icons): a plate's frame takes the other kind's config on every kind change, and the friendly config hangs the castbar, the aura areas and the quest icon off a health bar it turns off, so the hidden bar holds them where they'd sit if it were shown. Such a part gets its size and place only; its backdrop, alpha, level and bar setup wait for its next enable. Other units skip a part that's off. `UF:SetElementEnabled` never enables or disables in oUF, which enables every element when it builds a frame. `DisableElement` is used on plates only (their castbar and quest icon, by their config), because oUF's castbar `Disable` gives Blizzard's player and pet castbars their events back on the player's frame (never on a plate's), which the player castbar's option promises not to do.
- **The bars' faction flags.** Health's and power's `colorTapping` and `colorReaction` go through `UF.SetFactionColorFlags(bar, config)`: oUF's setters, forced, while oUF has the bar enabled and not paused, so `UNIT_FACTION` (their recolor event, which oUF registers only in the bar's Enable) is registered or dropped to match; plain fields before that, and on a disabled or paused bar (a plate showing only widgets), which oUF's next Enable or resume reads.
- **Texts.** The `st:name` tag (`tags.lua`) takes secret values (`.agents/clients.md`): a secret level, reaction or classification is left out of the text, and a secret name isn't cut or put in capitals and is joined to its level part and color by the game (`C_StringUtil.WrapString`), so the tag returns a secret, which oUF's tag code shows. The tag has no nameplate target mark any more: the target's border replaces it. The name's color is the first that applies (`NameColor`): Class color for a player (or NPC class, Pet class), then Color hostile (red under reaction 3, yellow under 5), then Color friendly (`name.color_friendly`, reaction 5 or more, in oUF's reaction color; off by default, on for the friendly plates). The Name tab offers Color friendly where `UF.CanShow(unit, 'npcs')` (`config/config.lua`), so not on Player, Party or the raids. It colors only names the tag draws: the test mode previews' names (`grouppreview.lua`) are drawn without the tag and ignore it. The tag names the config unit it reads (`[st:name(<base_unit>)]`), so the Name binds it once per config unit (`name.taggedUnit`, `elements/name.lua`) and, when the frame's `base_unit` changes (a plate changing kind), unbinds it and binds it again; the next oUF update writes the name from the new config. The health text's Short (`health.text.short`, off by default, on for the plates) shows 12.5K, 1.2M or 1.2B through the game's `AbbreviateNumbers` with SaftUI's own breakpoints (`SHORT` in `elements/health.lua`), which takes a secret health too; Percent with a secret health is the game's `UnitHealthPercent(unit, true, CurveConstants.ScaleTo100)` through `SetFormattedText('%.0f', ...)`; and the deficit and the percent are worked out only where they're shown. The power and additional power texts have the same Short (`power.text.short`, `additionalpower.text.short`, off by default; the same `UF.ShortNumber` in `elements/health.lua`, a secret value included; it doesn't apply to Percent or Hide full). The health, power and additional power texts each have their own color (`text.colorCustom`, off, and `text.customColor`, a white list, in every unit's defaults, set in /sui by the Text color row, `UF.CustomColorOption`): off, a text keeps its font's color (white); on, `UF:UpdateText` (`updaters.lua`) gives it the custom color after `SetFontObject`, and puts the font's back when it's turned off. Nothing in those elements recolors a text afterwards, Dead and a status color included (the bar takes the status colors, not the text), so the color stays through every update. Hide full applies only to a plain health: with a secret one the text shows, except under Deficit, where the game's `TruncateWhenZero` and `WrapString` blank a zero. Boss percent tests the skull only on a plain level, and with a secret health joins the parts in the game, `SetFormattedText('%s | %.1f', text, UnitHealthPercent(unit, true, CurveConstants.ScaleTo100))`. The tag's events are `UNIT_NAME_UPDATE UNIT_LEVEL PLAYER_LEVEL_UP UNIT_FACTION`, with no `PLAYER_TARGET_CHANGED`: oUF's target frame updates its own tags on a target change. Name's Max width (`name.max_width`, in pixels, 0 for none, every unit's default but the plates' 150) gives the name that width on one line, justified by its point's side, so the game cuts a longer name, a secret one too; 0 gives a name SaftUI sized before no width again.
- **The castbar** colors a cast from oUF's `notInterruptible` argument, which can be secret (then through `C_CurveUtil.EvaluateColorValueFromBoolean`), in `PostCastStart` (oUF runs it for channels too) and `PostCastInterruptible` (a cast that turns interruptible or not mid-cast). It reads no `CastingInfo`.
- **The quest icon** has an Override (`elements/indicators.lua`): shown for a unit one of the player's active quests is about (`C_QuestLog.UnitIsRelatedToActiveQuest`), else for a quest boss (`UnitIsQuestBoss`), a secret answer counting as no. No unit event says a unit's tie to a quest changed, so on `QUEST_LOG_UPDATE` a frame of indicators.lua's has every frame's icon ask again (`ForceUpdate`) where oUF runs it (enabled and not paused) and `UF:ElementWanted` says yes.
- **Aura filters** (`aurafilters.lua`, loaded after `tags.lua`). Every aura group is built with, and keeps, the filter string and candidate filters `UF.AuraFilter(unitframe, auraType, config)` gives: Buffs with Only buffs I can purge (`buffs.purgeable`, off by default, on for the plates) get `UF.PurgeFilter(UF:KnownRemovals())`; a plate's Debuffs get `HARMFUL|INCLUDE_NAME_PLATE_ONLY`, Only mine as the `isFromPlayerOrPlayerPet` candidate filter alone, so the pet's debuffs stay; any other area `HELPFUL` or `HARMFUL`, Only mine adding `|PLAYER` and that flag (`.agents/clients.md`). `AddGroup` notes what it built the group with (`auras.groupFilter`, `auras.groupCandidateFilters`), and every aura element's `UpdateConfig` runs `UF:ApplyAuraFilter(auras)` on a built group, which calls each of Blizzard's setters only if its part changed (each makes the container update every aura), so the filter applies live. So do the group's other options but two (`elements/auras.lua`): the max count, through the container's `SetAuraGroupMaxFrameCount` on every update of a built group (a container call that touches no button, so in combat too; it does nothing for the count it has), and the button size, which the container has no call for, so `StyleButton` sets each button's size from the config in use (`getButtonSize`, Relative size included) as it styles it: a new button in `PostCreateButton`, the others in the restyle, at once out of combat and at the end of combat in it (`RestyleButtons`), when the group is also laid out again (`SetAuraGroupLayout`, since the container lays out only when something marks its layout dirty, never because a button changed size). Which borders the buttons show and whether they get a cooldown are baked into each button as the container makes it, from the options the group was made with, so their options still say to reload. A group is made once per frame, on its first update with the area on: a plate's is made from Enemy nameplates while that page has the area on (a plate's first update is always from it), so the Friendly page's border and Cooldown → Show never reach its buttons then, even after a reload (ruling N2, `docs/followups.md`). The two options' notes say so on the two plate pages (`ReloadNote`, every other unit's says to reload): the Enemy page's that its settings make every plate's buttons while it has the area on, friendly plates' too, and the Friendly page's that its reach friendly plates only while the Enemy page has the area off, and then after a reload. `UF.PURGE_SPELLS` lists the purge, dispel and steal spells by client and class and what each removes (Magic, Enrage, stealable; `.agents/clients.md`), `UF:KnownRemovals()` asks `C_SpellBook.IsSpellKnown` which the player knows (a pet's in the pet's spellbook), and `UF.PurgeFilter(known)` turns them into `HELPFUL|RAID_PLAYER_DISPELLABLE` with `includeDispelTypes`, or `isStealable` for a player who can only steal, or no buffs for a player who can remove nothing. A frame of aurafilters.lua's runs `UF:RefreshPurgeFilters()` (every unit frame's purge filter again, waiting for the end of combat) on `SPELLS_CHANGED`, `PLAYER_TALENT_UPDATE`, `TRAIT_CONFIG_UPDATED` and the player's `UNIT_PET`.
- **Colors.** `UF:OnColorsChanged` reads each frame's oUF unit, `__unit` (`.unit` is set only by `UF.OnEnter`, so a frame never hovered has none), and skips a plate that isn't showing its unit. It works by key (`OnColorsChanged(group, key)`): `UF:UpdateColors(group, key)` copies only that color into oUF's (in place, no table made), and a frame is updated only when `UF.ColorReaches(frame, group, key)` says its unit shows it (a class token, a standing for a unit that isn't a player, or for a player whose Health or Power has Class off and Reaction on or whose name has Color friendly on and Class color off, a power type, offline or tapped, a role with `DAMAGER` also for none or unassigned; a secret answer counts as a match and is never compared), and only the elements `UF.COLOR_ELEMENTS` names for the group: Class and Reputation update Health and Power, Power updates Power, AdditionalPower (`MANA` only) and ClassPower (whichever frame has it, for any class power key), Status updates Health and Power (their Disconnected and Tapped flags), Roles the role corner (`GroupRoleIndicator`). Tags update for `UF.COLOR_TAGS` (class, reaction, and the Text keys the tags read: danger, warning, caution, success, muted; Normal, Strong and Shared reach none), and the test previews redraw for `UF.PREVIEW_GROUPS` (class, reaction, power, status, roles, and the Text keys they read, danger and caution; not threat). A frame that isn't visible (a plate is not skipped: oUF gives it no OnShow) and an element its config turns off (`UF:ElementWanted`) are skipped: oUF's OnShow updates every element, so a hidden frame takes the color when it shows. Text > Normal and a whole Text pass also write the threat text of each plate showing a unit. A key nil is the whole pass: every frame with a unit, the group's elements only. A pass only colors (`ForceUpdate`, `UpdateTags`) and makes no table, so it is safe in combat. For `threat` it retints the plates (`UF:UpdatePlateThreat`) and updates no other frame. For `theme` it draws the target's border on every plate again and rounds each plate to whole pixels again (Nameplates, below). `UF:ForEachUnitFrame` visits the plates' frames too, shown or not, so `UF:RefreshConfigReferences` (`UF:RefreshFrameConfig(frame)` on each: the frame's cached config and every element's, text's and icon's pointed at its config unit's in the current profile, plain table writes, safe in combat), `UF:RefreshPurgeFilters` and the color updates reach them.
- **Themes on unit frames.** `UF.UnitKind(unit)` is `'member'` for party, raid10 and raid40 (`UF.group_strings`) and `'unitframe'` for every other unit; the frame, its bars and the previews draw with `UF.SizedKind(unit, width, height)`, which is `'small'` instead of `'unitframe'` when the bronze box doesn't fit the size from the config (`UF.BoxFits`: under two corners less two insets, 12 today, on either side; the sizes come from the config through `UF:ElementSize`, never read off a frame). The fallback depends only on size, so such a bar's drawn kind is `small` under Thick and Thin too, where it looks as a bar. **One box per edge:** `UF:ElementTheme` gives None to a bar drawn as `unitframe` or `small` that fills its frame (`UF.FillsFrame`: Relative width and height on, both 0, no `position.element` or `position.frame`, point equal to relative point, offsets 0) while its own Theme and its frame's are both Blizzard, so the frame's box is the only one; otherwise each element draws its own pair. **The group border.** Under Blizzard each party and raid header (one for the whole raid, not one per real raid group), and a party or raid test mode preview container, sits in a border (`ART.groupborder`: Blizzard's `options_frame_child`, cut at 6 with no middle, the same rectangles on both clients; Forever's is the Camelot member, bronze with a faint dark middle, retail's grey with a clear middle). It is a plain frame of SaftUI's, the header's child at the header's level, anchored at `offsets` (-2, 2) / (2, -3) so it follows the header's layout in combat with no SaftUI code, made in `UF:CreateGroupHeaders` and kept in `groups.lua`'s weak table (`UF:GroupBorder`). It shows when `UF.GroupBorderShown(config)`: the frame's Theme, or health's where the frame's is None, resolves to Blizzard. `UF:UpdateGroupBorder` runs from `UF:ApplyConfig` (in and out of combat) and the preview's from `UF:UpdateGroupPreview`. A header with no member to show (a pending invite with Show player off, a group disbanding) still shows and sizes itself to a sliver, so the border sets its alpha to 0 from its own `OnSizeChanged` while either side is under two pieces (12). **The fills.** Under Blizzard a health, power or additional power bar whose texture is SaftUI Flat and whose own resolved Theme is Blizzard draws Blizzard's raid bar fills (`ART.unitbars`, `RaidFrame-Hp-Fill`, the resource fill on power, with their background atlases): `UF.BlizzardFill(element, config)` decides, `UF:SetBarFill(element, fill, flat)` draws the fill and background (or the flat texture and a blank background), `UpdateStatusBarElement` records `element.barFill` and `element.barFlat` (the flat texture, the user's pick among them), and a power update draws them again (`power.lua` and `grouppreview.lua`'s member power call `UF:RedrawBarFill`, so the fill, or the picked texture, survives ticks; `UF:SetBarFill` does nothing when asked to draw what is already drawn). A texture the user picked stays, under every theme.
- Layout "profiles" inside the SaftUI profile: `st.config.profile.unitframes.profiles[UF:GetProfile()]`, read through `UF:GetProfileConfig()`. They, the unit frame profile's dropdown and Manage on the Unit dropdown's line (`UF.GenerateProfileControl`, in each unit's `pickerControl` in `config/config.lua` and the nameplate pages' in `nameplates/options.lua`: `.agents/edit-mode.md`), and the Unit frame profiles dialog its Manage opens, which picks, makes, copies, renames, deletes, exports and imports them (`UF:OpenProfileDialog`, `UF.GenerateProfileConfigGroup`), are `SaftUI-Unitframes/config/profiles.lua`.
- A unit frame setting is read and written at `st.config.profile.unitframes.profiles[UF:GetProfile()][unit]...`; a page declares where with `UF.SavedIn(unit, ...)` and `UF.SavedAt(unit, ...)` (`config/config.lua`: Core's `st.Config.SavedIn` and `SavedAt` of `'unitframes', 'profiles', <the profile in use>, unit, ...`), which is how its reset finds the default (`.agents/edit-mode.md`).
- Unit frames are secure. See `.agents/taint.md` before moving or resizing them.

## Nameplates

SaftUI draws the nameplates as unit frames on the bundled oUF's nameplate driver, from two config units: `nameplate` (the Enemy nameplates page: enemy and neutral plates) and `friendlynameplate` (the Friendly nameplates page). `UF.PLATE_UNITS` lists them and `UF.IsPlateUnit(unit)` asks it (`unitframes.lua`). The design is `docs/superpowers/specs/2026-11-11-saftui-nameplates-design.md`, and the plan `docs/superpowers/plans/2026-11-11-saftui-nameplates.md`; the friendly plates' are `docs/superpowers/specs/2026-11-12-saftui-friendly-nameplates-design.md` and `docs/superpowers/plans/2026-11-12-saftui-friendly-nameplates.md`. The code is `SaftUI-Unitframes/nameplates/`, whose `nameplates.xml` lists `nameplates.lua`, `cvars.lua`, `target.lua`, `threat.lua`, `subtext.lua`, `options.lua` (the two pages in `/sui`, which `config/config.lua`'s `UF:GetConfigTable` builds with `UF.SetUpPlatePage` and `UF.DisablePlatePageTabs`) and `pixels.lua`, loaded after `elements/elements.xml` in both TOCs. Keep `pixels.lua` last: its `'updated'` callback rounds what the others made. The defaults are `config/units/nameplate.lua` and `config/units/friendlynameplate.lua` (an element's other settings are every unit's, `['**']`), whose top comments lay each look out; the enemy one gives its arithmetic. `nameplate` keeps the plates' switches whichever page shows them: `enable` (Nameplates), `friendly` (Friendly plates, on the Friendly page), `threat_solo` and `threat`. The boxes are `nameplate.use_friendly` and `friendlynameplate.use_enemy`, both off by default. Before you touch anything of Blizzard's on a plate, read `.agents/taint.md`, rule 13.

- **Spawning.** `UF:OnEnable` calls `UF:SpawnNameplates()` last, once every other unit is placed and the colors are set. It makes oUF's driver (`UF.oUF:SpawnNamePlates('SaftUI_')`, kept as `UF.plateDriver`) and returns true, or makes nothing and returns false when the driver exists already, Nameplates (`nameplate.enable`) is off, or another nameplate addon draws the plates: `UF:NameplateAddon()` names the first loaded one of `UF.NAMEPLATE_ADDONS` (Plater, EllesmereUINameplates, Kui_Nameplates, TidyPlates_ThreatPlates, NeatPlates, Platynator, whose folder name is unconfirmed, and ElvUI unless its own nameplates are off), a table in the code. oUF can make its driver only once, so a change to either needs a /reload. OnEnable then sets the game's nameplate settings (`UF:ApplyNameplateCVars`), or, with no plates of SaftUI's and no other addon drawing them, puts the user's own back (`UF:RestoreNameplateCVars`). There's no mover: the game places each plate.
- **The frames.** The game makes the plates (`NamePlate1`, ...) and hands each to unit after unit. oUF builds a frame of SaftUI's on a plate at its first add (`SaftUI_NamePlate1`: the plate's child, filling it, `isNamePlate`), which `UF.ConstructUnit` keeps by its plate's number in `UF.nameplates` (not `UF.allUnits`) and `UF.InitUnit` gives its first update; it stays on its plate for every later unit. oUF keeps a frame's `__unit` after the game takes its plate away (its remove clears the unit attribute, which its handler ignores), so whether a plate shows a unit is SaftUI's own record, kept from oUF's added callback to its removed one: `UF:PlateShowsUnit(frame)` asks it, and `UF:PlateForUnit(unit)` finds the frame showing a unit through a token-to-frame map the same two callbacks keep, without walking every plate. `UF:ForEachPlate(fn)` visits every frame, shown or not. A plate's frame takes no mouse, so a click on the plate reaches the game, which targets its unit (the click area, below). `UF:PlaceUnitFrame` places a plate's frame on its plate (`UF:PlacePlateFrame`, under Size) and returns true, and `UF:UpdateUnitFrame` places a plate's frame in combat too (it isn't secure, and its kind, with the config and size it's drawn at, can change mid-fight); `ClearUnitFramePoints` leaves the plates' points. `UF:ApplyConfig(unit, element)` with either plate key (`UF.IsPlateUnit`) does the same for both: with no element it sets the plates' size first (from the enemy look's config, so each frame is then placed, and its click area set again, on its plate's new size), then for every plate works out its config unit again (`UF:ApplyPlateConfig`, below): one that moved gets a full update from its new config, every other the update asked for. Every plate, whichever page it draws from, since the threat text is always the Enemy page's and a box decides which frames fill their plates. `UF:GetConfigFrame(unit)` for either plate key is the lowest-numbered plate's frame.
- **Plate callbacks.** `UF:RegisterPlateCallback(event, fn)` adds to what `UF:RunPlateCallbacks` runs, in the order registered, each in `xpcall` so one that errors leaves the rest to run: `'added'` (frame, unit), after oUF has set the frame's unit and before it updates the elements, never for a plate showing only widgets or a game object (oUF pauses and hides SaftUI's frame for those); `'removed'` (frame, unit); `'updated'` (frame), after every `UF:UpdateUnitFrame` on a plate, so also before `'added'` on a plate's first add and on a plate the game took away, where state from `'added'` or `__unit` can't be trusted (check `UF:PlateShowsUnit`); and `'kind'` (frame), once `UF:ApplyPlateKind` has set the plate's kind. On a plate handed to a new unit oUF also updates every element once (`OnAttributeChanged`) before the added callback, with the frame as the last unit left it. **On an add that changes the plate's config unit** (with the boxes off, a friend after an enemy or an enemy after a friend, and a friend's first add, the frame being built on `nameplate`), `'updated'` also fires inside `'added'`: the first `'added'` callback is `UF:ApplyPlateKind`, whose `UF:ApplyPlateConfig` runs a full `UF:UpdateUnitFrame`. So those `'updated'` callbacks run before `ApplyPlateKind` enables or disables the oUF parts and shows or hides each part, before `'kind'`, and before the other `'added'` callbacks (the scale pin, the target's border); they see `frame.friendly` and `frame.base_unit` already the new kind's. An `'updated'` callback that enables a part in oUF updates the frame again there (`OnShow`). So a plate reused for the other kind gets oUF's `UpdateAllElements` three or four times: `OnAttributeChanged` (oUF, with the old config), `OnShow` (the new config's full update), a second `OnShow` when that update's `'updated'` callback enabled a part (an enemy after a friend: the castbar), then `NAME_PLATE_UNIT_ADDED` (oUF). A friend's first add on a new plate is two full updates (`UF.InitUnit`'s from `nameplate`, then the friendly config's). An add of the kind the plate last showed changes no config unit and adds none (`docs/followups.md`, the cost of a kind change).
- **Friend or enemy.** `UF.IsFriendlyPlate(unit)` is `UnitIsFriend` and not `UnitCanAttack`, a secret answer counting as an enemy. It's broader than Blizzard's own on purpose: any friend you can attack (a duel, free-for-all PvP) gets an enemy's plate. **Each kind draws from its own config unit**, `UF.PlateConfigKey(friendly)` (`unitframes.lua`): an enemy from `nameplate`, or from `friendlynameplate` while `nameplate.use_friendly`; a friend from `friendlynameplate`, or from `nameplate` while `friendlynameplate.use_enemy`. The pages keep the two boxes from being on together; with both on (a profile from elsewhere) each kind takes the other's, and nothing recurses. The frame's `base_unit` names its config unit, which `frame:GetConfig()` and every element's read. `UF:ApplyPlateConfig(frame)` sets it to `UF.PlateConfigKey(frame.friendly)` and, when it changed, points every cached config at the new one (`UF:RefreshFrameConfig`, since the update re-points a part's own config but stops at a part that's off before its texts and icons), clears the points of everything the update places (`ClearPlacedPoints`: every part, and the texts and icons that are on in a part that's on) and gives the frame a full update from it (`UF:UpdateUnitFrame`: its parts, places, size, fonts, colors and the name's tag), all in one `xpcall`, so an update that errors is reported and the caller goes on; it returns whether it changed. The update places the parts one by one in `pairs()` order, each against the others where they are then, so without the clearing two parts anchored each way round across the two pages (the Friendly page's health bar under the name, the Enemy page's name on the bar) would close an anchor loop on a switch one way or the other, which the game refuses. A profile switch that keeps a plate's config unit still places its parts against the old profile's, as for every unit (`docs/followups.md`). So a plate applies a look again only when its config unit changes, never on a reuse of the same kind. Which parts a plate shows is its config's: by default a friend's name alone (no health bar), an enemy's every part. Only the threat text is hidden on a friend whatever the config says: `UF.PLATE_ENEMY_ONLY` is `{ Threat = true }` (`UF:ElementWanted`). `UF:ApplyPlateKind(frame, friendly)` sets `frame.friendly`, runs `UF:ApplyPlateConfig`, enables or disables the castbar and the quest icon in oUF by `UF:ElementWanted` (`OUF_SWITCHED`), shows or hides every part and turns the aura areas on or off (every part, since oUF's resume after a plate that showed only widgets turns them all on and shows the health bar), then runs the `'kind'` callbacks. It's the first `'added'` callback, so the others read the kind. A `UNIT_FACTION` for the plate's unit, or for the player (every showing plate), applies it again when the kind changed and then updates every element (`UpdateAllElements('UNIT_FACTION')`), which also draws the name again in the new kind's colors, and the `st:name` tag's own `UNIT_FACTION` redraws it too, a frame later, which also covers a faction change that keeps the kind (neutral to hostile). An `'updated'` callback enables in oUF what a config change turned on while the plate shows its unit.
- **Blizzard's widgets.** On every add (widget-only and game object plates too), a frame of SaftUI's moves the pooled UnitFrame's widget container and soft target icon onto the plate, by one point: the container's bottom on the plate's bottom for a plate showing only widgets, else its top under the plate. oUF moves them only at a plate's first add. `UF:RefreshPlateWidgets()` places them again on every plate, then the click areas, after `UF:ApplyNameplateCVars` and on the frame after anyone changes the friendly NPC plates setting, since Blizzard anchors them again when it changes.
- **The click area** (ruling N11, `.agents/taint.md` rule 13). The game takes a plate's clicks in its hit-test points, which oUF sets to SaftUI's frame on every add that shows the unit (`ClearAllHitTestPoints`, then `SetAllHitTestPoints(frame)`). Blizzard's pooled UnitFrame sets its own again outside the add (`UpdateHitTestArea`): when the driver's options update runs `ApplyFrameOptions` on every plate (a window resize, the options loading, one of Blizzard's nameplate options), and from its `CVarCallbackRegistry` callbacks on the friendly NPC plates setting and on showing only friendly players' names. `UF:RestorePlateHitTests()` runs oUF's two calls again for every plate SaftUI shows: from a post-hook on `NamePlateDriverFrame:UpdateNamePlateOptions`, at the end of `UF:RefreshPlateWidgets`, on the frame after either setting changes (its own callbacks on both, through `C_Timer.After(0)`, once however many change, since the registry's callbacks run in no set order), and at the end of `UF:ApplyPlateSize` (out of combat, like the size), since a new plate size resizes the frames that fill their plates. Each hook and callback goes in only where the client has the name (`WatchClickAreas`). `UF:RestorePlateHitTest(frame)` does the same for one plate SaftUI shows, run by `UF:PlacePlateFrame` whenever a frame's place or size changes (a kind change, a box, a Width or Height): whether the game's click area follows the frame's rect after the calls, or takes it when they're made, isn't said outright (`SetAllHitTestPoints`' doc, "to fully encompass the target region", reads as anchors, which would follow; an in-game check). In combat the game allows the calls only on a tick Blizzard's own code changed the click area or the plate got its unit (`CanChangeHitTestPoints`, asked before each of the two calls), so a plate it refuses waits for the end of combat (`QueueAfterCombat('NameplateHitTest')`, which then sets every plate SaftUI shows, one wait however many were refused, also from the single-plate form). Blizzard never sets the hit-test insets, which stay oUF's.
- **Size.** The game has one size for every plate, which also sets how they stack, set through oUF's driver by `UF:ApplyPlateSize()`, from the enemy look's config (`UF.PlateConfigKey(false)`: Enemy nameplates', or Friendly nameplates' while the Enemy page's box is checked), its width and height through `UF.PlateDriverSize`: the config's size is in UIParent's units, where one is a pixel, and the plates are WorldFrame's children, which take theirs in its units, so it's multiplied by UIParent's effective scale over WorldFrame's (a secret or zero scale gives the config's size as it is). The plate, where the game takes the clicks, and SaftUI's frame on it are then the config's size in pixels. The game refuses the size from addon code in combat, so in combat it waits (`QueueAfterCombat('NameplateSize')`). Blizzard sets its own size whenever its nameplate options change, so a post-hook on `NamePlateDriverFrame:UpdateNamePlateSize`, installed before SaftUI's first size, sets SaftUI's again. **A plate's frame** is placed by `UF:PlacePlateFrame(frame)` (`UF:PlaceUnitFrame`, so on every full update, in combat too; it reads `frame.config`, which the update sets first): a frame drawn from the enemy look's config fills its plate, as oUF made it (`SetAllPoints`); one drawn from the other config (a friend's, by default) sits on its plate's centre at that config's Width and Height (`st:SetSize`, in UIParent's units, a pixel each), so what's drawn, and what's clicked, is a friend's name box, not the plate round it. A weak table keeps how each frame was last placed (`'fill WxH'` or `'centre WxH'`, the config's size), noted once the anchors and size are set, so a place that errored is tried again by the next update; only a change places it again and sets its click area again (`UF:RestorePlateHitTest`).
- **The game's settings** (`cvars.lua`). `UF.NAMEPLATE_CVARS` maps each setting SaftUI sets while its plates are on to `value(config, current)`: `nameplateShowFriendlyPlayers` and `nameplateShowFriendlyNpcs` from Friendly plates (`nameplate.friendly`, on the Friendly nameplates page); `nameplateMinScale`, `nameplateMaxScale` and `nameplateSelectedScale` at 1, so the game scales no plate by distance or for the target (SaftUI's frame covers its plate); and `nameplateSimplifiedTypes` at its version character alone, which simplifies nothing (it's a bit array kept as text: `.agents/clients.md`). `UF:SetNameplateCVar` skips a setting the client lacks, and records the user's value the first time it changes one, per character and outside every profile (`st.config.char.nameplateCVars`). `UF:ApplyNameplateCVars()` sets every one only while SaftUI's driver exists and Nameplates is on, out of combat (`QueueAfterCombat('NameplateCVars')`), then runs `UF:RefreshPlateWidgets()`. `UF:RestoreNameplateCVars()` (the same key) puts each recorded value back and drops it from the record, keeping one the game refuses, so the next time the plates are on it records whatever is set then. Turning Nameplates off puts them back at once (the plates stay up until the reload), on again sets them, and Friendly plates sets them. A profile switch (the full pass of `UF:ApplyConfig`) sets them again only when Friendly plates differs from what was last set (`UF.appliedFriendly`, cleared by `UF:RestoreNameplateCVars`), so a key press of Blizzard's friendly plates binding stands until Friendly plates itself changes. The same pass clears each unit frame's, boss frame's, group button's, plate's and test preview's placed parts before placing them, so two parts anchored each way round across two profiles can't close a loop (`ClearAllPartPoints` in `unitframes.lua`, `UF.ClearPlacedPoints`; a part the new profile switches off is the exception: `docs/followups.md`).
- **The layout** (the defaults). An enemy's plate: the health bar fills the plate, 200 by 20, with the name inside on the left (Max width 150, no level or classification, hostile names colored) and the health inside on the right as a Short value. The castbar hangs 6 under it, 182 by 12, its 12 by 12 icon 6 to its left so the row starts at the bar's left edge, with no time and grey for a cast that can't be interrupted. Up to 6 of the player's debuffs sit 6 above the bar from its left edge, up to 4 buffs the player can purge 6 right of it, the quest icon 6 left of it and the raid mark centred 6 above the debuff row, which leaves the space above the bar's right end to the threat text. A friend's plate (`friendlynameplate.lua`) is a name: its frame 150 by 16 on the plate's centre, Theme None (every unit's frame default, `config/default.lua`, not set in `friendlynameplate.lua`), no health bar or health text, the name centred on the frame (anchored to the frame itself, `element = false`, which the Position editor shows as Unit frame, not to the bar that isn't there), Max width 150, Class color, Color friendly and Color hostile on, no level or classification, and the raid mark 16 square, its bottom 4 above the name's top. Its castbar, aura areas and quest icon are off, set as the enemy's for whoever turns them on, and hang off its hidden health bar, which is still laid out (Shown and enabled). Every size on a plate is an even number of pixels, so centred anchors stay on whole pixels (the half pixels bullet, above).
- **The target's border** (`target.lua`). The target's plate is found by its frame: a plate's frame marks the target when its parent is `C_NamePlate.GetNamePlateForUnit('target')` (`UF:IsPlateTarget`), never by `UnitIsUnit`. The border is drawn on `UF.PlateBorderFrame(frame)`: the health bar's drawn frame while the bar carries it (drawn, and wanted by its config: `UF:ElementWanted`, since a bar its config has off keeps the drawing it had), else the plate frame's while that is drawn, else none, as on a friend's name-only plate. Under Thick and Thin it's a white line through `st:SetBorderColor`, and every other plate gets the theme's own color back. Under Blizzard it's the control `nameplatetarget`'s art (themeart_data.lua) round what carries the border (the health bar, or the frame) at its offsets, a texture of a frame of SaftUI's two levels over the bar, kept in a weak table (`UF:PlateTargetArt`) and unsnapped. `UF:UpdatePlateTarget(frame)` runs from `'added'`, `'updated'`, `PLAYER_TARGET_CHANGED` (every plate) and `UF:OnColorsChanged('theme')`, and `st:KeepOwnColors` on both candidate borders keeps the color through a theme recolor or redraw, with one function for every frame (`RecolorBorder`, which finds the frame's plate), so keeping it again on each update makes nothing new.
- **Threat** (`threat.lua`). The player's threat on an enemy tints its health bar and shows as a percent above the bar's right end, in a party or raid, and on your own only with Threat when solo (`nameplate.threat_solo`). Threat is enemy-only whatever the settings, and always reads Enemy nameplates' settings (`nameplate.threat_solo`, `nameplate.threat`), whichever page an enemy's plate draws from: with the Enemy page's box checked, an enemy's plate takes everything else from the Friendly page, and the tint goes on that page's health bar (off by default, so only the percent shows). `UF.ThreatState(isTank, status, coTanked)` is the table by role over `UnitThreatSituation('player', unit)`: a tank's 3 good, 2 warning, 0 or 1 bad (good while another of the group's tanks holds the mob), anyone else's 0 good, 1 warning, 2 or 3 bad, and nil nothing. `UF:PlateThreat(frame)` gives nil for a friendly plate, on your own with Threat when solo off, a threat state `C_Secrets.ShouldUnitThreatStateBeSecret` says is secret, or a secret status, and reads the player's role from Blizzard's own `PlayerUtil.IsPlayerEffectivelyTank()`. For a tank who doesn't hold the mob, it reads the group (`party1`-`party4`, or `raid1`-`raid40`) for who does, but only for a mob in combat (`UnitAffectingCombat`; a mob out of combat has no threat list, and a secret answer still reads the group), by each member's threat state on it (2 or 3; a secret state is skipped), stopping at the first: another of the group's tanks (`UF.IsGroupTank`: the tank role, or a tank aura where the client has `UnitHasEffectivelyTankAura`) makes it good, and a member who isn't a tank makes it bad, the mob loose, even when the tank isn't on its threat list. `UF:UpdatePlateThreat(frame)` sets `frame.threatState`, which `elements/health.lua`'s `PostUpdateColor` puts on last each time oUF colors the bar (warning and bad, in the profile's `colors.threat`, the Colors tab's Threat section), and a bar that loses its tint gets one `Health:ForceUpdate()`. The text is the plates-only element `Threat`, enemy-only, with its own tab after Health on the Enemy page only; its constructor sets the text's `config` and `GetConfig` to `nameplate.threat`, so a plate drawing from `friendlynameplate` keeps the Enemy page's. It is: `UnitDetailedThreatSituation`'s scaled percent through `SetFormattedText('%.0f%%', ...)`, a secret one handed to the game as it is, in the tint's color, or Text Normal while good. It's written again only when its state, a non-secret percent or its color changed (a secret percent always is), or forced by `UF:UpdatePlateThreat(frame, true)`, which the `'kind'` and `'updated'` callbacks and `UF:OnColorsChanged('threat')` pass. A mob's threat list update retints its plate, found through `UF:PlateForUnit`; a threat situation update retints every plate for the player and a plate's own for its token; the roster, the roles, the player's spec and form or stance (`UPDATE_SHAPESHIFT_FORM`; a tanking form is a tank aura on Forever) retint every plate; and so do the `'kind'`, `'updated'` and `'removed'` callbacks. Only `nameplateN` tokens are looked for among the plates.
- **Subtext** (`subtext.lua`). A second line under a plate's name: an NPC's title (`<General Goods Vendor>`) or a player's guild (`<Some Guild>`), plain `<` and `>` with no color codes (the color is the config's, by `SetTextColor`). It is the plates-only element `Subtext` (`UF:AddTextElement`, its tab right after Name's on both plate pages, `order = 5.5`), drawn from the plate's `frame.base_unit` like the name, so it reads `subtext` of Enemy or Friendly nameplates: `npc` and `player` (the two boxes), `font`, `color`, `alpha`, `max_width` (the name's rule, `UF.SetMaxWidth` in `elements/name.lua`, shared) and `position`. `enable` is always true and not on the page: `UF:ElementWanted` needs it, and the two boxes decide what the tag returns. Friendly plates default to both boxes on, centred 2 under the name; enemy plates to both off, centred 24 under the health bar (under the castbar's row). The text is the `st:subtext(<config unit>)` tag (events `UNIT_NAME_UPDATE` and `PLAYER_GUILD_UPDATE`, both unit events to oUF), which returns `UF.PlateSubtext(unit, config)` or `''`, and `''` while it is bound to a config unit other than `UF.PlateConfigKey(UF.IsFriendlyPlate(unit))` (a plate just handed to the other kind), so nothing is read under the other kind's boxes. `UnitIsPlayer` is asked first (a secret answer gives nothing); with a kind's box off nothing is read for that kind, so no `C_TooltipInfo.GetUnit` call for an NPC with `npc` off. `UF.NpcTitle(unit)` is the tooltip's second line when it is a plain, non-empty, untyped (`Enum.TooltipDataLineType.None`) line that isn't the level line (`TOOLTIP_UNIT_LEVEL` as a pattern: a client may leave that line untyped); a pet's owner line is typed, so never a title. A player's guild is `GetGuildInfo(unit)`'s first return: plain gets brackets, a secret one is wrapped by the game (`C_StringUtil.WrapString`). The tag is bound again when `frame.base_unit` changes, from the `'updated'` plate callback (after the whole update, so the name's own rebinding comes first), followed by `frame:UpdateTags()`.
- **Whole pixels** (`pixels.lua`). Each plate's frame is pinned to UIParent's effective scale (`UF:PinPlateScale`: `SetIgnoreParentScale(true)` and `SetScale(UIParent:GetEffectiveScale())`; a secret scale leaves it as it is) on every add, and every plate again on `UI_SCALE_CHANGED` and `DISPLAY_SIZE_CHANGED`, which also set the plates' size again. `UF.RoundLayout(region, recursive)` turns on the game's `SetRoundLayoutToNearestPixel`, and for a texture turns its own snapping off (`SetSnapToPixelGrid(false)`, `SetTexelSnappingBias(0)`); with `recursive` it walks the region's regions and child frames. It reads and sets no size. It runs from SaftUI's frame on the plate after every update of the plate (`'updated'`) and again after a theme change (`UF:OnColorsChanged('theme')`, after the target's border), and skips, with everything under them, SaftUI's own aura containers by identity (`UF.auraContainers`, a weak-keyed set the aura element's constructor fills), forbidden regions, and anything `IsObjectType('AuraContainer')` says is one. It never reaches Blizzard's frames. `elements/auras.lua` rounds what SaftUI makes on a plate's aura buttons, each backdrop and Thick's inner debuff line, where it makes it. Anything made on a plate outside an update must call `UF.RoundLayout` itself. UIParent's scale is SaftUI's from login only: after a UI scale or display change the plates follow UIParent off whole pixels until a /reload (`docs/followups.md`).
- **Themes.** The plates draw as every unit does: the frame None by default (each page's own Theme), its bars as `unitframe` (under Blizzard the bronze box, with health on Blizzard's raid fill and the castbar on its own texture), the cast icon as a `control` (bare under Blizzard) and the aura buttons as `aura`. With the Enemy page's Theme Blizzard and the health bar's also Blizzard (its default, SaftUI's, under the Blizzard theme), health fills the plate and draws None (one box per edge), and the target's border goes on the plate frame's box.

## Micro menu bar

`SaftUI-Minimap/micromenu.lua`'s items (each `AddButton` option set: `art`, `icon`, `micro`) draw their panels (`micromenuart.lua`) as kind `control`, which Thick and Thin draw exactly as `small` and Blizzard leaves clear; under Blizzard the art is the bar's own (`Control('microbar')`, read once a pass), textures of the panel kept in the item's entry (`item.artTexture`, `item.pieces`) and never fields on a Blizzard frame. An item's `art` names its box (`header`, the default for the zone, clock, latency and FPS boxes: Forever's Camelot header button, stretched along the box; `square` (the default), the addon indicator's square, 23 x 22 centred; `tracking`: Forever's tracking button, 23 x 23, whose art has the magnifier drawn in, so the magnifier SaftUI draws on Forever (the item's `icon`) hides under Blizzard), and an atlas is set whole on the texture, centred or stretched along the box, 23 tall for the header; on retail every box is the grey minimap button kit laid by `ThemeArt.LayBorder` (nine pieces, with its Center), which draws no icon of its own, so every item keeps the icon it shows under Thick: on retail that's Blizzard's own tracking button for the search box, since SaftUI makes its magnifier only on Forever. There is no strip on retail. `MicroMenu:GetItemArt(button)` and `MicroMenu:GetStrip()` give the tests what was drawn. **The strip** (Forever only): a frame of SaftUI's, a child of `MicroMenu.Container` at the Container's level, made when it first shows, holding `UI-HUD-ActionBar-Frame` (BORDER, set whole so the engine slices it by the atlas's own slice data) and `UI-HUD-ActionBar-IconFrame-Background` 2 inside it; it runs from the first shown `micro` item's TOPLEFT (-4, 4) to the last one's BOTTOMRIGHT (4, -4) through `st:SafeReposition`, and hides unless SaftUI's look is Blizzard and a micro item is shown. The micro buttons' own holders carry `micro = true`. Blizzard's `MicroMenu.BorderArt` and `BackgroundArt` stay faded and unmoved under every look (`.agents/taint.md`): the strip replaces them. **Colors follow a pick live:** `MicroMenu:OnColorsChanged(group, key)` (`micromenu.lua`) calls `MicroMenu:ColorMicroButtons(key)` (`microbuttons.lua`: each Blizzard micro button's highlight at Buttons > Hover x 0.4, pushed fill at Buttons > Pushed x 0.6 and alert flash at Text > Caution, 0.5, set again on the regions SaftUI already colored, under Thick and Thin only, never under Blizzard's art) for Buttons `hover` and `pushed` and Text `caution`, and `MicroMenu:ColorDifficulty()` (`instancedifficulty.lua`, which the badge's skin calls too) for Item quality 1, 3 and 4; the bar items' own hover and pushed textures, the tracking, queue and expansion buttons' highlights are followers (`st:FollowColor`, with shared paints in `micromenuitems.lua`). Color setters on regions only, so it runs in combat.
