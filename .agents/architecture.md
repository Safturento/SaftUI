# Architecture

## Addons and load order

- Every folder `SaftUI-<Name>/` is a separate WoW addon. All of them `## RequiredDeps: SaftUI-Core` and `## Group: SaftUI-Core`.
- **TOCs:** Core and Unitframes have per-client TOCs (`*_Forever.toc` = `## Interface: 16001`, `*_Mainline.toc` = `120000`). The other addons use one TOC listing both (`## Interface: 120000, 16001`). When you add a file, add it to **every** TOC of that addon (and to the folder's `load.xml` where one is used, e.g. `SaftUI-Core/EditMode/load.xml`, `SaftUI-Misc/Skinning/load.xml`).
- Load order matters: Core loads first, then each module addon in its TOC order. Defaults (`st.defaults.*`) must be defined at file load, before Core creates the AceDB (see below).
- **Libraries:** Core bundles LibStub, CallbackHandler-1.0, Ace3 and the shared media libraries. An addon that needs more bundles them in its own `Libraries/` and lists them first in its TOC, without a second copy of LibStub or CallbackHandler: Unitframes has oUF, ActionBars has LibActionButton-1.0 and LibButtonGlow-1.0 (sources and versions in `SaftUI-ActionBars/Libraries/README.md`).

## The `st` object and modules

- `SaftUI-Core/init.lua` creates the addon: `SaftUI = AceAddon:NewAddon(st, 'SaftUI-Core', 'AceEvent-3.0', 'AceHook-3.0')`. Every file starts with `local st = SaftUI`.
- A module is `local M = st:NewModule('Name')` (AceAddon module, with AceEvent + AceHook mixed in). Module names are the keys used everywhere else: `st.modules[name]`, the `/sui` tree, and edit mode `configPath`s. Current modules include ActionBars, Auras, Chat, Colors, Config, EditMode, Experience, Fonts, General, Inventory, Loot, MicroMenu, Minimap, Movable, Skinning, SwingTimer, TaintFix, Theme, Tooltip, TotemBar, Unitframes, Utilities.
- Lifecycle: `OnInitialize` (rarely used), `OnEnable` (build frames, register movers, hook Blizzard), `UpdateConfig` (re-apply everything from the profile; see below), `GetConfigTable` (the module's `/sui` page; its top-level table's `category`, Frames, Combat or Info, groups it in the window's sidebar). Core's General, Fonts, Colors, Theme and EditMode modules give the tabs of the Global Settings page instead, in the order of `GLOBAL_TABS` in `SaftUI-Core/Config/config.lua` (see `.agents/edit-mode.md`). A `/sui <command>` with its own sidebar button is `st.Config:AddCommand` (see `.agents/edit-mode.md`).
- A module that shows profile colors can define `OnColorsChanged(group)`. `st:ColorsChanged(group)` (`SaftUI-Core/Media/colors.lua`) calls it on every module that has one (one per module: SaftUI-Loot's, in `init.lua`, hands it to the feed and the roll bars), after a Colors tab change; `group` is `text`, `button`, `class`, `reaction`, `renown`, `power`, `item_quality`, `status` or `threat`, or `theme` after a theme recolor or redraw put the theme's colors back on every drawn frame (see Themes, below). Skinning's skins are its submodules, which `st:ColorsChanged` doesn't reach, so `SK:OnColorsChanged` passes the call on to them. Anything that colors by item quality uses `st:QualityColor(quality)` (the profile's color, else Blizzard's).
- `SaftUI-Core/constants.lua` sets client flags and screen constants. `st.forever` is the only client flag (there is no `st.retail`); see `.agents/clients.md`.
- Core helpers live in `SaftUI-Core/api.lua`. The ones you'll use most:
  - position: `st:UnpackPoint`, `st:ResolveFrame`, `st:ValidateAnchor`, `st:RoundToPixel`, `st:GetPixelSize`
  - **Half pixels from centred anchors.** SaftUI's UI scale makes one unit one physical pixel, and `st:RoundToPixel` keeps sizes and offsets whole. But a frame anchored by its centre on an axis (TOP/BOTTOM centre it across, LEFT/RIGHT up and down, CENTER both) that's an odd number of pixels long on that axis has its edges half a pixel off the grid. So do its children. The game then rounds each child separately, and children either side of the centre round in opposite directions. Symptom: one gap in a row of buttons is a pixel short, right at the middle (a 12-button bar at 3px spacing is 573px wide). Fix: round the frame up to an even pixel length on each centred axis, so its edges and its centre stay on whole pixels and frames anchored to it line up too. `EvenIfCentred` in `SaftUI-ActionBars/bars.lua` does this, through `AB:PlaceFrame`, which sizes and places both the bars and the extra buttons' holders (`extras.lua`). When another addon needs it, move it into `api.lua`. Where the anchor can change without SaftUI's sizing code seeing it, round up on both axes whatever it is. The totem bar (`SaftUI-Misc/totembar.lua`, `EvenPixels`) is always sized even, with the spare pixel as empty bar at the right and the top: on a shaman SaftUI places it from its holder, whose Position can be anchored by any point and is changed by drags, and on other classes Blizzard's Edit Mode places it.
  - combat-safe moves: `st:CanMoveNow`, `st:SafeReposition`, `st:QueueAfterCombat`, `st:GetPoints`/`st:RestorePoints`
  - waiting for a Blizzard addon: `st:OnBlizzardAddon(name, fn)` runs `fn` at once if `C_AddOns.IsAddOnLoaded(name)`, else once on that addon's `ADDON_LOADED`, through one shared event frame (a wait made inside a waiting `fn` is kept; an error in a `fn` run from the event goes to the error handler and the others still run; a `fn` run at once raises into its caller). Use it instead of a module's own `ADDON_LOADED` method with `RegisterEvent`/`UnregisterEvent`. A site that already tests for its frame (`if SomeFrame then Setup() else st:OnBlizzardAddon('Blizzard_X', Setup) end`) keeps that test in front, and a guard such as `C_AddOns.DoesAddOnExist` goes before the wait. It is for one named Blizzard addon; a wait on any addon or on another author's addon stays a handler of its own
  - moving Blizzard frames whose methods are Lua overrides: `st:SetPointDirect`, `st:ClearAllPointsDirect`, `st:SetSizeDirect`
  - taking over a Blizzard Edit Mode frame: `st:PlaceHolder` (a holder of SaftUI's, from the profile), `st:HoldFrame` (the Blizzard frame over it) and `st:HideEditModeSelection` (its Edit Mode box); see `.agents/edit-mode.md`
- Styling: `st:SetBackdrop`, `st:SetTemplate`, `st:SetBackdropIn` (`theme.lua`, below), `st:CreateFrame` (`panels.lua`), `st:GetFont` and `st.OutlineFlag(outline)` (`Media/fonts.lua`; the font flag for a saved outline key, `'NONE'` giving `''`, so pass it to `SetFont` and never the raw key), `st.Clamp(value, low, high)` (`utilities.lua`; floors, nil is `low`), `st:CreateButton`/`st:SkinButton` (`Widgets/`). Colors other than the theme's live in `st.config.profile.colors`.

## Themes

SaftUI draws its frames in one theme, Thick, Thin or Blizzard, set on Global Settings' Theme tab, which any module can override. The design is `docs/superpowers/specs/2026-11-10-saftui-themes-design.md`, and the Blizzard theme's `docs/superpowers/specs/2026-11-10-saftui-blizzard-theme-design.md`. Blizzard draws each kind of frame in Blizzard's own art, on SaftUI's own frames: the engine resolves it, holds its art's tables and draws its art (`SaftUI-Core/themeart.lua`). The Theme tab and every module's override offer it, and no default is Blizzard.

- **The profile.** `st.config.profile.theme = { name, transparent, opacity }` (`thick`, a Transparent background, 0.9 by default). A `name` this version doesn't know (a later version's theme, in a profile opened by an older build) reads as Thick wherever it's read (`st:ResolveTheme`, and the Theme tab's rows), and stays saved until the user picks a theme. Each theme keeps its own colors, arrays in `st.config.profile.templates.thick`, `.thin` and `.blizzard` (`bordercolor`, `altbordercolor`, `backdropcolor`, and Blizzard's `windowcolor`, the fill of its windows; Thick's and Thin's windows take their `backdropcolor`; Blizzard's two fills both default to its dark grey, and can be set apart); `templates.close` is the close button's red. The key is still `templates`: saved variables may keep the word, only what the user sees changes.
- **A module's override** is a pair of config keys, `theme` (`'theme'`, `'thick'`, `'thin'`, `'blizzard'` or `'none'`) and `background` (`'theme'`, `'solid'` or `'transparent'`); `'theme'` follows SaftUI's. The Bags have a second pair for their item and currency slots, `buttontheme` and `buttonbackground`, and the unit frames one per unit and element. Core's `buttons` and `panels` have the pair with no option, following the theme. The options come from `generators.theme` and `generators.background` (`.agents/edit-mode.md`), and a change re-runs the module's `UpdateConfig`, which draws with the new pair.
- **The engine** is `SaftUI-Core/theme.lua`:
  - `st:ResolveTheme(theme, background, kind)` turns a pair into the look a frame is drawn with as kind (`{ name, inset, alpha, colors, kind }`, or nil for None); a Transparent background uses the profile's Opacity even while the toggle is off. `st:ThemeInset(theme, background, kind)` is how far in its border reaches, with the kind required as a draw call's is (an error unless the Theme is None): where content sits, for layouts that used to read `frame.thick`. `st:DrawnInset(frame)` and `st:DrawnKind(frame)` give the inset and kind a frame was last drawn at (a drawn frame, or the owner of a backdrop the engine drew; 0 for None, nil for never drawn), which `st:CalculateSpacing` reads. By the same lookup, `st:DrawnTheme(frame)` is the theme it was last drawn in (nil for None) and `st:DrawnFrame(frame)` the frame its look is on (itself, or its backdrop): a window's close button sits in the metal's socket by them (`st:CloseButtonInSocket`, `panels.lua`), and its header in the metal's title bar (`st:HeaderInTitleBar`: the title, the header's buttons and the window's content, placed under the header, move up with it; see `.agents/edit-mode.md`, the close button). The inset is 2 for Thick and 1 for Thin whatever the kind, 0 for None, and the kind's own under Blizzard (`st.ThemeArt.Inset`). With no kind, `st:ResolveTheme` gives a Blizzard look no inset. `st:IsBlizzardLook(theme, background)` says whether a pair draws in Blizzard's art, for controls that show that art themselves.
  - `SaftUI-Core/themeart.lua` (`st.ThemeArt`, loaded right after `theme.lua`) holds the Blizzard theme's tables: `KINDS` (each kind's inset per client, its art and its fill) and `ART` (the tooltip border, the character frame's metal, the unit frame's bronze box, the action and item buttons', the aura's and the close button's art, and every control's, among them the group border, the unit frame bars' fills, the resize grip, the micro menu bar's art and the nameplate target's, `nameplatetarget`: Forever's `UI-HUD-CoolDownManager-Selected-yellow` and retail's `UI-HUD-Nameplates-Selected`, each marked for its client, with the offsets it sits at round the health bar). The accessors read them for the client at call time (`ThemeArt.Client()`, `'forever'` or `'live'`): `Inset`, `Top` (how far the art reaches down from the drawn frame's top: a window's title bar), `TitleHeight`, `TitleStrip` (the strip of the title bar a window's header sits in, 20 on both clients, its bottom on the window's top), `MetalAbove` (how far the metal's art reaches above its drawn frame, 16), `MetalReach` (its reach past the drawn frame on the left, right, top and bottom: 8, 2, 16, 8 on Forever and 8, 4, 16, 3 on retail, which `/sui`'s window gives `st:KeepInScreenMargin` as its `reach`), `Close`, `State`, `Control` and `ClassPower`. It also draws a Blizzard look for `theme.lua` (`ThemeArt.Paint`, `ThemeArt.Color`, `ThemeArt.Clear`): textures made once per drawn frame and kept in its weak tables (`ThemeArt.Get`). A border's pieces are on the drawn frame. A button's ring lies over the icon's edge: on a button of SaftUI's (`st:SetBackdrop`) it's a texture of the button's own, in ARTWORK below 0 (over an icon in BACKGROUND or BORDER, under its texts and cooldown), and otherwise, or on a frame marked with `st:MarkForeign` (someone else's, still drawn with `st:SetBackdrop`), it's on a frame of SaftUI's over the backdrop. Under Blizzard a backdrop has a fill and no edge (a small frame keeps one line), a window's backdrop reaches its title bar above it, and `header`, `close` and `control` are cleared; Thick and Thin hide the art. An art name is an atlas unless it's a file under `Interface\` (the resize grip's three files, so it isn't among the atlases). Each atlas is marked as the tables are built, `Atlas(name)` for one both clients have and `Atlas(name, client)` for one only that client has (`'forever'` or `'live'`): Forever's Camelot minimap art (`ui-hud-minimap-header-button`, `-addon-indicator`, `-tracking-button`) is Forever's only and named only in Forever's art. `st:ThemeAtlases()` gives `{ [name] = true | 'forever' | 'live' }`, and `tests/core/theme_blizzard_test.lua` checks each atlas exists on the clients it's marked for. **Cut art.** The bronze box and the group border don't set an atlas on their textures: `ThemeArt.Cut(texture, atlas, rect)` reads the atlas's file and its coordinates from `C_Texture.GetAtlasInfo` (on Forever the Camelot member's) and sets the texture coordinates of `rect` (`{ x0, x1, y0, y1 }`, exclusive ends, in the atlas's own pixels) within the member, hiding the texture and returning false when the client gives no file, no texture coordinates or no size; a cut's pieces are anchored corners of `size` and stretched edges (`LayCut`), with no size read back from a frame. `ART.unitframe` is eight pieces (corners 8 x 8) cut from the target and player frames' art, per client because retail's art is a different drawing; `ThemeArt.PaintCut(frame, name)` lays a cut on a frame that is only that art (the group border) and `ThemeArt.Clear` hides it; `st:SetBorderColor` tints a cut's pieces as it does a border's. `ThemeArt.LayBorder(pieces, frame, border)` lays a nine-piece border on a frame in the caller's own pieces table (the tooltip border's way, and its Center, anchored between the corners and untiled, when the border has one: retail's minimap button kit does) and `ThemeArt.HidePieces(pieces)` hides them. SaftUI places the art itself and never runs Blizzard's nine-slice code (`.agents/taint.md`).
  - Every draw call names its kind of frame, last: `st:SetTemplate(frame, theme, background, kind)`, `st:SetBackdrop(frame, theme, background, kind)` and `st:SetBackdropIn(backdrops, frame, theme, background, kind)`. The kinds are `st.THEME_KINDS`: `panel` (a background), `window` (a window with SaftUI's title bar), `bar`, `action`, `slot`, `aura`, `tooltip`, `header` (header and footer strips), `close` (the close button), `control` (a small frame Blizzard draws with art of its own), `unitframe` (a unit frame or one of its bars), `member` (a party or raid member's frame or bar) and `small` (everything else), thirteen in all. Under Thick and Thin only `header` and `close` draw differently (SaftUI's theme's fill, no lines): a window draws as a panel, a control as a small frame and `unitframe` and `member` as a `bar`. Under Blizzard `unitframe` is the bronze box (inset 2) and `member` a bare Background fill (inset 0, no art). Blizzard's look is the kind's own (`themeart.lua`). A call with no kind is an error, unless its theme is `'none'` (which only clears). `st:SetTemplate` also takes a fifth, optional argument, the button its ring and own-color piece are textures of (for a frame drawn on itself behind a button that isn't SaftUI's, which holds its own texts: the totem bar's). Use the `st:` form even inside Core's own methods: `tests/core/theme_kinds_test.lua` scans every file the TOCs load for draw calls without a kind, and fails on any other form.
  - Each drawn frame is recorded with the arguments it was last drawn with. `st:RecolorThemed()` puts the current colors and opacity back on every one, moving nothing; `st:RedrawThemed()` draws each again at the current inset, and moves a backdrop only while it still sits where the last draw put it (one its caller anchored itself is repainted where it is). Both color or draw each frame on its own (`xpcall` to `geterrorhandler()`): one that errors is reported, and every other frame still takes the theme.
- **The Theme module** (`SaftUI-Core/Media/theme.lua`) is the tab. A color or Opacity change runs `st:RecolorThemed()`. A Theme or Transparent background change runs `st:ThemeChanged()`, which is `st.Config:UpdateConfig()`, the profile update: it redraws every drawn frame once (`st:RedrawThemed()`), has every module lay itself out again (the border's width moves what sits inside it), and ends with `st:ColorsChanged('theme')`. Both wait for the end of combat (one pending run, `st:QueueAfterCombat`).
- **A profile switch, copy or reset is a theme change** when the two profiles' themes or theme colors differ, so `Config:UpdateConfig` always redraws and recolors (below): no frame keeps the old profile's look until a reload.
- **A frame's own border color** goes on through `st:SetBorderColor(frame, r, g, b, a)`, never `SetBackdropBorderColor` on a drawn backdrop (`tests/core/theme_kinds_test.lua` scans for it); `frame` is the drawn frame the caller holds (`x.backdrop`, `backdrops[x]`, or one drawn with `st:SetTemplate`). With no color it puts the look's own border back, with no redraw. Under Thick and Thin it is the backdrop's border. Under Blizzard it is the kind's own: the tooltip and metal pieces tinted, `action`'s `UI-HUD-ActionBar-IconFrame-Border` or `slot`'s and `aura`'s `Interface\Common\WhiteIconFrame` shown in the color over the icon's edge (`st.ThemeArt.Get(frame).own`, a texture on the button of SaftUI's the way the ring is, or on a frame of SaftUI's over the backdrop for a frame that isn't SaftUI's: mark Hekili's or WeakAuras' with `st:MarkForeign` before the first draw), a `small` frame's line; a `control`, a frame never drawn and a frame drawn None are left alone. A recolor or redraw takes the color off, so a module colors again in `OnColorsChanged('theme')`.
- **Colors a frame's own code puts on its backdrop** (an item's quality border, a debuff's type, an equipped item, a tooltip's class border, a selected mover) would be wiped by a recolor or redraw, so they're put back two ways:
  - a module's `OnColorsChanged('theme')` colors the borders it tracks again (Bags, ActionBars, Loot's feed, Tooltip, the totem bar, Skinning's skins, edit mode's movers, and the unit frames: the target's border on every nameplate, `UF:UpdatePlateTarget`, each plate on its own);
  - `st:KeepOwnColors(frame, color)` registers `color(frame)` for one frame, run again after every recolor and redraw: Core's widgets, which have no module (a scroll bar thumb's hover, a radio group's picked button, a focused edit box; and Core's controls, which switch between their own look and Blizzard's art under the Blizzard theme: `st:SkinButton`'s panel button and tabs, `st:SkinCheckButton`'s check box and panel button, the scroll bar's own layers, an edit box's own border textures. `st:SkinButton` and `st:SkinCheckButton` register under a table of their own, since a module keeps its own colors under the same button), the lit border of a loot roll you've chosen on (`SaftUI-Loot/roll.lua`), the target's border on its nameplate (`SaftUI-Unitframes/nameplates/target.lua`, on both the health bar's and the plate frame's drawn frame, whichever carries it), and the unit frames' aura buttons (the dark line `auras.lua` draws inside each button's Thick border, `ColorInnerLine`, in Thick's outer border color, shown only under Thick; the dispel-type texture, a fill behind the icon or under Blizzard Blizzard's white icon border over the whole button, set by `StyleButton` when the element updates, is a separate texture a recolor or redraw never touches). nil forgets it. The frame is only a key, so it may be Blizzard's. A color function may keep another frame's colors (the plates' target border does, for a frame a redraw drew first): each pass walks a copy of the frames, so one kept during it runs from the next.
- **Saved template choices migrate.** Before themes, a module saved an old template name (`thicktransparent`, `thin`, `none`, ...) in a key named `template` or `<prefix>template` (`buttontemplate`). `st:MigrateTemplateKeys(tbl)` (`theme.lua`) walks a table and rewrites each such key holding a string into `<prefix>theme` and `<prefix>background` through the old names' table (`thicktransparent` is Thick and Transparent, `thin` Thin and Solid, `none` only None; `highlight`, `close` and any other string just go, so the module's defaults apply), and removes it. Every old choice was a string, so any other value under such a key is data and stays (a unit frame profile the user named `raid template` is a table, walked like any other). It reads only what's saved (never through AceDB's `**` defaults), and running it again changes nothing. `Config` runs it wherever saved data enters a profile: on `st.config.profile` right after `AceDB:New` at login, at the start of every `Config:UpdateConfig` (a profile switched to or copied from one the old version saved), and on the data `Config:Import` returns (so the unit frames' Import too). The unit frames' own profiles live inside the SaftUI profile, so they migrate with it, and their Copy copies a profile already migrated.

## Config, defaults and profiles

- Each module defines its defaults at file load in its own `config.lua`, as `st.defaults.<key> = { ... }`. Unit frames keep theirs in `SaftUI-Unitframes/config/`.
- `Config:InitializeAceConfig` (called from `SaftUI:OnEnable`) creates `st.config = AceDB:New('SaftUI_DB', { profile = st.defaults, ... })`. Read settings through `st.config.profile.<key>`.
- **Bind, don't cache.** In `OnEnable`, call `st:BindModuleConfig(self, '<key>')` instead of `self.config = st.config.profile.<key>`. On a profile change, AceDB switches to the new profile's tables and strips defaults from the old ones, so any reference cached at enable time (including upvalues and closures holding sub-tables) returns nil fields. Bound modules are re-pointed automatically. In option `get`/`set` functions and hooks, read through `self.config` at call time.
- **Per-character saved data** (not settings) goes in AceDB's char namespace, `st.config.char.<key>`, which a profile switch doesn't touch. SaftUI-Loot keeps its saved feed and recorded roll drops there (`Feed/history.lua`, `Feed/rolls.lua`). Read it through an accessor at call time (`st.config` doesn't exist at file load). Save only plain data (strings, numbers, booleans and tables of them), never a secret value (`.agents/clients.md`) and never test-mode entries, and keep each record to the fields its readers need.
- **Profile changes** (`OnProfileChanged`/`Copied`/`Reset`) run `Config:UpdateConfig()` in `SaftUI-Core/Config/config.lua`. Order:
  1. Migrate the profile's saved template choices (`st:MigrateTemplateKeys`, see Themes), then re-point every bound `module.config`.
  2. Redraw every drawn frame in the profile's theme (`st:RedrawThemed`), before any module lays itself out around its border. In combat the redraw and step 8 wait for the end of combat, as one pending run (`QueueAfterCombat('ThemeRedraw')`). In and out of combat they're two steps, each in `xpcall`, so a redraw that errors still has step 8 run after it.
  3. Clear mover anchors (`EM:ClearPositions`, which saves them and skips frames that are protected in combat).
  4. Apply fonts, then headers (`st:UpdateHeader`: every header's and footer's height and window title fonts, and each header in its window's metal title bar or back; a header or footer that's protected in combat waits for the end of it), then the screen edge margin (`st:UpdateScreenMargin`: every frame kept inside it; see `.agents/edit-mode.md`).
  5. Run every module's `UpdateConfig` inside `xpcall`, with errors going to `geterrorhandler()`.
  6. Re-apply edit mode movers (`EM:UpdateConfig`), restoring the old anchors of any frame left without points.
  7. Rebuild and refresh an open `/sui`.
  8. `st:ColorsChanged('theme')`, so what modules color themselves (quality borders, a selected mover) goes back on over the redrawn theme.

  In combat, protected work is deferred with `st:SafeReposition` / `st:QueueAfterCombat`, and one chat message says what will finish after combat.
- **Every module needs an `UpdateConfig`** that re-reads the profile and re-applies everything it controls (positions, sizes, its Theme and Background, fonts, colors, visibility). It must be idempotent: never create frames, font strings or hooks on each call. Create once, re-style on every call. Settings that genuinely can't apply live (module on/off toggles, secure header attributes) say "reload to apply" in their option description.
- Position config shape: `{ point, frame, rel_point, x_off, y_off }`, unpacked with `st:UnpackPoint`. Some older code used array positions (`{'BOTTOMRIGHT', -20, 20}`). Modules that converted (Bags, Chat, Experience) migrate saved arrays in place on enable and on profile change, filling missing slots from the old array defaults, because AceDB only saves slots that differ from the default.

## Bag categories

- Which category an item goes to is data in the profile, not code. The design is `docs/superpowers/specs/2026-11-10-saftui-bag-categories-design.md`. `INV.config.categories = { version, order, edits, custom, deleted, nextId }` and `INV.config.categoryPins = { [itemID] = id }` have no AceDB defaults: `INV:EnsureConfigTables` makes them, and `INV:MigrateCategories` turns an old profile's hide flags and Auto Vendor list into Show in flags and pins, once. The header of `SaftUI-Bags/categories.lua` lists the profile keys and every getter and setter.
- **The list** (`INV:GetCategoryList`) is the shipped defaults (`categorydefaults.lua`: today's filters, as block rules, in today's order) with the profile's edits over them, then the user's categories, in the saved order. A default's id is the name it shipped with, so renaming it changes only what headers show. An edit is stored against the shipped default and a field equal to it is removed, so a default changed in a later SaftUI version still reaches users who haven't edited that field. Setters copy the tables they keep and end in `INV:CategoriesChanged()`. Equipment sets, Miscellaneous (always last and on), Empty Slots and Currencies are entries or keys outside the plain rule list.
- **A rule** is a tree of groups (`and` or `or`, optionally negated) and blocks (`rules.lua`). `R.Compile` turns it into a closure that reads an item's facts (`INV:GetInventoryItemInfo`: class and subclass IDs, the lowercased and stripped name and tooltip text). A block or group it can't read matches nothing and NOT never flips that. A block with nothing set yet (a list with nothing picked, a level with no number, a yes/no with neither) can't be read, and new blocks of those types start that way, so no block matches everything as it's added. An OR skips children it can't read; an AND with any such child can't be read itself, so a half-built rule (an emptied group, a NOT on a block not yet filled in) catches less, never more. Every editor change saves at once, and for Grays/Auto Vendor more would mean selling the bag (see the `rules.lua` header). `INV:GetItemCategory(info)` returns the key and why (the block that caught it); the first category to catch an item wins, and a pin beats the rules.
- **Class and subclass names** are resolved to IDs per client (`itemclasses.lua`), so a block matches by ID where it can and by name where a client names a subclass differently (see `.agents/clients.md`).
- **An item whose tooltip hasn't arrived** is held for 10 reads, then filed without text and marked `tooltipMissing`, then refiled when its text arrives. Auto vendor never sells it, nor a Cosmetic, an equipment set item or a Protected one, whatever a pin or the Grays/Auto Vendor rule says (`INV:IsAutoVendorItem`). The seller is the category that carries the `sells` flag, found by the flag and not by name or place, so a rename or a move changes nothing; turned off, it sells nothing.
- No frame or slot is made in combat for a new category: the frames are made by `INV:EnsureCategoryFrames` out of combat.

## Unit frames

- These are oUF (`SaftUI-Unitframes/Libraries/oUF`, oUF master). In this oUF the active unit is `frame.__unit`, **not** `frame.unit`.
- Elements register through `UF:RegisterElement(name, Constructor, UpdateConfig, GetConfigTable, ValidUnit)`.
  - `ValidUnit(unit)` gets the config unit (`player`, `boss`, `party`, ...). A unit it rejects gets neither the element nor its `/sui` tab. ClassPower and AdditionalPower are player-only, Castbar skips `targettarget` and `focustarget` (as oUF does), ReadyCheckIndicator is party and raid only, Power, GroupRoleIndicator and RaidRoleIndicator skip both plate units (`UF.IsPlateUnit`: `nameplate` and `friendlynameplate`), and Threat (the nameplates' threat text) is `nameplate` only, so the Friendly nameplates page has no Threat tab. Every plate's frame is built as `nameplate` (its unit token's), so it has every element `nameplate` takes, Threat included, whichever config it draws from later (Nameplates).
  - `GetConfigTable(unit)` returns the element's tab. Its `set` calls `UF:UpdateConfig(unit, '<Element>')`, which re-runs that element's `UpdateConfig` on every frame of the unit.
  - oUF shows and hides many elements itself (castbar on a cast, indicators by state, additional power by power type), so `UF:SetElementEnabled` alone doesn't keep a disabled one hidden. Those elements also hide themselves again in an oUF hook (`ShouldShow`, `PostVisibility`, `PostUpdate`): the castbar's `ShouldShow` and the indicators' `PostUpdate` while `UF:ElementWanted` (below) says no, the others while their config is off.
  - Texts made by `UF:AddText` sit on the unit frame's `TextOverlay`, not on their element, so they don't hide with it. `UF:UpdateElement` hides them when the element is disabled.
  - `UF:UpdateElement` draws an element's Theme and Background on the element, except for the aura areas (Buffs, Debuffs) and the class power row (`BARE_ELEMENTS` in `updaters.lua`): their own `UpdateConfig` draws each aura button and point instead, and the area gets no backdrop. An aura area is Blizzard's AuraContainer, so nothing of SaftUI's is anchored to it (`.agents/taint.md`, rule 11).
- **How oUF builds a frame.** `UF:OnEnable` registers `UF.InitUnit` as oUF's init callback first, before the style and before anything is spawned. oUF then builds each frame in this order: the style function (`UF.ConstructUnit`), then it enables every oUF element whose widget the frame has, then the init callbacks. Single units get their first update from OnEnable's `UF:ApplyConfig`. Group buttons (made by their header as members appear) and the nameplates' frames (made at a plate's first add) get theirs in `UF.InitUnit`, after oUF's Enables, so the update has the last word (oUF's aura Enable turns every aura area on, and the update sets each by its config). A plate's frame gets that first update from `nameplate` whatever its unit's kind, and its first `'added'` callback then moves it to its kind's config (Nameplates). A group button made in combat is updated at once and again when combat ends (`st:QueueAfterCombat('uf_init_' .. name)`), since a secure frame can't be sized in combat; a plate's frame isn't secure, and its update in combat is whole. A widget oUF must enable has to exist when the style function returns, so a group button's range fade table (`self.Range`) is made in `UF.ConstructUnit`, and its alphas come from the update.
- **Shown and enabled.** `UF:ElementWanted(element)` (`updaters.lua`) is the element's config Enable, except that a friendly unit's nameplate never wants the parts only an enemy's shows: the threat text (`UF.PLATE_ENEMY_ONLY`, `{ Threat = true }`, `frame.friendly`; see Nameplates). A plate's config is its kind's, so a friend's castbar, aura areas and quest icon show by the Friendly page's Enable. `UF:SetElementEnabled` shows or hides by it and returns the config's Enable, which `UF:UpdateElement` places and sizes by, so a part a friendly plate hides is still laid out, ready for the plate's next enemy. On a plate, a part its own config turns off is still sized and placed by that config too (`UF:UpdateElement`, before it returns), when it's a part other parts can anchor to (`unitframe[element.name] == element`, the parts `UF:GetFrame` finds; not an element's texts and icons): a plate's frame takes the other kind's config on every kind change, and the friendly config hangs the castbar, the aura areas and the quest icon off a health bar it turns off, so the hidden bar holds them where they'd sit if it were shown. Such a part gets its size and place only; its backdrop, alpha, level and bar setup wait for its next enable. Other units skip a part that's off. `UF:SetElementEnabled` never enables or disables in oUF, which enables every element when it builds a frame. `DisableElement` is used on plates only (their castbar and quest icon, by their config), because oUF's castbar `Disable` gives Blizzard's player and pet castbars their events back on the player's frame (never on a plate's), which the player castbar's option promises not to do.
- **The bars' faction flags.** Health's and power's `colorTapping` and `colorReaction` go through `UF.SetFactionColorFlags(bar, config)`: oUF's setters, forced, while oUF has the bar enabled and not paused, so `UNIT_FACTION` (their recolor event, which oUF registers only in the bar's Enable) is registered or dropped to match; plain fields before that, and on a disabled or paused bar (a plate showing only widgets), which oUF's next Enable or resume reads.
- **Texts.** The `st:name` tag (`tags.lua`) takes secret values (`.agents/clients.md`): a secret level, reaction or classification is left out of the text, and a secret name isn't cut or put in capitals and is joined to its level part and color by the game (`C_StringUtil.WrapString`), so the tag returns a secret, which oUF's tag code shows. The tag has no nameplate target mark any more: the target's border replaces it. The name's color is the first that applies (`NameColor`): Class color for a player (or NPC class, Pet class), then Color hostile (red under reaction 3, yellow under 5), then Color friendly (`name.color_friendly`, reaction 5 or more, in oUF's reaction color; off by default, on for the friendly plates). The Name tab offers Color friendly where `UF.CanShow(unit, 'npcs')` (`config/config.lua`), so not on Player, Party or the raids. It colors only names the tag draws: the test mode previews' names (`groups.lua`) are drawn without the tag and ignore it. The tag names the config unit it reads (`[st:name(<base_unit>)]`), so the Name binds it once per config unit (`name.taggedUnit`, `elements/name.lua`) and, when the frame's `base_unit` changes (a plate changing kind), unbinds it and binds it again; the next oUF update writes the name from the new config. The health text's Short (`health.text.short`, off by default, on for the plates) shows 12.5K, 1.2M or 1.2B through the game's `AbbreviateNumbers` with SaftUI's own breakpoints (`SHORT` in `elements/health.lua`), which takes a secret health too; Percent with a secret health is the game's `UnitHealthPercent(unit, true, CurveConstants.ScaleTo100)` through `SetFormattedText('%.0f', ...)`; and the deficit and the percent are worked out only where they're shown. Boss percent and Hide full still read a secret as a number (`docs/followups.md`). Name's Max width (`name.max_width`, in pixels, 0 for none, every unit's default but the plates' 150) gives the name that width on one line, justified by its point's side, so the game cuts a longer name, a secret one too; 0 gives a name SaftUI sized before no width again.
- **The castbar** colors a cast from oUF's `notInterruptible` argument, which can be secret (then through `C_CurveUtil.EvaluateColorValueFromBoolean`), in `PostCastStart` (oUF runs it for channels too) and `PostCastInterruptible` (a cast that turns interruptible or not mid-cast). It reads no `CastingInfo`.
- **The quest icon** has an Override (`elements/indicators.lua`): shown for a unit one of the player's active quests is about (`C_QuestLog.UnitIsRelatedToActiveQuest`), else for a quest boss (`UnitIsQuestBoss`), a secret answer counting as no. No unit event says a unit's tie to a quest changed, so on `QUEST_LOG_UPDATE` a frame of indicators.lua's has every frame's icon ask again (`ForceUpdate`) where oUF runs it (enabled and not paused) and `UF:ElementWanted` says yes.
- **Aura filters** (`purge.lua`, loaded after `tags.lua`). Every aura group is built with, and keeps, the filter string and candidate filters `UF.AuraFilter(unitframe, auraType, config)` gives: Buffs with Only buffs I can purge (`buffs.purgeable`, off by default, on for the plates) get `UF.PurgeFilter(UF:KnownRemovals())`; a plate's Debuffs get `HARMFUL|INCLUDE_NAME_PLATE_ONLY`, Only mine as the `isFromPlayerOrPlayerPet` candidate filter alone, so the pet's debuffs stay; any other area `HELPFUL` or `HARMFUL`, Only mine adding `|PLAYER` and that flag (`.agents/clients.md`). `AddGroup` notes what it built the group with (`auras.groupFilter`, `auras.groupCandidateFilters`), and every aura element's `UpdateConfig` runs `UF:ApplyAuraFilter(auras)` on a built group, which calls each of Blizzard's setters only if its part changed (each makes the container update every aura), so the filter applies live. So do the group's other options but two (`elements/auras.lua`): the max count, through the container's `SetAuraGroupMaxFrameCount` on every update of a built group (a container call that touches no button, so in combat too; it does nothing for the count it has), and the button size, which the container has no call for, so `StyleButton` sets each button's size from the config in use (`getButtonSize`, Relative size included) as it styles it: a new button in `PostCreateButton`, the others in the restyle, at once out of combat and at the end of combat in it (`RestyleButtons`), when the group is also laid out again (`SetAuraGroupLayout`, since the container lays out only when something marks its layout dirty, never because a button changed size). Which borders the buttons show and whether they get a cooldown are baked into each button as the container makes it, from the options the group was made with, so their options still say to reload. A group is made once per frame, on its first update with the area on: a plate's is made from Enemy nameplates while that page has the area on (a plate's first update is always from it), so the Friendly page's border and Cooldown → Show never reach its buttons then, even after a reload (ruling N2, `docs/followups.md`). The two options' notes say so on the two plate pages (`ReloadNote`, every other unit's says to reload): the Enemy page's that its settings make every plate's buttons while it has the area on, friendly plates' too, and the Friendly page's that its reach friendly plates only while the Enemy page has the area off, and then after a reload. `UF.PURGE_SPELLS` lists the purge, dispel and steal spells by client and class and what each removes (Magic, Enrage, stealable; `.agents/clients.md`), `UF:KnownRemovals()` asks `C_SpellBook.IsSpellKnown` which the player knows (a pet's in the pet's spellbook), and `UF.PurgeFilter(known)` turns them into `HELPFUL|RAID_PLAYER_DISPELLABLE` with `includeDispelTypes`, or `isStealable` for a player who can only steal, or no buffs for a player who can remove nothing. A frame of purge.lua's runs `UF:RefreshPurgeFilters()` (every unit frame's purge filter again, waiting for the end of combat) on `SPELLS_CHANGED`, `PLAYER_TALENT_UPDATE`, `TRAIT_CONFIG_UPDATED` and the player's `UNIT_PET`.
- **Colors.** `UF:OnColorsChanged` reads each frame's oUF unit, `__unit` (`.unit` is set only by `UF.OnEnter`, so a frame never hovered has none), and skips a plate that isn't showing its unit. For `threat` it retints the plates (`UF:UpdatePlateThreat`) and updates no other frame. For `theme` it draws the target's border on every plate again and rounds each plate to whole pixels again (Nameplates, below). `UF:ForEachUnitFrame` visits the plates' frames too, shown or not, so `UF:RefreshConfigReferences` (`UF:RefreshFrameConfig(frame)` on each: the frame's cached config and every element's, text's and icon's pointed at its config unit's in the current profile, plain table writes, safe in combat), `UF:RefreshPurgeFilters` and the color updates reach them.
- **Themes on unit frames.** `UF.UnitKind(unit)` is `'member'` for party, raid10 and raid40 (`UF.group_strings`) and `'unitframe'` for every other unit; the frame, its bars and the previews draw with `UF.SizedKind(unit, width, height)`, which is `'small'` instead of `'unitframe'` when the bronze box doesn't fit the size from the config (`UF.BoxFits`: under two corners less two insets, 12 today, on either side; the sizes come from the config through `UF:ElementSize`, never read off a frame). The fallback depends only on size, so such a bar's drawn kind is `small` under Thick and Thin too, where it looks as a bar. **One box per edge:** `UF:ElementTheme` gives None to a bar drawn as `unitframe` or `small` that fills its frame (`UF.FillsFrame`: Relative width and height on, both 0, no `position.element` or `position.frame`, point equal to relative point, offsets 0) while its own Theme and its frame's are both Blizzard, so the frame's box is the only one; otherwise each element draws its own pair. **The group border.** Under Blizzard each party and raid header (one for the whole raid, not one per real raid group), and a party or raid test mode preview container, sits in a border (`ART.groupborder`: Blizzard's `options_frame_child`, cut at 6 with no middle, the same rectangles on both clients; Forever's is the Camelot member, bronze with a faint dark middle, retail's grey with a clear middle). It is a plain frame of SaftUI's, the header's child at the header's level, anchored at `offsets` (-2, 2) / (2, -3) so it follows the header's layout in combat with no SaftUI code, made in `UF:CreateGroupHeaders` and kept in `groups.lua`'s weak table (`UF:GroupBorder`). It shows when `UF.GroupBorderShown(config)`: the frame's Theme, or health's where the frame's is None, resolves to Blizzard. `UF:UpdateGroupBorder` runs from `UF:ApplyConfig` (in and out of combat) and the preview's from `UF:UpdateGroupPreview`. A header with no member to show (a pending invite with Show player off, a group disbanding) still shows and sizes itself to a sliver, so the border sets its alpha to 0 from its own `OnSizeChanged` while either side is under two pieces (12). **The fills.** Under Blizzard a health, power or additional power bar whose texture is SaftUI Flat and whose own resolved Theme is Blizzard draws Blizzard's raid bar fills (`ART.unitbars`, `RaidFrame-Hp-Fill`, the resource fill on power, with their background atlases): `UF.BlizzardFill(element, config)` decides, `UF:SetBarFill(element, fill, flat)` draws the fill and background (or the flat texture and a blank background), `UpdateStatusBarElement` records `element.barFill` and `element.barFlat` (the flat texture, the user's pick among them), and a power update draws them again (`power.lua` and `groups.lua`'s member power call `UF:RedrawBarFill`, so the fill, or the picked texture, survives ticks; `UF:SetBarFill` does nothing when asked to draw what is already drawn). A texture the user picked stays, under every theme.
- Layout "profiles" inside the SaftUI profile: `st.config.profile.unitframes.profiles[UF:GetProfile()]`, read through `UF:GetProfileConfig()`.
- Unit frames are secure. See `.agents/taint.md` before moving or resizing them.

## Nameplates

SaftUI draws the nameplates as unit frames on the bundled oUF's nameplate driver, from two config units: `nameplate` (the Enemy nameplates page: enemy and neutral plates) and `friendlynameplate` (the Friendly nameplates page). `UF.PLATE_UNITS` lists them and `UF.IsPlateUnit(unit)` asks it (`unitframes.lua`). The design is `docs/superpowers/specs/2026-11-11-saftui-nameplates-design.md`, and the plan `docs/superpowers/plans/2026-11-11-saftui-nameplates.md`; the friendly plates' are `docs/superpowers/specs/2026-11-12-saftui-friendly-nameplates-design.md` and `docs/superpowers/plans/2026-11-12-saftui-friendly-nameplates.md`. The code is `SaftUI-Unitframes/nameplates/`, whose `nameplates.xml` lists `nameplates.lua`, `cvars.lua`, `target.lua`, `threat.lua` and `pixels.lua`, loaded after `elements/elements.xml` in both TOCs. Keep `pixels.lua` last: its `'updated'` callback rounds what the others made. The defaults are `config/units/nameplate.lua` and `config/units/friendlynameplate.lua` (an element's other settings are every unit's, `['**']`), whose top comments lay each look out; the enemy one gives its arithmetic. `nameplate` keeps the plates' switches whichever page shows them: `enable` (Nameplates), `friendly` (Friendly plates, on the Friendly page), `threat_solo` and `threat`. The boxes are `nameplate.use_friendly` and `friendlynameplate.use_enemy`, both off by default. Before you touch anything of Blizzard's on a plate, read `.agents/taint.md`, rule 13.

- **Spawning.** `UF:OnEnable` calls `UF:SpawnNameplates()` last, once every other unit is placed and the colors are set. It makes oUF's driver (`UF.oUF:SpawnNamePlates('SaftUI_')`, kept as `UF.plateDriver`) and returns true, or makes nothing and returns false when the driver exists already, Nameplates (`nameplate.enable`) is off, or another nameplate addon draws the plates: `UF:NameplateAddon()` names the first loaded one of `UF.NAMEPLATE_ADDONS` (Plater, EllesmereUINameplates, Kui_Nameplates, TidyPlates_ThreatPlates, NeatPlates, Platynator, whose folder name is unconfirmed, and ElvUI unless its own nameplates are off), a table in the code. oUF can make its driver only once, so a change to either needs a /reload. OnEnable then sets the game's nameplate settings (`UF:ApplyNameplateCVars`), or, with no plates of SaftUI's and no other addon drawing them, puts the user's own back (`UF:RestoreNameplateCVars`). There's no mover: the game places each plate.
- **The frames.** The game makes the plates (`NamePlate1`, ...) and hands each to unit after unit. oUF builds a frame of SaftUI's on a plate at its first add (`SaftUI_NamePlate1`: the plate's child, filling it, `isNamePlate`), which `UF.ConstructUnit` keeps by its plate's number in `UF.nameplates` (not `UF.allUnits`) and `UF.InitUnit` gives its first update; it stays on its plate for every later unit. oUF keeps a frame's `__unit` after the game takes its plate away (its remove clears the unit attribute, which its handler ignores), so whether a plate shows a unit is SaftUI's own record, kept from oUF's added callback to its removed one: `UF:PlateShowsUnit(frame)` asks it, and `UF:PlateForUnit(unit)` finds the frame showing a unit through a token-to-frame map the same two callbacks keep, without walking every plate. `UF:ForEachPlate(fn)` visits every frame, shown or not. A plate's frame takes no mouse, so a click on the plate reaches the game, which targets its unit (the click area, below). `UF:PlaceUnitFrame` places a plate's frame on its plate (`UF:PlacePlateFrame`, under Size) and returns true, and `UF:UpdateUnitFrame` places a plate's frame in combat too (it isn't secure, and its kind, with the config and size it's drawn at, can change mid-fight); `ClearUnitFramePoints` leaves the plates' points. `UF:ApplyConfig(unit, element)` with either plate key (`UF.IsPlateUnit`) does the same for both: with no element it sets the plates' size first (from the enemy look's config, so each frame is then placed, and its click area set again, on its plate's new size), then for every plate works out its config unit again (`UF:ApplyPlateConfig`, below): one that moved gets a full update from its new config, every other the update asked for. Every plate, whichever page it draws from, since the threat text is always the Enemy page's and a box decides which frames fill their plates. `UF:GetConfigFrame(unit)` for either plate key is the lowest-numbered plate's frame.
- **Plate callbacks.** `UF:RegisterPlateCallback(event, fn)` adds to what `UF:RunPlateCallbacks` runs, in the order registered, each in `xpcall` so one that errors leaves the rest to run: `'added'` (frame, unit), after oUF has set the frame's unit and before it updates the elements, never for a plate showing only widgets or a game object (oUF pauses and hides SaftUI's frame for those); `'removed'` (frame, unit); `'updated'` (frame), after every `UF:UpdateUnitFrame` on a plate, so also before `'added'` on a plate's first add and on a plate the game took away, where state from `'added'` or `__unit` can't be trusted (check `UF:PlateShowsUnit`); and `'kind'` (frame), once `UF:ApplyPlateKind` has set the plate's kind. On a plate handed to a new unit oUF also updates every element once (`OnAttributeChanged`) before the added callback, with the frame as the last unit left it. **On an add that changes the plate's config unit** (with the boxes off, a friend after an enemy or an enemy after a friend, and a friend's first add, the frame being built on `nameplate`), `'updated'` also fires inside `'added'`: the first `'added'` callback is `UF:ApplyPlateKind`, whose `UF:ApplyPlateConfig` runs a full `UF:UpdateUnitFrame`. So those `'updated'` callbacks run before `ApplyPlateKind` enables or disables the oUF parts and shows or hides each part, before `'kind'`, and before the other `'added'` callbacks (the scale pin, the target's border); they see `frame.friendly` and `frame.base_unit` already the new kind's. An `'updated'` callback that enables a part in oUF updates the frame again there (`OnShow`). So a plate reused for the other kind gets oUF's `UpdateAllElements` three or four times: `OnAttributeChanged` (oUF, with the old config), `OnShow` (the new config's full update), a second `OnShow` when that update's `'updated'` callback enabled a part (an enemy after a friend: the castbar), then `NAME_PLATE_UNIT_ADDED` (oUF). A friend's first add on a new plate is two full updates (`UF.InitUnit`'s from `nameplate`, then the friendly config's). An add of the kind the plate last showed changes no config unit and adds none (`docs/followups.md`, the cost of a kind change).
- **Friend or enemy.** `UF.IsFriendlyPlate(unit)` is `UnitIsFriend` and not `UnitCanAttack`, a secret answer counting as an enemy. It's broader than Blizzard's own on purpose: any friend you can attack (a duel, free-for-all PvP) gets an enemy's plate. **Each kind draws from its own config unit**, `UF.PlateConfigKey(friendly)` (`unitframes.lua`): an enemy from `nameplate`, or from `friendlynameplate` while `nameplate.use_friendly`; a friend from `friendlynameplate`, or from `nameplate` while `friendlynameplate.use_enemy`. The pages keep the two boxes from being on together; with both on (a profile from elsewhere) each kind takes the other's, and nothing recurses. The frame's `base_unit` names its config unit, which `frame:GetConfig()` and every element's read. `UF:ApplyPlateConfig(frame)` sets it to `UF.PlateConfigKey(frame.friendly)` and, when it changed, points every cached config at the new one (`UF:RefreshFrameConfig`, since the update re-points a part's own config but stops at a part that's off before its texts and icons), clears the points of everything the update places (`ClearPlacedPoints`: every part, and the texts and icons that are on in a part that's on) and gives the frame a full update from it (`UF:UpdateUnitFrame`: its parts, places, size, fonts, colors and the name's tag), all in one `xpcall`, so an update that errors is reported and the caller goes on; it returns whether it changed. The update places the parts one by one in `pairs()` order, each against the others where they are then, so without the clearing two parts anchored each way round across the two pages (the Friendly page's health bar under the name, the Enemy page's name on the bar) would close an anchor loop on a switch one way or the other, which the game refuses. A profile switch that keeps a plate's config unit still places its parts against the old profile's, as for every unit (`docs/followups.md`). So a plate applies a look again only when its config unit changes, never on a reuse of the same kind. Which parts a plate shows is its config's: by default a friend's name alone (no health bar), an enemy's every part. Only the threat text is hidden on a friend whatever the config says: `UF.PLATE_ENEMY_ONLY` is `{ Threat = true }` (`UF:ElementWanted`). `UF:ApplyPlateKind(frame, friendly)` sets `frame.friendly`, runs `UF:ApplyPlateConfig`, enables or disables the castbar and the quest icon in oUF by `UF:ElementWanted` (`OUF_SWITCHED`), shows or hides every part and turns the aura areas on or off (every part, since oUF's resume after a plate that showed only widgets turns them all on and shows the health bar), then runs the `'kind'` callbacks. It's the first `'added'` callback, so the others read the kind. A `UNIT_FACTION` for the plate's unit, or for the player (every showing plate), applies it again when the kind changed and then updates every element (`UpdateAllElements('UNIT_FACTION')`), which also draws the name again in the new kind's colors, since the `st:name` tag has no faction event of its own. A faction change that keeps the kind (neutral to hostile) does neither, so the name keeps its old color until its next tag event (`docs/followups.md`). An `'updated'` callback enables in oUF what a config change turned on while the plate shows its unit.
- **Blizzard's widgets.** On every add (widget-only and game object plates too), a frame of SaftUI's moves the pooled UnitFrame's widget container and soft target icon onto the plate, by one point: the container's bottom on the plate's bottom for a plate showing only widgets, else its top under the plate. oUF moves them only at a plate's first add. `UF:RefreshPlateWidgets()` places them again on every plate, then the click areas, after `UF:ApplyNameplateCVars` and on the frame after anyone changes the friendly NPC plates setting, since Blizzard anchors them again when it changes.
- **The click area** (ruling N11, `.agents/taint.md` rule 13). The game takes a plate's clicks in its hit-test points, which oUF sets to SaftUI's frame on every add that shows the unit (`ClearAllHitTestPoints`, then `SetAllHitTestPoints(frame)`). Blizzard's pooled UnitFrame sets its own again outside the add (`UpdateHitTestArea`): when the driver's options update runs `ApplyFrameOptions` on every plate (a window resize, the options loading, one of Blizzard's nameplate options), and from its `CVarCallbackRegistry` callbacks on the friendly NPC plates setting and on showing only friendly players' names. `UF:RestorePlateHitTests()` runs oUF's two calls again for every plate SaftUI shows: from a post-hook on `NamePlateDriverFrame:UpdateNamePlateOptions`, at the end of `UF:RefreshPlateWidgets`, on the frame after either setting changes (its own callbacks on both, through `C_Timer.After(0)`, once however many change, since the registry's callbacks run in no set order), and at the end of `UF:ApplyPlateSize` (out of combat, like the size), since a new plate size resizes the frames that fill their plates. Each hook and callback goes in only where the client has the name (`WatchClickAreas`). `UF:RestorePlateHitTest(frame)` does the same for one plate SaftUI shows, run by `UF:PlacePlateFrame` whenever a frame's place or size changes (a kind change, a box, a Width or Height): whether the game's click area follows the frame's rect after the calls, or takes it when they're made, isn't said outright (`SetAllHitTestPoints`' doc, "to fully encompass the target region", reads as anchors, which would follow; an in-game check). In combat the game allows the calls only on a tick Blizzard's own code changed the click area or the plate got its unit (`CanChangeHitTestPoints`, asked before each of the two calls), so a plate it refuses waits for the end of combat (`QueueAfterCombat('NameplateHitTest')`, which then sets every plate SaftUI shows, one wait however many were refused, also from the single-plate form). Blizzard never sets the hit-test insets, which stay oUF's.
- **Size.** The game has one size for every plate, which also sets how they stack, set through oUF's driver by `UF:ApplyPlateSize()`, from the enemy look's config (`UF.PlateConfigKey(false)`: Enemy nameplates', or Friendly nameplates' while the Enemy page's box is checked), its width and height through `UF.PlateDriverSize`: the config's size is in UIParent's units, where one is a pixel, and the plates are WorldFrame's children, which take theirs in its units, so it's multiplied by UIParent's effective scale over WorldFrame's (a secret or zero scale gives the config's size as it is). The plate, where the game takes the clicks, and SaftUI's frame on it are then the config's size in pixels. The game refuses the size from addon code in combat, so in combat it waits (`QueueAfterCombat('NameplateSize')`). Blizzard sets its own size whenever its nameplate options change, so a post-hook on `NamePlateDriverFrame:UpdateNamePlateSize`, installed before SaftUI's first size, sets SaftUI's again. **A plate's frame** is placed by `UF:PlacePlateFrame(frame)` (`UF:PlaceUnitFrame`, so on every full update, in combat too; it reads `frame.config`, which the update sets first): a frame drawn from the enemy look's config fills its plate, as oUF made it (`SetAllPoints`); one drawn from the other config (a friend's, by default) sits on its plate's centre at that config's Width and Height (`st:SetSize`, in UIParent's units, a pixel each), so what's drawn, and what's clicked, is a friend's name box, not the plate round it. A weak table keeps how each frame was last placed (`'fill WxH'` or `'centre WxH'`, the config's size), noted once the anchors and size are set, so a place that errored is tried again by the next update; only a change places it again and sets its click area again (`UF:RestorePlateHitTest`).
- **The game's settings** (`cvars.lua`). `UF.NAMEPLATE_CVARS` maps each setting SaftUI sets while its plates are on to `value(config, current)`: `nameplateShowFriendlyPlayers` and `nameplateShowFriendlyNpcs` from Friendly plates (`nameplate.friendly`, on the Friendly nameplates page); `nameplateMinScale`, `nameplateMaxScale` and `nameplateSelectedScale` at 1, so the game scales no plate by distance or for the target (SaftUI's frame covers its plate); and `nameplateSimplifiedTypes` at its version character alone, which simplifies nothing (it's a bit array kept as text: `.agents/clients.md`). `UF:SetNameplateCVar` skips a setting the client lacks, and records the user's value the first time it changes one, per character and outside every profile (`st.config.char.nameplateCVars`). `UF:ApplyNameplateCVars()` sets every one only while SaftUI's driver exists and Nameplates is on, out of combat (`QueueAfterCombat('NameplateCVars')`), then runs `UF:RefreshPlateWidgets()`. `UF:RestoreNameplateCVars()` (the same key) puts each recorded value back and drops it from the record, keeping one the game refuses, so the next time the plates are on it records whatever is set then. Turning Nameplates off puts them back at once (the plates stay up until the reload), on again sets them, and Friendly plates sets them; a profile switch doesn't yet (`docs/followups.md`).
- **The layout** (the defaults). An enemy's plate: the health bar fills the plate, 200 by 20, with the name inside on the left (Max width 150, no level or classification, hostile names colored) and the health inside on the right as a Short value. The castbar hangs 6 under it, 182 by 12, its 12 by 12 icon 6 to its left so the row starts at the bar's left edge, with no time and grey for a cast that can't be interrupted. Up to 6 of the player's debuffs sit 6 above the bar from its left edge, up to 4 buffs the player can purge 6 right of it, the quest icon 6 left of it and the raid mark centred 6 above the debuff row, which leaves the space above the bar's right end to the threat text. A friend's plate (`friendlynameplate.lua`) is a name: its frame 150 by 16 on the plate's centre, Theme None (every unit's frame default, `config/default.lua`, not set in `friendlynameplate.lua`), no health bar or health text, the name centred on the frame (anchored to the frame itself, `element = false`, which the Position editor shows as Unit frame, not to the bar that isn't there), Max width 150, Class color, Color friendly and Color hostile on, no level or classification, and the raid mark 16 square, its bottom 4 above the name's top. Its castbar, aura areas and quest icon are off, set as the enemy's for whoever turns them on, and hang off its hidden health bar, which is still laid out (Shown and enabled). Every size on a plate is an even number of pixels, so centred anchors stay on whole pixels (the half pixels bullet, above).
- **The target's border** (`target.lua`). The target's plate is found by its frame: a plate's frame marks the target when its parent is `C_NamePlate.GetNamePlateForUnit('target')` (`UF:IsPlateTarget`), never by `UnitIsUnit`. The border is drawn on `UF.PlateBorderFrame(frame)`: the health bar's drawn frame while the bar carries it (drawn, and wanted by its config: `UF:ElementWanted`, since a bar its config has off keeps the drawing it had), else the plate frame's while that is drawn, else none, as on a friend's name-only plate. Under Thick and Thin it's a white line through `st:SetBorderColor`, and every other plate gets the theme's own color back. Under Blizzard it's the control `nameplatetarget`'s art (themeart.lua) round what carries the border (the health bar, or the frame) at its offsets, a texture of a frame of SaftUI's two levels over the bar, kept in a weak table (`UF:PlateTargetArt`) and unsnapped. `UF:UpdatePlateTarget(frame)` runs from `'added'`, `'updated'`, `PLAYER_TARGET_CHANGED` (every plate) and `UF:OnColorsChanged('theme')`, and `st:KeepOwnColors` on both candidate borders keeps the color through a theme recolor or redraw, with one function for every frame (`RecolorBorder`, which finds the frame's plate), so keeping it again on each update makes nothing new.
- **Threat** (`threat.lua`). The player's threat on an enemy tints its health bar and shows as a percent above the bar's right end, in a party or raid, and on your own only with Threat when solo (`nameplate.threat_solo`). Threat is enemy-only whatever the settings, and always reads Enemy nameplates' settings (`nameplate.threat_solo`, `nameplate.threat`), whichever page an enemy's plate draws from: with the Enemy page's box checked, an enemy's plate takes everything else from the Friendly page, and the tint goes on that page's health bar (off by default, so only the percent shows). `UF.ThreatState(isTank, status, coTanked)` is the table by role over `UnitThreatSituation('player', unit)`: a tank's 3 good, 2 warning, 0 or 1 bad (good while another of the group's tanks holds the mob), anyone else's 0 good, 1 warning, 2 or 3 bad, and nil nothing. `UF:PlateThreat(frame)` gives nil for a friendly plate, on your own with Threat when solo off, a threat state `C_Secrets.ShouldUnitThreatStateBeSecret` says is secret, or a secret status, and reads the player's role from Blizzard's own `PlayerUtil.IsPlayerEffectivelyTank()`. For a tank who doesn't hold the mob, it reads the group (`party1`-`party4`, or `raid1`-`raid40`) for who does, but only for a mob in combat (`UnitAffectingCombat`; a mob out of combat has no threat list, and a secret answer still reads the group), by each member's threat state on it (2 or 3; a secret state is skipped), stopping at the first: another of the group's tanks (`UF.IsGroupTank`: the tank role, or a tank aura where the client has `UnitHasEffectivelyTankAura`) makes it good, and a member who isn't a tank makes it bad, the mob loose, even when the tank isn't on its threat list. `UF:UpdatePlateThreat(frame)` sets `frame.threatState`, which `elements/health.lua`'s `PostUpdateColor` puts on last each time oUF colors the bar (warning and bad, in the profile's `colors.threat`, the Colors tab's Threat section), and a bar that loses its tint gets one `Health:ForceUpdate()`. The text is the plates-only element `Threat`, enemy-only, with its own tab after Health on the Enemy page only; its constructor sets the text's `config` and `GetConfig` to `nameplate.threat`, so a plate drawing from `friendlynameplate` keeps the Enemy page's. It is: `UnitDetailedThreatSituation`'s scaled percent through `SetFormattedText('%.0f%%', ...)`, a secret one handed to the game as it is, in the tint's color, or Text Normal while good. It's written again only when its state, a non-secret percent or its color changed (a secret percent always is), or forced by `UF:UpdatePlateThreat(frame, true)`, which the `'kind'` and `'updated'` callbacks and `UF:OnColorsChanged('threat')` pass. A mob's threat list update retints its plate, found through `UF:PlateForUnit`; a threat situation update retints every plate for the player and a plate's own for its token; the roster, the roles, the player's spec and form or stance (`UPDATE_SHAPESHIFT_FORM`; a tanking form is a tank aura on Forever) retint every plate; and so do the `'kind'`, `'updated'` and `'removed'` callbacks. Only `nameplateN` tokens are looked for among the plates.
- **Whole pixels** (`pixels.lua`). Each plate's frame is pinned to UIParent's effective scale (`UF:PinPlateScale`: `SetIgnoreParentScale(true)` and `SetScale(UIParent:GetEffectiveScale())`; a secret scale leaves it as it is) on every add, and every plate again on `UI_SCALE_CHANGED` and `DISPLAY_SIZE_CHANGED`, which also set the plates' size again. `UF.RoundLayout(region, recursive)` turns on the game's `SetRoundLayoutToNearestPixel`, and for a texture turns its own snapping off (`SetSnapToPixelGrid(false)`, `SetTexelSnappingBias(0)`); with `recursive` it walks the region's regions and child frames. It reads and sets no size. It runs from SaftUI's frame on the plate after every update of the plate (`'updated'`) and again after a theme change (`UF:OnColorsChanged('theme')`, after the target's border), and skips, with everything under them, SaftUI's own aura containers by identity (`UF.auraContainers`, a weak-keyed set the aura element's constructor fills), forbidden regions, and anything `IsObjectType('AuraContainer')` says is one. It never reaches Blizzard's frames. `elements/auras.lua` rounds what SaftUI makes on a plate's aura buttons, each backdrop and Thick's inner debuff line, where it makes it. Anything made on a plate outside an update must call `UF.RoundLayout` itself. UIParent's scale is SaftUI's from login only: after a UI scale or display change the plates follow UIParent off whole pixels until a /reload (`docs/followups.md`).
- **Themes.** The plates draw as every unit does: the frame None by default (each page's own Theme), its bars as `unitframe` (under Blizzard the bronze box, with health on Blizzard's raid fill and the castbar on its own texture), the cast icon as a `control` (bare under Blizzard) and the aura buttons as `aura`. With the Enemy page's Theme Blizzard and the health bar's also Blizzard (its default, SaftUI's, under the Blizzard theme), health fills the plate and draws None (one box per edge), and the target's border goes on the plate frame's box.

## Micro menu bar

`SaftUI-Minimap/micromenu.lua`'s items (each `AddButton` option set: `art`, `icon`, `micro`) draw their panels as kind `control`, which Thick and Thin draw exactly as `small` and Blizzard leaves clear; under Blizzard the art is the bar's own (`Control('microbar')`, read once a pass), textures of the panel kept in the item's entry (`item.artTexture`, `item.pieces`) and never fields on a Blizzard frame. An item's `art` names its box (`header`, the default for the zone, clock, latency and FPS boxes: Forever's Camelot header button, stretched along the box; `square` (the default), the addon indicator's square, 23 x 22 centred; `tracking`: Forever's tracking button, 23 x 23, whose art has the magnifier drawn in, so the magnifier SaftUI draws on Forever (the item's `icon`) hides under Blizzard), and an atlas is set whole on the texture, centred or stretched along the box, 23 tall for the header; on retail every box is the grey minimap button kit laid by `ThemeArt.LayBorder` (nine pieces, with its Center), which draws no icon of its own, so every item keeps the icon it shows under Thick: on retail that's Blizzard's own tracking button for the search box, since SaftUI makes its magnifier only on Forever. There is no strip on retail. `MicroMenu:GetItemArt(button)` and `MicroMenu:GetStrip()` give the tests what was drawn. **The strip** (Forever only): a frame of SaftUI's, a child of `MicroMenu.Container` at the Container's level, made when it first shows, holding `UI-HUD-ActionBar-Frame` (BORDER, set whole so the engine slices it by the atlas's own slice data) and `UI-HUD-ActionBar-IconFrame-Background` 2 inside it; it runs from the first shown `micro` item's TOPLEFT (-4, 4) to the last one's BOTTOMRIGHT (4, -4) through `st:SafeReposition`, and hides unless SaftUI's look is Blizzard and a micro item is shown. The micro buttons' own holders carry `micro = true`. Blizzard's `MicroMenu.BorderArt` and `BackgroundArt` stay faded and unmoved under every look (`.agents/taint.md`): the strip replaces them.
