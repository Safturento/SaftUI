# Architecture

## Addons and load order

- Every folder `SaftUI-<Name>/` is a separate WoW addon. All of them `## RequiredDeps: SaftUI-Core` and `## Group: SaftUI-Core`.
- **SaftUI-Misc's talent plan** (`SaftUI-Misc/TalentPlan/`, loaded by `TalentPlan\load.xml` after the other Misc files, `options.lua` last) is the module `TalentPlan` (`st:GetModule('TalentPlan')`, WoW Forever only: `TP:GetConfigTable()` is nil on retail and `SetupBlizzard` waits for `Blizzard_PlayerSpells`). Profile key `talentplan` (`enable`, `dim`; `st.defaults.talentplan`, `SaftUI-Misc/config.lua`), and `talentwindow.compact` for the compact window (module `TalentWindow`, `Skinning/blizzard/Blizzard_PlayerSpellsLayout.lua`). The plans are not settings: `st.config.global.talentplan = { nextID, plans = { [classFile] = { [id] = plan } } }` (account wide) and `st.config.char.talentplan = { active = { [specGroup] = id }, collapsed }` (per character), both through the accessors in `store.lua`. `TP:Refresh` is the one place that reads the tree and draws; `TP:UpdateConfig` only queues one. The plan is played against the tree's own rules by `TP.Sim` (`simulate.lua`, pure: `Run`, `CanAdd`, `CanRemove`, `CanMove`, `Check`, `ShowCount`), over the shape `D.Read` reads (`tree.shape`: groups, the budget of 51 points (levels 10 to 60, `M.POINTS`), and every visible node's cost, group, row, gates (5 points a row in its spec, `RowGates`, never the conditions), incoming edges and `plannable`); `TP:Refresh` keeps the run in `view.sim`, `TP:PlanClick` asks `CanAdd` and `CanRemove` before it changes the plan, and a drag in the panel (only while planning: the rows' handles show only then) asks `CanMove` (`TP:DropAllowed`: the drop line shows Danger where it would be refused, and a refused drop changes nothing and prints why), the panel draws a step the rules refuse as blocked, and `/sui tp check` (`TP:RunCheck`) compares the rules with the game's own flags. The talent buttons' look is the module `TalentFaces` (`Skinning/blizzard/Blizzard_TalentFaces.lua`, loaded after `Blizzard_PlayerSpellsSkin.lua`, WoW Forever only): a SaftUI face on each button from its real state, or, while planning, from `TP:PlanDisplay(nodeID)` (given to it by `TF:SetPlanSource` in `TP:OnEnable`, and redrawn by `TF:Queue()` after the plan or planning changes); the faces are in the Skinning look only (or in Blizzard's art while planning under the Blizzard theme). Tests: `tests/misc/talentplan_*_test.lua`, `tests/misc/talent_faces_test.lua`, `tests/misc/talent_window_layout_test.lua`.
- **SaftUI-Tracker** is SaftUI's own objective tracker: module `Tracker` (`st.Tracker`), profile key `tracker` (`st.defaults.tracker`, `SaftUI-Tracker/config.lua`), per-character data in `st.config.char.tracker` (`TR:CharData()`: `zones`, each collapsed zone group's header title (`TR.OTHER_KEY` for Other) to `true`, and `collapsed`, the whole tracker's). One TOC for both clients, with `## OptionalDeps: SaftUI-Misc` (Blizzard's tracker's skin and mover live there). It ships switched on (`tracker.enable = true`; AceDB drops a saved value equal to the default, so a profile that never chose is on, and one that had ticked it on still is), and the switch is read once, at login: `TR:IsOn()` latches on its first call (the switch on and none of `TR.TRACKER_ADDONS`, other tracker addons, loaded), so Misc's code may ask it before `TR:OnEnable` runs and every reader gets one answer all session. `TR:OnEnable` binds the config, then returns while `not TR:IsOn()`, else runs `TR:Build()` once. While off, the addon makes no frame, hook, event, mover or binding change at load or enable. `Bindings.xml` (read by the game, not listed in the TOC) names the nearest quest item key; its strings are in `config.lua`. A profile change or theme change runs `TR:UpdateConfig`, which says in chat, once per value, that a profile's differing switch "changes after a reload". The data layer is pure and made of functions only (nothing at file scope reads the profile, registers an event or makes a frame): `model.lua`'s `TR.Model.Read(show)` reads the game's quest API into `{ quests, popups, counts, zoneNames, focused, arena }` (every API guarded by presence, a secret value counted as missing, a quest with no title skipped), with `TR.Model.Shown`, `Compare`, `Finished` and `ZoneNames`, and `TR.MaxQuests()` (the log's size from `C_QuestLog.GetMaxNumQuestsCanAccept()`, else Forever's constant, else `TR.FALLBACK_MAX_QUESTS`: nothing assumes 35, the item pool is sized by it), and `TR.TitleText`, `TR.QuestLines` and `TR.TimeText` for what a row says; `groups.lua`'s `TR.Groups.Build(quests, settings, zoneNames, collapsed)` makes the zone groups (current zone first, campaigns, the log's header order, Other last under `TR.OTHER_KEY`, one `TR.ALL_KEY` list with Group by zone off), with `IsCurrent` and `Sort`. The window: `layout.lua` has `TR.LAYOUT` (every length the tracker draws with) and the pure `TR.Layout` (`WindowHeight`, `ViewHeight`, `ChildWidth`, `ScrollRange`, `Wheel`); `window.lua`'s `TR:BuildWindow()` (called by `TR:Build`) makes `TR.holder` (the mover's frame, Width by Max height), `TR.window` (`SaftUITracker`, `st:CreateFrame` on UIParent, strata `LOW`, level 10, drawn as a `'panel'` in the page's Theme and Background by `TR:DrawWindow`), `TR.header` (the title, `count`, `collapse` made by `TR:NewChevron`, a one pixel `line` in the drawn theme's border color), `TR.scroll` (`TR.NewScrollFrame`, in the game the bags' `st:CreateScrollFrame`) with child `TR.content`, and `TR.watcher`, whose one `OnUpdate` runs only while a hover rule needs it. Rows put their content in `TR.content` and tell the window its height with `TR:SetContentHeight(h)`, which sizes the window (up to Max height, then the list scrolls, with `st:ScrollBarRoom` kept while it does); `TR:ScrollTo(offset)` and `TR:GetScroll()` move and read the offset (clamped, whole pixels), `TR:SetCollapsed` / `TR:IsCollapsed()` the header-only state (per character, ignored with Header off), `TR:UpdateHeader(model)` the count. A size read back from the game (the bar's room) is rounded, never ceiled. The window is never protected. The window and the list take the mouse wheel only while the list scrolls (`TR.scrollRange > 0`), so the camera still zooms over a tracker that fits; the bar's own wheel, steppers and drag go through the tracker (the bar's `OnMouseWheel` is the window's, `SetPanExtent(40)`, and a guarded `OnVerticalScroll` hook rounds the offset or puts it back while `TR:IsScrollLocked()`). Max height as drawn is `TR:MaxHeight()` (the saved value, no taller than the screen less the edge margins). The module's one `TR:OnColorsChanged` is in `init.lua` and calls each part's own (`TR:ColorWindow()`); later parts add their call there, never a second definition. **The refresh and its stages** (`init.lua`, `rows.lua`): `TR.EVENTS` (the design's list; `UNIT_QUEST_LOG_CHANGED` for the player only, `PLAYER_MONEY` only while a quest needs more money than the player has) are registered on one frame by `TR:Build` and only call `TR:MarkDirty(event)`, which schedules one refresh however many marks come before it, through one throttle for every event: the first mark after a quiet gap refreshes on the next frame (`C_Timer.After(0)`), marks within `TR.REFRESH_GAP` (0.1 s) of the last refresh are coalesced into one at the end of that gap, and a pending refresh is never pushed back (the controller's ruling of 2026-11-14, spec "Settled" 6; `QUEST_DETAIL` and `QUEST_DATA_LOAD_RESULT` joined the list, Settled 7). A quest is scrolled into view only when the game said it was tracked (`QUEST_WATCH_LIST_CHANGED` with `added`, kept in the list `TR.trackedQuests`) or the focus changed, never while the mouse is over the tracker, within `TR.SCROLL_QUIET` (3 s) of the player's own scrolling (real input only: the wheel, and a mouse-down on the bar's thumb, track or steppers, not the bar setting the offset itself after a range change), collapsed or locked; tracks inside one gap are kept in a list (`TR:NoteTracked`, an untrack takes its quest off) and the scroll goes to the last. A collapsed tracker updates its header's count and nothing else (`TR.rowsStale`, drawn once when it opens). `QUEST_DATA_LOAD_RESULT` refreshes only for a quest in `TR.knownIds` (shown, a popup's, or waiting for its title: `model.waiting`). A popup row is keyed by quest ID and kind (`TR:GetPopupRow(id, kind)`), a font change marks through the same throttle. `TR:Refresh()` reads `TR.Model.Read(quests.show)`, then `TR:Redraw()` (also what a zone header's click runs, from the model already read): `TR.Groups.Build` (collapsed zones from `st.config.char.tracker.zones`), `TR:BuildEntries` (popups, zone headers, quests, or the empty line; each entry claims a pooled row, `TR:AcquireRow(kind, key)`), `TR.Layout.Rows` (pure; the real font strings measure through `TR:Measure(row, fs, text, width)`, kept per text and width), `TR:DrawRows`, `TR:SetContentHeight`, a scroll of the focused or a newly tracked quest into view (`TR.Layout.IntoView`), then `RefreshItems`, `UpdateHandover` and `ApplyVisibility` (the probes run on their own events and after a module's layout, not from the refresh), each only once a later task's file defines it. The list's width depends on whether it scrolls (the bar's room), so a layout that guessed wrong runs once more. Every text goes through `TR.SetText(fs, text)` (set only when changed, a secret always), every frame is moved or sized only when its place changed (`LayoutWindow` keys on its inputs), and a refresh that changed nothing sets no text, makes no frame and calls no setter on any widget; an objective's dash is its own font string (`part.dash`, the text after it, `metrics.dash`); a popup row is its label, 2 and its title, at least 22 tall; rows of what went are freed before new ones are taken; a Fonts tab change redraws through `TR:OnFontsChanged` (`if TR.model then TR:MarkDirty('FONTS') end`, run by `st:FontsChanged()`; `tests/tracker/rows_test.lua` measures it). A color change recolors shown rows in place (`TR:ColorRows`, inside the one `OnColorsChanged`): colors are read at draw time, never cached in a way that survives a change. **The tracker's own colors** (`colors.lua`, the Colors tab `TR.ColorsTab()` in `options.lua`): `TR.COLOR_PARTS` (header, current zone, zones, quest titles, objectives, progress bars) are saved as `{ r, g, b }` in `tracker.colors[part]` only once the player picks one; a part with none follows what it did before the tab (`TR.PartFallback`: Text > Normal or Muted, the bar `TR.BAR_COLOR`, Blizzard's progress blue), so a Colors page change still reaches it. `TR.PartColor(key)` is the one reader (rows.lua's `StateColor` takes the parts as states `title`, `objective`, `zone`, `current_zone`; a line the model calls `normal` paints as `objective`; the header's title and every bar fill, kept in `TR.barFills`, read it too). A pick or reset goes through `TR:SetPartColor(key, r, g, b | nil)`, which only paints (`TR:PaintColors`: `ColorWindow` and `ColorRows`) and treats a color equal to the part's fallback, to the byte, as a clear (the picker commits each drag step and its Cancel sets the opening color back); bar fills also repaint on every draw, so a profile switch reaches them; each row's hand default differs while a color is saved and resets by clearing it. Completed, Failed and Color by difficulty still win over the title and objective colors. The focused quest's accent bar is the window's own texture (`TR.focusBar`), not a row's, because the list's scroll frame clips what is left of its rows. **Blizzard's tracker** (`blizzard.lua`, run by `TR:Build` after the window): `TR:OwnsBlizzard()` is `TR:IsOn()` and Blizzard's `ObjectiveTrackerFrame` existing (Misc's tracker mover asks it at call time to stand down); `TR:SetupBlizzard()` (once, through `st:OnBlizzardAddon` when `Blizzard_ObjectiveTracker` isn't loaded yet) post-hooks the tracker's `SetPoint`, `ClearAllPoints` and `UpdateHeight` (each in `xpcall`, where the game has the function), hides its Edit Mode box and calls `TR:PlaceBlizzard('concealed')`; `TR:BlizzardTarget(where)` gives `parent, point, x, y` (`'place'`: its top right on the window's, the holder's top right for Grow down and the window's for Grow up; `'concealed'`: the y of the spot the mode reveals at and an x of `TR.BLIZZARD_OFF` past UIParent's left); `TR:PlaceBlizzard(where)` sets the clamp (off concealed, on otherwise) and its one anchor with the three C methods, skipping what is already so, and keeps `TR.blizzardWhere`. `TR:ApplyHolder` and `TR:UpdateConfig` place it again (a moved holder, a changed Grow). What it may and may not call is `.agents/taint.md` rule 5. The first position (`FirstPosition`, `window.lua`, for a profile with no tracker position) is the skin's saved position when Misc's mover has one (a top point copied, another converted to the TOPRIGHT form from the skin's width and `OTP.HOLDER_HEIGHT`), else where Blizzard's Edit Mode had the tracker (`EditModeSpot`: `C_EditMode.GetLayouts()` only, never a field of Blizzard's tracker frame; a preset layout or a tracker in its default position gives Blizzard's default spot; a top point is copied as it is, any other point is converted to TOPRIGHT from the width (Misc's skin's, else 260) and Edit Mode's own Height setting from the same layout; an anchor to a frame other than UIParent gives the default), else Blizzard's default. If Blizzard's manager hasn't applied the layouts yet (`EditModeManagerFrame.layoutInfo` is nil: a read only) the default is written and `EDIT_MODE_LAYOUTS_UPDATED` is watched on the tracker's own small frame (`TR.layoutsFrame`, not `TR.EVENTS`): the first time it fires the position moves to Edit Mode's spot, only while `config.position` is still the very table written with its values unchanged, then the watch ends. **The handover** (`probes.lua`, `handover.lua`, `TR:WatchModules` in `blizzard.lua`): `TR:Build` starts `TR.handoverState` at `'own'` (a `/reload` always does), builds the probe tables (`TR:BuildProbes`) and, once Blizzard's tracker is set up, hooks each module's `Update` and asks for a first probe pass (`TR:RunProbes`, which coalesces any number of asks into one pass, `TR:ProbePass`, on the next frame and no sooner than `TR.REFRESH_GAP` after the last). A pass reads each section's probe (`TR.Probes`) and the module signal, keeps when each last had content and asks for itself again when a hold (`TR.HOLD`, 2 s) ends, and ends in `TR:UpdateHandover()`, which also runs after every refresh (`TR:RunStages`) and every `TR:UpdateConfig`. `TR.Handover.Next` (pure) gives the new state and its actions, which `TR:UpdateHandover` runs through `TR:PlaceBlizzard`, the window (`TR:ApplyWindowShown`, hidden while the state is `'blizzard'`) and the item buttons (`TR:RefreshItems`, whose `Wanted` hands out none while the state is `'blizzard'`): the parts SaftUI's tracker gives up are derived from the state, so a state that returns to `'own'` can never leave one hidden. Blizzard's tracker is placed at `'concealed'`, `'place'` or `'beside'` for the state (`own`, `blizzard`, `both`), at the y of SaftUI's spot kept `TR.BLIZZARD_FLOOR` above the screen's bottom, and the beside spot is `TR.Layout.BesideSpot` past `TR:ColumnWidth()`.
  - **Quest item buttons** (`SaftUI-Tracker/items.lua`, the rows' item slot in `rows.lua`, `TR:IsScrollLocked` and `window.barLock` in `window.lua`; the rules are `.agents/taint.md` rule 15): `TR:BuildItems` (with the window) makes the pool's tables and a plain watcher frame, and `TR:RefreshItems` (the first of `TR:RunStages`, followed by `TR:RefreshNearest`, the nearest quest item button's own pass in `nearest.lua`, which `TR:BuildNearest` sets up with the tracker: its holder, mover and watcher; `.agents/taint.md` rule 16) does the rest, and `TR:PlaceItems` (a placement-only pass: no item told, no style) follows the rows after a scroll, a collapse, a hide, a screen size change (the watcher frame fills UIParent: `OnSizeChanged`) and an edit mode drag (a post-hook on the holder's `SetPoint`, which the mover sets every frame): out of combat it makes the layer `SaftUITrackerItems` (`TR:BuildItemLayer`, a secure frame on UIParent under a visibility driver) and a `SecureActionButtonTemplate` button per quest drawn in a row with an item (up to `TR.ItemPoolMax()`), tells each its item (`TR:SetButtonItem` through `TR.ItemAttributes`, the P3 seam) and places it at its row's top right by offsets from UIParent; in combat it only dims (`TR.Items.CombatAlpha`) and draws, and queues `'tracker_items'`. A quest row's item slot (`row.slot`, `TR:SetSlotMode`) is hidden under a button, greyed in combat with no button, a plain icon with Item buttons Off or no button to be had. `TR:IsScrollLocked` holds the list still in combat while a row button shows. Beside the tracker (`placement` `'beside'`) the same buttons sit in a numbered column 4 outside the window on the side nearer the screen's middle (`TR.Items.Side`, `TR.Items.Column`, pure; `TR:ColumnWidth()` is its width for the beside spot), each level with its quest's title, 2 under the one above when they would overlap; `Wanted` takes the quests the list draws, in list order, and `PlaceColumn` places them (the rows' entries say `item = 'beside'`, leaving the title room for the number: `metrics.tagRoom`, `TR:TagRoom`); a button's number is `button.numberText` (Pixel font, bottom left) and its row's `row.tag` (accent, at the title's end, `TR:SetTag`), both only set out of combat except the tag's text following the button. The Items tab is `tracker.items` (`TR.ItemsTab`): `placement` (In the row, Beside the tracker, Off), `size`, `cooldown`, `count`, `range`.
  - **Clicks, menu, tooltips** (`SaftUI-Tracker/clicks.lua`, called from the rows' scripts in `rows.lua`, so nothing runs with the switch off): `TR.ClickAction(quest, button, state)` is the pure choice (`link`, `untrack`, `track`, `complete`, `map`, `focus`, `menu`), `TR:OnQuestClick` reads the state and does it, `TR.MenuEntries` and `TR:OpenMenu` are Blizzard's menu through `MenuUtil`, `TR:ShowRowTooltip` the quest link, party progress and a click hint. A quest row's icon is its own button (focus toggle), a zone header's left click collapses it. `TR.ShowOnMapAllowed()` is the P5 seam; the combat rules are `.agents/taint.md` rule 14. The Quests tab's `tooltips` and `left_click` (`map` or `focus`) are in `tracker.quests`.
  - **Fading and hiding** (`SaftUI-Tracker/visibility.lua`; `tracker.visibility`, the Visibility tab, `TR.VisibilityTab`): six triggers (In combat, Out of combat, Mouse off, In instances, Boss fights, Mythic+), each Show, Fade or Hide (Mouse off Show or Fade; Mythic+ only where `C_ChallengeMode.IsChallengeModeActive` exists), all Show by default. `TR.Visibility` is pure: `Applies(hovered)` reads the game (`InCombatLockdown` or the combat events' word `TR.combatNow`, `IsInInstance`, `C_InstanceEncounter.IsEncounterInProgress` (else the deprecated global) or the encounter events' word `TR.encounterNow`, `C_ChallengeMode`), `Resolve(applies, settings, hovered)` gives `{ window, alpha, items, itemAlpha, hideItemsDirectly, background }` (the strongest wins, Hide over Fade over Show; Show fully under the mouse turns Fade into Show, never Hide; Hide quest items with the tracker off keeps the buttons at full alpha, on fades them never under `TR.BUTTON_MIN_ALPHA`) and `Driver(settings)` builds the item layer's state driver (`[petbattle] hide`, then `[combat]`, `[nocombat]` and `[@boss1,exists]` hide for the triggers set to Hide while the buttons go with the tracker). `TR:ApplyVisibility()` is the one place that decides: it runs after every refresh (`TR:RunStages`), on the events (`TR.VISIBILITY_EVENTS`, `TR:OnVisibilityEvent`, `PLAYER_REGEN_*`, `PLAYER_ENTERING_WORLD`), on a settings change and from `TR:StepFade` when the mouse comes or goes. The window shows or hides in `TR:ApplyWindowShown` (with the handover and an empty list: `TR.visHidden`), a window faded to alpha 0 takes no mouse (`TR:SetInput`: rows, header, chevrons, the wheel, the scroll lock's strip; new rows too), the panel is the window's backdrop frame's alpha, and the fade is one `OnUpdate` (`TR.fader`) that runs only while an alpha moves (`TR.FADE_TIME`, 0.2 s from faded to full) or the mouse is watched. The quest item buttons: `TR:SetItemAlpha` wears the fade (`TR.itemFade`, `button.fades`) under the 25% floor, the layer's driver is set by `TR:ApplyItemDriver` out of combat (queued as `'tracker_items'`), and Hide for In instances, Mythic+ and Boss fights is direct (`TR.itemsHidden`, which `Wanted` reads like the handover's state), out of combat only. With the buttons staying and the window hidden by a trigger the list keeps being laid out, so out of combat they are assigned and placed by their rows as usual (`RowLaidOut`); in combat they stay put and dim as always. The nearest button is never touched: its driver frame has `TR.NearestDriver()`, the pet battle's condition alone. During a handover `TR:PlaceBlizzard` conceals Blizzard's tracker while `TR.visHidden`, and `TR:SetBlizzardAlpha` holds its faded alpha (the C `SetAlpha`, put back after Blizzard's own by a post-hook), the hover read by `TR:IsTrackerHovered` (the window, the column, and while Blizzard's tracker shows the holder plus the rectangle SaftUI placed it in, cached by `PlaceBlizzard`). The rules and the in-game checks are `.agents/taint.md` rule 17.
- **TOCs:** Core and Unitframes have per-client TOCs (`*_Forever.toc` = `## Interface: 16001`, `*_Mainline.toc` = `120000`). The other addons use one TOC listing both (`## Interface: 120000, 16001`). When you add a file, add it to **every** TOC of that addon (and to the folder's `load.xml` where one is used, e.g. `SaftUI-Core/Config/load.xml`, `SaftUI-Core/EditMode/load.xml`, `SaftUI-Misc/Skinning/load.xml`).
- Load order matters: Core loads first, then each module addon in its TOC order. Defaults (`st.defaults.*`) must be defined at file load, before Core creates the AceDB (see below).
- **Libraries:** Core bundles LibStub, CallbackHandler-1.0, Ace3 and the shared media libraries. An addon that needs more bundles them in its own `Libraries/` and lists them first in its TOC, without a second copy of LibStub or CallbackHandler: Unitframes has oUF, ActionBars has LibActionButton-1.0 and LibButtonGlow-1.0 (sources and versions in `SaftUI-ActionBars/Libraries/README.md`).

## The `st` object and modules

- `SaftUI-Core/init.lua` creates the addon: `SaftUI = AceAddon:NewAddon(st, 'SaftUI-Core', 'AceEvent-3.0', 'AceHook-3.0')`. Every file starts with `local st = SaftUI`.
- A module is `local M = st:NewModule('Name')` (AceAddon module, with AceEvent + AceHook mixed in). Module names are the keys used everywhere else: `st.modules[name]`, the `/sui` tree, and edit mode `configPath`s. Current modules include ActionBars, Auras, Chat, Colors, Config, EditMode, Experience, Fonts, General, Inventory, Loot, MicroMenu, Minimap, Movable, ObjectiveTracker, Skinning, SwingTimer, TalentPlan, TalentWindow, Theme, Tooltip, TotemBar, Tracker, Unitframes, Utilities.
- Lifecycle: `OnInitialize` (rarely used), `OnEnable` (build frames, register movers, hook Blizzard), `UpdateConfig` (re-apply everything from the profile; see below), `GetConfigTable` (the module's `/sui` page; its top-level table's `category`, Frames, Combat or Info, groups it in the window's sidebar). Core's General, Fonts, Colors, Theme and EditMode modules give the tabs of the Global settings page instead, in the order of `GLOBAL_TABS` in `SaftUI-Core/Config/config.lua` (see `.agents/edit-mode.md`). A `/sui <command>` with its own sidebar button is `st.Config:AddCommand(command, label, func, icon)`, whose optional icon is the button the collapsed sidebar's footer shows (see `.agents/edit-mode.md`).
- **A color change** (`SaftUI-Core/Media/colors.lua`). A Colors row's set and reset, and the Accent row's, say `st:ColorChanged(group, key)` (key nil for `accent` and `renown`), never `st:ColorsChanged`. While SaftUI's color picker is open that is an **edit** (the picker and the Accent row's dots menu each hold it, `st:HoldColorEdit()` as they open and `st:ReleaseColorEdit()` as they close, after Cancel's restore: it begins with the first and ends when the last lets go, and only an edit a holder began is ended that way; `st:BeginColorEdit()` and `st:EndColorEdit()` are the raw begin and end; `st:InColorEdit()`): the change only marks the color, and one **pass** per marked color runs on the next frame from `CO.ticker`'s `OnUpdate`, however many changes came; outside an edit it passes at once. A pass runs the color's followers, its group's followers, then every module's `OnColorsChanged(group, key)` (one per module: SaftUI-Loot's, in `init.lua`, hands it to the feed, the roll bars and the loot window's skin), each in `xpcall`. `key` is the color that changed; **nil means any color of the group may have**, so a handler that ignores the key does what it did before. `st:ColorsChanged(group)` is the **whole pass**: every follower of the group with key nil, then each module's handler with no key. - **A held roll** (`SaftUI-Loot/rollinfo.lua`, `roll.lua`: `LT:HoldRoll`). After you choose on a roll Blizzard takes its bar away and SaftUI shows a bar of its own in its place. On a plain click (no confirmation) the client cancels the roll *inside* `RollOnLoot`: `CANCEL_LOOT_ROLL` is synchronous, so Blizzard's handler hides the frame and `OnBarHide` runs before `RollOnLoot` returns, and the post-hook on `RollOnLoot` would find no bar. So the choice is known before the call: a native `PreClick` hook on each roll button notes it as pending (roll ID, the type from the button's ID, the time left read then), `PostClick` clears it, and `OnBarHide` holds the roll from the bar's state at that hide, with `skin.shown` and the stack slot intact (a waiting roll may take the frame right after). The `RollOnLoot` post-hook still notes a choice whose bar stays up (a bind on pickup confirmation, a Need's dice animation), using the pending click's time, read before the call. A direct `RollOnLoot` call by an addon with no confirmation (no PreClick) is held too: `OnBarHide` keeps a snapshot (what the bar showed, its stack index, the timer) for the rest of the frame, and the post-hook holds from it if it names that roll. `/sui debug` prints `choice pending:` at PreClick, then `bar hid:`, then `held roll`. A held roll finishes (`LT:FinishHeldRoll`: 3 seconds locked, a half second fade, then released) on the first of three signals: its loot history drop resolves (`LT:UpdateRollBars`), chat's roll result line names its item (`LT:OnRollResultMessage` on `CHAT_MSG_LOOT`, from its own frame in `LT:InitializeRollFrame` since the feed owns the module's handler; the `LOOT_ROLL_WON`, `LOOT_ROLL_YOU_WON`, `LOOT_ROLL_ALL_PASSED` and `_NO_SPAM_` format strings turned into whole-line patterns; the oldest held copy of the item whose drop isn't still open; a line owed to a copy its drop already finished is used up on nothing, and a line that finished nothing is kept 10 seconds for a roll held after it, through `LT:OnRollHeld` at the end of `LT:HoldRoll`, as when the roll ends during a main spec Need's dice animation), or its time runs out. The chat line is what ends a roll the history never matched.

Use a Lucide icon where one fits a hand-drawn glyph. Lucide's ISC license is `Media/Textures/LUCIDE-LICENSE.txt`.
- Core helpers live in `SaftUI-Core/api.lua`. The ones you'll use most:
  - pixels: `st:GetPixelSize(frame)` (one pixel in the frame's units), `st:RoundToPixel(value, frame, minPixels)` (the nearest whole pixel; with `minPixels`, any value that isn't zero but is under that many pixels is that many pixels, its sign kept), `st:FloorToPixel` and `st:CeilToPixel` (the whole pixel below or above; a value within 1e-6 of a pixel stays on it), `st:EvenPixels` (the nearest whole pixel, one more away from zero when that count is odd) and `st:GetLineSize(frame)` (`st.lineWeight` pixels, never trimmed). All trimmed to 1e-4 but `GetLineSize`. `SaftUI-Core/uiscale.lua` is the scale model: `st.UIScale.Resolve(choice, screen, gameScale)` works out k (how many physical pixels one design pixel takes), UIParent's scale and the tokens from the screen and the player's choice, purely; `UIScale:SetTokens()` reads `st.pixel` (one pixel in UIParent's units), `st.lineWeight` (a line's whole pixels) and `st.line` (a line in UIParent's units) back from UIParent, so they are what is drawn, and `UIScale:Start()` (in `init.lua`'s `OnEnable`) sets UIParent's scale from the saved choice and `UIScale:Check()` sets it again after every change ("The UI scale", below). At k 1 (a 1440p screen, or pixel for pixel) every token is 1 and every helper gives today's whole number. The game hands a scale back in single precision (768 / 1440 as 0.53333336, a pixel of 0.99999995), so `st:GetPixelSize` takes a pixel whose k (1 / pixel) is within 1e-6, relative, of a whole number as exactly 1 / that number: `st.pixel`, `st.lineWeight` and `st.line` are exactly `1 1 1` at k 1 in game, and a line built from them carries no noise. `UIScale.ReadScreen` (so `Start`) needs both a width and a height, as the model's units wide come from the width; `GetPixelSize` needs only the height.
  - position: `st:DefaultTrackerPosition()` (Blizzard's objective tracker's default spot as a saved position, a fresh table on every call; Misc's tracker mover and SaftUI-Tracker's first position both start from it), `st:CornerOffset(frame, parent, point, screenX, screenY)` (the offsets that put `frame`'s `point` at a screen spot, anchored by `point` to `parent`'s `point`: the screen point less the parent's over the frame's effective scale, through `st:RoundToPixel`; nil for a secret, missing or zero value; Misc's tracker mover and SaftUI-Tracker place Blizzard's tracker with it), `st:UnpackPoint`, `st:PlaceAtPosition` (clear and set a frame from a saved position, the offsets rounded to whole pixels of the frame, the save never written; see `.agents/edit-mode.md`), `st:ResolveFrame`, `st:ValidateAnchor`, `st:RoundToPixel`, `st:GetPixelSize`
  - **Half pixels from centred anchors.** SaftUI's scale makes one physical pixel `st.pixel` units (one unit at k 1), and `st:RoundToPixel` keeps sizes and offsets to whole pixels. But a frame anchored by its centre on an axis (TOP/BOTTOM centre it across, LEFT/RIGHT up and down, CENTER both) that's an odd number of pixels long on that axis has its edges half a pixel off the grid. So do its children. The game then rounds each child separately, and children either side of the centre round in opposite directions. Symptom: one gap in a row of buttons is a pixel short, right at the middle (a 12-button bar at 3px spacing is 573px wide). Fix: round the frame up to an even pixel length on each centred axis, so its edges and its centre stay on whole pixels and frames anchored to it line up too. `EvenIfCentred` in `SaftUI-ActionBars/bars.lua` does this, through `AB:PlaceFrame`, which sizes and places both the bars and the extra buttons' holders (`extras.lua`). `st:EvenPixels` (`api.lua`) is that rounding for any addon, rounding the count away from zero when odd; `EvenIfCentred` and the totem bar's `EvenPixels` move onto it in a later phase (they return an even-count length unrounded, so the move changes non-whole inputs). Where the anchor can change without SaftUI's sizing code seeing it, round up on both axes whatever it is. The totem bar (`SaftUI-Misc/totemlayout.lua`, `EvenPixels`) is always sized even, with the spare pixel as empty bar at the right and the top: on a shaman SaftUI places it from its holder, whose Position can be anchored by any point and is changed by drags, and on other classes Blizzard's Edit Mode places it.
  - combat-safe moves: `st:CanMoveNow`, `st:SafeReposition`, `st:QueueAfterCombat`, `st:GetPoints`/`st:RestorePoints`
  - binding keys: `st:ShortBindingKey(key)` (a key in a few characters: `SHIFT-BUTTON4` is `SM4`), which the action bars' hotkeys and the tracker's nearest button call
  - waiting for a Blizzard addon: `st:OnBlizzardAddon(name, fn)` runs `fn` at once if `C_AddOns.IsAddOnLoaded(name)`, else once on that addon's `ADDON_LOADED`, through one shared event frame (a wait made inside a waiting `fn` is kept; an error in a `fn` run from the event goes to the error handler and the others still run; a `fn` run at once raises into its caller). Use it instead of a module's own `ADDON_LOADED` method with `RegisterEvent`/`UnregisterEvent`. A site that already tests for its frame (`if SomeFrame then Setup() else st:OnBlizzardAddon('Blizzard_X', Setup) end`) keeps that test in front, and a guard such as `C_AddOns.DoesAddOnExist` goes before the wait. It is for one named Blizzard addon; a wait on any addon or on another author's addon stays a handler of its own
  - moving Blizzard frames whose methods are Lua overrides: `st:SetPointDirect`, `st:ClearAllPointsDirect`, `st:SetSizeDirect`
  - taking over a Blizzard Edit Mode frame: `st:PlaceHolder` (a holder of SaftUI's, from the profile), `st:HoldFrame` (the Blizzard frame over it), `st:KeepHolderInScreenMargin` (the holder no nearer the screen's edges than the frame's own clamp lets the frame go, where that clamp would hold back the frame: chat, the swing timers, the tooltip) and `st:HideEditModeSelection` (its Edit Mode box); see `.agents/edit-mode.md`
- Styling: `st:SetBackdrop`, `st:SetTemplate`, `st:SetBackdropIn` (`theme.lua`, below), `st:CreateFrame` (`panels.lua`), `st.OutlineFlag(outline)` (`Media/fonts.lua`; the font flag for a saved outline key, `'NONE'` giving `''`, so pass it to `SetFont` and never the raw key), `st.Clamp(value, low, high)` (`utilities.lua`; floors, nil is `low`), `st:CreateButton`/`st:SkinButton` (`Widgets/`). Colors other than the theme's live in `st.config.profile.colors`, and are read through `st:Color(group, key)` and `st:ColorRGBA(group, key, strength)` (`Media/colors.lua`), which read the active profile at call time, fall back to `st.defaults`, and error (`SaftUI: no color <group>.<key>`) on a key with no default, so a renamed or retired key fails where it is read; Every Text, Buttons, Roles, Factions and Loot read, and every read of the accent, goes through them: `tests/core/color_reads_test.lua` scans every loaded file for a retired key (the six Text hues, `text.white` to `cyan`, `button.red`, and Buttons > Normal, Hover, Pushed and Checked among them), a group alias of one, a Buttons read through `st:Color` (rule F: it would leave the opacity out), a literal key with no default, a retired wrapper by its hue name (`Blue`, `LinkBlue`, `OWN_TEXT`, `Grey`, `GreyRGB`, `DIFF_COLOR`) or a retired constant (`HOVER_TINT`, `TINT_ROW`, `TINT_OBJECT`, `HOVER_ALPHA`, `PUSHED_ALPHA`, `HoverEdge`) or the tip line's old field (`red = true`), and for a direct read of `colors.text`, `colors.roles`, `colors.factions`, `colors.loot`, `colors.button`, `Colors().text` and the like, in a one-line alias (`local c = …colors; c.text`), as `['colors']['text']` or in `rawget(Colors(), …)`, or `theme.accent` (rule D; `Media/colors.lua` is the one exempt file). Groups named for a game concept (class, reaction, power, item quality, status, threat, objectives) keep their own reads. **Buttons holds Danger alone.** Every interaction state (a button's, a check box's, a scroll bar thumb's, a resize corner's, a slot's, a radio pick's, a micro button's, an action button's) is the Accent's, derived by rule and drawn by the states helpers (below), never a Buttons color; a close button's hover is Text > Muted and Danger, drawn by the file-level `LookClose(close)` from the button's own `hovered` and `blizzard` fields. **Buttons' opacity is drawn:** a Buttons color is read as `st:ColorRGBA('button', 'danger', strength)`, whose alpha is the reader's own strength times the color's opacity (a color with no `a` is fully opaque), so at the default (100%) every reader draws the alpha it always drew and at 50% half of it. The strengths: the action bar and totem button flash 0.4, and the bank's unbought slot 1 on the vertex (its region's own 0.3 is kept). The accessor returns four numbers and allocates nothing, so a reader on a hot path stays cheap. Core's state readers follow a pick at once through their states records (`st:FollowColor(rec, 'accent', ...)`); `st:KeepOwnColors`' list is unchanged. `st:IsBlizzardLook` builds no look table, so a pass may ask it, and so may `st:ThemeBorderColor(theme)` (the border color a Theme override draws, the profile's theme's for None: the two trackers' header lines). A bare check box (the bags' currency veil and the combined bank's eye) is a `'box'` with its hover Layer only: its caller restyles its checked texture, which no pass repaints. Text > Muted is `OB.Muted()` in the options kit (`r, g, b`, exported as `S.Muted`), `D.Muted()` in the bags' `dragparts.lua`, `MutedRGB()` in the RestedXP skin, and the diff icon draws it at `OB.DIFF_STRENGTH` (1); SaftUI's tracker's paint state for it is `'muted'`. Text's other rows are `strong` (plain item levels and counts, the character frame's item levels, the bank price you can afford, the share line under the mouse, loot roll timers over a minute, the tracker's progress percent, its paint state `'strong'`, and its chevron under the mouse), `danger` (errors and refusals, the chat's Error prefix and DEBUG label, urgency, remove icons and the close button's edge and cross under the mouse, hostile names, a much higher level, a durability under 20%), `warning`, `caution`, `success` and `shared`; Buttons > Danger is `st:ColorRGBA('button', 'danger', strength)` (locked bank slots at 1, the flash on an action bar or totem button at 0.4). A tip line (`W.ShowTip`) in Danger is `{ text = ..., danger = true }`. The accent is read as `st:Color('accent')`, or `OB.Accent()` in the options kit (`r, g, b`), and the own marks are the accent at `OB.OWN_STRENGTH` (1). Blue is not a color on the Colors tab: a profile's saved Buttons > Blue becomes its accent at migration step 2 (`st:MigrateColors`, `CO.MIGRATION_STEPS[2]`, which also retires Text > Blue, whose own saved value went to Tank and Alliance at step 1, and Buttons > Green). The chat prefix (`st:Print`, `st:Error`) is the accent's hex at print time, `00adf0` until the defaults exist, and `st:Error`'s word Error and `st:Debug`'s DEBUG are Text > Danger (`dc6464` until the defaults exist): the print reads the accessor inside a `pcall`, so a load-time print needs no direct read of a default.

## Themes

SaftUI draws its frames in one theme, Thick, Thin or Blizzard, set on Global settings' Theme tab, which any module can override. The design is `docs/superpowers/specs/2026-11-10-saftui-themes-design.md`, and the Blizzard theme's `docs/superpowers/specs/2026-11-10-saftui-blizzard-theme-design.md`. Blizzard draws each kind of frame in Blizzard's own art, on SaftUI's own frames: the engine resolves it, holds its art's tables and draws its art (`SaftUI-Core/themeart_data.lua` and `themeart.lua`). The Theme tab and every module's override offer it, and no default is Blizzard.

- **The profile.** `st.config.profile.theme = { name, transparent, opacity, optionsbackground, accent }` (the accent, `CreateColor(0, 0.68, 0.94)`, is one color for every theme; `thick`, see-through at 0.9 by default, `optionsbackground` `'theme'`; the Theme tab's Background color shows and sets the pair as its alpha: 100% when `transparent` is off, `opacity` when on). A `name` this version doesn't know (a later version's theme, in a profile opened by an older build) reads as Thick wherever it's read (`st:ResolveTheme`, and the Theme tab's rows), and stays saved until the user picks a theme. Each theme keeps its own colors, arrays in `st.config.profile.templates.thick`, `.thin` and `.blizzard` (`bordercolor`, `altbordercolor`, `backdropcolor`, and Blizzard's `windowcolor`, the fill of its windows; Thick's and Thin's windows take their `backdropcolor`; Blizzard's two fills both default to its dark grey, and can be set apart); `templates.close` is the close button's red. The key is still `templates`: saved variables may keep the word, only what the user sees changes.
- **A module's override** is a pair of config keys, `theme` (`'theme'`, `'thick'`, `'thin'`, `'blizzard'` or `'none'`) and `background` (`'theme'`, `'solid'` or `'transparent'`); `'theme'` follows SaftUI's. SaftUI's own config windows (the `/sui` window, edit mode's bar, floating window and History list, the small dialogs) are drawn with the Background `'options'`, which is not a choice but resolves (in `st:ResolveTheme`) to Global settings > Theme > Options windows (`theme.optionsbackground`: `'theme'` by default, which follows the theme's Background, or `'solid'` or `'transparent'`); what opens over content (lists, item menus, the search panel, the color picker) is drawn `'solid'`. The Bags have a second pair for their item and currency slots, `buttontheme` and `buttonbackground`, and the unit frames one per unit and element. Core's `buttons` and `panels` have the pair with no option, following the theme. The options come from `generators.theme` and `generators.background` (`.agents/edit-mode.md`), and a change re-runs the module's `UpdateConfig`, which draws with the new pair.
- **The engine** is `SaftUI-Core/theme.lua`:
  - `st:ResolveTheme(theme, background, kind)` turns a pair into the look a frame is drawn with as kind (`{ name, lines, inset, alpha, colors, kind }`, or nil for None; `lines` is below); a Transparent background uses the profile's Opacity even while the toggle is off. `st:ThemeInset(theme, background, kind)` is how far in its border reaches, with the kind required as a draw call's is (an error unless the Theme is None): where content sits, for layouts that used to read `frame.thick`. `st:DrawnInset(frame)` and `st:DrawnKind(frame)` give the inset and kind a frame was last drawn at (a drawn frame, or the owner of a backdrop the engine drew; 0 for None, nil for never drawn), which `st:CalculateSpacing` reads. By the same lookup, `st:DrawnTheme(frame)` is the theme it was last drawn in (nil for None) and `st:DrawnFrame(frame)` the frame its look is on (itself, or its backdrop): a window's close button sits in the metal's socket by them (`st:CloseButtonInSocket`, `panels.lua`), and its header in the metal's title bar (`st:HeaderInTitleBar`: the title, the header's buttons and the window's content, placed under the header, move up with it; see `.agents/edit-mode.md`, the close button). The inset is 2 lines for Thick and 1 for Thin whatever the kind, 0 for None, and the kind's own under Blizzard, in whole pixels (below). With no kind, `st:ResolveTheme` gives a Blizzard look no inset. `st:IsBlizzardLook(theme, background)` says whether a pair draws in Blizzard's art, for controls that show that art themselves.
  - `SaftUI-Core/themeart_data.lua` (loaded right after `theme.lua`; it makes `st.ThemeArt` and holds the tables and the `Atlas()` helpers that build them) and `SaftUI-Core/themeart.lua` (loaded next, with the accessors and the drawing) hold the Blizzard theme's tables: `KINDS` (each kind's inset per client, its art and its fill) and `ART` (the box, the character frame's metal, the action and item buttons', the aura's and the close button's art, and every control's, among them the unit frame bars' fills, the resize grip, `/sui`'s size arrows (`sizebutton`: Blizzard's `MaximizeMinimizeButtonFrameTemplate` art, `RedButton-Expand` for grow and `RedButton-Condense` for shrink with their `-Pressed` and `-Disabled` and the additive `RedButton-Highlight`, 24 square, every atlas on both clients and marked for both, drawn by `S.LookSizeButton` in `SaftUI-Core/Config/optionssizes.lua` as textures of the arrow's own), the nameplate target's, `nameplatetarget`: Forever's `UI-HUD-CoolDownManager-Selected-yellow` and retail's `UI-HUD-Nameplates-Selected`, each marked for its client, with the offsets it sits at round the health bar). The accessors read them for the client at call time (`ThemeArt.Client()`, `'forever'` or `'live'`): `Inset`, `Top` (how far the art reaches down from the drawn frame's top: a window's title bar), `TitleHeight`, `TitleStrip` (the strip of the title bar a window's header sits in, 20 on both clients, its bottom on the window's top), `MetalAbove` (how far the metal's art reaches above its drawn frame, 16), `MetalReach` (its reach past the drawn frame on the left, right, top and bottom: 8, 2, 16, 8 on Forever and 8, 4, 16, 3 on retail, which `/sui`'s window gives `st:KeepInScreenMargin` as its `reach`), `Close`, `State`, `Control` and `ClassPower`. It also draws a Blizzard look for `theme.lua` (`ThemeArt.Paint`, `ThemeArt.Color`, `ThemeArt.Clear`): textures made once per drawn frame and kept in its weak tables (`ThemeArt.Get`). A border's pieces are on the drawn frame. A button's ring lies over the icon's edge: on a button of SaftUI's (`st:SetBackdrop`) it's a texture of the button's own, in ARTWORK below 0 (over an icon in BACKGROUND or BORDER, under its texts and cooldown), and otherwise, or on a frame marked with `st:MarkForeign` (someone else's, still drawn with `st:SetBackdrop`), it's on a frame of SaftUI's over the backdrop. Under Blizzard a backdrop has a fill and no edge (a small frame keeps one line), a window's backdrop reaches its title bar above it, and `header`, `close` and `control` are cleared; Thick and Thin hide the art. An art name is an atlas unless it's a file under `Interface\` (the resize grip's three files, so it isn't among the atlases). Each atlas is marked as the tables are built, `Atlas(name)` for one both clients have and `Atlas(name, client)` for one only that client has (`'forever'` or `'live'`): Forever's Camelot minimap art (`ui-hud-minimap-header-button`, which the box is cut from) is Forever's only and named only in Forever's art. `st:ThemeAtlases()` gives `{ [name] = true | 'forever' | 'live' }`, and `tests/core/theme_blizzard_test.lua` checks each atlas exists on the clients it's marked for. **Cut art.** Forever's box doesn't set an atlas on its textures: `ThemeArt.Cut(texture, atlas, rect)` reads the atlas's file and its coordinates from `C_Texture.GetAtlasInfo` (on Forever the Camelot member's) and sets the texture coordinates of `rect` (`{ x0, x1, y0, y1 }`, exclusive ends, in the atlas's own pixels) within the member, hiding the texture and returning false when the client gives no file, no texture coordinates or no size; a cut's pieces are anchored corners of `size` and stretched edges (`LayCut`), with no size read back from a frame. The unit frame's box is the one box every `art = 'box'` kind draws (`KINDS.unitframe`), at any size; `ThemeArt.PaintBox(frame)` lays this client's box on a frame that is only that art (the group border) and `ThemeArt.Clear` hides it; `st:SetBorderColor` tints a cut's pieces as it does a border's. `ThemeArt.LayBorder(pieces, frame, border)` lays a nine-piece border on a frame in the caller's own pieces table (the tooltip border's way, and its Center, anchored between the corners and untiled, when the border has one: retail's minimap button kit does) and `ThemeArt.HidePieces(pieces)` hides them. SaftUI places the art itself and never runs Blizzard's nine-slice code (`.agents/taint.md`).
  - Every draw call names its kind of frame, last: `st:SetTemplate(frame, theme, background, kind)`, `st:SetBackdrop(frame, theme, background, kind)` and `st:SetBackdropIn(backdrops, frame, theme, background, kind)`. The kinds are `st.THEME_KINDS`: `panel` (a background), `window` (a window with SaftUI's title bar), `bar`, `action`, `slot`, `aura`, `tooltip`, `header` (header and footer strips), `close` (the close button), `control` (a small frame Blizzard draws with art of its own), `unitframe` (a unit frame or one of its bars), `member` (a party or raid member's frame or bar) and `small` (everything else), thirteen in all. Under Thick and Thin only `header` and `close` draw differently (SaftUI's theme's fill, no lines): a window draws as a panel, a control as a small frame and `unitframe` and `member` as a `bar`. Under Blizzard `unitframe` is the box (`ART.box`, inset 2, at any size) and `member` a bare Background fill (inset 0, no art). Blizzard's look is the kind's own (`ThemeArt.KINDS` in `themeart_data.lua`). A call with no kind is an error, unless its theme is `'none'` (which only clears). `st:SetTemplate` also takes a fifth, optional argument, the button its ring and own-color piece are textures of (for a frame drawn on itself behind a button that isn't SaftUI's, which holds its own texts: the totem bar's). Use the `st:` form even inside Core's own methods: `tests/core/theme_kinds_test.lua` scans every file the TOCs load for draw calls without a kind, and fails on any other form. ## Config, defaults and profiles

- Each module defines its defaults at file load in its own `config.lua`, as `st.defaults.<key> = { ... }`. Unit frames keep theirs in `SaftUI-Unitframes/config/`.
- `Config:InitializeAceConfig` (called from `SaftUI:OnEnable`) creates `st.config = AceDB:New('SaftUI_DB', { profile = st.defaults, ... })`. Read settings through `st.config.profile.<key>`.
- **A page says where its settings are saved, and the kit reads the default.** `st:DefaultAt(...) -> found, value` (`SaftUI-Core/Config/optionsdefault.lua`) is the default of a saved path in `st.defaults` as AceDB-3.0 fills a profile (the first table that names a key decides, tables merge, a `'**'` is merged into the child it sits beside and into a child an earlier table made, a key nothing names takes the last `'**'` or `'*'`), which `tests/core/default_at_acedb_test.lua` checks leaf for leaf against a real `AceDB:New` over every addon's defaults, so a reset icon needs no second copy of a default. A table it gives is `st.defaults`' own (one table) or a merged copy (several): copy it before writing. A group's options say where they are saved with SaftUI's `saved` field beside the `get` that reads them (`saved = st.Config.SavedIn('chat')` for `self.config[info[#info]]`; an option with its own `get` takes `st.Config.SavedAt('chat', 'editbox', 'height')`; `false` for a value that is not a profile key), or a hand `default`, or `noReset = '<why>'`; `tests/lib/reset_walk.lua` fails a value row with none, and a `saved` that names another setting's key. See `.agents/edit-mode.md`, "A setting's own reset". Read defaults from `st.defaults` (this function), never through `st.config.profile`: AceDB's `'**'` creates a table on read.
- **Bind, don't cache.** In `OnEnable`, call `st:BindModuleConfig(self, '<key>')` instead of `self.config = st.config.profile.<key>`. On a profile change, AceDB switches to the new profile's tables and strips defaults from the old ones, so any reference cached at enable time (including upvalues and closures holding sub-tables) returns nil fields. Bound modules are re-pointed automatically. In option `get`/`set` functions and hooks, read through `self.config` at call time.
- **Per-character saved data** (not settings) goes in AceDB's char namespace, `st.config.char.<key>`, which a profile switch doesn't touch. SaftUI-Loot keeps its saved feed and recorded roll drops there (`Feed/history.lua`; the recorded drops' accessor `RecordedDrops` is in `Feed/loothistory.lua`, and `Feed/rolls.lua` records them). Read it through an accessor at call time (`st.config` doesn't exist at file load). Save only plain data (strings, numbers, booleans and tables of them), never a secret value (`.agents/clients.md`) and never test-mode entries, and keep each record to the fields its readers need. SaftUI-Tracker's `st.config.char.tracker` (`TR:CharData()`) is the same kind of thing, and so is the talent plan's `st.config.char.talentplan` (`active`, the plan each spec tab shows by spec group, and `collapsed`).
- **Account-wide saved values** (not settings) go in AceDB's `global` namespace, `st.config.global.<key>` (the options window's place, height, size and sidebar, `optionsWindow`; `debug`; `uiScale`, the player's UI scale choice `{ mode, size }`, absent while it is the default; `uiScaleNotice`, the version of the first-login line already shown, set only when it is shown; `talentplan`, the talent plan's saved plans, `nextID` and `plans` by class and id), which a profile switch, copy or reset never touches.
- **Profile changes** (`OnProfileChanged`/`Copied`/`Reset`) run `Config:UpdateConfig()` in `SaftUI-Core/Config/config.lua`. Order:
  1. Migrate the profile's saved template choices (`st:MigrateTemplateKeys`, see Themes) and its colors (`st:MigrateColors`, see below), then re-point every bound `module.config`.
  2. Redraw every drawn frame in the profile's theme (`st:RedrawThemed`), before any module lays itself out around its border. In combat the redraw and step 8 wait for the end of combat, as one pending run (`QueueAfterCombat('ThemeRedraw')`). In and out of combat they're two steps, each in `xpcall`, so a redraw that errors still has step 8 run after it.
  3. Clear mover anchors (`EM:ClearPositions`, which saves them and skips frames that are protected in combat).
  4. Apply fonts (the Fonts module's `UpdateConfig`: Heading's face step, then the objects; then `Config:UpdateConfig` runs `st:FontsChanged()`), then headers (`st:UpdateHeader`: every header's and footer's height and window title fonts, and each header in its window's metal title bar or back; a header or footer that's protected in combat waits for the end of it), then the screen edge margin (`st:UpdateScreenMargin`: every frame kept inside it; see `.agents/edit-mode.md`).
  5. Run every module's `UpdateConfig` inside `xpcall`, with errors going to `geterrorhandler()`.
  6. Re-apply edit mode movers (`EM:UpdateConfig`), restoring the old anchors of any frame left without points.
  7. Rebuild and refresh an open `/sui`.
  8. `st:ColorsChanged('theme')`, so what modules color themselves (quality borders, a selected mover) goes back on over the redrawn theme, then `st:ColorsChanged('accent')`, so what draws in the accent follows, then every other group's whole pass (`st:ColorsChanged(group)` for each of `st.COLOR_GROUPS` but `accent`, in the Colors page's order, each in `xpcall`: a switch, copy, reset or import can change any color), in combat too once it ends.

  In combat, protected work is deferred with `st:SafeReposition` / `st:QueueAfterCombat`, and one chat message says what will finish after combat.
- **Every module needs an `UpdateConfig`** that re-reads the profile and re-applies everything it controls (positions, sizes, its Theme and Background, fonts, colors, visibility). It must be idempotent: never create frames, font strings or hooks on each call. Create once, re-style on every call. Settings that genuinely can't apply live (module on/off toggles, secure header attributes) say "reload to apply" in their option description.
- Position config shape: `{ point, frame, rel_point, x_off, y_off }`, unpacked with `st:UnpackPoint`. Some older code used array positions (`{'BOTTOMRIGHT', -20, 20}`). Modules that converted (Bags, Chat, Experience) migrate saved arrays in place on enable and on profile change, filling missing slots from the old array defaults, because AceDB only saves slots that differ from the default.
- **Fonts** (`SaftUI-Core/Media/fonts.lua`, module `Fonts`). `FN.FONTS` is the fixed list of the six shared fonts, in the order of the Fonts tab and every font list: Text `normal`, Small text `pixel`, Large numbers `pixel_med`, Heading `heading`, Huge title `title`, Subtitle `subtitle`. Their names and jobs are in code (a profile's saved `name` is ignored), their objects are `SaftUI_<key>Font`, and every walk is over `FN.FONTS`, never `pairs(st.config.profile.fonts)`, which may hold a saved `version` and edits to a dropped font. `FN.DROPPED` has Pixel Huge and Normal Med, which no code reads but a profile's font setting may still name: such a key reads as the typeface it looked like, with `profile.fonts[key]` over it, and nothing is written. **Heading's defaults**: Heading is the default of `tracker.header_font` (SaftUI's tracker's header line, count and zone headers) and `inventory.fonts.titles` (the bags' category titles), and the face of RestedXP's guide title (`restedxp.lua`, at RestedXP's size plus 3). That is the bags' category titles, item levels and Icon font, the loot rolls', feed's and window's texts, the tracker's rows, header and count and its item buttons' count, number and key texts, the unit frames' elements and texts (`UF:UpdateElement`, `UF:UpdateText`, the aura count and timer, the name), and the action bars' texts. Step 1 split Text > Red, Yellow, Green, Blue, White and Purple and Buttons > Yellow into Roles, Factions and Loot. Step 2 made Buttons > Blue the accent. Steps 7 and 8 each retire `button.normal`, `hover`, `pushed` and `checked` (the states are the Accent's: step 7 while their defaults stood, step 8 once the defaults and readers were gone), so a profile at any earlier version, or at 7 with one saved since, ends with all four dropped and no other color touched, at version 8; steps 5 and 6 act on keys that no longer have a default, so they change nothing a profile keeps (Danger's opacity is still put back to 100%). Text > Muted is what the options kit, edit mode's hint lines, the bag categories' counts and edited marker, SaftUI's tracker's zone headers, counts and chevrons and a far lower level's tag draw in; it follows on the next draw (the window repaints its hints, notes and titles at each draw) or after a reload, as the Text section's note says. **The action bars' and buffs' texts** ship Small text, the key `'pixel'` (their `size` and `outline` defaults stay the old copy's, Homespun's 10 and monochrome outline, which only a typeface picked later reads), and Small text's shadow is 0, 0 as the copy's was, so an untouched profile draws what it did. `AB:ConvertFonts()` (marker `actionbars.fontsVersion = 1`, no default) and `AP:ConvertFonts()` (`auras.fontsVersion`) keep a saved text's look: a text on `'pixel'` whose size or outline is not the old copy's (a size or outline saved without a face, since AceDB kept only what differed from the old default) gets the old face, `Homespun` (`AB.OLD_TEXT_FONT`, `AP.OLD_TEXT_FONT`), as a typeface; a saved face is left. The action bars' runs first in `AB:ConvertProfile` (so in `OnEnable`, `UpdateConfig` and, through `AB:TryConvertProfile`, first in `AB:OnFontsChanged`, which the profile update calls before `UpdateConfig`): on a profile not yet converted to All bars it converts each bar's own text tables, before that step compares them, and on one already converted it converts All bars' text tables and then each bar's effective values, so a bar whose effective font is Small text (followed, or owned but never saved because it was the old default face) with a size or an outline that is not the old copy's owns the old face too (`own['<kind>.font']`); a bar that owns a typeface keeps it. ## Bag categories

- Which category an item goes to is data in the profile, not code. The design is `docs/superpowers/specs/2026-11-10-saftui-bag-categories-design.md`. `INV.config.categories = { version, order, edits, custom, deleted, nextId }` and `INV.config.categoryPins = { [itemID] = id }` have no AceDB defaults: `INV:EnsureConfigTables` makes them, and `INV:MigrateCategories` turns an old profile's hide flags and Auto Vendor list into Show in flags and pins, once. The header of `SaftUI-Bags/categories.lua` lists the profile keys and every getter and setter.
- **The list** (`INV:GetCategoryList`) is the shipped defaults (`categorydefaults.lua`: today's filters, as block rules, in today's order) with the profile's edits over them, then the user's categories, in the saved order. A default's id is the name it shipped with, so renaming it changes only what headers show. An edit is stored against the shipped default and a field equal to it is removed, so a default changed in a later SaftUI version still reaches users who haven't edited that field. Setters copy the tables they keep and end in `INV:CategoriesChanged()`. Equipment sets, Miscellaneous (always last and on), Empty Slots and Currencies are entries or keys outside the plain rule list. The bag window's Edit view checkbox of a `Set: ...` category does nothing while the Equipment sets entry hides that window (a click puts its check back, and a hover says which entry hides it): the box stays enabled, since a disabled button gets no hover without `SetMotionScriptsWhileDisabled` and SaftUI's check box has the template's disabled-checked texture stripped.
- **Resets.** The Bags page declares where each row is saved (`saved = st.Config.SavedIn('inventory'[, id])`, the two font rows `SavedAt('inventory', 'fonts', key)`), so every row has a derived reset. In the Categories editor a shipped category's Name, On, Show in and rule each carry a hand `default` against `INV:GetDefaultCategory(id)` (a category of your own a `noReset`), and the list's order has `INV:CategoryOrderDiffers()` (the shipped categories are out of their order) and `INV:ResetCategoryOrder()` (the shipped order, each of yours right after the category it follows now, Miscellaneous last; pins, edits and your categories untouched). `INV:ResetCategory` and `INV:ResetAllCategories` stay in the store (tests use them) but no button calls them.
- **A rule** is a tree of groups (`and` or `or`, optionally negated) and blocks (`rules.lua`). `R.Compile` turns it into a closure that reads an item's facts (`INV:GetInventoryItemInfo`: class and subclass IDs, the lowercased and stripped name and tooltip text). A block or group it can't read matches nothing and NOT never flips that. A block with nothing set yet (a list with nothing picked, a level with no number, a yes/no with neither) can't be read, and new blocks of those types start that way, so no block matches everything as it's added. An OR skips children it can't read; an AND with any such child can't be read itself, so a half-built rule (an emptied group, a NOT on a block not yet filled in) catches less, never more. Every editor change saves at once, and for Grays/Auto Vendor more would mean selling the bag (see the `rules.lua` header). A level block's mode picked before any number is typed is kept in the rule editor only (`w.levelPick`, no profile data): the row shows it, a number typed in either box of between with no number yet is both bounds (so no order of typing saves a rule that catches more than the finished one), and the pick waits through a window redraw (it is parked for the next frame when the editor is released) until an edit of the editor or the editor closing. `INV:GetItemCategory(info)` returns the key and why (the block that caught it); the first category to catch an item wins, and a pin beats the rules.
- **Class and subclass names** are resolved to IDs per client (`itemclasses.lua`), so a block matches by ID where it can and by name where a client names a subclass differently (see `.agents/clients.md`).
- **An item whose tooltip hasn't arrived** is held for 10 reads, then filed without text and marked `tooltipMissing`, then refiled when its text arrives. Auto vendor never sells it, nor a Cosmetic, an equipment set item or a Protected one, whatever a pin or the Grays/Auto Vendor rule says (`INV:IsAutoVendorItem`). The seller is the category that carries the `sells` flag, found by the flag and not by name or place, so a rename or a move changes nothing; turned off, it sells nothing. The shipped rule's Old gear block is ANDed with NOT Equip slot `INVTYPE_BODY`, `INVTYPE_TABARD` (the slot list's own order, so turning a slot on and off leaves the rule as shipped), so a tabard or a shirt is never old gear and never sold through it (the old filter's test for it never matched); a profile that has not edited the rule picks that up, and one that edited it keeps its own.
- **How auto vendor sells** (`SaftUI-Bags/autovendor.lua`, tests `tests/bags/autovendor_sale_test.lua`). `INV:GetVendorItems()` returns the stacks it would sell in sale order (`SaleOrder`: grays first, then everything else; each from the cheapest stack, vendor price times count, up, then by bag and slot) and their profit; the footer's Vendor profit reads it (the junk coin reads `IsAutoVendorItem` itself). A merchant's buyback list keeps the last 12 sales of any quality, one entry per stack sold (Blizzard's `MerchantFrame.lua`, both branches: `BUYBACK_ITEMS_PER_PAGE = 12`, `GetNumBuybackItems()` entries, the newest last), so the promise is per visit: every non-gray stack sold without asking is still in it when the visit ends, unless the player answers Sell them to a later question (which says how many stacks sold earlier this visit it would push out: of `tailSold` plus the sales in flight only the last `size` are still in the buyback, and the new stacks leave room for `size` minus their number of them, so the figure is the count of earlier stacks that really leave and is never above the number of new stacks past 12). `INV:BuybackSize()` is the game's constant, never more than 12. `MERCHANT_SHOW` (`INV:HandleMerchant`, not in combat) starts a visit; `INV:VendorPass()` runs every 2 seconds from one `OnUpdate` on `INV.vendorFrame` (the game throttles selling), paused in combat, and ends when the merchant closes (`MERCHANT_CLOSED`, or `MerchantFrame` hidden), the setting is turned off, or nothing is left. Grays are sold first and alone: the non-grays wait for a pass with no gray left. From the first non-gray sold, every stack sold counts toward the size (`tailSold`); the stacks left (non-grays, and a gray that turned up late) sell when they fit, else it asks once (`st.OptionsWidgets.Confirm` in the world, centered on the screen, `{ yes = 'Sell them', no = 'Keep them', enter = false }`: Enter answers nothing, only a click answers, Esc is Keep them). While the question is up nothing in it sells, whatever the count drops to. Sell them sells exactly the stacks the question named, each re-checked (same item and count, not locked, quality known) at the moment of sale; a stack not named needs its own question. Keep them (Esc, a click outside, the merchant closing) sells no more non-grays that visit; the next visit asks again. A fight taking the question down (`PLAYER_REGEN_DISABLED`; its key catcher can't hand keys on in combat) counts as not answered and it is asked again after the fight if still needed. A sale in flight (the stack still in its slot, locked) stays pending: counted in the tail and the budget until it lands, and a gray in flight keeps the non-grays waiting. A stack counts as sold when it has left its slot or its slot holds another item, another count or another GUID (`Sell` records `C_Item.GetItemGUID`, in `ItemDocumentation` on both clients: a purchase into the slot is a new stack, and so is a slot that answers no GUID where one was recorded, which only asks sooner), and leaves the question's named list then (a stack bought back into its slot needs a new question); the chat summary counts only those, waits a second after a merchant that closed right after a pass, and names the stacks left after 3 tries. A locked stack is skipped without a try; one of unknown quality counts as non-gray and is not sold until known; a visit waiting on either reads the bags every 2 seconds until the merchant closes (accepted). The question's names are item links (their quality color) and its values are vendor prices. No setting: this is how it always sells.
- No frame or slot is made in combat for a new category: the frames are made by `INV:EnsureCategoryFrames` out of combat.
- **Item groups** (`itemgroups_data.lua`, `itemgroups.lua`; the design is `docs/superpowers/specs/2026-11-25-bag-item-groups-fish-design.md`). Useful sets of items that Blizzard's classes scatter, today one: Fish, the raw fish you catch (28 on Forever). `itemgroups_data.lua` is generated by `tools/item-groups.cjs` from a Forever build's tables (`.agents/clients.md`) and committed; never edit it by hand, change the group's `tools/item-groups/<group>.overrides.txt` and run the tool again. It sets `INV.ItemGroupsData = { forever = { fish = { [itemID] = true } } }`. `INV.ItemGroups` (`IG`) serves it: `IG.Groups()` (the ids and labels, in order, kept in `itemgroups.lua`), `IG.Label(id)` (nil for an unknown id) and `IG.Set(id)`, this client's set or an empty table, read at call time (so retail, which has no data, gets empty sets). The `group` block (`{ block = 'group', group = 'fish' }`, "Item group is") takes its set once when compiled and is one lookup per item; an unknown or missing group is unreadable, like any unfilled block. A compiled rule keeps the set it took, so data swapped after a compile needs `INV:CategoriesChanged()`, which drops the compiled rules (`INV.CategoryDefaults.Reset()` alone doesn't); in game the data is fixed at load. The Fish default sits right before Flasks/Potions/Food, since three raw fish are class Food and others Trade Goods or Quest. A new group is data and generator rules only: the next ones are a followup.

## Unit frames

- These are oUF (`SaftUI-Unitframes/Libraries/oUF`, oUF master). In this oUF the active unit is `frame.__unit`, **not** `frame.unit`.
- Elements register through `UF:RegisterElement(name, Constructor, UpdateConfig, GetConfigTable, ValidUnit)`.
  - `ValidUnit(unit)` gets the config unit (`player`, `boss`, `party`, ...). A unit it rejects gets neither the element nor its `/sui` tab. ClassPower and AdditionalPower are player-only, Castbar skips `targettarget` and `focustarget` (as oUF does), ReadyCheckIndicator is party and raid only, Power, GroupRoleIndicator and RaidRoleIndicator skip both plate units (`UF.IsPlateUnit`: `nameplate` and `friendlynameplate`), and Threat (the nameplates' threat text) is `nameplate` only, so the Friendly nameplates page has no Threat tab. Every plate's frame is built as `nameplate` (its unit token's), so it has every element `nameplate` takes, Threat included, whichever config it draws from later (Nameplates).
  - `GetConfigTable(unit)` returns the element's tab. Its `set` calls `UF:UpdateConfig(unit, '<Element>')`, which re-runs that element's `UpdateConfig` on every frame of the unit.
  - Where that table lands on the page is `UF.PARTS`' (`SaftUI-Unitframes/config/parts.lua`): a part's options are its row's menu in General's Parts section (the very option tables of the group, but Enable, which is the row's box), or the group as a tab when its line says `place = 'tab'`; Health text and Power text are also the Health and Power tabs' Text section (`mirrorOf`). A new element with options is a tab unless it gets a line in `UF.PARTS`; the page's order and nesting are `UF.PlaceElements`'s. See `.agents/edit-mode.md`, "The unit pages: parts and five tabs".
  - oUF shows and hides many elements itself (castbar on a cast, indicators by state, additional power by power type), so `UF:SetElementEnabled` alone doesn't keep a disabled one hidden. Those elements also hide themselves again in an oUF hook (`ShouldShow`, `PostVisibility`, `PostUpdate`): the castbar's `ShouldShow` and the indicators' `PostUpdate` while `UF:ElementWanted` (below) says no, the others while their config is off.
  - Texts made by `UF:AddText` sit on the unit frame's `TextOverlay`, not on their element, so they don't hide with it. `UF:UpdateElement` hides them when the element is disabled.
  - `UF:UpdateElement` draws an element's Theme and Background on the element, except for the aura areas (Buffs, Debuffs) and the class power row (`BARE_ELEMENTS` in `updaters.lua`): their own `UpdateConfig` draws each aura button and point instead (a class power point is a `control` where Blizzard has art for the power type and a `small` border where it has none, `PointKind` in `classpower.lua`), and the area gets no backdrop. An aura area is Blizzard's AuraContainer, so nothing of SaftUI's is anchored to it (`.agents/taint.md`, rule 11).
- **How oUF builds a frame.** `UF:OnEnable` registers `UF.InitUnit` as oUF's init callback first, before the style and before anything is spawned. oUF then builds each frame in this order: the style function (`UF.ConstructUnit`), then it enables every oUF element whose widget the frame has, then the init callbacks. Single units get their first update from OnEnable's `UF:ApplyConfig`. Group buttons (made by their header as members appear) and the nameplates' frames (made at a plate's first add) get theirs in `UF.InitUnit`, after oUF's Enables, so the update has the last word (oUF's aura Enable turns every aura area on, and the update sets each by its config). A plate's frame gets that first update from `nameplate` whatever its unit's kind, and its first `'added'` callback then moves it to its kind's config (Nameplates). A group button made in combat is updated at once and again when combat ends (`st:QueueAfterCombat('uf_init_' .. name)`), since a secure frame can't be sized in combat; a plate's frame isn't secure, and its update in combat is whole. A widget oUF must enable has to exist when the style function returns, so a group button's range fade table (`self.Range`) is made in `UF.ConstructUnit`, and its alphas come from the update.
- **Shown and enabled.** `UF:ElementWanted(element)` (`updaters.lua`) is the element's config Enable, except that a friendly unit's nameplate never wants the parts only an enemy's shows: the threat text (`UF.PLATE_ENEMY_ONLY`, `{ Threat = true }`, `frame.friendly`; see Nameplates). A plate's config is its kind's, so a friend's castbar, aura areas and quest icon show by the Friendly page's Enable. `UF:SetElementEnabled` shows or hides by it and returns the config's Enable, which `UF:UpdateElement` places and sizes by, so a part a friendly plate hides is still laid out, ready for the plate's next enemy. A part its own config turns off is still sized and placed by that config too, on a unit frame as on a plate (`UF:UpdateElement`, before it returns; a profile switch clears every part's points first, `UF.ClearPartPoints`), when it's a part other parts can anchor to (`unitframe[element.name] == element`, the parts `UF:GetFrame` finds; not an element's texts and icons): a plate's frame takes the other kind's config on every kind change, and the friendly config hangs the castbar, the aura areas and the quest icon off a health bar it turns off, so the hidden bar holds them where they'd sit if it were shown (an aura area that's off is sized to one button, so a part hung from its far edge doesn't sit as it would with the area on; a config with no `position` is skipped). Such a part gets its size and place only; its backdrop, alpha, level and bar setup wait for its next enable. `UF:SetElementEnabled` never enables or disables in oUF, which enables every element when it builds a frame. `DisableElement` is used on plates only (their castbar and quest icon, by their config), because oUF's castbar `Disable` gives Blizzard's player and pet castbars their events back on the player's frame (never on a plate's), which the player castbar's option promises not to do.
- **The bars' faction flags.** Health's and power's `colorTapping` and `colorReaction` go through `UF.SetFactionColorFlags(bar, config)`: oUF's setters, forced, while oUF has the bar enabled and not paused, so `UNIT_FACTION` (their recolor event, which oUF registers only in the bar's Enable) is registered or dropped to match; plain fields before that, and on a disabled or paused bar (a plate showing only widgets), which oUF's next Enable or resume reads.
- **Texts.** The `st:name` tag (`tags.lua`) takes secret values (`.agents/clients.md`): a secret level, reaction or classification is left out of the text, and a secret name isn't cut or put in capitals and is joined to its level part and color by the game (`C_StringUtil.WrapString`), so the tag returns a secret, which oUF's tag code shows. The tag has no nameplate target mark any more: the target's border replaces it. The name's color is the first that applies (`NameColor`): Class color for a player (or NPC class, Pet class), then Color hostile (red under reaction 3, yellow under 5), then Color friendly (`name.color_friendly`, reaction 5 or more, in oUF's reaction color; off by default, on for the friendly plates). The Name tab offers Color friendly where `UF.CanShow(unit, 'npcs')` (`config/config.lua`), so not on Player, Party or the raids. It colors only names the tag draws: the test mode previews' names (`grouppreview.lua`) are drawn without the tag and ignore it. The tag names the config unit it reads (`[st:name(<base_unit>)]`), so the Name binds it once per config unit (`name.taggedUnit`, `elements/name.lua`) and, when the frame's `base_unit` changes (a plate changing kind), unbinds it and binds it again; the next oUF update writes the name from the new config. The health text's Short (`health.text.short`, off by default, on for the plates) shows 12.5K, 1.2M or 1.2B through the game's `AbbreviateNumbers` with SaftUI's own breakpoints (`SHORT` in `elements/health.lua`), which takes a secret health too; Percent with a secret health is the game's `UnitHealthPercent(unit, true, CurveConstants.ScaleTo100)` through `SetFormattedText('%.0f', ...)`; and the deficit and the percent are worked out only where they're shown. The power and additional power texts have the same Short (`power.text.short`, `additionalpower.text.short`, off by default; the same `UF.ShortNumber` in `elements/health.lua`, a secret value included; it doesn't apply to Percent or Hide full). The health, power and additional power texts each have their own color (`text.colorCustom`, off, and `text.customColor`, a white list, in every unit's defaults, set in /sui by the Text color row, `UF.CustomColorOption`): off, a text keeps its font's color (white); on, `UF:UpdateText` (`updaters.lua`) gives it the custom color after `SetFontObject`, and puts the font's back when it's turned off. Nothing in those elements recolors a text afterwards, Dead and a status color included (the bar takes the status colors, not the text), so the color stays through every update. Hide full applies only to a plain health: with a secret one the text shows, except under Deficit, where the game's `TruncateWhenZero` and `WrapString` blank a zero. Boss percent tests the skull only on a plain level, and with a secret health joins the parts in the game, `SetFormattedText('%s | %.1f', text, UnitHealthPercent(unit, true, CurveConstants.ScaleTo100))`. The tag's events are `UNIT_NAME_UPDATE UNIT_LEVEL PLAYER_LEVEL_UP UNIT_FACTION`, with no `PLAYER_TARGET_CHANGED`: oUF's target frame updates its own tags on a target change. Name's Max width (`name.max_width`, in pixels, 0 for none, every unit's default but the plates' 150) gives the name that width on one line, so the game cuts a longer name, a secret one too; 0 gives a name SaftUI sized before no width again. **Max width and Align on every text** (`max_width` and `justify` in every text's config: Name, Health and Power text, Additional power's text, the castbar's spell name and time, the plates' Subtext and Threat; `G.max_width` and `G.justify` in `Config/generators.lua`). `UF.SetMaxWidth(text, config)` (`updaters.lua`, run after the font in `UF:UpdateElement` for a font string element, `UF:UpdateText` and name.lua, since `SetFontObject` puts the font's justification back) gives the text its Max width on one line, or no width again at 0, then justifies it: `UF.TextJustify(config)` takes Align (`LEFT`, `CENTER`, `RIGHT`) only while Max width is above 0, the one case where it shows; `AUTO` (the default), and every text with no width, justify by the point's side (left for a left point, right for a right one, else centered), as before. The Align row is disabled while its text's Max width is 0. Every default is 0 but the plates' name and subtext; the unit frame rows are shared as step 1 entries: every unit's default and All units' is the same, so no member owns one.
- **The castbar** colors a cast from oUF's `notInterruptible` argument, which can be secret (then through `C_CurveUtil.EvaluateColorValueFromBoolean`), in `PostCastStart` (oUF runs it for channels too) and `PostCastInterruptible` (a cast that turns interruptible or not mid-cast). It reads no `CastingInfo`.

- **Aura filters** (`aurafilters.lua`, loaded after `tags.lua`). Every aura group is built with, and keeps, the filter string and candidate filters `UF.AuraFilter(unitframe, auraType, config)` gives: Buffs with Only buffs I can purge (`buffs.purgeable`, off by default, on for the plates) get `UF.PurgeFilter(UF:KnownRemovals())`; a plate's Debuffs get `HARMFUL|INCLUDE_NAME_PLATE_ONLY`, Only mine as the `isFromPlayerOrPlayerPet` candidate filter alone, so the pet's debuffs stay; any other area `HELPFUL` or `HARMFUL`, Only mine adding `|PLAYER` and that flag (`.agents/clients.md`). `AddGroup` notes what it built the group with (`auras.groupFilter`, `auras.groupCandidateFilters`), and every aura element's `UpdateConfig` runs `UF:ApplyAuraFilter(auras)` on a built group, which calls each of Blizzard's setters only if its part changed (each makes the container update every aura), so the filter applies live. So do the group's other options but two (`elements/auras.lua`): the max count, through the container's `SetAuraGroupMaxFrameCount` on every update of a built group (a container call that touches no button, so in combat too; it does nothing for the count it has), and the button size, which the container has no call for, so `StyleButton` sets each button's size from the config in use (`getButtonSize`, Relative size included) as it styles it: a new button in `PostCreateButton`, the others in the restyle, at once out of combat and at the end of combat in it (`RestyleButtons`), when the group is also laid out again (`SetAuraGroupLayout`, since the container lays out only when something marks its layout dirty, never because a button changed size). Which borders the buttons show and whether they get a cooldown are baked into each button as the container makes it, from the options the group was made with, so their options still say to reload. A group is made once per frame, on its first update with the area on: a plate's is made from Enemy nameplates while that page has the area on (a plate's first update is always from it), so the Friendly page's border and Cooldown → Show never reach its buttons then, even after a reload (ruling N2, `docs/followups.md`). The two options' notes say so on the two plate pages (`ReloadNote`, every other unit's says to reload): the Enemy page's that its settings make every plate's buttons while it has the area on, friendly plates' too, and the Friendly page's that its reach friendly plates only while the Enemy page has the area off, and then after a reload. `UF.PURGE_SPELLS` lists the purge, dispel and steal spells by client and class and what each removes (Magic, Enrage, stealable; `.agents/clients.md`), `UF:KnownRemovals()` asks `C_SpellBook.IsSpellKnown` which the player knows (a pet's in the pet's spellbook), and `UF.PurgeFilter(known)` turns them into `HELPFUL|RAID_PLAYER_DISPELLABLE` with `includeDispelTypes`, or `isStealable` for a player who can only steal, or no buffs for a player who can remove nothing. A frame of aurafilters.lua's runs `UF:RefreshPurgeFilters()` (every unit frame's purge filter again, waiting for the end of combat) on `SPELLS_CHANGED`, `PLAYER_TALENT_UPDATE`, `TRAIT_CONFIG_UPDATED` and the player's `UNIT_PET`.
- **Colors.** `UF:OnColorsChanged` reads each frame's oUF unit, `__unit` (`.unit` is set only by `UF.OnEnter`, so a frame never hovered has none), and skips a plate that isn't showing its unit. It works by key (`OnColorsChanged(group, key)`): `UF:UpdateColors(group, key)` copies only that color into oUF's (in place, no table made; a color oUF has none of yet is made once by `oUF:CreateColor` from the profile's, a copy with oUF's methods, never the profile's own table), and a frame is updated only when `UF.ColorReaches(frame, group, key)` says its unit shows it (a class token, a standing for a unit that isn't a player, or for a player whose Health or Power has Class off and Reaction on or whose name has Color friendly on and Class color off, a power color for the bar oUF draws in it: the unit's token's own color, else (with no game color for it) its power type's, else Mana's, compared as oUF's tables, which a pass keeps by merging in place, so a token oUF has no color for is reached by the pick of the color it is drawn in; offline or tapped, a role with `DAMAGER` also for none or unassigned; a secret answer counts as a match and is never compared), and only the elements `UF.COLOR_ELEMENTS` names for the group: Class and Reputation update Health and Power, Power updates Power, AdditionalPower (`MANA` only) and ClassPower (whichever frame has it, for any class power key), Status updates Health and Power (their Disconnected and Tapped flags), Roles the role corner (`GroupRoleIndicator`). A frame that isn't visible (a plate is not skipped: oUF gives it no OnShow) and an element its config turns off (`UF:ElementWanted`) are skipped: oUF's OnShow updates every element, so a hidden frame takes the color when it shows. Text > Normal and a whole Text pass also write the threat text of each plate showing a unit. A key nil is the whole pass: every frame with a unit, the group's elements only. A pass only colors (`ForceUpdate`, `UpdateTags`) and makes no table, so it is safe in combat. For `threat` it retints the plates (`UF:UpdatePlateThreat`) and updates no other frame. For `theme` it draws the target's border on every plate again and rounds each plate to whole pixels again (Nameplates, below). `UF:ForEachUnitFrame` visits the plates' frames too, shown or not, so `UF:RefreshConfigReferences` (`UF:RefreshFrameConfig(frame)` on each: the frame's cached config and every element's, text's and icon's pointed at its config unit's in the current profile, plain table writes, safe in combat), `UF:RefreshPurgeFilters` and the color updates reach them.
- **Themes on unit frames.** `UF.UnitKind(unit)` is `'member'` for party, raid10 and raid40 (`UF.group_strings`) and `'unitframe'` for every other unit; the frame, its bars and the previews draw with that kind at any size (there is no small-frame fallback for a thin bar: the box draws on a bar as thin as the config makes it). `UF:UpdateUnitFrame` and a preview's `StylePreviewFrame` draw the frame's backdrop after its elements, so the frame's box (levelled once at draw time by `ThemeArt.LevelAbove`) lies over its bars' frame levels, which an element's update sets. **One box per edge:** `UF:ElementTheme` gives None to a bar drawn as `unitframe` that fills its frame (`UF.FillsFrame`: Relative width and height on, both 0, no `position.element` or `position.frame`, point equal to relative point, offsets 0) while its own Theme and its frame's are both Blizzard, so the frame's box is the only one; otherwise each element draws its own pair. **The group border.** Under Blizzard each party and raid header (one for the whole raid, not one per real raid group), and a party or raid test mode preview container, sits in the box (`ThemeArt.PaintBox`, no middle). It is a plain frame of SaftUI's, the header's child, anchored `ThemeArt.Reach('unitframe')` (4) outside it in whole pixels so it follows the header's layout in combat with no SaftUI code, and raised over the header's children and their children (`ThemeArt.LevelAbove(header, border, 2)`: each member and its bars, so the rim covers the bars' outer pixels) by `UF:UpdateGroupBorder` out of combat only (a draw in combat keeps its last level), made in `UF:CreateGroupHeaders` and kept in `groups.lua`'s weak table (`UF:GroupBorder`). It shows when `UF.GroupBorderShown(config)`: the frame's Theme, or health's where the frame's is None, resolves to Blizzard. `UF:UpdateGroupBorder` runs from `UF:ApplyConfig` (in and out of combat) and the preview's from `UF:UpdateGroupPreview`. A header with no member to show (a pending invite with Show player off, a group disbanding) still shows and sizes itself to a sliver, so the border sets its alpha to 0 from its own `OnSizeChanged` while either side is under two pieces (12; the box is 4 outside, so a header under 4). **The fills.** Under Blizzard a health, power or additional power bar whose texture is SaftUI Flat and whose own resolved Theme is Blizzard draws Blizzard's raid bar fills (`ART.unitbars`, `RaidFrame-Hp-Fill`, the resource fill on power, with their background atlases): `UF.BlizzardFill(element, config)` decides, `UF:SetBarFill(element, fill, flat)` draws the fill and background (or the flat texture and a blank background), `UpdateStatusBarElement` records `element.barFill` and `element.barFlat` (the flat texture, the user's pick among them), and a power update draws them again (`power.lua` and `grouppreview.lua`'s member power call `UF:RedrawBarFill`, so the fill, or the picked texture, survives ticks; `UF:SetBarFill` does nothing when asked to draw what is already drawn). A texture the user picked stays, under every theme.

- **Shared unit frame settings (All units, `config/shared.lua`, `config/units/all.lua`; wired: `UF:OnEnable` and every no-unit `UF:UpdateConfig` call `UF:PrepareShared`, out of combat only; All units is first in the Unit picker).** Eleven members (`UF.SHARE_MEMBERS`: Player, Target, TargetTarget, Focus, FocusTarget, Pet, PetTarget, Boss, Party, Raid 10, Raid 40; the plates are not members) follow All units for each setting they have until they own it. `UF.SHARED` lists the 196 shared settings (every row of a member's page under a part or a bar, and the frame's Theme and Background; never a frame's Enable, size, place, Layout or Range, Class power or Additional power): `{ key, part, element, name, type, paths, shows, since }`, indexed by `UF.SHARED_BY_KEY` and `UF.SHARED_BY_PATH` (every path, joined by `.`). A member *has* a setting (`UF:HasShared(unit, key)`) when its page shows the row: the element is registered with a `ValidUnit` that passes and `UF.CanShow(unit, entry.shows)` holds.
- **Where it is stored.** In the unit frame profile (`unitframes.profiles.<name>`), so a profile copy, rename, export and import carry it: All units' values in `<profile>.all` (a unit-shaped table; its defaults are AceDB's unit wildcard with `st.ALL_UNITS_DEFAULTS` (`config/units/all.lua`: Debuffs > Enable on) laid over it by `UF.DefaultShared`; they are NOT registered with AceDB, so a profile's saved data gains no `all` block before it is converted, and the first conversion writes Debuffs on into All units), each member's own flags in `<unit>.own['<key>'] = true | false` (dotted keys, cleared to `false` and never `nil`; AceDB fills `own` with the element defaults at login, so never iterate it, only read the keys the entries name), and the marker `all.version` (`UF.SHARED_VERSION`, read and written with `rawget` and `rawset`: a missing key under a unit-shaped table reads as a new table through AceDB's wildcard). Each member's stored values stay where they are and hold what the member shows (its own value where it owns the setting, else a copy of All units'), so no reader, oUF element or hot path changes; `UF:SharedValue(unit, key)` is the one definition and `UF:SyncShared(profile)` puts any drift right (and writes nothing otherwise). A re-upgrade after edits made in an older SaftUI reverts them (the sync puts a follower back to All units' value), and a change to a shared setting's shipped default for some members needs a conversion step as a new setting does.
- **The conversion** (`UF:ConvertShared(profile)`, once per profile, a step per `UF.SHARED_VERSION` above the marker; an entry's `since` says which step converts it, and an entry no step covers is an error): All units takes the value most members show (`UF.SameShared` groups them: offsets as numbers, never rounded to a pixel, so the result is the same at every UI scale; a color as bytes; a typeface by what it draws; a colortoggle the same when both are unticked), a tie going to All units' default when it is among the tied values, else to the first member; a member owns exactly the settings where it shows something else; nothing is written into a member. It computes everything first (a member is compared by what it will show after the next login: a key nil in the session counts as the default AceDB refills), then writes the one-time backup (`<profile>.backup = { version, when, units }`: per member the values of the shared settings it has that differ from its default, and its own flags for them, as plain data, made before the first conversion and never again; `UF:RestoreShared(profile)` writes them back into the live tables in place, so AceDB's wildcards and a color's methods stay and nothing else in the profile changes, drops All units, and so clears the marker), All units' values, the own flags, and the marker last. `UF:PrepareShared(profile)` is the one guarded entry (`xpcall`): the conversion, then the sync only while the marker equals `UF.SHARED_VERSION`; on any error nothing more is written and the frames build from the stored values. A fresh profile owns 155 settings (Player 29, Target 19, TargetTarget 2, Focus 21, FocusTarget 2, Pet 2, PetTarget 2, Boss 10, Party 19, Raid 10 24, Raid 40 25) and its All units holds the defaults.
- **The API** (table writes only, safe in combat, applies nothing): `UF:SetShared(unit, key, value, part)`, `UF:OwnShared(unit, key)`, `UF:FollowAll`, `UF:ApplyToAll`, `UF:ApplyTo(unit, key, targets)`, each returning the units whose stored value changed; `UF.CopyShared(entry, from, to)` copies a position part by part (an anchor that isn't set as `false`), a color in place in its shape, a typeface as a copy. What changes a frame is `UF:UpdateShared(units, element)`: it marks the units and shows `UF.sharedTicker`, whose `OnUpdate` runs `UF:UpdateConfig(unit, element)` once per mark on the next frame (a held slider on All units costs one update of each follower per frame), and `UF:PropagateShared(element)` copies All units' values for one element's entries into the followers and marks those that changed.
- **What guards a layout** (`config/shared.lua`; each pinned by `tests/unitframes/shared_guard_test.lua`). `UF:PrepareShared` leaves a table with no AceDB metatable (an import in this session) alone, returning `false, 'plain'`: it converts at the login that fills it, on the data the frames will read. `UF:ConvertShared` raises, writing nothing, for such a table and while any element an entry names is not registered. Every writer (`SyncShared`, `SetShared`, `FollowAll`, `ApplyToAll`, `ApplyTo`, `PropagateShared`) returns `false` and a reason, writing nothing, unless `UF:SharedReady(profile)` (the marker equals `UF.SHARED_VERSION`) and every element is registered; `OwnShared` needs only `UF:CanMarkOwn`. The conversion's writes go in the order backup, All units' values, own flags, marker, so an error at any step leaves no marker and the next try converges. The unit wildcard's `castbar` names `width = 0` and `relative_width = true` (the values the element wildcard gives anyway) so AceDB does not strip them from a follower that holds them. The ticker reports an error in one unit's update and runs the rest.
- **Who calls it.** `UF:OnEnable` calls `UF:PrepareShared()` first, before anything spawns (in combat it queues `UF:UpdateConfig()` instead, which converts when combat ends); `UF:UpdateConfig()` with no unit (every profile switch, copy, reset and import, a unit frame profile switch) queues for combat first (`self:RefreshConfigReferences()` re-points the cached config at once; the frames read the stored values, which are what the units show by construction) and, out of combat, calls `UF:PrepareShared()` before anything is applied, with table writes only: nothing converts in combat. `UF:UpdateConfig('all', element)` returns `UF:PropagateShared(element)` and nothing else. `tests/unitframes/shared_guard_test.lua`'s scan lists the only top-level functions of the only files that may mention the API (by name, an alias, `self:` or a string key); any other mention fails it.
- **When sharing is off for a profile** (`UF:SharedState(profile)`: `'ready'` or one of `'none'`, `'plain'`, `'restored'`, `'newer'`, `'missing'`, `'failed'`, `'pending'`): `UF:PrepareShared` writes nothing, the frames build from the stored values exactly as before sharing existed, `UF.DecorateShares` draws no share on any page, All units' picker entry is `UF.SharedNoticePage` (it says why, and has a button where the owner can ask for sharing: after a restore or a failed setup), and `UF.SharedStateText(state)` says it once in chat per profile and reason (`SharedTold`, weak by profile table): `plain` for an import made in this session (no AceDB tables: `UF:SharedReady` is false for it, and it converts at the next login; a copy is never plain, it keeps its source's tables), `restored`, `newer` (a downgrade then an upgrade: its flags are a newer SaftUI's), `missing` (an element did not load), `failed` (the setup raised an error: reported through the error handler once and not tried again this session: `SharedFailed`, until `UF:EnableShared`). `UF:SharedValue`, `UF:IsOwn` and `UF:OwnersOf` never create `all` (`AllOf` reads it with `rawget` unless it is making it): a read of a profile that is not converted writes nothing.
- **Going back.** `UF:RestoreShared(profile)` refuses while an element is not registered (it would restore every other element and clear the marker), puts the backup's values and flags back into the live tables in place, drops All units (so the marker) and records `restored = <time>` in the profile: no login or update converts a restored profile again by itself (`UF:SharedState` says `'restored'`), so the owner stays where they were until they ask. `UF:EnableShared(profile)` (`/sui uf share`, or the All units page's button: both go through `UF:RequestShare`, which in combat says so in one line and waits for combat's end as a restore does, then `UF:ShareNow` converts, runs `UF:UpdateConfig` so the frames take what the sync changed, and refreshes the pages) clears the flag, drops the old backup (it was of before the restore), forgets a failed setup and converts like a login, with a fresh backup. `/sui uf restore` says what it would do, naming the backup's day; `/sui uf restore confirm` does it (`UF:RestoreSharedNow`), refreshes the frames and the open window, and needs no reload; in combat it queues for combat's end and says so. `Config:AddSubcommand(word, func)` (`SaftUI-Core/Config/config.lua`) is how `/sui uf <rest>` reaches `UF:RunShareCommand`, with no sidebar button.
- **Profile changes** (`config/profiles.lua`). New: `UF:UpdateConfig()` converts the new profile from its own (default) values. Copy and Export use `UF.CopyProfileData` (a deep copy without the backup and the restore's marks, which belong to the profile they were made for, so a copy of a restored profile converts like any other); a copy keeps its source's All units, flags and marker, so it is ready at once, and a copy of a profile that was never converted converts from its own values. Import makes a plain table (AceDB gives it its tables at the next login, and says so once). Rename moves the table (and its backup) as it is. Delete and the Profile select switch to another profile, which `UF:UpdateConfig()` prepares. After each, `UF.RefreshPages()` builds the open /sui window's tree again (the pages draw shares only while the profile in use shares), then re-renders. Copy from (`UF:CopySettings`) stays: what it copies is the unit's own wherever it differs from All units' (`UF:OwnShared`), the rest keeps following.
- **What keeps an edit and the owner's profile.** (1) A conversion never runs in combat (see who calls it). (2) An edit is never lost: a profile that is converted (by any version) takes the own flag whatever else is wrong (`UF:CanMarkOwn`, used by `UF:OwnShared`): `UF.DecorateShares` wraps member rows' sets with the flag alone and draws no share (a part did not load, a newer marker, a paused sync), and Copy from (`UF:CopySettings`) marks what it copied by the same rule, so a copy made while sharing is paused survives the sync that follows; Import drops the export's `all`, flags, backup and restore marks, so the next login converts the profile from what each unit shows. (3) A failed sync on a converted profile raises one error, says one line, and pauses sharing for that profile for the session (`SharedFailed`: `UF:SharedReady` false, every writer but `OwnShared` refuses). (4) A restored profile says it is off once, at the first login after the restore (`restoredTold` in the profile); the All units page keeps saying it. `/sui uf share` after a restore says what it replaces and needs `confirm`, as the page's button does. Every conversion says one line (`Shared unit frame settings are set up ...`), so a login that finally converts tells the owner. Deleting a unit frame profile says which became active. Copy from's history step carries the ownership as a second change (`ufown`), so Undo gives the flags back with the values.

## Nameplates

SaftUI draws the nameplates as unit frames on the bundled oUF's nameplate driver, from two config units: `nameplate` (the Enemy nameplates page: enemy and neutral plates) and `friendlynameplate` (the Friendly nameplates page). `UF.PLATE_UNITS` lists them and `UF.IsPlateUnit(unit)` asks it (`unitframes.lua`). The design is `docs/superpowers/specs/2026-11-11-saftui-nameplates-design.md`, and the plan `docs/superpowers/plans/2026-11-11-saftui-nameplates.md`; the friendly plates' are `docs/superpowers/specs/2026-11-12-saftui-friendly-nameplates-design.md` and `docs/superpowers/plans/2026-11-12-saftui-friendly-nameplates.md`. The code is `SaftUI-Unitframes/nameplates/`, whose `nameplates.xml` lists `nameplates.lua`, `cvars.lua`, `target.lua`, `threat.lua`, `subtext.lua`, `options.lua` (the two pages in `/sui`, which `config/config.lua`'s `UF:GetConfigTable` builds with `UF.SetUpPlatePage` and `UF.DisablePlatePageTabs`), `preview.lua` (the preview plate at the top of the two pages) and `pixels.lua`, loaded after `elements/elements.xml` in both TOCs. Keep `pixels.lua` last: its `'updated'` callback rounds what the others made. The defaults are `config/units/nameplate.lua` and `config/units/friendlynameplate.lua` (an element's other settings are every unit's, `['**']`), whose top comments lay each look out; the enemy one gives its arithmetic. `nameplate` keeps the plates' switches whichever page shows them: `enable` (Nameplates), `friendly` (Friendly plates, on the Friendly page), `threat_solo` and `threat`. The boxes are `nameplate.use_friendly` and `friendlynameplate.use_enemy`, both off by default. Before you touch anything of Blizzard's on a plate, read `.agents/taint.md`, rule 13.

- **Spawning.** `UF:OnEnable` calls `UF:SpawnNameplates()` last, once every other unit is placed and the colors are set. It makes oUF's driver (`UF.oUF:SpawnNamePlates('SaftUI_')`, kept as `UF.plateDriver`) and returns true, or makes nothing and returns false when the driver exists already, Nameplates (`nameplate.enable`) is off, or another nameplate addon draws the plates: `UF:NameplateAddon()` names the first loaded one of `UF.NAMEPLATE_ADDONS` (Plater, EllesmereUINameplates, Kui_Nameplates, TidyPlates_ThreatPlates, NeatPlates, Platynator, whose folder name is unconfirmed, and ElvUI unless its own nameplates are off), a table in the code. oUF can make its driver only once, so a change to either needs a /reload. OnEnable then sets the game's nameplate settings (`UF:ApplyNameplateCVars`), or, with no plates of SaftUI's and no other addon drawing them, puts the user's own back (`UF:RestoreNameplateCVars`). There's no mover: the game places each plate.
- **The frames.** The game makes the plates (`NamePlate1`, ...) and hands each to unit after unit. oUF builds a frame of SaftUI's on a plate at its first add (`SaftUI_NamePlate1`: the plate's child, filling it, `isNamePlate`), which `UF.ConstructUnit` keeps by its plate's number in `UF.nameplates` (not `UF.allUnits`) and `UF.InitUnit` gives its first update; it stays on its plate for every later unit. oUF keeps a frame's `__unit` after the game takes its plate away (its remove clears the unit attribute, which its handler ignores), so whether a plate shows a unit is SaftUI's own record, kept from oUF's added callback to its removed one: `UF:PlateShowsUnit(frame)` asks it, and `UF:PlateForUnit(unit)` finds the frame showing a unit through a token-to-frame map the same two callbacks keep, without walking every plate. `UF:ForEachPlate(fn)` visits every frame, shown or not. A plate's frame takes no mouse, so a click on the plate reaches the game, which targets its unit (the click area, below). `UF:PlaceUnitFrame` places a plate's frame on its plate (`UF:PlacePlateFrame`, under Size) and returns true, and `UF:UpdateUnitFrame` places a plate's frame in combat too (it isn't secure, and its kind, with the config and size it's drawn at, can change mid-fight); `ClearUnitFramePoints` leaves the plates' points. `UF:ApplyConfig(unit, element)` with either plate key (`UF.IsPlateUnit`) does the same for both: with no element it sets the plates' size first (from the enemy look's config, so each frame is then placed, and its click area set again, on its plate's new size), then for every plate works out its config unit again (`UF:ApplyPlateConfig`, below): one that moved gets a full update from its new config, every other the update asked for. Every plate, whichever page it draws from, since the threat text is always the Enemy page's and a box decides which frames fill their plates. `UF:GetConfigFrame(unit)` for either plate key is the lowest-numbered plate's frame.
- **Plate callbacks.** `UF:RegisterPlateCallback(event, fn)` adds to what `UF:RunPlateCallbacks` runs, in the order registered, each in `xpcall` so one that errors leaves the rest to run: `'added'` (frame, unit), after oUF has set the frame's unit and before it updates the elements, never for a plate showing only widgets or a game object (oUF pauses and hides SaftUI's frame for those); `'removed'` (frame, unit); `'updated'` (frame), after every `UF:UpdateUnitFrame` on a plate, so also before `'added'` on a plate's first add and on a plate the game took away, where state from `'added'` or `__unit` can't be trusted (check `UF:PlateShowsUnit`); and `'kind'` (frame), once `UF:ApplyPlateKind` has set the plate's kind. On a plate handed to a new unit oUF also updates every element once (`OnAttributeChanged`) before the added callback, with the frame as the last unit left it. **On an add that changes the plate's config unit** (with the boxes off, a friend after an enemy or an enemy after a friend, and a friend's first add, the frame being built on `nameplate`), `'updated'` also fires inside `'added'`: the first `'added'` callback is `UF:ApplyPlateKind`, whose `UF:ApplyPlateConfig` runs a full `UF:UpdateUnitFrame`. So those `'updated'` callbacks run before `ApplyPlateKind` enables or disables the oUF parts and shows or hides each part, before `'kind'`, and before the other `'added'` callbacks (the scale pin, the target's border); they see `frame.friendly` and `frame.base_unit` already the new kind's. An `'updated'` callback that enables a part in oUF updates the frame again there (`OnShow`). So a plate reused for the other kind gets oUF's `UpdateAllElements` three or four times: `OnAttributeChanged` (oUF, with the old config), `OnShow` (the new config's full update), a second `OnShow` when that update's `'updated'` callback enabled a part (an enemy after a friend: the castbar), then `NAME_PLATE_UNIT_ADDED` (oUF). A friend's first add on a new plate is two full updates (`UF.InitUnit`'s from `nameplate`, then the friendly config's). An add of the kind the plate last showed changes no config unit and adds none (`docs/followups.md`, the cost of a kind change).
- **Friend or enemy.** `UF.IsFriendlyPlate(unit)` is `UnitIsFriend` and not `UnitCanAttack`, a secret answer counting as an enemy. It's broader than Blizzard's own on purpose: any friend you can attack (a duel, free-for-all PvP) gets an enemy's plate. **Each kind draws from its own config unit**, `UF.PlateConfigKey(friendly)` (`unitframes.lua`): an enemy from `nameplate`, or from `friendlynameplate` while `nameplate.use_friendly`; a friend from `friendlynameplate`, or from `nameplate` while `friendlynameplate.use_enemy`. The pages keep the two boxes from being on together; with both on (a profile from elsewhere) each kind takes the other's, and nothing recurses. The frame's `base_unit` names its config unit, which `frame:GetConfig()` and every element's read. `UF:ApplyPlateConfig(frame)` sets it to `UF.PlateConfigKey(frame.friendly)` and, when it changed, points every cached config at the new one (`UF:RefreshFrameConfig`, since the update re-points a part's own config but stops at a part that's off before its texts and icons), clears the points of everything the update places (`UF.ClearPartPoints`: every part, and the texts and icons that are on in a part that's on) and gives the frame a full update from it (`UF:UpdateUnitFrame`: its parts, places, size, fonts, colors and the name's tag), all in one `xpcall`, so an update that errors is reported and the caller goes on; it returns whether it changed. The update places the parts one by one in `pairs()` order, each against the others where they are then, so without the clearing two parts anchored each way round across the two pages (the Friendly page's health bar under the name, the Enemy page's name on the bar) would close an anchor loop on a switch one way or the other, which the game refuses. A profile switch that keeps a plate's config unit still places its parts against the old profile's, as for every unit (`docs/followups.md`). So a plate applies a look again only when its config unit changes, never on a reuse of the same kind. Which parts a plate shows is its config's: by default a friend's name alone (no health bar), an enemy's every part. Only the threat text is hidden on a friend whatever the config says: `UF.PLATE_ENEMY_ONLY` is `{ Threat = true }` (`UF:ElementWanted`). `UF:ApplyPlateKind(frame, friendly)` sets `frame.friendly`, runs `UF:ApplyPlateConfig`, enables or disables the castbar and the quest icon in oUF by `UF:ElementWanted` (`OUF_SWITCHED`), shows or hides every part and turns the aura areas on or off (every part, since oUF's resume after a plate that showed only widgets turns them all on and shows the health bar), then runs the `'kind'` callbacks. It's the first `'added'` callback, so the others read the kind. A `UNIT_FACTION` for the plate's unit, or for the player (every showing plate), applies it again when the kind changed and then updates every element (`UpdateAllElements('UNIT_FACTION')`), which also draws the name again in the new kind's colors, and the `st:name` tag's own `UNIT_FACTION` redraws it too, a frame later, which also covers a faction change that keeps the kind (neutral to hostile). An `'updated'` callback enables in oUF what a config change turned on while the plate shows its unit.
- **Blizzard's widgets.** On every add (widget-only and game object plates too), a frame of SaftUI's moves the pooled UnitFrame's widget container and soft target icon onto the plate, by one point: the container's bottom on the plate's bottom for a plate showing only widgets, else its top under the plate. oUF moves them only at a plate's first add. `UF:RefreshPlateWidgets()` places them again on every plate, then the click areas, after `UF:ApplyNameplateCVars` and on the frame after anyone changes the friendly NPC plates setting, since Blizzard anchors them again when it changes.
- **The click area** (ruling N11, `.agents/taint.md` rule 13). The game takes a plate's clicks in its hit-test points, which oUF sets to SaftUI's frame on every add that shows the unit (`ClearAllHitTestPoints`, then `SetAllHitTestPoints(frame)`). Blizzard's pooled UnitFrame sets its own again outside the add (`UpdateHitTestArea`): when the driver's options update runs `ApplyFrameOptions` on every plate (a window resize, the options loading, one of Blizzard's nameplate options), and from its `CVarCallbackRegistry` callbacks on the friendly NPC plates setting and on showing only friendly players' names. `UF:RestorePlateHitTests()` runs oUF's two calls again for every plate SaftUI shows: from a post-hook on `NamePlateDriverFrame:UpdateNamePlateOptions`, at the end of `UF:RefreshPlateWidgets`, on the frame after either setting changes (its own callbacks on both, through `C_Timer.After(0)`, once however many change, since the registry's callbacks run in no set order), and at the end of `UF:ApplyPlateSize` (out of combat, like the size), since a new plate size resizes the frames that fill their plates. Each hook and callback goes in only where the client has the name (`WatchClickAreas`). `UF:RestorePlateHitTest(frame)` does the same for one plate SaftUI shows, run by `UF:PlacePlateFrame` whenever a frame's place or size changes (a kind change, a box, a Width or Height): whether the game's click area follows the frame's rect after the calls, or takes it when they're made, isn't said outright (`SetAllHitTestPoints`' doc, "to fully encompass the target region", reads as anchors, which would follow; an in-game check). In combat the game allows the calls only on a tick Blizzard's own code changed the click area or the plate got its unit (`CanChangeHitTestPoints`, asked before each of the two calls), so a plate it refuses waits for the end of combat (`QueueAfterCombat('NameplateHitTest')`, which then sets every plate SaftUI shows, one wait however many were refused, also from the single-plate form). Blizzard never sets the hit-test insets, which stay oUF's.
- **Size.** The game has one size for every plate, which also sets how they stack, set through oUF's driver by `UF:ApplyPlateSize()`, from the enemy look's config (`UF.PlateConfigKey(false)`: Enemy nameplates', or Friendly nameplates' while the Enemy page's box is checked), its width and height through `UF.PlateDriverSize`: the config's size is in UIParent's units, and so is the game's plate size (`C_NamePlate.SetNamePlateSize` takes uiUnit; seen in game 2026-11-19: a size of 200 by 20 gives a plate whose `GetWidth` and `GetHeight` are 200 and 20, as are those of SaftUI's frame on it, pinned to UIParent's scale, drawn at the size it had before; the stubs model it as a plate at UIParent's effective scale, which the in-game check's `/dump` confirms or not). The size is counted in UIParent's pixels (`st:GetPixelSize(UIParent)`), made a whole, even number of them on each axis (`2 * floor(n / 2 + 0.5)`, the count first trimmed to 1e-4 as the pixel helpers trim a length, so float noise doesn't tip a tie: 15 pixels is 16), and handed over in UIParent's units (a secret or zero scale gives the config's size as it is). It is never turned into WorldFrame's units: until 2026-11-19 it was (multiplied by UIParent's effective scale over WorldFrame's), which at 1440p handed the game about half the size: the plates sat off their units' centres and no click on a plate targeted, and handing over the config's size fixed both (how the game places a plate by its size isn't documented; the mechanism is inferred). The plate, where the game takes the clicks, and SaftUI's frame on it are then that many pixels: 200 by 20 is 150 by 16 at a scale of 0.75 and 310 by 32 at 1.55, and at a scale of 1 it is the config's size (an odd config size is made even). Pinned and sized again from `st.UIScale:OnChanged`. The game refuses the size from addon code in combat, so in combat it waits (`QueueAfterCombat('NameplateSize')`). Blizzard sets its own size whenever its nameplate options change, so a post-hook on `NamePlateDriverFrame:UpdateNamePlateSize`, installed before SaftUI's first size, sets SaftUI's again. **A plate's frame** is placed by `UF:PlacePlateFrame(frame)` (`UF:PlaceUnitFrame`, so on every full update, in combat too; it reads `frame.config`, which the update sets first): a frame drawn from the enemy look's config fills its plate, as oUF made it (`SetAllPoints`); one drawn from the other config (a friend's, by default) sits on its plate's centre at that config's Width and Height (`st:SetSize`, in UIParent's units, a pixel each), so what's drawn, and what's clicked, is a friend's name box, not the plate round it. A weak table keeps how each frame was last placed (`'fill WxH'` or `'centre WxH'`, the config's size), noted once the anchors and size are set, so a place that errored is tried again by the next update; only a change places it again and sets its click area again (`UF:RestorePlateHitTest`).
- **The game's settings** (`cvars.lua`). `UF.NAMEPLATE_CVARS` maps each setting SaftUI sets while its plates are on to `value(config, current)`: `nameplateShowFriendlyPlayers` and `nameplateShowFriendlyNpcs` from Friendly plates (`nameplate.friendly`, on the Friendly nameplates page); `nameplateMinScale`, `nameplateMaxScale` and `nameplateSelectedScale` at 1, so the game scales no plate by distance or for the target (SaftUI's frame covers its plate); and `nameplateSimplifiedTypes` at its version character alone, which simplifies nothing (it's a bit array kept as text: `.agents/clients.md`). `UF:SetNameplateCVar` skips a setting the client lacks, and records the user's value the first time it changes one, per character and outside every profile (`st.config.char.nameplateCVars`). `UF:ApplyNameplateCVars()` sets every one only while SaftUI's driver exists and Nameplates is on, out of combat (`QueueAfterCombat('NameplateCVars')`), then runs `UF:RefreshPlateWidgets()`. `UF:RestoreNameplateCVars()` (the same key) puts each recorded value back and drops it from the record, keeping one the game refuses, so the next time the plates are on it records whatever is set then. Turning Nameplates off puts them back at once (the plates stay up until the reload), on again sets them, and Friendly plates sets them. A profile switch (the full pass of `UF:ApplyConfig`) sets them again only when Friendly plates differs from what was last set (`UF.appliedFriendly`, cleared by `UF:RestoreNameplateCVars`), so a key press of Blizzard's friendly plates binding stands until Friendly plates itself changes. The same pass clears each unit frame's, boss frame's, group button's, plate's and test preview's placed parts before placing them, so two parts anchored each way round across two profiles can't close a loop (`ClearAllPartPoints` in `unitframes.lua`, `UF.ClearPartPoints`; a part the new profile switches off is the exception: `docs/followups.md`).
- **The layout** (the defaults). An enemy's plate: the health bar fills the plate, 200 by 20, with the name inside on the left (Max width 150, no level or classification, hostile names colored) and the health inside on the right as a Short value. The castbar hangs 6 under it, 182 by 12, its 12 by 12 icon 6 to its left so the row starts at the bar's left edge, with no time and grey for a cast that can't be interrupted. Up to 6 of the player's debuffs sit 6 above the bar from its left edge, up to 4 buffs the player can purge 6 right of it, the quest icon 6 left of it and the raid mark centred 6 above the debuff row, which leaves the space above the bar's right end to the threat text. A friend's plate (`friendlynameplate.lua`) is a name: its frame 150 by 16 on the plate's centre, Theme None (every unit's frame default, `config/default.lua`, not set in `friendlynameplate.lua`), no health bar or health text, the name centred on the frame (anchored to the frame itself, `element = false`, which the Position editor shows as Unit frame, not to the bar that isn't there), Max width 150, Class color, Color friendly and Color hostile on, no level or classification, and the raid mark 16 square, its bottom 4 above the name's top. Its castbar, aura areas and quest icon are off, set as the enemy's for whoever turns them on, and hang off its hidden health bar, which is still laid out (Shown and enabled). Every size on a plate is an even number of pixels, so centred anchors stay on whole pixels (the half pixels bullet, above).
- **The target's and hovered plate's border** (`target.lua`). The target's plate is found by its frame: a plate's frame marks the target when its parent is `C_NamePlate.GetNamePlateForUnit('target')` (`UF:IsPlateTarget`), never by `UnitIsUnit`. The border is drawn on `UF.PlateBorderFrame(frame)`: the health bar's drawn frame while the bar carries it (drawn, and wanted by its config: `UF:ElementWanted`, since a bar its config has off keeps the drawing it had), else the plate frame's while that is drawn, else none, as on a friend's name-only plate. Under Thick and Thin it's a line through `st:SetBorderColor` in the plate config's `target_color` (white by default), and every other plate gets the theme's own color back. The plate under the cursor gets the same in `hover_color` while `hover_highlight` is on; the hovered target keeps the target's look. Each plate reads the config it's drawn from (`frame.base_unit`: Enemy or Friendly nameplates'), whose General tabs have Target color, Highlight on hover and Hover color. The hovered plate is found by its frame too, `C_NamePlate.GetNamePlateForUnit('mouseover')` (`UF:IsPlateHovered`), on `UPDATE_MOUSEOVER_UNIT`; the game fires nothing when the cursor leaves a unit, so while a plate is hovered a `C_Timer.NewTicker` looks again every 0.05 s, redraws the plate it left and the one it's on, and is cancelled once nothing is hovered. Under Blizzard it's the control `nameplatetarget`'s art (themeart_data.lua) round what carries the border (the health bar, or the frame) at its offsets, tinted by the color (white leaves the atlas as it is; another color desaturates it first, since Forever's atlas is yellow), a texture of a frame of SaftUI's two levels over the bar, kept in a weak table (`UF:PlateTargetArt`) and unsnapped. `UF:UpdatePlateTarget(frame)` runs from `'added'`, `'updated'`, `PLAYER_TARGET_CHANGED` (every plate) and `UF:OnColorsChanged('theme')`, and `st:KeepOwnColors` on both candidate borders keeps the color through a theme recolor or redraw, with one function for every frame (`RecolorBorder`, which finds the frame's plate), so keeping it again on each update makes nothing new.
- **Threat** (`threat.lua`). The player's threat on an enemy tints its health bar and shows as a percent above the bar's right end, in a party or raid, and on your own only with Threat when solo (`nameplate.threat_solo`). Threat is enemy-only whatever the settings, and always reads Enemy nameplates' settings (`nameplate.threat_solo`, `nameplate.threat`), whichever page an enemy's plate draws from: with the Enemy page's box checked, an enemy's plate takes everything else from the Friendly page, and the tint goes on that page's health bar (off by default, so only the percent shows). `UF.ThreatState(isTank, status, coTanked)` is the table by role over `UnitThreatSituation('player', unit)`: a tank's 3 good, 2 warning, 0 or 1 bad (good while another of the group's tanks holds the mob), anyone else's 0 good, 1 warning, 2 or 3 bad, and nil nothing. `UF:PlateThreat(frame)` gives nil for a friendly plate, on your own with Threat when solo off, a threat state `C_Secrets.ShouldUnitThreatStateBeSecret` says is secret, or a secret status, and reads the player's role from Blizzard's own `PlayerUtil.IsPlayerEffectivelyTank()`. For a tank who doesn't hold the mob, it reads the group (`party1`-`party4`, or `raid1`-`raid40`) for who does, but only for a mob in combat (`UnitAffectingCombat`; a mob out of combat has no threat list, and a secret answer still reads the group), by each member's threat state on it (2 or 3; a secret state is skipped), stopping at the first: another of the group's tanks (`UF.IsGroupTank`: the tank role, or a tank aura where the client has `UnitHasEffectivelyTankAura`) makes it good, and a member who isn't a tank makes it bad, the mob loose, even when the tank isn't on its threat list. `UF:UpdatePlateThreat(frame)` sets `frame.threatState`, which `elements/health.lua`'s `PostUpdateColor` puts on last each time oUF colors the bar (warning and bad, in the profile's `colors.threat`, the Colors tab's Threat section), and a bar that loses its tint gets one `Health:ForceUpdate()`. The text is the plates-only element `Threat`, enemy-only, with its own tab after Health on the Enemy page only; its constructor sets the text's `config` and `GetConfig` to `nameplate.threat`, so a plate drawing from `friendlynameplate` keeps the Enemy page's. It is: `UnitDetailedThreatSituation`'s scaled percent through `SetFormattedText('%.0f%%', ...)`, a secret one handed to the game as it is, in the tint's color, or Text Normal while good. It's written again only when its state, a non-secret percent or its color changed (a secret percent always is), or forced by `UF:UpdatePlateThreat(frame, true)`, which the `'kind'` and `'updated'` callbacks and `UF:OnColorsChanged('threat')` pass. A mob's threat list update retints its plate, found through `UF:PlateForUnit`; a threat situation update retints every plate for the player and a plate's own for its token; the roster, the roles, the player's spec and form or stance (`UPDATE_SHAPESHIFT_FORM`; a tanking form is a tank aura on Forever) retint every plate; and so do the `'kind'`, `'updated'` and `'removed'` callbacks. Only `nameplateN` tokens are looked for among the plates.
- **Subtext** (`subtext.lua`). A second line under a plate's name: an NPC's title (`<General Goods Vendor>`) or a player's guild (`<Some Guild>`), plain `<` and `>` with no color codes (the color is the config's, by `SetTextColor`). It is the plates-only element `Subtext` (`UF:AddTextElement`, its tab right after Name's on both plate pages, `order = 5.5`), drawn from the plate's `frame.base_unit` like the name, so it reads `subtext` of Enemy or Friendly nameplates: `npc` and `player` (the two boxes), `font`, `color`, `alpha`, `max_width` and `justify` (Align; every text's rule, `UF.SetMaxWidth` in `updaters.lua`) and `position`. `enable` is always true and not on the page: `UF:ElementWanted` needs it, and the two boxes decide what the tag returns. Friendly plates default to both boxes on, centred 2 under the name; enemy plates to both off, centred 24 under the health bar (under the castbar's row). The text is the `st:subtext(<config unit>)` tag (events `UNIT_NAME_UPDATE` and `PLAYER_GUILD_UPDATE`, both unit events to oUF), which returns `UF.PlateSubtext(unit, config)` or `''`, and `''` while it is bound to a config unit other than `UF.PlateConfigKey(UF.IsFriendlyPlate(unit))` (a plate just handed to the other kind), so nothing is read under the other kind's boxes. `UnitIsPlayer` is asked first (a secret answer gives nothing); with a kind's box off nothing is read for that kind, so no `C_TooltipInfo.GetUnit` call for an NPC with `npc` off. `UF.NpcTitle(unit)` is the tooltip's second line when it is a plain, non-empty, untyped (`Enum.TooltipDataLineType.None`) line that isn't the level line (`TOOLTIP_UNIT_LEVEL` as a pattern: a client may leave that line untyped); a pet's owner line is typed, so never a title. A player's guild is `GetGuildInfo(unit)`'s first return: plain gets brackets, a secret one is wrapped by the game (`C_StringUtil.WrapString`). The tag is bound again when `frame.base_unit` changes, from the `'updated'` plate callback (after the whole update, so the name's own rebinding comes first), followed by `frame:UpdateTags()`.
- **The preview plate** (`preview.lua`). A sample plate in a fixed band at the top of the Enemy and Friendly nameplates pages, on every tab, under the Unit picker line: `UF.PlatePreviewBand(page)` is the page's `pickerBand` (Core's band, `.agents/edit-mode.md`; one table per page, set by `UF.SetUpPlatePage`). `UF:PlatePreviewFrame(page)` makes the page's frame once, a plain frame (no oUF frame, unit, secure frame or Blizzard frame, so it works in combat) with the plate's fields (`isNamePlate`, `friendly`, `base_unit`, `GetConfig`, `TextOverlay`, `elements`, no-op `Tag`/`Untag`/`UpdateTags` for Name's and Subtext's config code) and every registered part that takes `nameplate`, the aura areas aside (below); `UF:StylePlatePreview(page)` is `UF:UpdateUnitFrame`'s order on it (`base_unit` re-read from `UF.PlateConfigKey`, so the source page's config while the box is checked; configs refreshed; parts' points cleared; frame size; each part's `UpdateConfig`; the backdrop) and then fills made-up data: health value and colour, health text from `UF.PlainHealthText`, name from `UF.NameParts` and `UF.FormatName`, the cast, the threat text `87%` (shown by `UF:ElementWanted`, so Enemy only), the subtext by the page's NPC or Player box, the skull and the quest icon. The sample is Thornfang Ravager (hostile elite NPC) on the Enemy page and Aldric (the player's class) on the Friendly one. The aura areas (`Buffs`, `Debuffs`) are the preview's own plain frames, never `CreateAuras` or Blizzard's container (taint rule 11): each has `config`, `GetConfig`, `name`, `unitframe` and `noSize`, is placed and shown by `UF:UpdateElement` (bare, no backdrop) and sized by `UF.AuraAreaSize` (`elements/auras.lua`, the sums `UpdateConfig` uses too), and holds `buttons`, `min(Max, 6 debuffs or 4 buffs)` plain frames with `Icon`, `Count`, `Cooldown` and `Border`, styled by the real `StyleButton` (`UF.StyleAuraButton`, size from `UF.AuraButtonSize`) and placed from the Initial anchor by a size plus Spacing per step, a new row after Per row, along Grow right and Grow up. Made-up icons and stacks, a dispel type colour on the debuffs' border where Dispel type border is on, the stealable colour on the first buff where Stealable border is on, the swipe part way and paused, the timer text only where its Enable is on. The extent and the levels count the buttons too. `UF.PlatePreviewExtent(frame)` is how far the shown parts reach above the bar's top and below its bottom. The band's `height` is `nil` while another nameplate addon draws, else the extent plus the bar's height and a 12 margin each side, kept between 120 and 200 and whole; `draw` and `refresh` (a slider drag) style the frame, parent it to the holder and put the bar's centre under the holder's, its top 12 plus the extent above it below the holder's top; `release` hides it. The preview's frame levels are relative to the holder (the configured part levels ranked and compressed to the holder + 1 to + 15, texts and cooldowns above, all under the window's pop-ups at the holder + 19) and real plates are untouched. It is styled from the page's draw, not from `UF:UpdateConfig`, so a change in combat shows at once. Tests: `tests/unitframes/nameplate_preview_test.lua`.
- **Whole pixels** (`pixels.lua`). Each plate's frame is pinned to UIParent's effective scale (`UF:PinPlateScale`: `SetIgnoreParentScale(true)` and `SetScale(UIParent:GetEffectiveScale())`; a secret scale leaves it as it is) on every add, and every plate again from `UIScale:OnChanged` (after the scale is set and the pass has run; the plates hear no screen event of their own), which also sets the plates' size again. `UF.RoundLayout(region, recursive)` turns on the game's `SetRoundLayoutToNearestPixel`, and for a texture turns its own snapping off (`SetSnapToPixelGrid(false)`, `SetTexelSnappingBias(0)`); with `recursive` it walks the region's regions and child frames. It reads and sets no size. It runs from SaftUI's frame on the plate after every update of the plate (`'updated'`) and again after a theme change (`UF:OnColorsChanged('theme')`, after the target's border), and skips, with everything under them, SaftUI's own aura containers by identity (`UF.auraContainers`, a weak-keyed set the aura element's constructor fills), forbidden regions, and anything `IsObjectType('AuraContainer')` says is one. It never reaches Blizzard's frames. `elements/auras.lua` rounds what SaftUI makes on a plate's aura buttons, each backdrop and Thick's inner debuff line, where it makes it. Anything made on a plate outside an update must call `UF.RoundLayout` itself. In combat a scale change waits whole (the check, the pass and so the pin and the size), so in The game's UI scale the plates are off UIParent's scale until the fight ends; in Automatic and Pixel for pixel the pin they keep is the right one.
- **Themes.** The plates draw as every unit does: the frame None by default (each page's own Theme), its bars as `unitframe` (under Blizzard the box, with health on Blizzard's raid fill and the castbar on its own texture), the cast icon as a `control` (bare under Blizzard) and the aura buttons as `aura`. With the Enemy page's Theme Blizzard and the health bar's also Blizzard (its default, SaftUI's, under the Blizzard theme), health fills the plate and draws None (one box per edge), and the target's border goes on the plate frame's box.

## The UI scale

`st.UIScale` (`SaftUI-Core/uiscale.lua`, a table, not a module, because it runs inside `SaftUI:OnEnable` before any module enables) works out how big SaftUI draws and keeps UIParent at it. Its model (`Resolve`, the tokens, `Normalize`) is in "The `st` object and modules"; this is the runtime.

- **The choice.** `st.config.global.uiScale = { mode, size }` (account wide, never in a profile; absent while it is Automatic at 100%, so nothing is written for most players). `mode` is `'auto'` (the screen's height against 1440, times the size), `'pixel'` (one unit a pixel) or `'game'` (Blizzard's own UI scale). `UIScale:Saved()` reads it (`Normalize`, never writing: a save that isn't a choice reads as the default and stays as it is), `UIScale:Current()` is the preview, else the saved, else the default, `UIScale:Default()` what the default makes of this screen, `UIScale:Applied()` what the last check applied. `st.config.global.uiScaleNotice` is the version of the first-login line (`UIScale.NOTICE_VERSION`, 1): `Start` prints `UIScale.FIRST_LOGIN` and sets it only when nothing is saved and the automatic size isn't 1 (k not 1), so the owner's 1440p screen is never told and another screen of the same account still is. `UIScale.MODE_NAMES` are the three modes' names, which the Scale select, the prompt and `/sui scale` all say.
- **At login.** `SaftUI:OnEnable` makes the AceDB (`InitializeAceConfig`), then runs `UIScale:Start()` in `xpcall`, then the rest, so every module builds at the final scale and reads the final tokens. `Start` resolves the saved choice on `UIScale.ReadScreen()` (`GetPhysicalScreenSize()`), sets `UIParent:SetScale(uiScale)` in Automatic and Pixel for pixel (in The game's UI scale it sets nothing), measures the tokens (`SetTokens`), records what it applied and listens for `UIScale.EVENTS`. It runs no pass and no callback: nothing is built yet. In combat (a `/reload` in combat) it sets nothing and queues the check for the end of it. On the 1440p owner's screen it makes exactly the call login always made (`768 / 1440`).
- **The events and the check.** `UI_SCALE_CHANGED`, `DISPLAY_SIZE_CHANGED` and (in `pcall`, so a client without it loses only that) `NOTCHED_DISPLAY_MODE_CHANGED` call `UIScale:ScheduleCheck()`: one `C_Timer.After(0)` however many events come in a frame (they come in pairs). The engine sets UIParent's scale over SaftUI's on a UI Scale slider change and on a display change, by the time the events arrive, and it stays (`.agents/clients.md`), so the check on the next frame puts it back; `UIScale.RECHECK` (seconds to a second check) is nil because that is all that was seen. SaftUI's own `SetScale` fires neither event, so an event that arrives while the check runs is its own and asks for nothing: no loop.
- **`UIScale:Check()`.** (1) Resolve the current choice on the screen now, with UIParent's scale as the game's scale; nil returns. (2) In combat, queue itself (`st:QueueAfterCombat('UIScale', ...)`) and return: nothing is set, measured or run in combat. (3) In Automatic and Pixel for pixel, when UIParent's scale differs from the wanted by more than 1e-5, `UIParent:SetScale(uiScale)` (scales read back in single precision, so never `==`). Just switched to The game's UI scale: `UIParent:SetScale(UIScale.GameScale())` once (Blizzard's slider while Use UI Scale is on, else `GetDefaultScale()`; when the game doesn't say, nothing is set and chat says the size shows after `/reload`). (4) `SetTokens()`. When the check set UIParent back, or UIParent's scale, the pixel or the line weight differs from the last check's, run the pass, then the callbacks; otherwise only `st:UpdateScreenMargin()`. A set-back counts as a change because whatever was drawn while the engine's scale was in force (in a fight, or in the frame before the check) must be drawn again and the plates pinned again; it costs one profile update per slider move or display change. **The guard:** an engine that sets its scale again after every set-back would be fought every frame, so after 5 set-backs on one screen within a second (counted per screen: a window dragged through sizes trips nothing) the check leaves the engine's scale and says so once in chat (untick Use UI Scale, or choose The game's UI scale); a change of screen, `Preview`, `Apply`, `Revert` or the scale being right again starts over (`UIScale:GaveUp()` says it is in force, and `/sui`'s line under the UI scale rows says so then). **Blizzard's slider line:** when the check sets the scale back in Automatic or Pixel for pixel and `useUiScale` or `uiScale` reads differently from the check before (which tells the player's move from a display change), chat says once a session `UIScale.SLIDER_LINE` ("SaftUI sets the UI's scale itself. To use the game's UI Scale, choose The game's UI scale in /sui > Global settings > General."); every check takes the reading, so a later display change says nothing. **Blizzard's Use UI Scale row** (`SaftUI-Core/uiscalelock.lua`): while the choice in effect isn't The game's UI scale, a cover of SaftUI's own lies over the row in Options > Graphics (dims its checkbox and slider, takes their clicks, and its tooltip, `UIScale.LOCK_TOOLTIP`, says where the size is set); `UIScale:IsLocked()` says it is up, `UIScale:RefreshLock()` puts it on or off and runs at the end of every check, so a choice made in `/sui` with the options open follows. How it finds the row without taint: `.agents/taint.md` rule 6. In The game's UI scale a changed reading has to repeat on the next frame before the pass, so a pair of events split across two frames is one pass. `UIScale.TOLERANCE` (1e-5) is far over single precision's noise (3e-8) and far under a 5% size step (0.02 or more).
- **The pass** is the profile update, `st.Config:UpdateConfig()` (where Config has one; the test shell's has none): every drawn frame redrawn in the new line (`st:RedrawThemed()`), every module laid out again, the margin and every mover placed again, an open `/sui` rebuilt. It is not a history step. A profile switch, copy or reset never runs a scale pass: the choice is account wide.
- **`UIScale:OnChanged(fn)`** registers `fn(resolved)`, run after every pass in the order registered, each in `xpcall`. The nameplates (`nameplates/pixels.lua`: pin every plate, set the size) listen; edit mode's bar, floating window, grid and Coordinates label (each its screen events' function, also given here) and `/sui`'s size (`OW:FitToScreen()`) listen too.
- **The interface.** `Preview(choice)` tries a choice without saving it (`ok, why`: `'combat'`, `'mode'`, `'size'`, `'screen'`; it keeps the choice in effect before the first preview); `Apply(choice)` saves it (`Apply(nil)` and `Apply(DEFAULT)` remove the save; `true, 'combat'` when the scale will follow the end of the fight, and it saves in combat too); `Previous()` is the choice in effect before the first preview (nil when not previewing); `Revert()` ends a preview, back to the saved choice (in combat the preview ends at once and the scale follows the fight, with `OnChanged` the signal that it applied); each runs the check at once. `Describe(resolved)` is the line `/sui` shows. A preview is held in memory only: a `/reload` or logout comes back at the saved choice.
- **The Keep prompt** (`SaftUI-Core/Config/uiscaleprompt.lua`, `st.UIScalePrompt`, `.agents/edit-mode.md`) is the one way a UI size is changed with a question: `Ask(choice)` runs `Preview`, `Keep()` runs `Apply(Current())`, `GoBack()` runs `Revert()` (to the choice before the first preview, `Previous()`), and `/sui scale` is its command. It listens on `OnChanged` to hide once a revert that waited for combat has applied.
- **Fonts follow the scale, unrounded.** A font's size is in units like every size, so it grows and shrinks with k (Homespun is 7.5 pixels at 1080p, which the owner has seen and approved). Whether Homespun and the Lucide icons are crisp at the Mac's 1.55 is not known: it waits for the Mac friend's check (the followups "UI scale: phase 5" and "Delete the font demo"), and the font demo (`/suifonts`) stays until then.
- **What is not whole-pixel yet at a k other than 1** (each has a followup in `docs/followups.md`; the owner's 1440p screen, k = 1, has none of these). Phase 1 made every line SaftUI's theme engine draws whole, and every frame it places by `st:PlaceAtPosition`, the screen margin and the plates. Still off: the options kit's boxes, buttons, hairlines and labels, including the Keep prompt's buttons (phase 2); the docked edit mode bar's place and the Coordinates label, which shows stored units (phase 3); a nameplate's inner parts, the action bars' and the totem bar's own even-pixel helpers, the bags' loading overlay and the two `st:ThemeInset` readers without a frame, `SaftUI-Misc/totemskin.lua` and `SaftUI-Bags/categoriestab.lua`, and every other addon's one-unit lines (phase 4); and the Blizzard theme's art, whose atlas corners and edges scale with k and are not placed on whole pixels in a scaled frame (allowed by the plan's Ruling 11). One-pixel lines stay one pixel on frames Blizzard scales (the Cooldown Manager and buffs at an Icon size other than 100%; the owner's call). An odd nameplate Width or Height is one pixel larger at k = 1 (the driver's even pixels).
- **Tests.** `start_uiscale(choice)` in the shell starts it; the engine's moves are `stub.change_display`, `stub.engine_set_scale` and `stub.engine_resets_scale` (`.agents/testing.md`).

## Micro menu bar

`SaftUI-Minimap/micromenu.lua`'s items (each `AddButton` option set: `icon`, `micro`) draw their panels (`micromenuart.lua`) as kind `control`, which Thick and Thin draw exactly as `small` and Blizzard leaves clear; under Blizzard every item (the zone, clock, latency, FPS, addon count, expansion, mail, difficulty, queue and search items and each micro button's holder) stands on the same box, `ThemeArt.LayBox(item.boxPieces, item.backdrop, true)` (the minimap header button's box, with its centre), laid on the item's panel at the item's own rect: the bar's height (`MicroMenu:BarHeight()`) by the item's width (`S.ItemWidth`). The panel has no fill of its own, so the box is all there is; its pieces are textures of the panel, kept in the item's entry (`item.boxPieces`) and never fields on a Blizzard frame, and Thick and Thin hide them. A micro button's holder (`theme = 'none'`: under Thick and Thin the button's own panel is its box) gets a panel only under Blizzard, one level under the holder, so Blizzard's button art stays above its box; a turned-off item's holder is concealed at alpha 0 and takes its box with it. The search item keeps the magnifier SaftUI draws on Forever (`icon`) on its box; on retail it keeps Blizzard's own tracking button icon. There is no strip under the micro buttons on either client. `MicroMenu:GetItemBox(button)` gives the tests the pieces. Blizzard's `MicroMenu.BorderArt` and `BackgroundArt` stay faded and unmoved under every look (`.agents/taint.md`). **Colors follow a pick live:** `MicroMenu:OnColorsChanged(group, key)` (`micromenu.lua`) calls `MicroMenu:ColorMicroButtons(key)` (`microbuttons.lua`: each Blizzard micro button's alert flash at Text > Caution, 0.5, set again on the region SaftUI already colored, under Thick and Thin only, never under Blizzard's art) for Text `caution`, and `MicroMenu:ColorDifficulty()` (`instancedifficulty.lua`, which the badge's skin calls too) for Item quality 1, 3 and 4; the micro buttons', the bar items' and the tracking, queue and expansion buttons' hover and pushed are the states helpers' (they follow the Accent through their own records, above). Color setters on regions only, so it runs in combat.

**The bar's settings** (`micromenuoptions.lua`, defaults in `SaftUI-Minimap/config.lua`'s `micromenu`): `height` and `spacing` (`MicroMenu:BarHeight`, `MicroMenu:Spacing`, held to `HEIGHT_MIN..MAX` and `SPACING_MIN..MAX`) lay out every item; Blizzard's micro buttons keep the template's 32 x 40 shape at the height (`MicroMenu:MicroWidth`) and their icons, art and emblem scale with it. Each item has a `key` (`AddButton`'s option: `zone`, `clock`, `latency`, `fps`, `addons`, `tracking`, `expansion`, `mail`, `difficulty`, `queue`, and `micro_<name>` from a micro button's global name, `MicroMenu.MicroKey`): `widths[key]` sets a text item's width, `show[key] == false` turns an item off (`show['*'] = true`, so the page stores only `false`). An item turned off is concealed, never hidden or reparented (`S.Conceal`; a micro button's through `S.ConcealMicro`, whose `OnEnable`/`OnDisable` post-hooks keep it at alpha 0 after Blizzard's own alpha write), and `UpdateButtons` skips it. `font` is the text items' and the bar buttons' labels' font (`MicroMenu:TextFont`, `MicroMenu:OnFontsChanged`). `visibility = 'mouseover'` fades the bar to `fade_alpha` until the mouse is over the Container (`MicroMenu:UpdateFade`, `MicroMenu.Fader`): the Container, Blizzard's `MicroMenu` while it sits in `MicroMenuContainer`, and the micro buttons' panels (`S.FadeMicro`); in a pet battle or vehicle bar Blizzard's buttons are drawn whole, and `MicroMenu:ReapplyFade` (from `microbuttons.lua`'s `Refresh`, after Blizzard's `Layout`) re-applies the bar's alpha when Blizzard moves `MicroMenu`. A turned-off micro button's holder also takes alpha 0, so a box laid on it draws nothing. Tests: `tests/minimap/micromenu_settings_test.lua`.

The bags' states (`SaftUI-Bags/`) are the helper's and nothing is hand-rolled: a view button (`header.lua`) is Core's `st:CreateButton` box with its glyph merged in (`st:AddStates(button, 'box', { glyph = button.glyph, glyphRest = Text > Normal })`: the glyph pieces are white colour textures, the helper's vertex colour is the icon's colour; `ColorGlyph` puts the rest colour on every piece, also under Blizzard, then `st:PaintStates`), and the current view is `st:SetButtonPressed(button, on)` (the helper's selected state: accent edge and fade; Blizzard's pressed panel button under Blizzard); never pass `text` in a merged `st:AddStates` on a Core-skinned button. An item slot's pushed texture is kept under Thick and Thin (`INV:SkinSlot` no longer clears it), Core's `st:SkinActionButton` colors hover T+ and pushed T-; the bag bar's slots (Blizzard's buttons, `containers/bag.lua`) are an `'icon'` with `pieces = { hover = slot:GetHighlightTexture(), pushed = slot:GetPushedTexture() }` registered before `RestyleBagSlot` is hooked, which puts the texture, points and `BLEND` back after Blizzard's `UpdateTextures` and ends in `st:PaintStates(slot)`. The Categories list's rows (`categoriestab.lua`) are `'row'` (`bar = 'left'`, `text = f.name`, `textRest` Muted for an off category else Text > Normal, `blizzard` while the row wears the Settings list art, whose hover and picked atlases stay on `f.hover` and `f.tint`), `st:SetState(row, 'selected', ...)` on every layout; `+ New category` and the rule editor's `+ Block` and `+ Group` are `'glyph'` links (`glyphRest` the Accent, `glyphHover` Text > Strong); the rule editor's NOT box is a kit `'box'` (`W.HoverStates`, selected while on, its label rests Muted and is picked over the fade), its check boxes `'check'` with the helper's mark, and the Caught now tint is Text > Warning at its own `CAUGHT_ALPHA` (0.25). The category filter check and the currency and bank checks are Core's check and `'bare'` styles (the 8 box's mark is `floor(8 / 6)` = 1 in); the Edit toggle is Core's `'button'` check style, whose label rests white (`textRest`).
