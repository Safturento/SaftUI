# Architecture

## Addons and load order

- Every folder `SaftUI-<Name>/` is a separate WoW addon. All of them `## RequiredDeps: SaftUI-Core` and `## Group: SaftUI-Core`.
- **TOCs:** Core and Unitframes have per-client TOCs (`*_Forever.toc` = `## Interface: 16001`, `*_Mainline.toc` = `120000`). The other addons use one TOC listing both (`## Interface: 120000, 16001`). When you add a file, add it to **every** TOC of that addon (and to the folder's `load.xml` where one is used, e.g. `SaftUI-Core/EditMode/load.xml`, `SaftUI-Misc/Skinning/load.xml`).
- Load order matters: Core loads first, then each module addon in its TOC order. Defaults (`st.defaults.*`) must be defined at file load, before Core creates the AceDB (see below).
- **Libraries:** Core bundles LibStub, CallbackHandler-1.0, Ace3 and the shared media libraries. An addon that needs more bundles them in its own `Libraries/` and lists them first in its TOC, without a second copy of LibStub or CallbackHandler: Unitframes has oUF, ActionBars has LibActionButton-1.0 and LibButtonGlow-1.0 (sources and versions in `SaftUI-ActionBars/Libraries/README.md`).

## The `st` object and modules

- `SaftUI-Core/init.lua` creates the addon: `SaftUI = AceAddon:NewAddon(st, 'SaftUI-Core', 'AceEvent-3.0', 'AceHook-3.0')`. Every file starts with `local st = SaftUI`.
- A module is `local M = st:NewModule('Name')` (AceAddon module, with AceEvent + AceHook mixed in). Module names are the keys used everywhere else: `st.modules[name]`, the `/sui` tree, and edit mode `configPath`s. Current modules include ActionBars, Auras, Chat, Colors, Config, EditMode, Experience, Fonts, General, Inventory, Loot, MicroMenu, Minimap, Movable, Skinning, SwingTimer, TaintFix, Theme, Tooltip, TotemBar, Unitframes, Utilities.
- Lifecycle: `OnInitialize` (rarely used), `OnEnable` (build frames, register movers, hook Blizzard), `UpdateConfig` (re-apply everything from the profile; see below), `GetConfigTable` (the module's `/sui` page; its top-level table's `category`, Frames, Combat or Info, groups it in the window's sidebar). Core's General, Fonts, Colors, Theme and EditMode modules give the tabs of the Global Settings page instead, in the order of `GLOBAL_TABS` in `SaftUI-Core/Config/config.lua` (see `.agents/edit-mode.md`). A `/sui <command>` with its own sidebar button is `st.Config:AddCommand` (see `.agents/edit-mode.md`).
- A module that shows profile colors can define `OnColorsChanged(group)`. `st:ColorsChanged(group)` (`SaftUI-Core/Media/colors.lua`) calls it on every module that has one (one per module: SaftUI-Loot's, in `init.lua`, hands it to the feed and the roll bars), after a Colors tab change; `group` is `text`, `button`, `class`, `reaction`, `renown`, `power`, `item_quality` or `status`, or `theme` after a theme recolor or redraw put the theme's colors back on every drawn frame (see Themes, below). Skinning's skins are its submodules, which `st:ColorsChanged` doesn't reach, so `SK:OnColorsChanged` passes the call on to them. Anything that colors by item quality uses `st:QualityColor(quality)` (the profile's color, else Blizzard's).
- `SaftUI-Core/constants.lua` sets client flags and screen constants. See `.agents/clients.md` for `st.retail` / `st.forever`.
- Core helpers live in `SaftUI-Core/api.lua`. The ones you'll use most:
  - position: `st:UnpackPoint`, `st:ResolveFrame`, `st:ValidateAnchor`, `st:RoundToPixel`, `st:GetPixelSize`
  - **Half pixels from centred anchors.** SaftUI's UI scale makes one unit one physical pixel, and `st:RoundToPixel` keeps sizes and offsets whole. But a frame anchored by its centre on an axis (TOP/BOTTOM centre it across, LEFT/RIGHT up and down, CENTER both) that's an odd number of pixels long on that axis has its edges half a pixel off the grid. So do its children. The game then rounds each child separately, and children either side of the centre round in opposite directions. Symptom: one gap in a row of buttons is a pixel short, right at the middle (a 12-button bar at 3px spacing is 573px wide). Fix: round the frame up to an even pixel length on each centred axis, so its edges and its centre stay on whole pixels and frames anchored to it line up too. `EvenIfCentred` in `SaftUI-ActionBars/bars.lua` does this, through `AB:PlaceFrame`, which sizes and places both the bars and the extra buttons' holders (`extras.lua`). When another addon needs it, move it into `api.lua`. Where the anchor can change without SaftUI's sizing code seeing it, round up on both axes whatever it is. The totem bar (`SaftUI-Misc/totembar.lua`, `EvenPixels`) is always sized even, with the spare pixel as empty bar at the right and the top: on a shaman SaftUI places it from its holder, whose Position can be anchored by any point and is changed by drags, and on other classes Blizzard's Edit Mode places it.
  - combat-safe moves: `st:CanMoveNow`, `st:SafeReposition`, `st:QueueAfterCombat`, `st:GetPoints`/`st:RestorePoints`
  - moving Blizzard frames whose methods are Lua overrides: `st:SetPointDirect`, `st:ClearAllPointsDirect`, `st:SetSizeDirect`
- Styling: `st:SetBackdrop`, `st:SetTemplate`, `st:SetBackdropIn` (`theme.lua`, below), `st:CreateFrame` (`panels.lua`), `st:GetFont` (`Media/fonts.lua`), `st:CreateButton`/`st:SkinButton` (`Widgets/`). Colors other than the theme's live in `st.config.profile.colors`.

## Themes

SaftUI draws its frames in one theme, Thick, Thin or Blizzard, set on Global Settings' Theme tab, which any module can override. The design is `docs/superpowers/specs/2026-11-10-saftui-themes-design.md`, and the Blizzard theme's `docs/superpowers/specs/2026-11-10-saftui-blizzard-theme-design.md`. Blizzard is being built: the engine resolves it, holds its art's tables and draws its art (`SaftUI-Core/themeart.lua`), but no option offers it yet.

- **The profile.** `st.config.profile.theme = { name, transparent, opacity }` (`thick`, a Transparent background, 0.9 by default). A `name` this version doesn't know (a later version's theme, in a profile opened by an older build) reads as Thick wherever it's read (`st:ResolveTheme`, and the Theme tab's rows), and stays saved until the user picks a theme. Each theme keeps its own colors, arrays in `st.config.profile.templates.thick`, `.thin` and `.blizzard` (`bordercolor`, `altbordercolor`, `backdropcolor`, and Blizzard's `windowcolor`, the fill of its windows; Thick's and Thin's windows take their `backdropcolor`); `templates.close` is the close button's red. The key is still `templates`: saved variables may keep the word, only what the user sees changes.
- **A module's override** is a pair of config keys, `theme` (`'theme'`, `'thick'`, `'thin'` or `'none'`; the engine also takes `'blizzard'`, which no option offers yet) and `background` (`'theme'`, `'solid'` or `'transparent'`); `'theme'` follows SaftUI's. The Bags have a second pair for their item and currency slots, `buttontheme` and `buttonbackground`, and the unit frames one per unit and element. Core's `buttons` and `panels` have the pair with no option, following the theme. The options come from `generators.theme` and `generators.background` (`.agents/edit-mode.md`), and a change re-runs the module's `UpdateConfig`, which draws with the new pair.
- **The engine** is `SaftUI-Core/theme.lua`:
  - `st:ResolveTheme(theme, background, kind)` turns a pair into the look a frame is drawn with as kind (`{ name, inset, alpha, colors, kind }`, or nil for None); a Transparent background uses the profile's Opacity even while the toggle is off. `st:ThemeInset(theme, background, kind)` is how far in its border reaches: where content sits, for layouts that used to read `frame.thick`. `st:DrawnInset(frame)` and `st:DrawnKind(frame)` give the inset and kind a frame was last drawn at (a drawn frame, or the owner of a backdrop the engine drew; 0 for None, nil for never drawn), which `st:CalculateSpacing` reads. The inset is 2 for Thick and 1 for Thin whatever the kind, 0 for None, and the kind's own under Blizzard (`st.ThemeArt.Inset`). With no kind, `st:ResolveTheme` gives a Blizzard look no inset, and `st:ThemeInset` reads a panel's until every call names one. `st:IsBlizzardLook(theme, background)` says whether a pair draws in Blizzard's art, for controls that show that art themselves.
  - `SaftUI-Core/themeart.lua` (`st.ThemeArt`, loaded right after `theme.lua`) holds the Blizzard theme's tables: `KINDS` (each kind's inset per client, its art and its fill) and `ART` (the tooltip border, the character frame's metal, the action and item buttons', the aura's and the close button's art, and every control's). The accessors read them for the client at call time (`ThemeArt.Client()`, `'forever'` or `'live'`): `Inset`, `Top` (how far the art reaches down from the drawn frame's top: a window's title bar), `TitleHeight`, `Close`, `State`, `Control` and `ClassPower`. It also draws a Blizzard look for `theme.lua` (`ThemeArt.Paint`, `ThemeArt.Color`, `ThemeArt.Clear`): textures made once per drawn frame and kept in its weak tables (`ThemeArt.Get`). A border's pieces are on the drawn frame. A button's ring lies over the icon's edge: on a button of SaftUI's (`st:SetBackdrop`) it's a texture of the button's own, in ARTWORK below 0 (over an icon in BACKGROUND or BORDER, under its texts and cooldown), and otherwise, or on a frame marked with `st:MarkForeign` (someone else's, still drawn with `st:SetBackdrop`), it's on a frame of SaftUI's over the backdrop. Under Blizzard a backdrop has a fill and no edge (a small frame keeps one line), a window's backdrop reaches its title bar above it, and `header`, `close` and `control` are cleared; Thick and Thin hide the art. An art name is an atlas unless it's a file under `Interface\`; `st:ThemeAtlases()` lists every atlas the tables name, and `tests/core/theme_blizzard_test.lua` checks each exists on both clients. SaftUI places the art itself and never runs Blizzard's nine-slice code (`.agents/taint.md`).
  - Every draw call names its kind of frame, last: `st:SetTemplate(frame, theme, background, kind)`, `st:SetBackdrop(frame, theme, background, kind)` and `st:SetBackdropIn(backdrops, frame, theme, background, kind)`. The kinds are `st.THEME_KINDS`: `panel` (a background), `window` (a window with SaftUI's title bar), `bar`, `action`, `slot`, `aura`, `tooltip`, `header` (header and footer strips), `close` (the close button), `control` (a small frame Blizzard draws with art of its own) and `small` (everything else). Under Thick and Thin only `header` and `close` draw differently (SaftUI's theme's fill, no lines): a window draws as a panel and a control as a small frame. Blizzard's look is the kind's own (`themeart.lua`). A call with no kind is an error, unless its theme is `'none'` (which only clears). Use the `st:` form even inside Core's own methods: `tests/core/theme_kinds_test.lua` scans every file the TOCs load for draw calls without a kind, and fails on any other form.
  - Each drawn frame is recorded with the arguments it was last drawn with. `st:RecolorThemed()` puts the current colors and opacity back on every one, moving nothing; `st:RedrawThemed()` draws each again at the current inset, and moves a backdrop only while it still sits where the last draw put it (one its caller anchored itself is repainted where it is). Both color or draw each frame on its own (`xpcall` to `geterrorhandler()`): one that errors is reported, and every other frame still takes the theme.
- **The Theme module** (`SaftUI-Core/Media/theme.lua`) is the tab. A color or Opacity change runs `st:RecolorThemed()`. A Theme or Transparent background change runs `st:ThemeChanged()`, which is `st.Config:UpdateConfig()`, the profile update: it redraws every drawn frame once (`st:RedrawThemed()`), has every module lay itself out again (the border's width moves what sits inside it), and ends with `st:ColorsChanged('theme')`. Both wait for the end of combat (one pending run, `st:QueueAfterCombat`).
- **A profile switch, copy or reset is a theme change** when the two profiles' themes or theme colors differ, so `Config:UpdateConfig` always redraws and recolors (below): no frame keeps the old profile's look until a reload.
- **A frame's own border color** goes on through `st:SetBorderColor(frame, r, g, b, a)`, never `SetBackdropBorderColor` on a drawn backdrop (`tests/core/theme_kinds_test.lua` scans for it); `frame` is the drawn frame the caller holds (`x.backdrop`, `backdrops[x]`, or one drawn with `st:SetTemplate`). With no color it puts the look's own border back, with no redraw. Under Thick and Thin it is the backdrop's border. Under Blizzard it is the kind's own: the tooltip and metal pieces tinted, `action`'s `UI-HUD-ActionBar-IconFrame-Border` or `slot`'s and `aura`'s `Interface\Common\WhiteIconFrame` shown in the color over the icon's edge (`st.ThemeArt.Get(frame).own`, a texture on the button of SaftUI's the way the ring is, or on a frame of SaftUI's over the backdrop for a frame that isn't SaftUI's: mark Hekili's or WeakAuras' with `st:MarkForeign` before the first draw), a `small` frame's line; a `control`, a frame never drawn and a frame drawn None are left alone. A recolor or redraw takes the color off, so a module colors again in `OnColorsChanged('theme')`.
- **Colors a frame's own code puts on its backdrop** (an item's quality border, a debuff's type, an equipped item, a tooltip's class border, a selected mover) would be wiped by a recolor or redraw, so they're put back two ways:
  - a module's `OnColorsChanged('theme')` colors the borders it tracks again (Bags, ActionBars, Loot's feed, Tooltip, the totem bar, Skinning's skins, edit mode's movers);
  - `st:KeepOwnColors(frame, color)` registers `color(frame)` for one frame, run again after every recolor and redraw: Core's widgets, which have no module (a scroll bar thumb's hover, a radio group's picked button, a focused edit box), the lit border of a loot roll you've chosen on (`SaftUI-Loot/roll.lua`), and the unit frames' aura buttons (the dark line `auras.lua` draws inside each button's Thick border, `ColorInnerLine`, in Thick's outer border color, shown only under Thick; the dispel-type fill is a separate texture a recolor or redraw never touches). nil forgets it. The frame is only a key, so it may be Blizzard's.
- **Saved template choices migrate.** Before themes, a module saved an old template name (`thicktransparent`, `thin`, `none`, ...) in a key named `template` or `<prefix>template` (`buttontemplate`). `st:MigrateTemplateKeys(tbl)` (`theme.lua`) walks a table and rewrites each such key holding a string into `<prefix>theme` and `<prefix>background` through the old names' table (`thicktransparent` is Thick and Transparent, `thin` Thin and Solid, `none` only None; `highlight`, `close` and any other string just go, so the module's defaults apply), and removes it. Every old choice was a string, so any other value under such a key is data and stays (a unit frame profile the user named `raid template` is a table, walked like any other). It reads only what's saved (never through AceDB's `**` defaults), and running it again changes nothing. `Config` runs it wherever saved data enters a profile: on `st.config.profile` right after `AceDB:New` at login, at the start of every `Config:UpdateConfig` (a profile switched to or copied from one the old version saved), and on the data `Config:Import` returns (so the unit frames' Import too). The unit frames' own profiles live inside the SaftUI profile, so they migrate with it, and their Copy copies a profile already migrated.

## Config, defaults and profiles

- Each module defines its defaults at file load in its own `config.lua`, as `st.defaults.<key> = { ... }`. Unit frames keep theirs in `SaftUI-Unitframes/config/`.
- `Config:InitializeAceConfig` (called from `SaftUI:OnEnable`) creates `st.config = AceDB:New('SaftUI_DB', { profile = st.defaults, ... })`. Read settings through `st.config.profile.<key>`.
- **Bind, don't cache.** In `OnEnable`, call `st:BindModuleConfig(self, '<key>')` instead of `self.config = st.config.profile.<key>`. On a profile change, AceDB switches to the new profile's tables and strips defaults from the old ones, so any reference cached at enable time (including upvalues and closures holding sub-tables) returns nil fields. Bound modules are re-pointed automatically. In option `get`/`set` functions and hooks, read through `self.config` at call time.
- **Per-character saved data** (not settings) goes in AceDB's char namespace, `st.config.char.<key>`, which a profile switch doesn't touch. SaftUI-Loot keeps its saved feed and recorded roll drops there (`Feed/history.lua`, `Feed/rolls.lua`). Read it through an accessor at call time (`st.config` doesn't exist at file load). Save only plain data (strings, numbers, booleans and tables of them), never a secret value (`.agents/clients.md`) and never test-mode entries, and keep each record to the fields its readers need.
- **Profile changes** (`OnProfileChanged`/`Copied`/`Reset`) run `Config:UpdateConfig()` in `SaftUI-Core/Config/config.lua`. Order:
  1. Migrate the profile's saved template choices (`st:MigrateTemplateKeys`, see Themes), then re-point every bound `module.config`.
  2. Redraw every drawn frame in the profile's theme (`st:RedrawThemed`), before any module lays itself out around its border. In combat the redraw and step 8 wait for the end of combat, as one pending run (`QueueAfterCombat('ThemeRedraw')`). In and out of combat they're two steps, each in `xpcall`, so a redraw that errors still has step 8 run after it.
  3. Clear mover anchors (`EM:ClearPositions`, which saves them and skips frames that are protected in combat).
  4. Apply fonts, then headers (`st:UpdateHeader`: every header's and footer's height and window title fonts), then the screen edge margin (`st:UpdateScreenMargin`: every frame kept inside it; see `.agents/edit-mode.md`).
  5. Run every module's `UpdateConfig` inside `xpcall`, with errors going to `geterrorhandler()`.
  6. Re-apply edit mode movers (`EM:UpdateConfig`), restoring the old anchors of any frame left without points.
  7. Rebuild and refresh an open `/sui`.
  8. `st:ColorsChanged('theme')`, so what modules color themselves (quality borders, a selected mover) goes back on over the redrawn theme.

  In combat, protected work is deferred with `st:SafeReposition` / `st:QueueAfterCombat`, and one chat message says what will finish after combat.
- **Every module needs an `UpdateConfig`** that re-reads the profile and re-applies everything it controls (positions, sizes, its Theme and Background, fonts, colors, visibility). It must be idempotent: never create frames, font strings or hooks on each call. Create once, re-style on every call. Settings that genuinely can't apply live (module on/off toggles, secure header attributes) say "reload to apply" in their option description.
- Position config shape: `{ point, frame, rel_point, x_off, y_off }`, unpacked with `st:UnpackPoint`. Some older code used array positions (`{'BOTTOMRIGHT', -20, 20}`). Modules that converted (Bags, Chat, Experience) migrate saved arrays in place on enable and on profile change, filling missing slots from the old array defaults, because AceDB only saves slots that differ from the default.

## Unit frames

- These are oUF (`SaftUI-Unitframes/Libraries/oUF`, oUF master). In this oUF the active unit is `frame.__unit`, **not** `frame.unit`.
- Elements register through `UF:RegisterElement(name, Constructor, UpdateConfig, GetConfigTable, ValidUnit)`.
  - `ValidUnit(unit)` gets the config unit (`player`, `boss`, `party`, ...). A unit it rejects gets neither the element nor its `/sui` tab. ClassPower and AdditionalPower are player-only, Castbar skips `targettarget` and `focustarget` (as oUF does), and ReadyCheckIndicator is party and raid only.
  - `GetConfigTable(unit)` returns the element's tab. Its `set` calls `UF:UpdateConfig(unit, '<Element>')`, which re-runs that element's `UpdateConfig` on every frame of the unit.
  - oUF shows and hides many elements itself (castbar on a cast, indicators by state, additional power by power type), so `UF:SetElementEnabled` alone doesn't keep a disabled one hidden. Those elements also check `config.enable` in an oUF hook (`ShouldShow`, `PostVisibility`, `PostUpdate`).
  - Texts made by `UF:AddText` sit on the unit frame's `TextOverlay`, not on their element, so they don't hide with it. `UF:UpdateElement` hides them when the element is disabled.
  - `UF:UpdateElement` draws an element's Theme and Background on the element, except for the aura areas (Buffs, Debuffs) and the class power row (`BARE_ELEMENTS` in `updaters.lua`): their own `UpdateConfig` draws each aura button and point instead, and the area gets no backdrop. An aura area is Blizzard's AuraContainer, so nothing of SaftUI's is anchored to it (`.agents/taint.md`, rule 11).
- Layout "profiles" inside the SaftUI profile: `st.config.profile.unitframes.profiles[UF:GetProfile()]`, read through `UF:GetProfileConfig()`.
- Unit frames are secure. See `.agents/taint.md` before moving or resizing them.
